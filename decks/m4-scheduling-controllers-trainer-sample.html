Lesson 1

How Kubernetes schedules a Pod

By the end: you can explain the scheduling cycle and show where the selected node is recorded.

Scheduling starts here

A new Pod has no node yet

The API server stores the Pod first. The scheduler must assign a node.

  • The Pod exists in the API.
  • spec.nodeName is empty.
  • The Pod phase remains Pending.
  • The scheduler watches for this state.
Teaching cueA Pod object is not yet a running container. Placement must happen first.
apiVersion: v1
kind: Pod
metadata:
  name: api-worker
spec:
  # nodeName is not set
  containers:
  - name: worker
    image: registry.k8s.io/pause:3.9

status:
  phase: Pending

Scheduling cycle

One Pod moves through one scheduling cycle

The scheduler processes one unscheduled Pod and writes one placement decision.

1

Queue

Wait for a scheduling attempt.

2

Filter

Remove nodes that fail a hard rule.

3

Score

Rank the nodes that remain.

4

Reserve

Update scheduler state for the assumed placement.

5

Permit

Run any final approval step.

6

Bind

Write the node name to the Pod.

What happens after bind?The kubelet on the selected node sees the Pod and starts the containers.

The scheduling decision

Bind records the node name

The result of scheduling is an API write, not a container start command.

Before scheduling

Pod is waiting

spec:
  nodeName: ""

status:
  phase: Pending

The scheduler can consider this Pod.

After bind

Pod has an assigned node

spec:
  nodeName: kwok-node-1

status:
  phase: Pending

The kubelet now owns the next step. The phase may remain Pending while containers start.

Lesson 2

How placement rules select a node

By the end: you can tell which rules reject a node and which inputs affect ranking.

Filter stage

Filters apply hard placement rules

A node must pass every required rule before it can be scored.

Resources

Can this one node satisfy the Pod's CPU and memory requests?

EventInsufficient cpu

Labels and affinity

Do the node labels match the Pod's selector or required affinity?

Eventdidn't match node selector

Taints

Does the Pod tolerate every NoSchedule taint on the node?

Eventuntolerated taint

Resource fit

Resource requests must fit on one node

The scheduler uses requests. It does not use the current CPU graph for placement.

resources:
  requests:
    cpu: "9000"
    memory: 4Gi

# Candidate node
Allocatable CPU: 32
Already requested: 28
Free for scheduling: 4
28 used+9000 requested>32 allocatable
  • The request must fit on one node.
  • Adding many small nodes may not help one very large Pod.
  • Fix the request or add a node that can satisfy it.

Label contract

A node selector requires a matching label

The Pod asks for a label. At least one eligible node must have it.

Pod requirement
spec:
  nodeSelector:
    disktype: nvme
  • This is a hard rule.
  • A spelling error can block the Pod.
Live node labels
$ kubectl get nodes \
  -L disktype

NAME          DISKTYPE
worker-0      ssd
kwok-node-1   <none>
ResultNo node has disktype=nvme, so the Pod remains Pending.

Taints and tolerations

A toleration allows a tainted node

The toleration removes one restriction. It does not force the Pod onto that node.

Node policy

Taint on the node

dedicated=gpu:NoSchedule
  • NoSchedule blocks new Pods.
  • The scheduler still checks resources and labels.
Pod permission

Matching toleration

tolerations:
- key: dedicated
  operator: Equal
  value: gpu
  effect: NoSchedule

Use a selector or affinity as well when the Pod must run on the dedicated pool.

Score stage

Scoring ranks the nodes that remain

Scoring cannot bring back a node that failed a hard placement rule.

  • Resource balance can affect the score.
  • Topology spread can prefer a different zone.
  • Image locality may add points.
  • The highest total score becomes the selected node.

worker-zone-b

Lesson 3

How to diagnose a Pending Pod

By the end: you can read FailedScheduling and choose the next check without guessing.

First evidence

Start with the FailedScheduling event

Read the scheduler's reason before changing the workload or the cluster.

$ kubectl describe pod too-big -n m4-lab

Events:
  Type     Reason            From
  Warning  FailedScheduling  default-scheduler

  0/5 nodes are available:
  4 Insufficient cpu, 1 node had untolerated taint.
  preemption: 5 Preemption is not helpful for scheduling.

1. Find the reason

Read each rejected-node count.

2. Check that rule

Inspect requests, labels or taints.

3. Make one change

Fix the exact rule that failed.

4. Verify again

Watch the event and Pod phase.

Pending cause 1

The resource request is too large

4 Insufficient cpu

$ kubectl get pod too-big -n m4-lab \
  -o jsonpath='{.spec.containers[*].resources.requests}'

{"cpu":"9000"}

$ kubectl describe node kwok-node-0 | grep -A5 Allocatable
Allocatable:
  cpu: 32
What to explain
  • The Pod asks for more CPU than any candidate node can provide.
  • Preemption cannot help if the request is larger than node capacity.
  • Reduce the request or add a larger node type.
  • Recreate the Pod because requests are immutable for an existing Pod.

Pending cause 2

The node selector matches nothing

4 node(s) didn't match Pod's node affinity/selector

$ kubectl get pod wrong-selector -n m4-lab \
  -o jsonpath='{.spec.nodeSelector}'
{"disktype":"nvme-that-does-not-exist"}

$ kubectl get nodes -L disktype
NAME          DISKTYPE
worker-0      <none>
kwok-node-1   <none>
What to explain
  • Compare the Pod selector with live node labels.
  • Check spelling, case and expected node pool.
  • Fix the selector or label the intended node.
  • Do not add a label to an unsuitable node only to make the Pod run.

Pending cause 3

The Pod cannot tolerate a taint

4 node(s) had untolerated taint

$ kubectl get node kwok-node-0 \
  -o jsonpath='{.spec.taints}'

[{"key":"kwok.x-k8s.io/node",
  "value":"fake",
  "effect":"NoSchedule"}]

$ kubectl get pod no-toleration -n m4-lab \
  -o jsonpath='{.spec.tolerations}'
[]
What to explain
  • Read the taint key, value and effect.
  • Compare them with the Pod tolerations.
  • Add a narrow toleration only if the Pod belongs on that node pool.
  • Use placement rules as well when the Pod must use that pool.

Diagnostic workflow

Use the event to choose the next check

Each scheduler reason points to a different part of the Pod and node contract.

FailedScheduling reasonCheck nextSafe fix to consider
Insufficient cpuPod requests, node allocatable, existing requestsRight-size the request or add a node with enough capacity

preemption is not helpfulHard constraints that removing another Pod cannot solveFix the impossible constraint before changing priority

Lesson 4

How controllers process changes

By the end: you can explain how a controller receives work, retries safely and selects one active replica.

Controller internals

A controller watches, queues and reconciles

The same mechanism is used by built-in controllers and many operators.

Informer

Watches the API and keeps a local cache.

Work queue

Stores object keys, removes duplicates and rate limits retries.

Reconcile

Reads current state, compares it with desired state and acts.

Done or requeue

Success ends this item. Error returns it with backoff.

Why use a local cache?

Controllers can read repeated state without sending every read to etcd.

Why use backoff?

One broken object will not create a tight loop against the API server.

Leader election

Leader election lets one copy act

Several controller replicas can run, but only the Lease holder performs reconciliation.

  • Every replica competes for the same Lease.
  • One replica renews the leader election Lease.
  • The leader processes work from the queue.
  • A standby takes over when Lease renewal stops.
ReasonWithout leader election, several controller copies could act on the same object at the same time.

Lesson 5

What happens when a node stops reporting

By the end: you can explain the path from a lost Node Lease to Pod eviction and replacement.

Node health

A lost Lease changes node health

The control plane separates node detection from Pod eviction.

Lease renewal stops

The kubelet no longer updates its Node Lease.

Ready becomes Unknown

The node controller marks the node as unreachable.

System taints appear

unreachable or not-ready is added.

Pod timers continue

Existing Pods remain until their toleration expires.

What to point outThe scheduler avoids the unhealthy node immediately, while existing Pods may remain bound for a grace period.

Taint effects

NoSchedule and NoExecute do different jobs

One effect controls new placement. The other can remove Pods already on the node.

EffectNew PodsExisting PodsCommon use
NoScheduleBlocked unless toleratedRemain on the nodeDedicated pools, control-plane protection
PreferNoScheduleAvoided when possibleRemain on the nodeSoft isolation preference
NoExecuteBlocked unless toleratedEvicted when not tolerated or when the timer expiresNode failure and maintenance tests
Lab linkThe lab adds a custom maintenance=cordon:NoExecute taint so you can observe the eviction path safely on a KWOK node.

Eviction grace period

tolerationSeconds controls the eviction delay

The default not-ready and unreachable tolerations are commonly 300 seconds.

Node returns before 300 seconds

The Pod remains bound

  • The Lease starts renewing again.
  • The system taint is removed.
  • The workload avoids an unnecessary restart.
Timer expires first

The Pod is marked for deletion

  • Taint Manager processes the NoExecute taint.
  • The old Pod is deleted from the failed node.
  • A workload controller may create a replacement Pod.
Production decisionA short timer reacts faster but can restart Pods during a brief network problem. A long timer delays recovery from a dead node.
