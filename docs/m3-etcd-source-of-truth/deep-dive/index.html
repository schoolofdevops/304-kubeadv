Deep Dive - Inside etcd's Keyspace: Revisions, Snapshots, and the Events Problem

This deep dive reads Kubernetes data directly from etcd. You will inspect the keyspace, connect revisions with resourceVersion, verify a snapshot, and measure Event churn. Use these checks before restoring a backup or when the API server is unavailable.

▶ M3: etcd Deep DiveOpen fullscreen ↗

Run everything from the repo root against the core-internals profile.

Where this picks up

The cluster from the lab is still running (recreate with bash labs/clusters/core-internals/create.sh if not). Everything here goes through kubectl exec into the etcd static pod: no host installs. Type the helper below once per terminal session; it wraps the TLS flags every etcdctl call needs, while keeping the real invocation visible:

etcdc() {
  kubectl -n kube-system exec etcd-kubeadv-core-control-plane -- etcdctl \
    --endpoints=https://127.0.0.1:2379 \
    --cacert=/etc/kubernetes/pki/etcd/ca.crt \
    --cert=/etc/kubernetes/pki/etcd/server.crt \
    --key=/etc/kubernetes/pki/etcd/server.key "$@"
}
kubectl create namespace m3-deepdive --dry-run=client -o yaml | kubectl apply -f -
kubectl create configmap m3-probe -n m3-deepdive --from-literal=stage=one --dry-run=client -o yaml | kubectl apply -f -

[ Expected output ]

namespace/m3-deepdive created
configmap/m3-probe created

PART I - Reading the keyspace directly​

kubectl is the bank teller: every request goes through the window, your identity is checked, the transaction is logged, and you get a typed, formatted statement. etcdctl against the etcd endpoint is standing inside the vault. Same money, no window: and no rules. Read the ConfigMap you just created, as etcd stores it:

etcdc get /registry/configmaps/m3-deepdive/m3-probe

[ Expected output ]

/registry/configmaps/m3-deepdive/m3-probe
k8s\x00 ... v1 ... ConfigMap ... m3-probe ... m3-deepdive ...
... (protobuf bytes trimmed; readable strings remain inside a binary value)

Two things to notice. The key is not an ID: it is a path: /registry/<resource-plural>/<namespace>/<name>. And the value is not YAML: it is the object serialized as protobuf (the k8s\x00 envelope at the front), which is why the strings m3-probe and stage are readable but the structure around them is binary. Everything kubectl shows you: the typed fields, the table columns, the -o yaml: is the API server decoding and re-serializing this blob. Down here there is only the blob.

Tour the structure. Every Kubernetes object in your cluster lives under /registry/, one prefix per resource type:

etcdc get /registry/ --prefix --keys-only | grep -v '^$' | cut -d/ -f3 | sort | uniq -c | sort -rn | head

[ Expected output ]

  72 clusterroles
  65 events
  58 clusterrolebindings
  46 serviceaccounts
  21 apiregistration.k8s.io
  15 configmaps
  12 roles
  12 rolebindings
  11 pods
  11 flowschemas

Pods, leases, events, secrets: the whole cluster is a flat, ordered key-value namespace, and range reads over prefixes are exactly how the API server implements every LIST you costed in M2. Now the operational point, and it matters more than the mechanics: RBAC does not exist at this layer. No authentication beyond the client cert, no admission, no validation, no audit event. The read above would have returned a Secret's payload just as readily as a ConfigMap's: and unless encryption at rest is configured, Secrets sit in this keyspace as plainly as m3-probe does. This is why etcd access is cluster root: anyone holding the etcd peer/server certs or a copy of the data directory can read every credential and write any object, bypassing every control you configured in M2. Treat etcd certs, snapshots, and disk with the same handling as your CA key: and when you audit a cluster, who can reach 2379/2380 and who can read the etcd volume belong on the checklist next to the RBAC review.

PART II - The revision ↔ resourceVersion bridge​

In M2 you treated resourceVersion as an opaque freshness token, which is still the correct client contract. For a built-in resource stored by this kube-apiserver in etcd, you can also observe the implementation underneath it: the object's numeric resourceVersion matches the key's etcd mod_revision. Treat that as an internals observation, not as permission to calculate with arbitrary resource versions. Prove the relationship on this ConfigMap. Read its resourceVersion through the teller, then read the same object from the vault with -w json, which reports the MVCC metadata around the base64-encoded blob:

kubectl get configmap m3-probe -n m3-deepdive -o jsonpath='{.metadata.resourceVersion}{"\n"}'
etcdc get /registry/configmaps/m3-deepdive/m3-probe -w json | grep -o '"mod_revision":[0-9]*'

[ Expected output ]

1343
"mod_revision":1343

Same number in this storage path. The object's resourceVersion reflects its key's mod_revision, which is the revision at which it was last written. The current etcd revision itself is one status call away:

etcdc endpoint status -w json

[ Expected output ]

[{"Endpoint":"https://127.0.0.1:2379","Status":{"header":{"cluster_id":17872035879968285421,"member_id":17094317486111276271,"revision":1360,"raft_term":2},"version":"3.6.6","dbSize":606208,"leader":17094317486111276271,"raftIndex":2008,"raftTerm":2,"raftAppliedIndex":2008,"dbSizeInUse":606208,"storageVersion":"3.6.0","dbSizeQuota":268435456,"downgradeInfo":{}}}]…

The header's revision is the ledger's current line number; every write to any key increments it. Do not turn that implementation fact into a cross-resource ordering rule. Kubernetes 1.35 only guarantees numeric ordering for objects from the same API resource type; use audit events for a timeline that crosses Pods, Deployments, Secrets, and other types. Because MVCC keeps history, you can also read this key's ledger backwards. Write the probe twice more, then replay its history with a watch that starts at an old revision:

OLD=$(etcdc get /registry/configmaps/m3-deepdive/m3-probe -w json | grep -o '"mod_revision":[0-9]*' | grep -o '[0-9]*')
kubectl patch configmap m3-probe -n m3-deepdive --type merge -p '{"data":{"stage":"two"}}'
kubectl patch configmap m3-probe -n m3-deepdive --type merge -p '{"data":{"stage":"three"}}'
etcdc watch /registry/configmaps/m3-deepdive/m3-probe --rev=${OLD}

[ Expected output ]

PUT
/registry/configmaps/m3-deepdive/m3-probe
k8s

v1	ConfigMap·
·
PUT
/registry/configmaps/m3-deepdive/m3-probe
k8s

v1	ConfigMap·
·
^C

The command replays the historical PUTs and then waits for new changes. Use Ctrl-C after the replay.

Both PUT events arrive instantly: that is not the future streaming in, it is the past being replayed from history. This is precisely what serves an API watch that starts from an older resourceVersion. And it has a floor: compaction. The API server compacts etcd every five minutes in the background (discarding history, not space: the lab's distinction), so compacting manually to the current revision is safe on this cluster. Do it, then ask for history from below the floor:

REV=$(etcdc endpoint status -w json | grep -o '"revision":[0-9]*' | head -1 | grep -o '[0-9]*')
etcdc compact ${REV}
etcdc watch /registry/configmaps/m3-deepdive/m3-probe --rev=2

[ Expected output ]

watch was canceled (etcdserver: mvcc: required revision has been compacted)
Error: watch is canceled by the server

No events replay, and you don't need Ctrl-C: the server cancels the watch itself (exit code 5). You have met this error before wearing a different coat: it is exactly what the API server converts into the 410 Gone that forced re-lists in M2. The compaction window in etcd is the resumability window for every informer in your cluster. One storage-layer fact drives two modules' worth of client behavior.

PART III - Snapshot forensics: verify before you trust​

A backup you have never inspected is a fire safe you have never opened. The time to discover it is empty is not during the fire. Take a snapshot now: writing it into /var/lib/etcd, the one path guaranteed writable inside the pod: and then interrogate it with etcdutl, the offline tool that reads the file directly (no TLS, no running server needed):

kubectl -n kube-system exec etcd-kubeadv-core-control-plane -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /var/lib/etcd/m3-deepdive.snap
kubectl -n kube-system exec etcd-kubeadv-core-control-plane -- etcdutl snapshot status /var/lib/etcd/m3-deepdive.snap -w table

[ Expected output ]

{"level":"info","ts":"2026-07-15T18:22:41.753820Z","caller":"snapshot/v3_snapshot.go:83","msg":"created temporary db file","path":"/var/lib/etcd/m3-deepdive.snap.part"}
{"level":"info","ts":"2026-07-15T18:22:41.766669Z","logger":"client","caller":"v3@v3.6.6/maintenance.go:236","msg":"opened snapshot stream; downloading"}
{"level":"info","ts":"2026-07-15T18:22:41.775472Z","caller":"snapshot/v3_snapshot.go:96","msg":"fetching snapshot","endpoint":"https://127.0.0.1:2379"}
{"level":"info","ts":"2026-07-15T18:22:41.783859Z","logger":"client","caller":"v3@v3.6.6/maintenance.go:302","msg":"completed snapshot read; closing"}
... (trimmed)
+----------+----------+------------+------------+---------+
|   HASH   | REVISION | TOTAL KEYS | TOTAL SIZE | VERSION |
+----------+----------+------------+------------+---------+
| 8da20ab0 |     1482 |        372 |     725 kB |   3.6.0 |

Four fields, four questions you answer before trusting any backup: hash: does it verify, i.e. is the file intact and not truncated by a failed copy? revision: how recent is it? Compare against the endpoint status revision you read above; the gap is your data loss if you restore. total keys: is the count plausible for this cluster, or did you snapshot the wrong (or an empty) etcd? size: consistent with the db size you watched in the lab? A restore decision made without these four answers is a guess. In production, this check belongs in the backup job itself, not in the incident.

Instructor extension: snapshot restore

Restore (etcdutl snapshot restore) is deliberately not part of this page: it rewrites the data directory, mints a new cluster identity, and requires stopping the API server: run against this cluster it would destroy the course environment that M4 continues on. The instructor-led extension walks it on a disposable cluster. The takeaway stands without executing it: restore is a rebuild, not an undo.

PART IV - Why Events deserve their own etcd​

Every keyspace under /registry/ pays rent in the same building: one write log, one compaction cycle, one 256 MB quota (on this cluster). Most tenants are quiet; Events are not. Count what Events contribute against a workload keyspace like pods:

etcdc get /registry/events/ --prefix --keys-only | grep -c '^/registry/events/'
etcdc get /registry/pods/ --prefix --keys-only | grep -c '^/registry/pods/'

[ Expected output ]

65
11

Even on an idle two-node cluster, Events outnumber pods: and every one of them is a write (often several: create, then count-increment patches), each incrementing the global revision, each adding history that compaction must sweep, all with a default 1-hour TTL guaranteeing perpetual churn. Events are write-heavy and low-value: nothing reconciles from them, and losing them loses convenience, not state. At production scale that tenant gets loud enough to matter: in the OpenAI incident you studied, Events traffic was significant enough that their clusters run a dedicated etcd for Events, so event churn cannot add write latency, db-size growth, or compaction load to the etcd that stores pods and leases.

The mechanism is a single API server flag, and it works per key prefix:

# Not run on this cluster: shown for the mechanics (requires a second etcd to point at):
# kube-apiserver --etcd-servers-overrides=/events#https://etcd-events-0:2379,https://etcd-events-1:2379

The format is <prefix>#<comma-separated servers>, semicolon-separated for multiple overrides: any resource whose keyspace matches the prefix is stored in the override cluster, everything else stays in --etcd-servers. The general lesson outlives the flag: when a write-heavy, low-value keyspace shares storage with your source of truth, isolate it. The same reasoning tells you to keep verbose operators from spamming Events, and to notice: on the Storage lens from the lab: when db-size growth is churn, not state.

Summary​

Where you will use this
  • Objects are keys; kubectl is a view: /registry/<plural>/<ns>/<name> holds protobuf, readable by anyone with etcd certs, with no RBAC, admission, or audit in the path. Use it when: auditing cluster security: etcd endpoints, certs, snapshots, and volumes are cluster-root credentials; and during API-server-down incidents, when etcdctl is the only working view of cluster state.
  • For this kube-apiserver storage path, resourceVersion reflects etcd's mod_revision, and compaction sets the floor: watches replay history down to the compacted revision, then error: surfaced to clients as 410 Gone. Use it when: correlating client-side re-list storms with storage-side compaction settings. In client code, keep treating the value as server-owned and compare versions only within the same API resource type.
  • etcdutl snapshot status is the pre-restore gate: hash proves integrity, revision measures data loss, total keys and size prove you snapshotted the right cluster. Use it when: writing backup jobs (verify in the job, not in the incident) and as the first command of any restore decision.
  • Write-heavy, low-value keyspaces get isolated: Events churn is perpetual by design; --etcd-servers-overrides=/events#... moves it off the etcd that holds real state. Use it when: a large cluster shows etcd write latency or db-size pressure that tracks event volume, not workload changes: the OpenAI pattern: or when sizing etcd for a cluster with chatty operators.

Teardown​

Remove this page's probe namespace and the snapshot file; keep the core-internals cluster running: M4 continues on it:

kubectl delete namespace m3-deepdive
docker exec kubeadv-core-control-plane rm -f /var/lib/etcd/m3-deepdive.snap   # the etcd image is distroless (no rm); the kind node has a shell

[ Expected output ]

namespace "m3-deepdive" deleted
