Filling etcd and Recovering from NOSPACE

Before you start

New here? Complete the Setup section first. Rancher Desktop should be running with the Moby/dockerd engine, and docker, kind, and kubectl should all respond.

All commands below run from the root of the lab repo (304-labs/). This lab continues on the core-internals cluster used in M1 and M2.

In this lab, you are going to fill the etcd database until it stops accepting writes. You would then recover it using compaction and defragmentation.

This is a practice failure. You are going to run it on the core-internals cluster created for this course.

By the end of this lab, you will:

  • check the current etcd database size and quota
  • fill etcd using a controlled script
  • observe why reads work while writes fail
  • recover etcd and validate that the cluster can accept writes again

Pre Requisites​

Check the current Kubernetes context.

kubectl config current-context

[ Expected output ]

kind-kubeadv-core

If the core-internals cluster is not running, create it as,

bash labs/clusters/core-internals/create.sh

[ Expected output ]

Creating kind cluster 'kubeadv-core' ...
Waiting for all nodes to be Ready ...
OK: core-internals profile verified — 2/2 nodes Ready, API server healthy.

PART I - Examine etcd​

Verify the Cluster Profile​

To begin with, verify the cluster profile.

bash labs/clusters/core-internals/verify.sh

[ Expected output ]

Waiting for all nodes to be Ready ...
node/kubeadv-core-control-plane condition met
node/kubeadv-core-worker condition met
OK: core-internals profile verified — 2/2 nodes Ready, API server healthy.
audit mode: ENABLED — stream with: kubectl logs -n kube-system kube-apiserver-kubeadv-core-control-plane
etcd quota: 256MB — metrics on :2381 (M3 profile knobs present)
NAME                         STATUS   ROLES           AGE   VERSION
kubeadv-core-control-plane   Ready    control-plane   28s   v1.35.0
kubeadv-core-worker          Ready    <none>          15s   v1.35.0

Make sure that both nodes are in Ready state. Also check that the output shows etcd quota: 256MB.

If verify says "etcd knobs: missing"

Your cluster may have been created before the M3 settings were added. The etcd flags cannot be changed after creating the cluster. Recreate it once as,

bash labs/clusters/core-internals/teardown.sh
bash labs/clusters/core-internals/create.sh

[ Expected output ]

Deleting cluster "kubeadv-core" ...
Creating kind cluster 'kubeadv-core' ...
Waiting for all nodes to be Ready ...
OK: core-internals profile verified — 2/2 nodes Ready, API server healthy.

Then run verify.sh again and make sure it reports the etcd quota line. The M1 and M2 labs do not need any objects from the old cluster.

Lets now examine the etcd process flags from the static pod.

kubectl -n kube-system get pod etcd-kubeadv-core-control-plane -o jsonpath='{.spec.containers[0].command}' | tr ',' '\n' | grep -e quota-backend-bytes -e listen-metrics-urls

[ Expected output ]

"--listen-metrics-urls=http://0.0.0.0:2381"
"--quota-backend-bytes=268435456"

The first flag exposes etcd metrics on port 2381. The second flag sets the database quota to 256 MB.

Connect to etcd​

etcd uses TLS certificates for client connections. The certificates and the etcdctl command are already available inside the etcd pod.

Define the following helper function in your terminal.

etcdctl() {
  kubectl exec -n kube-system etcd-kubeadv-core-control-plane -- etcdctl \
    --cacert /etc/kubernetes/pki/etcd/ca.crt \
    --cert /etc/kubernetes/pki/etcd/server.crt \
    --key /etc/kubernetes/pki/etcd/server.key \
    "$@"
}

[ Expected output ]

(no output)

The function is available only in the current terminal. If you open a new terminal, define it again.

Check the health of the etcd member.

etcdctl endpoint health

[ Expected output ]

127.0.0.1:2379 is healthy: successfully committed proposal: took = 7.569958ms

The duration would be different on your machine. Make sure the endpoint reports is healthy.

Now list the detailed status.

etcdctl endpoint status -w table

[ sample output ]

+----------------+------------------+---------+-----------------+---------+--------+-----------------------+--------+-----------+
|    ENDPOINT    |        ID        | VERSION | STORAGE VERSION | DB SIZE | IN USE | PERCENTAGE NOT IN USE | QUOTA  | IS LEADER |
+----------------+------------------+---------+-----------------+---------+--------+-----------------------+--------+-----------+
| 127.0.0.1:2379 | ed3b372f1d693cef |   3.6.6 |           3.6.0 |  1.2 MB | 1.2 MB |                    0% | 268 MB |      true |
+----------------+------------------+---------+-----------------+---------+--------+-----------------------+--------+-----------+

This cluster has one etcd member. The member ID, database size and Raft values may differ on your cluster.

Capture the Baseline​

Before creating a failure, record the current database size and revision.

etcdctl endpoint status -w json | tr ',' '\n' | grep -e '"revision"' -e dbSize

[ sample output ]

"revision":540
"dbSize":1171456
"dbSizeInUse":1171456
"dbSizeQuota":268435456

where,

  • dbSize is the physical size of the database file. The quota is checked against this value.
  • dbSizeInUse is the part of the database which contains live data and history.
  • revision is the current MVCC revision.

Lets also read the same values from the etcd metrics endpoint.

kubectl get --raw /api/v1/namespaces/kube-system/pods/http:etcd-kubeadv-core-control-plane:2381/proxy/metrics | grep -e '^etcd_server_quota_backend_bytes' -e '^etcd_mvcc_db_total_size_in_bytes' -e '^etcd_mvcc_db_total_size_in_use_in_bytes'

[ sample output ]

etcd_mvcc_db_total_size_in_bytes 1.171456e+06
etcd_mvcc_db_total_size_in_use_in_bytes 1.171456e+06
etcd_server_quota_backend_bytes 2.68435456e+08

The quota metric should report 2.68435456e+08, which is 256 MB.

Open the Storage View​

Open a new terminal and launch Cluster X-Ray as,

bash labs/tools/xray/serve.sh

[ Expected output ]

│  context : kind-kubeadv-core
│  open    : http://127.0.0.1:8001/xray/
│  Ctrl-C stops the proxy. Port busy? PORT=8002 bash serve.sh

Open http://127.0.0.1:8001/xray/ and select the Storage tab. Keep it open while running the next part of the lab.

The values on your screen would be different. Make sure the watch reports connected and the Storage view shows the database size, quota, MVCC revision and health probes.

PART II - Fill etcd and Observe NOSPACE​

Fill the Database​

The fill script creates ConfigMaps with a payload of about 950 KiB. It stops at the first NOSPACE error or after 300 writes.

Run the script as,

bash labs/m3/fill-etcd.sh

[ sample output ]

Filling etcd: up to 300 ConfigMaps (~950 KiB each) into 'etcd-lab' ...
Stops at the first NOSPACE rejection — that is the goal, not a failure.
  10/300 written (db is growing — watch the Storage lens)
  20/300 written (db is growing — watch the Storage lens)
  30/300 written (db is growing — watch the Storage lens)
...
NOSPACE: etcd rejected write 258 after 257 successful writes this run:
  Error from server: error when creating "STDIN": etcdserver: mvcc: database space exceeded

The exact write number would be different. Make sure the script ends with etcdserver: mvcc: database space exceeded.

Go back to the Storage view and observe what happened.

Your Storage view should now look similar to the screenshot. The exact size and revision would differ, but the red NOSPACE alarm should be visible and the physical database should be close to its quota.

  • Did the physical database size reach the quota?
  • Did the NOSPACE alarm appear?
  • Did the MVCC revision increase with every write?

Check the Failure​

Lets now try to create a ConfigMap.

kubectl create configmap should-fail -n default --from-literal=test=nospace

[ Expected output ]

error: failed to create configmap: etcdserver: mvcc: database space exceeded

The cluster is not accepting writes. Check the active etcd alarm.

etcdctl alarm list

[ sample output ]

memberID:17094317486111276271 alarm:NOSPACE

The member ID would be different. The alarm should be NOSPACE.

Now check whether reads are still working.

kubectl get nodes
kubectl get pods -n kube-system --no-headers | head -5

[ sample output ]

NAME                         STATUS   ROLES           AGE     VERSION
kubeadv-core-control-plane   Ready    control-plane   2m20s   v1.35.0
kubeadv-core-worker          Ready    <none>          2m7s    v1.35.0

Check the API server readiness probe for etcd.

kubectl get --raw /readyz/etcd

[ Expected output ]

ok

What happened?

  • The API server can still read from etcd.
  • The etcd readiness probe still returns ok.
  • Any command which tries to write fails with database space exceeded.

This is the failure you need to identify. A read-only health check would not detect it.

PART III - Recover etcd​

Delete the Test Data​

Compaction removes old history. It cannot remove the current value of a live object. Begin by deleting the ConfigMaps created by the fill script.

kubectl delete configmaps -n etcd-lab --all --request-timeout=120s

[ sample output ]

configmap "fill-0001" deleted from etcd-lab namespace
configmap "fill-0002" deleted from etcd-lab namespace
configmap "fill-0003" deleted from etcd-lab namespace
...
configmap "kube-root-ca.crt" deleted from etcd-lab namespace

Do not delete the namespace at this stage. Namespace deletion needs an update to its finalizers, and updates are blocked while the NOSPACE alarm is active.

Compact the History​

Get the current revision and compact the old history as,

rev=$(etcdctl endpoint status -w json | grep -o '"revision":[0-9]*' | head -1 | cut -d: -f2)
echo "compacting up to revision ${rev}"
etcdctl compaction "$rev"

[ sample output ]

compacting up to revision 1179
compacted revision 1179

Check the database size again.

etcdctl endpoint status -w json | tr ',' '\n' | grep dbSize

[ sample output ]

"dbSize":268050432
"dbSizeInUse":589824
"dbSizeQuota":268435456

Observe the difference between dbSize and dbSizeInUse.

  • dbSizeInUse has reduced because compaction removed old history.
  • dbSize is still close to the quota because the physical file has not reduced.

Defragment the Database​

To reduce the physical database file, run,

etcdctl --command-timeout=60s defrag

[ sample output ]

Finished defragmenting etcd member[127.0.0.1:2379]. took 63.504166ms

Check the size once again.

etcdctl endpoint status -w json | tr ',' '\n' | grep dbSize

[ sample output ]

"dbSize":495616
"dbSizeInUse":487424
"dbSizeQuota":268435456

The physical size should now be close to the in-use size and well below the quota.

Disarm the Alarm​

The database has free space, but the alarm does not clear automatically. Disarm it and list the alarms again.

etcdctl alarm disarm
etcdctl alarm list

[ sample output ]

memberID:17094317486111276271 alarm:NOSPACE

The first command prints the alarm which was cleared. The second command should not print anything.

Validate the Recovery​

Create and delete a ConfigMap to confirm that writes are working again.

kubectl create configmap recovery-probe -n default --from-literal=recovered=yes
kubectl delete configmap recovery-probe -n default

[ Expected output ]

configmap/recovery-probe created
configmap "recovery-probe" deleted from default namespace

Run the final checks.

bash labs/clusters/core-internals/verify.sh
etcdctl alarm list
etcdctl endpoint status -w table
kubectl get configmaps -n etcd-lab -l module=m3 --no-headers | wc -l

[ sample output ]

OK: core-internals profile verified — 2/2 nodes Ready, API server healthy.
etcd quota: 256MB — metrics on :2381 (M3 profile knobs present)
+----------------+------------------+---------+-----------------+---------+--------+-----------------------+--------+-----------+
|    ENDPOINT    |        ID        | VERSION | STORAGE VERSION | DB SIZE | IN USE | PERCENTAGE NOT IN USE | QUOTA  | IS LEADER |
+----------------+------------------+---------+-----------------+---------+--------+-----------------------+--------+-----------+
| 127.0.0.1:2379 | ed3b372f1d693cef |   3.6.6 |           3.6.0 |  495 kB | 487 kB |                    2% | 268 MB |      true |
+----------------+------------------+---------+-----------------+---------+--------+-----------------------+--------+-----------+
0

Make sure that:

  • the cluster verification passes
  • alarm list has no output
  • the database size is below 256 MB
  • the ConfigMap count is 0

Troubleshooting​

Troubleshooting
  • The database size did not reduce after defragmentation — make sure you deleted the fill ConfigMaps and compacted the current revision before running defragmentation.
  • Writes fail again after disarming the alarm — the physical database file is probably still at the quota. Follow the order again: delete, compact, defragment and then disarm.
  • The etcdctl command is not found — the helper function was defined in another terminal. Define it again in your current terminal.
  • The fill script was interrupted — resume it with an offset: OFFSET=120 COUNT=100 bash labs/m3/fill-etcd.sh. Replace 120 with the last ConfigMap number printed by your run.
  • The fill script completed all 300 writes — add more writes with OFFSET=300 COUNT=60 bash labs/m3/fill-etcd.sh.
  • The cluster is still in NOSPACE after compaction and defragmentation — the live ConfigMaps are still using the space. Delete them first, then compact, defragment and disarm again.

Cleanup​

Delete the empty etcd-lab namespace.

kubectl delete namespace etcd-lab

[ Expected output ]

namespace "etcd-lab" deleted

Run one final compaction and defragmentation so that the next module starts with a clean database.

rev=$(etcdctl endpoint status -w json | grep -o '"revision":[0-9]*' | head -1 | cut -d: -f2)
etcdctl compaction "$rev"
etcdctl defrag
etcdctl endpoint status -w table

[ sample output ]

+----------------+------------------+---------+-----------------+---------+--------+-----------------------+--------+-----------+
|    ENDPOINT    |        ID        | VERSION | STORAGE VERSION | DB SIZE | IN USE | PERCENTAGE NOT IN USE | QUOTA  | IS LEADER |
+----------------+------------------+---------+-----------------+---------+--------+-----------------------+--------+-----------+
| 127.0.0.1:2379 | ed3b372f1d693cef |   3.6.6 |           3.6.0 |  1.2 MB | 1.2 MB |                    0% | 268 MB |      true |
+----------------+------------------+---------+-----------------+---------+--------+-----------------------+--------+-----------+

Keep the core-internals cluster running. You are going to use the same cluster in Module 4.

Summary​

In this lab, you filled the etcd database and observed the NOSPACE alarm. You also learnt why the cluster could continue reading while every write failed.

You then recovered the database in the correct order: delete the live test data, compact old history, defragment the physical file and disarm the alarm. In the next module, you are going to use the recovered cluster to examine scheduling and controllers.
