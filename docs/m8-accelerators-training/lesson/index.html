Scheduling accelerators and distributed model training

What you will learn​

  • Explain why GPU count alone does not predict training speed
  • Compare device plugins with Dynamic Resource Allocation, or DRA
  • Follow a ResourceClaim from device selection to node preparation
  • Explain how Kueue controls quota, priority, and all-or-nothing admission
  • Separate device, admission, workload, communication, and storage responsibilities

1. Why eight GPUs can be slower than four​

A training job receives every GPU it requested, but it runs more slowly than a smaller job. This is possible because distributed training spends time moving data and synchronising gradients. The slowest communication link can limit the complete job.

For example, four GPUs connected through NVLink may communicate much faster than eight GPUs split across two nodes. The second job has more devices, but every training step must cross the network.

The production result is completed work, not allocated GPU count. Measure:

  • training step time,
  • communication time,
  • GPU idle time,
  • data-loading time,
  • checkpoint duration,
  • and work lost after failure or preemption.

Before adding GPUs, ask which stage is waiting. More devices will not fix a storage, quota, topology, or synchronisation bottleneck.

2. Device plugins vs Dynamic Resource Allocation​

Think of the GPU fleet as a warehouse.

Device plugins: numbered shelves​

In the older warehouse, a shelf only reports a count: nvidia.com/gpu: 8. A worker asks for two items and receives any two available items. The request cannot easily say "A100", "at least 40 GiB of memory", or "same NVLink group".

This is the device-plugin model. It is simple and remains suitable when nodes have one predictable device type and workloads only need a count.

DRA: barcoded inventory​

In the newer warehouse, every device has a barcode. The inventory includes model, memory, family, driver information, and other properties. A workload can request devices that match specific attributes.

This is Dynamic Resource Allocation, or DRA. It represents devices as structured API data instead of one opaque integer. The scheduler can evaluate selectors and allocate named devices.

Use DRA when attributes, sharing, or topology solve a real workload problem. Do not migrate only because the API is newer. A production platform normally keeps a small, well-tested catalogue of DeviceClass objects instead of allowing every team to invent a different device vocabulary.

DRA uses four core objects in resource.k8s.io/v1:

ObjectScopeTypical ownerPurpose
ResourceSliceClusterDRA driverPublishes devices and their attributes
DeviceClassClusterPlatform teamDefines a supported class and selectors
ResourceClaimNamespaceWorkload ownerRequests one or more suitable devices
ResourceClaimTemplateNamespaceWorkload ownerCreates a separate claim for each Pod

The older and newer models can exist in the same cluster. Choose per workload and device driver.

3. How DRA selects and prepares accelerators​

The DRA flow has two different jobs. The scheduler selects a suitable device and node. The node-side driver prepares that allocated device for the container.

This gives you two useful failure boundaries:

No matching allocation
  -> inspect the claim, class, slices, selectors, and scheduler events

Allocation exists but Pod cannot start
  -> inspect kubelet and the node-side DRA driver preparation path

Do not treat both as a generic "GPU scheduling failure". They have different owners and evidence.

Attribute selection with CEL​

A claim can use Common Expression Language, or CEL, to match device attributes:

apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: training-gpus
spec:
  devices:
    requests:
    - name: gpu
      exactly:
        deviceClassName: gpu.example.com
        count: 2
        selectors:
        - cel:
            expression: >-
              device.attributes["gpu.example.com"].model == "A100"
              && device.capacity["gpu.example.com"].memory.compareTo(quantity("40Gi")) >= 0

This request asks for two A100 devices with at least 40 GiB of memory. Put hard requirements in the selector only when the job truly cannot run without them. A long list of preferences written as hard requirements can leave expensive capacity unused.

What the driver publishes​

A DRA driver discovers node hardware and publishes a ResourceSlice:

apiVersion: resource.k8s.io/v1
kind: ResourceSlice
spec:
  driver: gpu.example.com
  nodeName: worker-1
  devices:
  - name: gpu-0
    basic:
      attributes:
        gpu.example.com:
          model: { stringValue: "A100" }
          family: { stringValue: "Ampere" }
          uuid:   { stringValue: "GPU-abc-123" }
      capacity:
        gpu.example.com:
          memory: "80Gi"
  - name: gpu-1
    basic:
      attributes:
        gpu.example.com:
          model: { stringValue: "T4" }
          family: { stringValue: "Turing" }
      capacity:
        gpu.example.com:
          memory: "16Gi"

The API objects are part of your incident evidence. Check the published inventory, the selected allocation in claim status, and the node preparation logs. For every driver upgrade, test create, schedule, use, delete, and cleanup. A successful allocation is not enough if a failed Pod leaves a device locked.

4. How Kueue admits batch and AI jobs​

DRA answers, "Which devices match this Pod?" It does not answer, "Should this training job start now?"

For that question, imagine a hiring desk in front of the warehouse. A team submits a complete job request. The hiring desk checks team quota, priority, and whether all required workers can begin. Only then does it allow the workers to enter the warehouse.

Kueue provides this admission layer. The Kubernetes scheduler still places Pods on nodes. Kueue decides whether a batch workload may create active Pods and consume quota.

Kueue uses these main objects:

ObjectScopePurpose
ResourceFlavorClusterDescribes a resource or node flavour
ClusterQueueClusterHolds quota and preemption policy
LocalQueueNamespaceGives users a namespace-level queue name
WorkloadNamespaceRepresents the admitted or waiting job
WorkloadPriorityClassClusterOrders admission and supports preemption

Admission sequence​

A suspended workload is often cheaper and clearer than hundreds of Pending Pods. It does not hold partial node resources while waiting for the rest of a distributed job.

Kueue can also preempt a lower-priority workload. Use this only when the victim can recover from a checkpoint. Priority without checkpoint policy converts urgent work into lost work.

For all-or-nothing jobs, configure admission and readiness rules so the complete worker group starts or the workload returns to the queue. Five running workers out of eight may consume GPUs without making useful progress.

5. GPU topology and division of responsibility​

The scheduler may allocate the correct model and count while choosing a slow communication path. The approximate hierarchy looks like this:

PlacementExample linkRelative behaviour
Same accelerator fabricNVLinkHighest bandwidth, lowest latency
Same PCIe complexPCIeSlower than direct accelerator fabric
Cross CPU socketUPI or Infinity FabricAdds another host boundary
Cross nodeEthernet or InfiniBandNetwork becomes part of every collective operation

NCCL, the NVIDIA Collective Communications Library, chooses communication algorithms from the topology it receives. It cannot remove a slow physical link chosen by placement.

Measure step time and collective communication bandwidth. Then express only the topology rule that the workload needs, such as same node or same topology block. Packing every job into the smallest domain can reduce cluster utilisation, so topology should follow evidence.

The complete system has clear ownership boundaries:

LayerMain systemDecision
Device selectionDRA and scheduler pluginWhich exact devices satisfy the claim
Job admissionKueueWhether quota and priority allow the job to start
Workload lifecycleJobSet or Kubeflow TrainerHow the multi-Pod job starts, retries, and completes
CommunicationFramework and NCCLHow workers exchange gradients and tensors
Data and checkpointsStorage and training platformHow data arrives and completed work survives failure

When a job is slow, use these boundaries. Do not ask the scheduler team to fix a slow dataset read, and do not ask the training framework team to fix an unsatisfied ResourceClaim.

Data and checkpoint paths​

Large training jobs may spend more time moving data than computing.

  • Shard training data so every worker does not read the same full dataset.
  • Use a fast local tier for active data where it improves measured throughput.
  • Write frequent local checkpoints, then copy them asynchronously to durable storage.
  • Record checkpoint age so the admission system knows the cost of preemption.

A large model plus optimiser state can produce checkpoints of hundreds of gigabytes. Local NVMe is fast but does not survive node loss. Durable object or network storage survives, but may slow the training step. A two-tier design gives you both speed and recovery.

6. A production accelerator and checkpoint policy​

Set policy around completed work and recovery, not around allocation percentage.

DecisionRecommended practiceAvoidEvidence
Device modelKeep simple workloads on device plugins; use DRA when attributes or topology matterMigrating only because DRA is newerClaim status, driver health, scheduler events
Device classesOffer a small platform-owned catalogueA separate class and vocabulary for every teamClass use, unmatched claims, capacity fragmentation
AdmissionLet Kueue admit the complete workload against team quotaCreating Pods first and hoping capacity appearsWorkload conditions and queue usage
TopologyDerive co-location rules from communication measurementsRequesting only "8 GPUs" for a tightly coupled jobStep time, NCCL bandwidth, allocated topology
PreemptionPreempt checkpoint-capable workloads and include recovery costGiving every workload the highest priorityCheckpoint age, lost steps, preemption count
Data pathCombine a fast working tier with durable checkpointsTreating shared storage as unlimitedGPU idle time, read rate, checkpoint duration
Driver changeCanary and test allocation, preparation, release, and cleanupUpgrading all GPU nodes togetherClaim lifecycle, node logs, leaked allocations
The production question

Ask, "Which stage is waiting?" If the answer is quota, data, another worker, network communication, or checkpoint I/O, adding GPUs increases cost without increasing completed work.

In the lab, you will inspect simulated GPU inventory, allocate devices by attribute, and observe Kueue admission with quota. Use the API objects to identify which layer made each decision.
