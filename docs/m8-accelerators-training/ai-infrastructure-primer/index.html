AI infrastructure for Kubernetes engineers

Module 8 uses terms such as GPU topology, AllReduce, NCCL, NVLink, DRA, and Kueue. These terms can be difficult to connect if your experience is mainly with application and Kubernetes platforms.

This primer explains each foundation before the main Module 8 lesson uses it. It starts with the AI workload, follows the data through one GPU and several GPU servers, and then shows which decisions Kubernetes controls.

You do not need prior experience with machine learning or GPU servers.

AI workload foundations​

AI training​

AI training is the process of changing a model's parameters so that its predictions improve. A training program repeats the following loop:

  1. Read a batch of training examples.
  2. Run the model and produce a prediction. This is called the forward pass.
  3. Compare the prediction with the expected result and calculate a loss value.
  4. Calculate how each parameter contributed to that loss. This is called the backward pass.
  5. Use those calculations to update the model parameters.

The parameters being updated are normally called weights. A large model can contain billions of weights. Training also keeps temporary values and optimizer state, so it needs much more memory than storing the weights alone.

AI inference​

AI inference uses a model that has already been trained. The model receives an input and produces an output without updating its weights.

For a language model, the input is converted into tokens. The model processes those tokens and generates output tokens. The runtime keeps temporary attention data in a KV cache while the request is active.

Training and inference use the same type of GPU, but their resource patterns differ:

WorkloadData it keepsMain operational concern
TrainingWeights, activations, gradients, optimizer state, checkpointsTime required to complete a training step
InferenceWeights, activations, KV cache, request batchesRequest latency and tokens produced per second

Module 8 focuses on training and accelerator allocation. Module 9 covers inference serving in more detail.

Model data​

The following terms describe data that moves through an AI system:

TermWhat it containsWhen it is used
WeightsValues learned by the modelTraining and inference
ActivationsIntermediate outputs created by model layersForward and backward passes
GradientsValues that describe how weights should changeTraining
Optimizer stateAdditional values used while updating weightsTraining
KV cacheAttention data retained for active language-model requestsInference
CheckpointA saved copy of model and training stateFailure recovery and restart

These values can be larger than one GPU's memory. They may also need to move between GPUs during every training step. That is why AI infrastructure depends on memory and interconnect topology as well as compute capacity.

GPU​

A Graphics Processing Unit, or GPU, is a processor with many parallel execution units. AI frameworks use those units to perform large tensor and matrix operations.

A CPU has fewer, more general-purpose cores. It is suitable for control flow, data preparation, and operating-system work. A GPU can perform many similar numerical operations at the same time. This is useful because model training repeatedly applies the same mathematical operations across large arrays of values.

A GPU is not only compute units. It also includes local memory, memory controllers, caches, and links to the rest of the server.

HBM​

High Bandwidth Memory, or HBM, is the local memory attached to a data-center GPU. The GPU stores active weights, activations, gradients, optimizer state, or KV cache in HBM while it uses them.

HBM has two independent properties:

  • Capacity is the amount of data that fits in memory.
  • Bandwidth is the rate at which the GPU can read and write that data.

A model may fail to fit because HBM capacity is too small. A model may fit but still run slowly if the compute units wait for memory reads. GPU monitoring must therefore include both memory use and memory throughput.

PCI Express​

PCI Express, or PCIe, is the general I/O connection inside a server. It connects the CPU and system memory to devices such as GPUs, network cards, NVMe storage, DPUs, and FPGAs.

PCIe links have a generation and a lane count. A GPU commonly uses a link such as PCIe Gen 5 x16. The generation controls the transfer rate per lane. The x16 value means that the link has sixteen lanes.

Data crosses PCIe when a model moves from CPU memory into GPU memory, when the GPU communicates with a PCIe network card, or when storage data reaches the GPU through the normal host path. PCIe is much slower than local HBM, so repeated host-to-device transfers can leave GPU compute units waiting.

NUMA​

Large servers often have more than one CPU socket. Each socket has local memory and local PCIe connections. This arrangement is called Non-Uniform Memory Access, or NUMA, because local and remote access take different paths.

If a GPU and network card are attached below the same CPU socket and PCIe root complex, their data path is short. If they are attached to different sockets, traffic may cross the CPU interconnect. The devices may have the same specifications but produce different performance because their physical paths differ.

Commands such as nvidia-smi topo -m show GPU, CPU, NUMA, and network-card relationships on NVIDIA systems. Kubernetes requires topology information from hardware drivers before it can make useful placement decisions.

Distributed training foundations​

Distributed training​

Distributed training uses more than one worker to train a model. A worker is usually one process associated with one GPU. Frameworks assign each worker a rank so that the workers can identify one another.

There are several ways to divide the work:

  • Data parallelism gives each worker a different training batch while keeping a copy of the model on every worker.
  • Tensor parallelism splits tensor operations across GPUs.
  • Pipeline parallelism places different model stages on different workers.
  • Expert parallelism places different mixture-of-experts components on different workers.

Module 8 mainly needs the data-parallel case because it clearly shows why workers must exchange gradients.

Gradient synchronization​

In data parallel training, every worker starts a step with the same model weights. Each worker processes a different batch and calculates different local gradients.

The workers must combine those gradients before updating their model copies. Otherwise, every worker would update its weights differently and the model copies would no longer match. This exchange is called gradient synchronization.

The next training step cannot safely start until the required synchronization completes. One slow worker or network path can therefore delay the complete worker group.

Collective operations​

A collective operation is a communication operation involving a group of workers. The operation defines which workers contribute data and which workers receive the result.

Common collective operations include:

OperationWhat it does
BroadcastSends data from one worker to every worker
AllGatherCollects a different data section from each worker and gives the complete set to every worker
ReduceScatterCombines values and gives a different result section to each worker
AllReduceCombines values from every worker and gives the combined result to every worker

These are communication patterns, not network products. A communication library implements them using the available GPU and network links.

AllReduce​

AllReduce combines a value from every worker and returns the combined result to every worker. For gradient synchronization, the combined value is commonly a sum or average.

Consider four workers with local gradients g0, g1, g2, and g3. AllReduce performs two logical jobs:

  1. Reduce the four gradient sets into one result.
  2. Distribute that result back to all four workers.

The implementation does not need to send every value through one central worker. Ring and tree algorithms divide the transfer into smaller steps. The chosen algorithm depends on message size, worker count, and topology.

NCCL​

NVIDIA Collective Communications Library, or NCCL, is a library that implements collective operations for NVIDIA GPUs. Training frameworks such as PyTorch call NCCL when GPU workers need to run operations such as AllReduce or AllGather.

NCCL examines the visible topology and chooses communication algorithms and transports. Depending on the system, it may use NVLink, PCIe, shared memory, InfiniBand, RoCE, or ordinary IP networking.

NCCL does not schedule Pods, allocate GPUs, or make a slow link faster. It uses the devices and paths that the platform and scheduler have made available.

GPU interconnects and network fabrics​

NVLink​

NVLink is NVIDIA's high-bandwidth connection for supported GPUs and accelerated systems. It provides a direct GPU communication path with more bandwidth than ordinary GPU-to-GPU transfers through the host PCIe path.

Training and inference runtimes can use NVLink when model data, activations, or gradients must move between connected GPUs. NVLink is a physical interconnect. NCCL is the software library that can use that interconnect for collective operations.

NVSwitch​

NVSwitch is a switch that connects several NVLink-capable GPUs into one GPU fabric. Direct links between every pair of GPUs become difficult as the number of GPUs grows. NVSwitch provides high-bandwidth paths across a larger group.

An eight-GPU server connected through NVSwitch behaves differently from a server containing eight independent PCIe GPUs. Both servers report eight GPUs, but their GPU-to-GPU communication paths are not equivalent.

Network fabrics​

Communication leaves the local GPU fabric when workers run on different servers. The following network technologies may carry that traffic:

FabricDescription
EthernetGeneral-purpose data-center network
InfiniBandHigh-bandwidth, low-latency network designed for HPC and AI communication
RoCERDMA over Converged Ethernet, which carries RDMA traffic over a configured Ethernet network

The network interface card, switch fabric, congestion controls, routing, and topology all affect distributed-training performance.

RDMA​

Remote Direct Memory Access, or RDMA, allows one machine to read or write registered memory on another machine with less CPU and operating-system involvement.

Without RDMA, data normally passes through the sender's network stack and CPU memory, crosses the network, and passes through the receiver's CPU memory and network stack. RDMA reduces these copies and software-processing steps.

RDMA is a data-transfer mechanism. InfiniBand and RoCE are common network fabrics that provide it.

GPUDirect RDMA​

GPUDirect RDMA allows a supported network card to exchange data directly with GPU memory. The normal alternative stages the data through CPU memory before the network card can send it.

The direct path reduces CPU involvement and avoids an extra host-memory copy. It still depends on the GPU, network card, PCIe topology, driver, and network being configured correctly.

GPUDirect RDMA matters when distributed workers exchange large tensors or gradients across servers.

Scale up and scale out​

Scale up connects more GPUs within one high-bandwidth system. NVLink and NVSwitch are common parts of this local scale-up domain.

Scale out connects several GPU servers over a network fabric. InfiniBand, RoCE, or Ethernet carry traffic in this domain.

Training a model across eight GPUs inside one NVSwitch system is not the same as training it across eight GPUs placed on eight servers. The GPU count is the same, but the communication distance is different.

Topology-aware placement​

Topology describes how CPUs, memory, GPUs, PCIe switches, network cards, servers, and network switches are connected.

A topology-aware placement system tries to keep tightly communicating workers inside the smallest domain that satisfies the request. It may prefer the same NVLink group, then the same server, then the same rack, before using a more distant path.

Topology is a requirement only when the workload depends on it. Packing every job into the smallest domain can reduce cluster utilization. Platform teams should derive placement rules from measured communication time and training-step time.

Kueue's Topology-Aware Scheduling represents hierarchy through node labels and a Topology object referenced by a ResourceFlavor. A workload can prefer or require a topology level such as a rack. Kueue assigns suitable topology domains during admission; the Kubernetes scheduler still selects the individual nodes that satisfy that assignment.

Kubernetes accelerator control​

Device plugins​

A Kubernetes device plugin discovers node devices and advertises an extended resource such as nvidia.com/gpu. A Pod requests an integer count:

resources:
  limits:
    nvidia.com/gpu: 2

The kubelet asks the plugin to allocate suitable devices before starting the container. This model works well for a uniform fleet, but the resource count does not describe device memory, model, sharing mode, or interconnect topology.

Dynamic Resource Allocation​

Dynamic Resource Allocation, or DRA, represents devices through Kubernetes API objects. Drivers publish device inventory and attributes in ResourceSlice objects. Workloads request devices through ResourceClaim objects.

A DRA request can select a device class and match attributes or capacity with CEL expressions. The scheduler selects named devices and records the allocation in claim status before the kubelet prepares them for the container.

DRA gives Kubernetes more information than an integer resource count. It still depends on drivers publishing the attributes and topology that a workload needs.

Accelerator scheduling layers​

Accelerator workloads pass through three separate scheduling decisions:

LayerQuestion it answersMain controls
KueueShould this workload run now?Queue, quota, priority, fairness, group admission
kube-schedulerWhich node should run each Pod?Filter, score, reserve, and bind
DRAWhich exact device should the workload receive?ResourceClaim, ResourceSlice, device class, attributes, capacity

These layers complement one another. Kueue does not replace the Kubernetes scheduler, and DRA does not decide which team's work should consume scarce capacity first.

Gang scheduling​

A distributed training job may need several worker Pods before useful computation can begin. Consider four workers that each request eight GPUs. The complete workload needs 32 GPUs.

If only 24 GPUs are free, starting three workers can reserve expensive devices while the fourth worker remains Pending. The three running workers may be unable to make progress because the training runtime expects the complete group.

Gang scheduling means admitting the worker group together or keeping the group waiting. When all 32 GPUs can be made available, the workload is admitted and its four workers can start.

Kueue​

Kueue is a Kubernetes batch admission controller. It decides whether a complete workload may start based on quota, priority, and admission policy.

Kueue normally suspends a queued Job before its Pods consume resources. When quota becomes available, Kueue admits the workload and allows the Job to create active Pods. Higher-priority work may preempt lower-priority work when policy allows it.

Kueue does not select the physical GPU. DRA and the Kubernetes scheduler handle device and node selection after admission.

Kueue organizes team-facing queues and shared resource pools:

  • A LocalQueue gives workloads in a namespace a submission point.
  • A ClusterQueue defines shared quota, resource flavors, priority, preemption, fair sharing, and admission policy.
  • A Workload represents the group that Kueue admits. It may come from a Job, JobSet, PyTorchJob, MPIJob, RayJob, or another supported controller.

Kueue's waitForPodsReady behavior can stop an admitted workload from holding resources indefinitely when the expected Pods cannot become ready together.

DRA and Kueue together​

For a multi-worker training job, the control flow is:

  1. Kueue checks quota, priority, policy, and whether the workload can be admitted as a group.
  2. The workload controller creates or activates the worker Pods.
  3. The Kubernetes scheduler selects suitable nodes.
  4. DRA matches each ResourceClaim to named devices from the published ResourceSlice inventory.
  5. The kubelet and DRA driver prepare those devices for the containers.

Kueue allocates the opportunity to run. DRA allocates the devices used by the admitted workload.

Kueue applicability​

Using a GPU does not automatically require Kueue.

ScenarioDRA or device pluginKueue
Inference Deployment whose replicas can start independentlyYesUsually no
Occasional single-GPU Job in a cluster with spare capacityYesUsually no
Many queued GPU JobsYesYes
Several teams sharing accelerator quotaYesYes
Distributed training that needs all workers togetherYesYes
Priority, fair sharing, or workload preemptionDevice side onlyYes

Introduce Kueue when scarce resources are oversubscribed, workloads compete for quota, or a multi-Pod workload must be admitted as a group. Do not introduce it merely because a Pod requests an accelerator.

Responsibility boundaries​

Each layer owns a separate decision:

LayerMain componentDecision
Training logicPyTorch, JAX, TensorFlowWhat computation runs
Collective communicationNCCLHow GPU workers exchange data
Multi-worker lifecycleJobSet, Kubeflow TrainerHow the worker group starts and completes
AdmissionKueueWhether quota and priority allow the workload to start
Placement and allocationScheduler, device plugin, DRAWhich node and devices satisfy the request
Device preparationKubelet, container runtime, vendor driverHow the container receives the device
Physical executionGPU, HBM, PCIe, NVLink, NIC, storageHow fast the selected data path runs

When a workload is Pending, inspect admission, claims, scheduler events, and driver state. When it is Running but slow, inspect data loading, memory use, collective time, and physical topology.

Reading the Module 8 lab​

M8 lab scope​

The Module 8 lab does not require a physical GPU. The example DRA driver publishes simulated GPU devices. This lets you inspect the Kubernetes control-plane decisions on a normal laptop.

The lab proves:

  • device inventory through ResourceSlice,
  • device requests through ResourceClaim,
  • attribute and capacity selection through CEL,
  • selected devices recorded in claim status,
  • Kueue quota and admission,
  • and priority-based preemption.

The simulation does not measure HBM bandwidth, PCIe throughput, NVLink, NCCL, RDMA, or real training performance. Those require physical hardware and a distributed training runtime.

Question to carry into Module 8

Do not ask only whether the Job received eight GPUs. Ask whether it received suitable GPUs in a useful topology, and whether the complete worker group could start together.
