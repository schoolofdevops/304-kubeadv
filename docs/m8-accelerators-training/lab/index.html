Scheduling Accelerators and Training Jobs

Before you start

All commands in this lab run against the core-internals cluster and from the root of the lab repo (304-labs/).

The setup downloads the DRA example driver and Kueue images. The first installation may take a few minutes.

In this lab, you are going to install a Dynamic Resource Allocation driver with simulated GPUs.

You would then use Kueue to admit, queue and preempt training Jobs based on quota and priority.

By the end of this lab, you will:

  • inspect GPUs published as ResourceSlices
  • allocate devices with ResourceClaims
  • select devices using CEL expressions
  • manage training Jobs with Kueue quota and priority

Pre Requisites​

Check the current Kubernetes context.

kubectl config current-context

[ Expected output ]

kind-kubeadv-core

PART I - Allocate Accelerator Devices​

Install the DRA Driver and Kueue​

Run the setup script to install the DRA example driver and Kueue.

Inspect the Device Inventory​

The DRA driver publishes the available devices through a ResourceSlice. Examine the first device.

kubectl --context kind-kubeadv-core get resourceslice -o jsonpath='{.items[0].spec.devices[0]}' | python3 -m json.tool

[ sample output ]

{
    "attributes": {
        "driverVersion": {
            "version": "1.0.0"
        },
        "index": {
            "int": 0
        },
        "model": {
            "string": "LATEST-GPU-MODEL"
        },
        "uuid": {
            "string": "gpu-<unique-id>"
        }
    },
    "capacity": {
        "compute": {
            "value": "100"
        },
        "memory": {
            "value": "80Gi"
        }
    },
    "name": "gpu-0"
}

Each GPU has a name, attributes and capacities. In this example, the device reports its model, driver version, UUID, index, memory and compute capacity.

A traditional device plugin publishes a resource count. DRA also exposes information about each device.

List the device names.

kubectl --context kind-kubeadv-core get resourceslice -o jsonpath='{.items[0].spec.devices[*].name}'

[ Expected output ]

gpu-0 gpu-1 gpu-2 gpu-3 gpu-4 gpu-5 gpu-6 gpu-7

Make sure that the ResourceSlice contains eight devices.

Allocate a GPU with a ResourceClaim​

Create a ResourceClaim which requests one GPU from the gpu.example.com DeviceClass.

kubectl --context kind-kubeadv-core -n m8-lab apply -f - <<'EOF'
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: single-gpu
spec:
  devices:
    requests:
    - name: gpu
      exactly:
        deviceClassName: gpu.example.com
        count: 1
EOF

[ Expected output ]

resourceclaim.resource.k8s.io/single-gpu created

The claim is not allocated until a Pod references it. Create a Pod which uses the claim.

kubectl --context kind-kubeadv-core -n m8-lab apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: gpu-test
spec:
  containers:
  - name: worker
    image: busybox:1.36
    command: ["sleep", "3600"]
    resources:
      claims:
      - name: gpu
  resourceClaims:
  - name: gpu
    resourceClaimName: single-gpu
  restartPolicy: Never
EOF

[ Expected output ]

pod/gpu-test created

Wait for the Pod to become ready.

kubectl --context kind-kubeadv-core -n m8-lab wait --for=condition=ready pod gpu-test --timeout=120s

[ Expected output ]

pod/gpu-test condition met

Examine the device allocated to the claim.

kubectl --context kind-kubeadv-core -n m8-lab get resourceclaim single-gpu \
  -o jsonpath='{.status.allocation.devices.results[0]}' | python3 -m json.tool

[ sample output ]

{
    "device": "gpu-0",
    "driver": "gpu.example.com",
    "pool": "kubeadv-core-worker",
    "request": "gpu"
}

The claim status contains the device name, driver and pool. The exact device name may differ on your cluster.

Examine the allocation exposed inside the container.

kubectl --context kind-kubeadv-core -n m8-lab exec gpu-test -- env | grep GPU

[ sample output ]

DRA_RESOURCE_DRIVER_NAME=gpu.example.com
GPU_DEVICE_GPU_0_RESOURCE_CLAIM=<claim-uid>
GPU_DEVICE_0=gpu-0
GPU_DEVICE_0_SHARING_STRATEGY=TimeSlicing
GPU_DEVICE_0_TIMESLICE_INTERVAL=Default

The environment variables include the device name, driver, claim UID and sharing strategy.

Select Devices with CEL​

Create another claim. This time, use a CEL expression to select two GPUs with at least 40 GiB of memory.

kubectl --context kind-kubeadv-core -n m8-lab apply -f - <<'EOF'
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: large-memory-gpu
spec:
  devices:
    requests:
    - name: gpu
      exactly:
        deviceClassName: gpu.example.com
        count: 2
        selectors:
        - cel:
            expression: "device.capacity['gpu.example.com'].memory.compareTo(quantity('40Gi')) >= 0"
EOF

[ Expected output ]

resourceclaim.resource.k8s.io/large-memory-gpu created

Create a Pod which uses this claim.

kubectl --context kind-kubeadv-core -n m8-lab apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: gpu-large
spec:
  containers:
  - name: worker
    image: busybox:1.36
    command: ["sleep", "3600"]
    resources:
      claims:
      - name: gpu
  resourceClaims:
  - name: gpu
    resourceClaimName: large-memory-gpu
  restartPolicy: Never
EOF

[ Expected output ]

pod/gpu-large created
kubectl --context kind-kubeadv-core -n m8-lab wait --for=condition=ready pod gpu-large --timeout=120s

[ Expected output ]

pod/gpu-large condition met

Examine the allocation.

kubectl --context kind-kubeadv-core -n m8-lab get resourceclaim large-memory-gpu \
  -o jsonpath='{.status.allocation.devices.results}' | python3 -m json.tool

[ sample output ]

[
    {
        "device": "gpu-1",
        "driver": "gpu.example.com",
        "pool": "kubeadv-core-worker",
        "request": "gpu"
    },
    {
        "device": "gpu-2",
        "driver": "gpu.example.com",
        "pool": "kubeadv-core-worker",
        "request": "gpu"
    }
]

Two devices should be present. Each simulated GPU has 80 GiB of memory and matches the CEL expression.

The device names may differ because the scheduler selects from the devices which are still available.

PART II - Manage Training Jobs with Kueue​

Create the Kueue Infrastructure​

Create a ResourceFlavor, ClusterQueue, LocalQueue and two priority classes.

kubectl --context kind-kubeadv-core apply -f - <<'EOF'
apiVersion: kueue.x-k8s.io/v1beta2
kind: ResourceFlavor
metadata:
  name: default-flavor
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: team-queue
spec:
  namespaceSelector: {}
  preemption:
    withinClusterQueue: LowerPriority
    reclaimWithinCohort: Never
  resourceGroups:
  - coveredResources: ["cpu", "memory"]
    flavors:
    - name: default-flavor
      resources:
      - name: "cpu"
        nominalQuota: 4
      - name: "memory"
        nominalQuota: "4Gi"
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: LocalQueue
metadata:
  namespace: m8-lab
  name: team-a
spec:
  clusterQueue: team-queue
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: WorkloadPriorityClass
metadata:
  name: low-priority
value: 100
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: WorkloadPriorityClass
metadata:
  name: high-priority
value: 1000
EOF

[ Expected output ]

resourceflavor.kueue.x-k8s.io/default-flavor created
clusterqueue.kueue.x-k8s.io/team-queue created
localqueue.kueue.x-k8s.io/team-a created
workloadpriorityclass.kueue.x-k8s.io/low-priority created
workloadpriorityclass.kueue.x-k8s.io/high-priority created

The team-queue has a quota of four CPUs. You are going to submit Jobs against this quota.

Submit a Job within Quota​

Submit a low-priority Job which requests three CPUs.

kubectl --context kind-kubeadv-core -n m8-lab apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: low-priority-job
  labels:
    kueue.x-k8s.io/queue-name: team-a
    kueue.x-k8s.io/priority-class: low-priority
spec:
  parallelism: 3
  completions: 3
  template:
    spec:
      containers:
      - name: worker
        image: busybox:1.36
        command: ["sleep", "120"]
        resources:
          requests:
            cpu: "1"
            memory: "200Mi"
      restartPolicy: Never
EOF

[ Expected output ]

job.batch/low-priority-job created

Check the Workload created by Kueue.

kubectl --context kind-kubeadv-core -n m8-lab get workloads

[ sample output ]

NAME                         QUEUE    RESERVED IN   ADMITTED   FINISHED   AGE
job-low-priority-job-d68b0   team-a   team-queue    True                  9s

The Workload is admitted because its three-CPU request fits within the four-CPU quota. Check the Job.

kubectl --context kind-kubeadv-core -n m8-lab get jobs

[ sample output ]

NAME               STATUS    COMPLETIONS   DURATION   AGE
low-priority-job   Running   0/3           9s         9s

Submit a Job beyond Quota​

Submit another three-CPU Job. Both Jobs cannot fit within the four-CPU quota at the same time.

kubectl --context kind-kubeadv-core -n m8-lab apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: overflow-job
  labels:
    kueue.x-k8s.io/queue-name: team-a
    kueue.x-k8s.io/priority-class: low-priority
spec:
  parallelism: 3
  completions: 3
  template:
    spec:
      containers:
      - name: worker
        image: busybox:1.36
        command: ["sleep", "120"]
        resources:
          requests:
            cpu: "1"
            memory: "200Mi"
      restartPolicy: Never
EOF

[ Expected output ]

job.batch/overflow-job created
kubectl --context kind-kubeadv-core -n m8-lab get workloads

[ sample output ]

NAME                         QUEUE    RESERVED IN   ADMITTED   FINISHED   AGE
job-low-priority-job-d68b0   team-a   team-queue    True                  33s
job-overflow-job-66c8c       team-a                                       11s

The overflow Workload has no value under RESERVED IN or ADMITTED. Kueue is holding it because the total request would exceed the quota.

kubectl --context kind-kubeadv-core -n m8-lab get jobs

[ sample output ]

NAME               STATUS      COMPLETIONS   DURATION   AGE
low-priority-job   Running     0/3           33s        33s
overflow-job       Suspended   0/3                      11s

The overflow Job is suspended. Kueue will start it only when quota becomes available.

Preempt with High Priority​

Submit a high-priority Job which also requests three CPUs.

kubectl --context kind-kubeadv-core -n m8-lab apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: urgent-job
  labels:
    kueue.x-k8s.io/queue-name: team-a
    kueue.x-k8s.io/priority-class: high-priority
spec:
  parallelism: 3
  completions: 3
  template:
    spec:
      containers:
      - name: worker
        image: busybox:1.36
        command: ["sleep", "60"]
        resources:
          requests:
            cpu: "1"
            memory: "200Mi"
      restartPolicy: Never
EOF

[ Expected output ]

job.batch/urgent-job created
kubectl --context kind-kubeadv-core -n m8-lab get workloads

[ sample output ]

NAME                         QUEUE    RESERVED IN   ADMITTED   FINISHED   AGE
job-low-priority-job-d68b0   team-a                 False                 62s
job-overflow-job-66c8c       team-a                                       40s
job-urgent-job-397dc         team-a   team-queue    True                  20s

Observe the Workload states:

  • urgent-job is admitted.
  • low-priority-job reports ADMITTED=False because it was preempted.
  • overflow-job is still waiting for quota.
kubectl --context kind-kubeadv-core -n m8-lab get jobs

[ sample output ]

NAME               STATUS      COMPLETIONS   DURATION   AGE
low-priority-job   Suspended   0/3                      62s
overflow-job       Suspended   0/3                      40s
urgent-job         Running     0/3           19s        20s

The low-priority Job is now suspended. Kueue performed admission-level preemption before the scheduler placed the replacement Pods.

Validate​

Make sure that:

  • the ResourceSlice lists eight devices with attributes and capacity
  • single-gpu is allocated one named device
  • large-memory-gpu is allocated two devices matching the CEL expression
  • low-priority-job was initially admitted
  • overflow-job remained suspended when quota was unavailable
  • urgent-job preempted the lower-priority Workload

Teardown​

Delete the lab resources, DRA driver and Kueue.

kubectl --context kind-kubeadv-core delete namespace m8-lab

kubectl --context kind-kubeadv-core delete clusterqueue team-queue
kubectl --context kind-kubeadv-core delete resourceflavor default-flavor
kubectl --context kind-kubeadv-core delete workloadpriorityclass low-priority high-priority

helm uninstall dra-example-driver --namespace dra-example-driver --kube-context kind-kubeadv-core
kubectl --context kind-kubeadv-core delete namespace dra-example-driver

kubectl --context kind-kubeadv-core delete -f https://github.com/kubernetes-sigs/kueue/releases/download/v0.17.2/manifests.yaml

# Belt-and-suspenders: the manifest delete above can leave the two Kueue
# visibility APIServices behind (stale "ServiceNotFound" registrations once
# their backing Service is gone). A stale APIService breaks API discovery
# cluster-wide — every future `kubectl create`/`apply` for ANY object starts
# failing with "failed calling webhook" or "unable to retrieve the complete
# list of server APIs", and kueue-system hangs in Terminating forever. Clean
# them up explicitly so M9 starts from a healthy cluster:
kubectl --context kind-kubeadv-core delete apiservice v1beta1.visibility.kueue.x-k8s.io v1beta2.visibility.kueue.x-k8s.io --ignore-not-found

[ sample output ]

namespace "m8-lab" deleted
clusterqueue.kueue.x-k8s.io "team-queue" deleted
resourceflavor.kueue.x-k8s.io "default-flavor" deleted
workloadpriorityclass.kueue.x-k8s.io "low-priority" deleted
workloadpriorityclass.kueue.x-k8s.io "high-priority" deleted
release "dra-example-driver" uninstalled
namespace "dra-example-driver" deleted
namespace "kueue-system" deleted
customresourcedefinition.apiextensions.k8s.io "clusterqueues.kueue.x-k8s.io" deleted
... (trimmed — CRDs, RBAC, webhooks) ...
apiservice.apiregistration.k8s.io "v1beta1.visibility.kueue.x-k8s.io" deleted
apiservice.apiregistration.k8s.io "v1beta2.visibility.kueue.x-k8s.io" deleted
If API Discovery Fails after Teardown

Check for a stale Kueue APIService.

kubectl get apiservices | grep False

[ Expected output ]

(no output)

Delete the two *.visibility.kueue.x-k8s.io APIServices if they are still present.

The core-internals cluster remains running for Module 9.

Summary​

In this lab, you inspected simulated GPUs as ResourceSlice devices and allocated them using ResourceClaims.

You also used CEL to select devices by capacity.

You then configured Kueue quota, queued a Job which did not fit and used priority to preempt a lower-priority Workload.
