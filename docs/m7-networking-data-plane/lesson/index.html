Networking and the data plane: iptables, nftables, eBPF, and Cilium

What you will learn​

  • Trace same-node Pod traffic and Service traffic through the Linux kernel
  • Explain what a CNI plugin does when Kubernetes creates a Pod
  • Compare Service routing with iptables, nftables, and eBPF
  • Diagnose NetworkPolicy drops with Hubble evidence
  • Explain how DNS search paths and conntrack can cause delay

1. Why green Pods can still have broken networking​

A Deployment can show the correct replica count while users still see timeouts. The Pods are Running, but the request may fail at DNS, Service routing, NetworkPolicy, the CNI data path, or the node network.

This is why Pod health is not enough evidence for a network incident. Start with one failed request. Record its source, destination, port, and time. Then test each part of the path instead of restarting several components together.

Use this order:

DNS -> Service and EndpointSlice -> NetworkPolicy -> CNI data path -> node network
The first production question

Ask, "Where did this one packet stop?" This gives the team a smaller and safer problem to solve.

2. Kubernetes networking as a postal system​

Think of a Kubernetes cluster as a city. A Pod is a house with its own address, the Pod IP. A Service is like a post-office box. It keeps one stable address and sends each letter to one of the available houses.

The control plane decides what should exist. The data plane moves the actual packets through the kernel. It is the combination of roads, sorting rules, and delivery staff in our postal system.

Kubernetes has used three common routing approaches:

ApproachHow it finds a routeSimple analogyProduction concern
iptables with kube-proxyWalks chains of rulesA clerk checks a large binderLarge rule sets take longer to update and inspect
nftablesUses sets and mapsA clerk uses an indexBetter rule handling, but still uses netfilter
eBPF with CiliumRuns programs and map lookups in the kernelThe sorting rule is placed near the senderFaster lookups and richer flow evidence, but different tools and skills are required

The choice matters when a cluster has thousands of Services and endpoints. It changes update cost, packet cost, and the evidence available during an incident.

3. How CNI gives a Pod its network​

The kubelet creates the Pod sandbox, but it does not build the Pod network itself. It calls a Container Network Interface, or CNI, plugin. CNI is a standard contract between the container runtime and a network plugin.

The main CNI operations are ADD, DEL, CHECK, and VERSION.

  • ADD prepares networking for a new sandbox.
  • DEL removes that networking when the sandbox goes away.
  • CHECK verifies an existing setup.
  • VERSION reports supported CNI versions.

During ADD, a Cilium-based setup normally does four things:

  1. Creates a virtual Ethernet pair, called a veth pair. One end is inside the Pod network namespace and the other is on the host.
  2. Uses IP address management, or IPAM, to assign an address.
  3. Adds routes and attaches eBPF programs to the host-side interface.
  4. Gives the Pod a Cilium security identity based on its labels.

If a Pod is stuck at sandbox creation, check the Pod events and CNI agent logs before checking application logs. If existing Pods work but every new Pod fails, the CNI ADD path is a strong suspect.

For a CNI upgrade, test the full lifecycle on a small group of nodes: create a Pod, connect to it, delete it, and confirm that addresses and interfaces are cleaned up.

4. Same-node Pod-to-Pod packet path​

Two Pods on one node can communicate without using the physical network.

With a traditional Linux path, the packet leaves Pod A through its veth, enters the host network namespace, follows bridge or routing rules, and enters Pod B through the other veth. Netfilter rules may allow or drop the packet.

With Cilium eBPF host routing, a program on the host-side veth can identify that Pod B is local and redirect traffic closer to the interface. This can avoid parts of the normal bridge, routing, and netfilter path.

During diagnosis, compare two tests:

same-node Pod -> Pod
cross-node Pod -> Pod

If the same-node test works and the cross-node test fails, investigate node routing, tunnelling, cloud routes, or the physical network. If both fail, look closer to the Pod, policy, or CNI setup.

5. Service routing and the DNAT problem​

A Service ClusterIP is virtual. No Pod owns that IP. A data-plane component must translate it to a real endpoint. This is destination network address translation, or DNAT.

In kube-proxy iptables mode, kube-proxy watches Services and EndpointSlices and writes iptables chains. A Service with three endpoints may look like this:

-A KUBE-SVC-XXXX -m statistic --mode random --probability 0.333 -j KUBE-SEP-AAA
-A KUBE-SVC-XXXX -m statistic --mode random --probability 0.500 -j KUBE-SEP-BBB
-A KUBE-SVC-XXXX -j KUBE-SEP-CCC

Ten thousand Services with three endpoints can create more than 30,000 rules on every node. Rule updates and troubleshooting become expensive as this set grows.

Cilium can store Service and endpoint information in eBPF maps. A connection uses a map lookup instead of walking a long chain. This changes the implementation, but the operational question is the same: did the Service select a healthy endpoint, and did DNAT send the request there?

Compare these two tests during an incident:

request the endpoint Pod IP directly
request the Service ClusterIP

If the endpoint works but the Service fails, inspect the Service selector, EndpointSlice, and Service-routing data plane. Do not begin by changing the application.

6. NetworkPolicy as an allow-list firewall​

Kubernetes NetworkPolicy follows an allow-list model. With no policy selecting a Pod, traffic is allowed by default. When a policy selects that Pod for ingress or egress, the Pod becomes isolated for that direction. Only traffic allowed by a matching policy can pass.

This causes a common production mistake. A team adds one rule to allow the frontend to reach the backend. They expect all other traffic to continue. Instead, monitoring, DNS, or another caller stops working because it was not included in the allow list.

Cilium enforces policy with security identities derived from labels. For a packet arriving at a Pod, the eBPF program can check:

  1. the source identity,
  2. the destination identity and port,
  3. the relevant policy map,
  4. the final FORWARDED or DROPPED verdict.

Hubble records these flows with workload identities and policy context:

hubble observe --verdict DROPPED

Roll out policy in stages. First observe current communication, then add narrow allow rules, then introduce default deny. Attach an owner and a test to each rule. Never delete all policies during an incident just to see whether traffic returns. That changes the blast radius and removes useful evidence.

7. The DNS five-second trap and Hubble evidence​

The kubelet normally gives each Pod a resolver configuration similar to this:

nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

ndots:5 means that a name with fewer than five dots is first tried with each search suffix. A request for api.stripe.com may create these queries:

  1. api.stripe.com.default.svc.cluster.local
  2. api.stripe.com.svc.cluster.local
  3. api.stripe.com.cluster.local
  4. api.stripe.com.

The first three are expected to fail. One application lookup can therefore create four DNS queries. At scale, that can multiply CoreDNS load.

Some environments also show a five-second delay when parallel A and AAAA queries interact badly with conntrack. Conntrack is the kernel table that remembers active network flows. If one DNS reply is dropped, the resolver waits before retrying.

Useful fixes depend on evidence:

  • Use an absolute external name with a trailing dot, such as api.stripe.com..
  • Set a lower ndots value for workloads that mostly call external names.
  • Use single-request-reopen where the resolver and operating system support it.
  • Reduce query amplification and size CoreDNS from measured query load.

Use Hubble to confirm whether DNS requests and replies are flowing. Then check CoreDNS latency, errors, cache behaviour, and restarts. Hubble can show the network boundary, but it cannot explain an application bug or a slow upstream DNS server by itself.

8. Production networking incidents and lessons​

DNS amplification during a rollout​

Reddit described a March 2023 incident where DNS behaviour contributed to a large outage. A rollout created many new lookups, search-path expansion multiplied the work, and DNS capacity became part of a failure loop.

The production lesson is not to copy one fixed ndots value everywhere. Measure the names your applications resolve, the query amplification, CoreDNS capacity, and cache behaviour before a large rollout.

Conntrack exhaustion​

A node has a finite conntrack table. Agents, proxies, service meshes, and applications with high connection churn all share it. When the table fills, new flows can be dropped and the symptom may look random.

Monitor nf_conntrack_count against nf_conntrack_max, along with insert failures and drops. Increasing the limit may create time, but first remove unnecessary connection churn and check node memory.

9. A production network diagnostic standard​

Use a fixed order so that every team collects comparable evidence.

AreaRecommended practiceAvoidFirst evidence
CNI lifecyclePin versions, canary upgrades, and test new-Pod networkingUpgrading every node togetherCNI health, sandbox events, connectivity test
NetworkPolicyUse small allow rules with owners and automated testsOne large policy that nobody can explainHubble verdict, identities, policy name
DNSMeasure query load, cache hits, latency, and restartsRaising timeouts to hide query amplificationResolver queries and CoreDNS metrics
Service routingCompare endpoint-IP and ClusterIP requestsAssuming a healthy Pod proves the Service pathService, EndpointSlice, data-plane state
ConntrackAlert on use and insert failures; reduce connection churnTreating intermittent timeout as only an application problemCount, maximum, drops, node memory

During an incident:

  1. Record one failed request with source, destination, port, and time.
  2. Check DNS only if the request used a name.
  3. Confirm that the Service has ready EndpointSlice entries.
  4. Compare the direct endpoint and Service paths.
  5. Check Hubble for forwarded and dropped flows.
  6. Compare same-node and cross-node behaviour.
  7. Change one narrow control only after the evidence points to it.
Protect the evidence

Do not restart CoreDNS, CNI agents, and workloads together. Do not remove all NetworkPolicies. These actions may restore traffic for a short time, but they also hide the failed part of the path and can increase the incident impact.

The main production rule is simple: a green Pod proves very little about the complete request path. Trace one request across each network boundary and let the evidence choose the next check.
