Tracing and Controlling Kubernetes Network Traffic

Before you start

This lab uses a dedicated cilium-networking cluster with Cilium, kube-proxy replacement and Hubble.

All commands run from the root of the lab repo (304-labs/).

The first cluster creation may take three to five minutes while the Cilium images are downloaded.

In this lab, you are going to deploy a frontend and backend application. You would then trace its traffic with Hubble and control it using NetworkPolicy.

You would also examine the ndots:5 DNS behaviour and apply a Pod-level fix.

By the end of this lab, you will:

  • trace DNS, service translation and TCP flows
  • examine Cilium security identities
  • test default-deny and allow NetworkPolicies
  • reduce unnecessary DNS queries with ndots:1

Pre Requisites​

  • kind, kubectl, cilium and hubble should be installed.
  • Stop other kind clusters to leave enough memory for the three-node Cilium cluster.

PART II - Trace and Control Network Traffic​

Observe the Baseline Traffic with Hubble​

Send a request from the frontend Pod to the backend Service.

FRONTEND=$(kubectl --context kind-cilium-networking -n m7-lab get pod -l app=frontend -o jsonpath='{.items[0].metadata.name}')
kubectl --context kind-cilium-networking -n m7-lab exec $FRONTEND -- curl -s -o /dev/null -w "HTTP %{http_code} in %{time_total}s\n" http://backend

[ Expected output ]

HTTP 200 in 0.041s

Start a port-forward to Hubble Relay.

kubectl --context kind-cilium-networking -n kube-system port-forward svc/hubble-relay 4245:80 &

[ Expected output ]

Forwarding from 127.0.0.1:4245 -> 4245

Examine the recent flows from the namespace.

hubble observe --server localhost:4245 -n m7-lab --last 20

[ sample output ]

m7-lab/frontend-...:58858 (ID:26061) -> kube-system/coredns-...:53 (ID:28617) FORWARDED (UDP)
m7-lab/frontend-...:58858 (ID:26061) <- kube-system/coredns-...:53 (ID:28617) FORWARDED (UDP)
m7-lab/frontend-... (ID:26061) <> m7-lab/backend:80 (world) SOCK_XLATE_POINT_UNKNOWN TRACED (TCP)
m7-lab/frontend-...:49242 (ID:26061) -> m7-lab/backend-...:80 (ID:54397) FORWARDED (TCP Flags: SYN)
m7-lab/frontend-...:49242 (ID:26061) <- m7-lab/backend-...:80 (ID:54397) FORWARDED (TCP Flags: SYN, ACK)
m7-lab/frontend-...:49242 (ID:26061) -> m7-lab/backend-...:80 (ID:54397) FORWARDED (TCP Flags: ACK, PSH)
Reading the Flow

The flow shows three parts:

  1. DNS: the frontend resolves backend through CoreDNS on UDP port 53.
  2. SOCK_XLATE: Cilium translates the Service address to a backend endpoint.
  3. TCP: the trace shows the SYN, SYN/ACK and application data.

The numeric IDs are Cilium security identities derived from Pod labels. The identity remains useful when a replacement Pod receives a different IP address.

Examine Cilium Identities​

List the Cilium endpoints.

kubectl --context kind-cilium-networking -n m7-lab get ciliumendpoints

[ Expected output ]

NAME                        SECURITY IDENTITY   ENDPOINT STATE   IPV4
backend-7f78bfb4d8-789xg    54397               ready            10.244.2.228
backend-7f78bfb4d8-xxpnw    54397               ready            10.244.1.146
frontend-5ffcbcc5df-4vjgj   26061               ready            10.244.2.2

Both backend Pods share the same identity because they have the same labels. The frontend has a different identity.

Cilium applies policy to these identities rather than individual Pod IPs.

Apply a Default-Deny NetworkPolicy​

Apply a NetworkPolicy which denies ingress to every Pod in the namespace.

kubectl --context kind-cilium-networking -n m7-lab apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes:
  - Ingress
EOF

[ Expected output ]

networkpolicy.networking.k8s.io/default-deny-ingress created

Test the frontend-to-backend request again.

kubectl --context kind-cilium-networking -n m7-lab exec $FRONTEND -- curl -s -o /dev/null -w "HTTP %{http_code} in %{time_total}s\n" --connect-timeout 5 http://backend

[ Expected output ]

HTTP 000 in 5.002s
command terminated with exit code 28

The request times out. An empty podSelector selects every Pod in the namespace, and no ingress rule has been allowed.

Check the dropped flows in Hubble.

hubble observe --server localhost:4245 -n m7-lab --verdict DROPPED --last 5

[ sample output ]

m7-lab/frontend-...:53050 (ID:26061) <> m7-lab/backend-...:80 (ID:54397) Policy denied DROPPED (TCP Flags: SYN)
m7-lab/frontend-...:53050 (ID:26061) <> m7-lab/backend-...:80 (ID:54397) Policy denied DROPPED (TCP Flags: SYN)
NetworkPolicy Isolation

Once an ingress policy selects a Pod, traffic which is not allowed by a matching policy is denied.

Make sure every required source and port is covered before applying the policy in production.

Allow Frontend to Backend Traffic​

Create another policy which allows the frontend Pods to connect to the backend Pods on TCP port 80.

kubectl --context kind-cilium-networking -n m7-lab apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 80
EOF

[ Expected output ]

networkpolicy.networking.k8s.io/allow-frontend-to-backend created

Test the request again.

kubectl --context kind-cilium-networking -n m7-lab exec $FRONTEND -- curl -s -o /dev/null -w "HTTP %{http_code} in %{time_total}s\n" --connect-timeout 5 http://backend

[ Expected output ]

HTTP 200 in 0.066s

The request should succeed. Confirm the forwarded flow in Hubble.

hubble observe --server localhost:4245 -n m7-lab --verdict FORWARDED --protocol TCP --last 5

[ sample output ]

m7-lab/frontend-...:47638 (ID:26061) -> m7-lab/backend-...:80 (ID:54397) FORWARDED (TCP Flags: ACK, PSH)
m7-lab/frontend-...:47638 (ID:26061) <- m7-lab/backend-...:80 (ID:54397) FORWARDED (TCP Flags: ACK, PSH)

PART III - Examine Kubernetes DNS​

Observe the ndots:5 Behavior​

Examine the DNS configuration inside the frontend Pod.

kubectl --context kind-cilium-networking -n m7-lab exec $FRONTEND -- cat /etc/resolv.conf

[ Expected output ]

search m7-lab.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5

The ndots:5 option treats a name with fewer than five dots as a relative name. The resolver appends the configured search domains while resolving it.

Resolve the short name backend and examine the search-domain expansion.

kubectl --context kind-cilium-networking -n m7-lab exec $FRONTEND -- nslookup backend

[ sample output ]

Server:    10.96.0.10
Address:   10.96.0.10:53

Name:      backend.m7-lab.svc.cluster.local
Address:   10.96.249.10

** server can't find backend.cluster.local: NXDOMAIN
** server can't find backend.svc.cluster.local: NXDOMAIN

The resolver found backend.m7-lab.svc.cluster.local. It also tried the other search domains.

An external name with fewer than five dots would also be expanded before it is tried as an absolute name.

DNS Query Volume

Search-domain expansion can multiply the number of CoreDNS queries generated by an application. Check the query pattern before increasing CoreDNS replicas or cache settings.

Override ndots for External Names​

Create a Pod which overrides the setting with ndots:1.

kubectl --context kind-cilium-networking -n m7-lab run dns-fixed \
  --image=curlimages/curl:8.11.0 \
  --restart=Never \
  --overrides='{"spec":{"dnsConfig":{"options":[{"name":"ndots","value":"1"}]}}}' \
  --command -- sleep 300
kubectl --context kind-cilium-networking -n m7-lab wait --for=condition=ready pod/dns-fixed --timeout=30s

[ Expected output ]

pod/dns-fixed created
pod/dns-fixed condition met

Examine its resolver configuration.

kubectl --context kind-cilium-networking -n m7-lab exec dns-fixed -- cat /etc/resolv.conf

[ Expected output ]

search m7-lab.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:1

With ndots:1, a name containing a dot is tried as an absolute name first. Short internal names such as backend still use the search domains.

Validate​

Make sure that:

  • Cilium reports all components as healthy
  • Hubble shows the DNS, Service translation and TCP flows
  • the default-deny policy produces a dropped verdict
  • the allow policy restores the frontend-to-backend request
  • the second DNS test shows options ndots:1

Troubleshooting​

Troubleshooting
  • Cilium is still becoming ready — the cluster may be downloading the Cilium and Hubble images. Check cilium status --context kind-cilium-networking again after a minute.
  • Hubble cannot connect to localhost:4245 — restart the Hubble Relay port-forward.
  • SOCK_XLATE_POINT_UNKNOWN appears in a flow — this is the eBPF socket-level Service translation event, not a failure.
  • Traffic still succeeds after default deny — confirm that the policy exists in m7-lab and selects the backend Pod.
  • Port 4245 is already in use — stop the previous Hubble port-forward before starting another one.

Teardown​

Stop the Hubble port-forward if it is still running.

kill %1 2>/dev/null || true

[ Expected output ]

(no output)

Delete the Cilium cluster and recreate core-internals.

bash labs/clusters/cilium-networking/teardown.sh

[ Expected output ]

Deleting cluster "cilium-networking" ...
Creating kind cluster 'kubeadv-core' ...
OK: core-internals profile verified — 2/2 nodes Ready, API server healthy.

Keep the core-internals cluster running for the next module.

Summary​

In this lab, you traced a frontend-to-backend request with Hubble. You observed DNS traffic, eBPF Service translation and the TCP connection using Cilium security identities.

You also blocked and restored traffic using NetworkPolicy, and reduced DNS search expansion with ndots:1.
