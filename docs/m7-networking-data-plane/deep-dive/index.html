Deep Dive - Networking & the Data Plane

This deep dive examines the CNI call path, conntrack, Hubble L7 visibility, Cilium policies, and eBPF attachment points. Complete the main lab first and keep the cilium-networking cluster running.

▶ M7: Networking Deep DiveOpen fullscreen ↗

PART I - iptables rule explosion (the legacy problem)​

In a traditional kube-proxy iptables cluster, every Service/endpoint combination generates chains. You cannot observe this on the cilium-networking cluster (no kube-proxy), but you can understand the math:

For 5,000 Services with 3 endpoints each:

  • 5,000 KUBE-SVC-* chains (one per Service)
  • 15,000 KUBE-SEP-* chains (one per endpoint)
  • Each new connection walks the entire KUBE-SERVICES jump table (O(n) rules)
  • A single Service endpoint change triggers a full iptables-restore (atomic replace of ALL rules)

The latency isn't just per-packet: the rule programming itself becomes the bottleneck. At 10,000+ Services, iptables-restore takes seconds. During that window, new connections may hit stale rules pointing at terminated endpoints.

nftables improvement: uses hash-based sets instead of linear chains. Lookup is O(1) regardless of Service count. Rule changes are incremental (add/remove set members), not full-table replace. Kubernetes added nftables kube-proxy mode in v1.31.

Cilium's approach: eliminates both. eBPF maps (hash tables in kernel memory) store Service→endpoint mappings. Translation happens at the socket layer (before any packet traverses the kernel network stack). No iptables, no nftables, no netfilter at all.

Verify on your cluster: there are zero iptables rules for Services:

docker exec cilium-networking-control-plane iptables-save 2>/dev/null | grep -c "KUBE-SVC" || echo "0"

[ Expected output ]

0

PART II - The CNI execution model​

The CNI spec defines how kubelet delegates networking. Understanding the exact execution sequence helps debug pod-creation failures.

Pod startup networking sequence:

  1. kubelet creates the pod sandbox (pause container) → gets a new network namespace
  2. kubelet calls the CNI binary (/opt/cni/bin/cilium-cni) with the ADD command
  3. CNI binary receives: container ID, network namespace path, interface name, CNI config
  4. Cilium's CNI plugin:
    • Creates a veth pair (one end in pod netns, one on host)
    • Allocates an IP from the node's IPAM pool
    • Programs eBPF on the host-side veth (datapath programs)
    • Registers the endpoint with the Cilium agent (gets a security identity)
  5. Returns IP + routes to kubelet → pod becomes Ready (network-wise)

Inspect the CNI configuration on a cluster node:

docker exec cilium-networking-control-plane cat /etc/cni/net.d/05-cilium.conflist 2>/dev/null | head -20

[ sample output ]

{
  "cniVersion": "0.3.1",
  "name": "cilium",
  "plugins": [{"type": "cilium-cni"}]
}

Inspect a pod's veth pair:

FRONTEND=$(kubectl --context kind-cilium-networking -n m7-lab get pod -l app=frontend -o jsonpath='{.items[0].metadata.name}')
kubectl --context kind-cilium-networking -n m7-lab exec $FRONTEND -- ip link show eth0

[ sample output ]

3: eth0@if25: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP

The eth0@ifNN notation shows the veth pair index: the other end lives on the host.

PART III - Conntrack and the five-second DNS delay​

The five-second DNS delay is a Linux kernel race condition in the conntrack subsystem. Here's the exact mechanism:

  1. Pod resolver sends A and AAAA queries simultaneously (standard dual-stack behavior)
  2. Both UDP packets share the same source port + destination (CoreDNS :53)
  3. The kernel's conntrack table creates an entry on the first packet
  4. If the second packet arrives at the exact same instant (before the conntrack entry is fully committed), it creates a duplicate conntrack entry
  5. The duplicate entry causes one response to be silently dropped (conntrack sees it as unsolicited)
  6. The resolver waits for the missing response → 5-second timeout → retry

Why it's intermittent: the race window is nanoseconds. Under load, you hit it often enough to matter (0.1–1% of DNS queries). At scale, that's thousands of 5-second delays per minute.

Three fixes (any one works):

FixMechanismTrade-off
ndots:1 in dnsConfigFewer DNS queries total → fewer race opportunitiesInternal short names still work (< 1 dot)
single-request-reopen in resolv.confSerializes A/AAAA (never sends simultaneously)Adds ~1ms latency per resolution (sequential)
Node-local DNS cache (NodeLocal DNSCache)Pods talk to a local daemon on a link-local IP → no conntrack for DNSExtra DaemonSet to maintain

The conntrack table has a finite size (nf_conntrack_max). Check it:

docker exec cilium-networking-worker sysctl net.netfilter.nf_conntrack_max
docker exec cilium-networking-worker cat /proc/sys/net/netfilter/nf_conntrack_count

[ sample output ]

net.netfilter.nf_conntrack_max = 262144
184

PART IV - Hubble deep: L7 visibility and flow filtering​

Hubble can observe beyond L3/L4 when Cilium is configured for L7 visibility. With the default installation, you see TCP/UDP flows. With L7 annotations, you can see HTTP methods, paths, and response codes.

Enable L7 visibility for the backend pods:

kubectl --context kind-cilium-networking -n m7-lab annotate pod -l app=backend \
  policy.cilium.io/proxy-visibility="<Ingress/80/TCP/HTTP>"

[ Expected output ]

pod/backend annotated

Now generate traffic and observe L7 details:

kubectl --context kind-cilium-networking -n m7-lab exec $FRONTEND -- curl -s http://backend/
hubble observe --server localhost:4245 -n m7-lab --protocol HTTP --last 5

[ sample output ]

frontend: curl -s http://backend/ => 200
frontend -> backend http-request FORWARDED (GET /)
backend -> frontend http-response FORWARDED (200)

With L7 visibility enabled, Hubble shows HTTP method, URL, and response code: production-grade request tracing without a service mesh.

PART V - CiliumNetworkPolicy (beyond standard K8s)​

Standard Kubernetes NetworkPolicy is limited: L3/L4 only, no FQDN rules, no L7 filtering. Cilium extends this with CiliumNetworkPolicy:

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: backend-l7
  namespace: m7-lab
spec:
  endpointSelector:
    matchLabels:
      app: backend
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: frontend
    toPorts:
    - ports:
      - port: "80"
        protocol: TCP
      rules:
        http:
        - method: GET
          path: "/"

This allows frontend → backend only on GET /: any other HTTP method or path is denied at L7. The standard K8s NetworkPolicy cannot express this.

FQDN-based egress (for external APIs):

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-stripe
  namespace: m7-lab
spec:
  endpointSelector:
    matchLabels:
      app: frontend
  egress:
  - toFQDNs:
    - matchName: "api.stripe.com"
    toPorts:
    - ports:
      - port: "443"
        protocol: TCP

This allows egress to api.stripe.com:443 only: Cilium resolves the FQDN and programs the eBPF map with the IP addresses. As DNS TTL rotates IPs, the map updates automatically.

PART VI - eBPF datapath internals​

Where exactly does eBPF run in the Linux kernel?

Attachment points (TC = Traffic Control):

Pod netns                  Host netns
┌──────────┐              ┌───────────────────────────────────┐
│ eth0     │──── veth ────│ lxc_xxx                           │
│          │              │   ├─ tc-ingress: from-container   │
│          │              │   └─ tc-egress: to-container      │
└──────────┘              │                                   │
                          │ cilium_host                        │
                          │   ├─ tc-ingress: to-host          │
                          │   └─ tc-egress: from-host         │
                          └───────────────────────────────────┘

Each eBPF program makes a routing decision:

  • from-container: Is the destination local? (redirect to peer veth) Or remote? (send to tunnel)
  • to-container: Policy check: is the source identity allowed?
  • Service DNAT happens at from-container or connect() hook (socket-level LB)

Inspect attached eBPF programs:

docker exec cilium-networking-worker cilium-dbg bpf endpoint list 2>/dev/null | head -10

[ sample output ]

ENDPOINT   POLICY (ingress)   POLICY (egress)
120        Enabled            Enabled

PART VII - Troubleshooting production networking​

A decision tree for real incidents:

Symptom: intermittent timeouts (not total failure)

  1. Check conntrack table exhaustion: nf_conntrack_count near nf_conntrack_max?
  2. Check DNS: is ndots:5 amplifying under load? CoreDNS CPU at limit?
  3. Check NetworkPolicy: Hubble --verdict DROPPED: is policy too aggressive?

Symptom: total connectivity failure for new pods

  1. CNI binary missing/broken: kubectl describe pod shows NetworkPlugin cni failed
  2. Cilium agent down: cilium status shows agents not ready
  3. IPAM exhausted: no more IPs in the node's allocation pool

Symptom: Service resolution fails but pod-to-pod works

  1. CoreDNS pods not running: kubectl -n kube-system get pods -l k8s-app=kube-dns
  2. EndpointSlices stale: check kubectl get endpointslices -l kubernetes.io/service-name=X
  3. Cilium service map out of sync: cilium-dbg service list vs actual endpoints

Key diagnostic commands:

# Cilium connectivity test (end-to-end)
cilium connectivity test --context kind-cilium-networking

# Specific pod's eBPF policy verdict
cilium-dbg policy get --context kind-cilium-networking

# Monitor real-time drops
hubble observe --server localhost:4245 --verdict DROPPED --follow

[ sample output ]

All 42 tests (312 actions) successful
... policy entries for the selected endpoint ...
(the Hubble command waits for dropped flows; use Ctrl-C to stop it)
Where you will use this
  • Use the CNI execution model when new Pods fail before containers start.
  • Use conntrack evidence for intermittent timeouts that affect unrelated applications on the same node.
  • Use Hubble identities and verdicts when a NetworkPolicy looks correct in YAML but packets are still denied.
  • Use the DNS path when Pod-to-Pod works but names or Services fail.
  • Escalate to packet capture only after structured flow, policy, EndpointSlice, and DNS evidence have narrowed the path.

In production, restore the smallest broken link. Restarting every networking component at once may recover service, but it removes the evidence needed to prevent recurrence.

Teardown​

kubectl --context kind-cilium-networking -n m7-lab annotate pod -l app=backend \
  policy.cilium.io/proxy-visibility-
