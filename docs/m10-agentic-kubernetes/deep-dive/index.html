Deep Dive - MCP Internals, RBAC Design, and Agent Governance

This deep dive examines MCP messages, ServiceAccount tokens, agent RBAC, audit policy, sandboxing, and governance. Use these controls to limit what an agent identity and its tool server can change.

PART I - MCP protocol internals​

The Model Context Protocol uses JSON-RPC 2.0 as its wire format. Every message is a JSON object with jsonrpc, method, id, and params fields. The protocol defines three transports and a strict session lifecycle.

JSON-RPC 2.0 envelope​

A request:

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "list_pods",
    "arguments": {"namespace": "production"}
  }
}

A successful response:

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [{"type": "text", "text": "[...]"}],
    "isError": false
  }
}

An error response:

{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {"code": -32601, "message": "Method not found: pods/list"}
}

The id field correlates requests with responses: critical for multiplexed transports where multiple requests can be in flight simultaneously. Notifications (server-initiated messages with no id) do not expect a response.

Transport options​

MCP supports three transports, each suited to different deployment patterns:

Streamable HTTP: the primary transport for networked deployments. The client sends POST requests to the server's MCP endpoint. The server can respond with a single JSON response or switch to SSE (Server-Sent Events) for streaming results. On Kubernetes, this is the natural fit: the MCP server is a Service, the client connects via standard HTTP networking.

SSE (Server-Sent Events): used when the server needs to push events to the client. The client opens a long-lived GET connection and the server streams JSON-RPC messages as SSE events. Useful for watch-style operations where the server monitors cluster state and pushes changes.

stdio: the server reads JSON-RPC from stdin and writes to stdout. Used for local tool servers that run as child processes of the agent runtime. Not relevant for Kubernetes deployments but common in development workflows (Claude Code uses stdio transport for local MCP servers).

Session lifecycle​

  1. Initialize: the client sends initialize with its protocol version and capabilities. The server responds with its own capabilities (tools, resources, prompts).
  2. Initialized notification: the client sends notifications/initialized to confirm the handshake is complete.
  3. Normal operation: tools/list to discover tools, tools/call to invoke them. The server may also expose resources/list and prompts/list for structured data and prompt templates.
  4. Shutdown: either side closes the connection.

The lab's MCP server implements a simplified version: it handles initialize, tools/list, and tools/call over HTTP POST. The initialized notification and resource/prompt capabilities are omitted because the lab focuses on tool invocation and RBAC enforcement, not protocol completeness.

Tool schema​

Each tool declares its input schema using JSON Schema:

{
  "name": "get_pod",
  "description": "Get details of a specific pod",
  "inputSchema": {
    "type": "object",
    "properties": {
      "namespace": {"type": "string"},
      "name": {"type": "string"}
    },
    "required": ["namespace", "name"]
  }
}

The schema serves two purposes. First, the agent runtime uses it to validate arguments before sending them: catching type errors on the client side. Second, AI models use the schema as context when deciding which tool to call and what arguments to provide. The description and property names are part of the model's prompt, so clear naming directly improves tool selection accuracy.

Error handling​

MCP distinguishes protocol errors from tool errors. Protocol errors (malformed JSON, unknown method) return a JSON-RPC error object. Tool errors (the Kubernetes API returned 403) return a normal result with isError: true. This separation matters for agent behavior: a protocol error means the MCP server is misconfigured; a tool error means the operation failed but the server is healthy.

PART II - Kubernetes ServiceAccount tokens in depth​

The MCP server in the lab authenticates to the Kubernetes API using a ServiceAccount token mounted at /var/run/secrets/kubernetes.io/serviceaccount/token. Understanding how this token works is essential for configuring agent identity correctly.

Legacy tokens vs bound tokens​

Kubernetes originally used legacy tokens: long-lived secrets stored as Secret objects in the same namespace as the ServiceAccount. These tokens never expired, were not audience-scoped, and persisted until manually deleted. If an attacker extracted the token from a pod, it remained valid indefinitely.

Starting in Kubernetes 1.22, bound service account tokens (TokenRequest API) replaced legacy tokens. Bound tokens have three properties legacy tokens lack:

  • Audience scoping: the token is valid only for a specific audience (typically https://kubernetes.default.svc). A token intended for the Kubernetes API cannot be replayed against a different service.
  • Time-bound: the token has an expiration time (default: 1 hour). The kubelet refreshes the token before expiry using the TokenRequest API. If a pod is deleted, its tokens become invalid.
  • Pod-bound: the token is bound to the specific pod that requested it. The API server validates that the pod still exists; if the pod is deleted, the token is immediately invalid.

Projected volume mount​

The token appears at /var/run/secrets/kubernetes.io/serviceaccount/ via a projected volume. Three files are mounted:

  • token: the JWT, refreshed automatically by the kubelet
  • ca.crt: the cluster CA certificate for TLS verification
  • namespace: the pod's namespace as a plain string

The lab's MCP server reads all three:

SA_TOKEN_PATH = "/var/run/secrets/kubernetes.io/serviceaccount/token"
SA_CA_PATH = "/var/run/secrets/kubernetes.io/serviceaccount/ca.crt"
SA_NS_PATH = "/var/run/secrets/kubernetes.io/serviceaccount/namespace"

The token file is refreshed in-place by the kubelet. A long-running server that reads the token once at startup will eventually use an expired token. In production, agent tool servers should re-read the token periodically or on each request. The lab server reads once because the lab runs for minutes, not hours.

Token content​

Decoding the JWT (base64, not encrypted) reveals the bound token's claims:

{
  "iss": "https://kubernetes.default.svc",
  "sub": "system:serviceaccount:m10-lab:ai-agent",
  "aud": ["https://kubernetes.default.svc"],
  "exp": 1753123456,
  "iat": 1753119856,
  "kubernetes.io": {
    "namespace": "m10-lab",
    "pod": {"name": "mcp-server-6dcc7bbb8c-mwj5c", "uid": "..."},
    "serviceaccount": {"name": "ai-agent", "uid": "..."},
    "node": {"name": "kubeadv-core-worker", "uid": "..."}
  }
}

The API server uses these claims when processing requests: the sub field becomes the username that appears in audit logs, and the pod/node claims appear in the audit event's user.extra fields (as shown in the lab).

Why TokenRequest API is preferred​

For agent workloads, the TokenRequest API offers additional control:

kubectl create token ai-agent \
  --namespace m10-lab \
  --audience https://kubernetes.default.svc \
  --duration 10m

[ sample output ]

eyJhbGciOiJSUzI1NiIsImtpZCI6Ii4uLiJ9...

This creates a token with a custom audience and short duration: 10 minutes instead of the default 1 hour. For agents that perform one-shot diagnosis tasks, a short-lived token minimizes the window of compromise if the token is extracted.

PART III - RBAC design patterns for agents​

The lab used a single ClusterRole with read-only permissions. Production agent deployments require more nuanced RBAC design.

Namespace-scoped vs cluster-scoped roles​

A ClusterRole applies across all namespaces: the lab's ai-agent-readonly can list pods in every namespace, including kube-system. This is appropriate for a diagnostic agent that needs cluster-wide visibility.

A Role (not ClusterRole) applies to a single namespace. For an agent that operates only within its own namespace:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: agent-ns-readonly
  namespace: my-app
rules:
  - apiGroups: [""]
    resources: ["pods", "services", "events", "configmaps"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch"]

Bind with a RoleBinding (not ClusterRoleBinding) to restrict scope:

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: agent-ns-readonly-binding
  namespace: my-app
subjects:
  - kind: ServiceAccount
    name: app-agent
    namespace: my-app
roleRef:
  kind: Role
  name: agent-ns-readonly
  apiGroup: rbac.authorization.k8s.io

Now the agent can see pods in my-app but not in kube-system or any other namespace.

Aggregated ClusterRoles​

Kubernetes supports label-based ClusterRole aggregation. Define a base role and extension roles:

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: agent-base
  labels:
    rbac.agent.io/aggregate-to-agent: "true"
aggregationRule:
  clusterRoleSelectors:
    - matchLabels:
        rbac.agent.io/aggregate-to-agent: "true"
rules: []  # filled by aggregation
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: agent-core-read
  labels:
    rbac.agent.io/aggregate-to-agent: "true"
rules:
  - apiGroups: [""]
    resources: ["pods", "events", "nodes"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: agent-apps-read
  labels:
    rbac.agent.io/aggregate-to-agent: "true"
rules:
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets"]
    verbs: ["get", "list", "watch"]

The agent-base role automatically includes rules from all roles with the matching label. When you need to add CRD access for a new agent capability, create a new labeled ClusterRole: the base role aggregates it without modification.

Escalation prevention​

Kubernetes RBAC has a built-in escalation guard: you cannot grant permissions you do not have. If the ai-agent ServiceAccount has only get and list permissions, it cannot create a RoleBinding that grants create or delete to another ServiceAccount. This prevents a compromised agent from escalating its own privileges through RBAC manipulation.

The exception: users with the escalate verb on roles or clusterroles can bypass this guard. Never grant escalate to an agent ServiceAccount.

Common RBAC mistakes for agents​

Wildcard verbs: verbs: ["*"] grants every verb including deletecollection, which deletes all resources of a type in one call. Always enumerate specific verbs.

Wildcard resources: resources: ["*"] includes secrets, service accounts, roles, and role bindings. An agent with wildcard read access can extract every secret in the cluster.

Including secrets: even read-only access to secrets lets the agent read database passwords, TLS certificates, and API keys. Exclude secrets from agent roles unless the agent specifically needs them, and even then scope to named secrets.

Non-resource URLs: paths like /healthz, /metrics, /logs, and /debug/pprof can expose sensitive information. The lab's ClusterRole has no non-resource URL rules, which means the agent cannot access any of these paths.

Forgetting about subresources: pods/exec, pods/log, and pods/portforward are separate resources. Granting get on pods does not grant pods/exec, but explicitly listing pods/exec would allow the agent to exec into containers: a Tier 3 operation.

PART IV - Audit policy design​

The core-internals cluster writes audit events to the API server's stdout (audit-log-path: "-"), which the lab reads via kubectl logs. Production clusters need structured audit backends.

Audit levels​

Each rule in the audit policy specifies a level:

LevelWhat is recordedUse case
NoneNothingSystem health checks, liveness probes
MetadataUser, verb, resource, timestamp, response codeDefault for all operations: who did what
RequestMetadata + request bodyWhen you need to see what was submitted (RBAC changes, admission)
RequestResponseRequest + response bodyDeep debugging, compliance: expensive in volume

The lab cluster uses Metadata as the default level, which captures enough for the audit trail exercise without the volume of request/response bodies.

Tuning for agent activity​

Agent workloads generate significantly more API calls than human operators. A diagnostic agent running a control loop might issue 50 list/get operations per minute. Without tuning, the audit log fills with routine reads.

A production audit policy for agent namespaces:

apiVersion: audit.k8s.io/v1
kind: Policy
omitStages: ["RequestReceived"]
rules:
  # Agent write attempts (including denied): capture request body
  - level: Request
    users: ["system:serviceaccount:agents:*"]
    verbs: ["create", "update", "patch", "delete", "deletecollection"]

  # Agent reads: metadata only (no bodies, high volume)
  - level: Metadata
    users: ["system:serviceaccount:agents:*"]
    verbs: ["get", "list", "watch"]

  # Non-agent system traffic: suppress noise
  - level: None
    users: ["system:kube-*", "system:apiserver"]

  # Everything else
  - level: Metadata

This policy captures full request bodies for agent write attempts (including denied ones: the body shows what the agent tried to create), lightweight metadata for reads, and suppresses system controller noise.

Structured audit backends​

Beyond stdout, Kubernetes supports:

  • File backend: writes JSON lines to a file on disk. Requires log rotation (the API server does not rotate audit logs). Use --audit-log-maxage, --audit-log-maxbackup, and --audit-log-maxsize flags.
  • Webhook backend: sends audit events to an external HTTPS endpoint. Used for centralizing audit logs in SIEM systems (Splunk, Elastic, Datadog). Configure with --audit-webhook-config-file.
  • Dynamic auditing (alpha/beta): AuditSink resources that configure webhook backends without restarting the API server.

For agent governance, the webhook backend is most practical: it sends audit events to a system that can alert on denied mutations, unusual access patterns, or high request volumes from agent ServiceAccounts.

PART V - kagent architecture​

kagent extends Kubernetes with CRDs that manage AI agent lifecycle. Its architecture follows the same operator pattern from M5.

Controller reconciliation​

The kagent controller watches three custom resources:

  • Agent: the primary resource. Declares model config, system prompt, tools, and ServiceAccount.
  • Tool: optional. Wraps an MCP server reference with additional configuration.
  • ModelConfig: optional. Shared model configuration referenced by multiple Agents.

When you create an Agent resource, the controller:

  1. Validates the Agent spec (model config exists, referenced MCP servers exist as Services)
  2. Creates a Deployment for the agent runtime (a container that runs the agent loop)
  3. Configures MCP client connections in the runtime's environment
  4. Creates a Service for the agent's API (status, health, chat interface)
  5. Updates the Agent's status subresource with runtime state

When you update the Agent (change model, add a tool), the controller reconciles: updates the Deployment, which triggers a rolling update of the agent runtime pod.

When you delete the Agent, the controller removes the Deployment, Service, and any owned resources (garbage collection via owner references: the same mechanism from M5).

Tool binding​

kagent's tool binding connects the agent runtime to MCP servers running as separate Kubernetes Services:

spec:
  tools:
    - name: kubectl-readonly
      type: mcp
      mcpServer:
        name: kubectl-mcp      # Service name
        namespace: agents       # Service namespace
        transport: http         # streamableHttp or stdio

The controller resolves kubectl-mcp.agents.svc and injects the URL into the agent runtime's configuration. The agent runtime connects to the MCP server using standard Kubernetes DNS: no special networking required.

This separation means the MCP server runs with its own ServiceAccount (scoped RBAC) while the agent runtime runs with a different ServiceAccount (minimal RBAC: only needs to call MCP servers, not the Kubernetes API directly).

Current state​

kagent is in early development (v0.1.x, alpha CRDs). The API is not stable. Production use requires pinning to a specific version and expecting breaking changes. The value is architectural: it demonstrates how the Kubernetes operator pattern naturally extends to agent lifecycle management.

PART VI - Agent Sandbox isolation layers​

Running untrusted code that an AI agent generates requires defense-in-depth isolation. The Kubernetes Agent Sandbox project layers multiple security mechanisms.

gVisor kernel interception​

gVisor (runsc) implements a user-space kernel that intercepts system calls from the sandboxed process. Instead of the container's code calling the host kernel directly, gVisor's Sentry process handles system calls in a restricted environment.

The isolation model:

Container Process → gVisor Sentry (user-space kernel) → limited host syscalls

For agent-generated code, this prevents:

  • Direct filesystem access to the host
  • Raw network socket creation
  • Kernel exploit escalation
  • Device access

gVisor supports about 60% of Linux system calls, which covers most interpreted languages (Python, JavaScript, shell) but may break programs that use specialized syscalls (io_uring, eBPF, FUSE).

Layered security controls​

A production sandbox combines multiple Kubernetes security features:

Pod Security Standards: the restricted profile enforces:

  • runAsNonRoot: true: no root processes
  • allowPrivilegeEscalation: false: child processes cannot gain privileges
  • readOnlyRootFilesystem: true: cannot modify the container filesystem
  • seccompProfile: RuntimeDefault: baseline syscall filtering

NetworkPolicy: deny all egress and ingress:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: sandbox-deny-all
spec:
  podSelector:
    matchLabels:
      sandbox: "true"
  policyTypes: ["Ingress", "Egress"]

No ingress means nothing can connect to the sandbox. No egress means the sandbox cannot initiate connections: no DNS lookups, no HTTP calls, no data exfiltration.

ResourceQuota: limit total resources the sandbox namespace can consume:

apiVersion: v1
kind: ResourceQuota
metadata:
  name: sandbox-quota
spec:
  hard:
    pods: "10"
    requests.cpu: "4"
    requests.memory: 2Gi
    limits.cpu: "8"
    limits.memory: 4Gi

Even if an agent creates many sandbox pods, the quota prevents resource exhaustion.

LimitRange: set per-pod defaults:

apiVersion: v1
kind: LimitRange
metadata:
  name: sandbox-limits
spec:
  limits:
    - type: Container
      default:
        cpu: 500m
        memory: 256Mi
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      max:
        cpu: "1"
        memory: 512Mi

Timeout enforcement​

The sandbox controller kills pods that exceed their timeout:

  1. Create the pod with a activeDeadlineSeconds field
  2. The kubelet kills the pod when the deadline expires
  3. The sandbox controller reads the pod status and reports the timeout to the agent

activeDeadlineSeconds is enforced by the kubelet, not by the container: even a runaway process that ignores SIGTERM will be killed when the deadline passes.

PART VII - Production agent governance​

RBAC and audit are necessary but not sufficient for production agent deployments. Organizations need governance patterns that span the full agent lifecycle.

Approval workflows​

Two patterns for gating agent mutations:

Admission webhook: a ValidatingAdmissionWebhook intercepts API requests from agent ServiceAccounts and holds them pending approval:

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionWebhook
metadata:
  name: agent-approval-gate
webhooks:
  - name: approve.agent.io
    rules:
      - operations: ["CREATE", "UPDATE", "DELETE"]
        apiGroups: ["*"]
        apiVersions: ["*"]
        resources: ["*"]
    objectSelector:
      matchExpressions:
        - key: agent-managed
          operator: Exists
    clientConfig:
      service:
        name: approval-service
        namespace: governance

The approval service can check a database for pre-approved changes, send a Slack notification and wait for human response, or evaluate an OPA policy.

GitOps-based changes: the agent proposes changes as a Git commit or pull request rather than applying them directly:

  1. Agent diagnoses the issue and generates a remediation (YAML patch, Helm values change)
  2. Agent creates a branch and commits the change to a GitOps repository
  3. Agent creates a PR with diagnostic evidence and proposed fix
  4. Human reviews and merges (or the PR is auto-merged after policy checks pass)
  5. Flux or Argo CD applies the change from Git

This approach provides a complete audit trail in Git, peer review, and easy rollback (revert the commit). The trade-off is latency: the change takes minutes instead of seconds to apply.

Blast radius containment​

Namespace isolation: each agent operates in its own namespace with RBAC scoped to that namespace. Cross-namespace access requires explicit RoleBindings.

Resource quotas: prevent an agent from consuming unlimited resources, even if it has create permissions:

apiVersion: v1
kind: ResourceQuota
metadata:
  name: agent-quota
  namespace: agent-workspace
spec:
  hard:
    pods: "20"
    services: "5"
    configmaps: "10"
    requests.cpu: "4"
    requests.memory: 4Gi

Rate limiting: API Priority and Fairness (from M2) can limit the request rate from agent ServiceAccounts:

apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata:
  name: agent-rate-limit
spec:
  priorityLevelConfiguration:
    name: agent-restricted
  matchingPrecedence: 1000
  rules:
    - subjects:
        - kind: ServiceAccount
          serviceAccount:
            name: ai-agent
            namespace: m10-lab
      resourceRules:
        - verbs: ["*"]
          apiGroups: ["*"]
          resources: ["*"]

The agent-restricted PriorityLevelConfiguration can have a low concurrency share, preventing the agent from starving human operators or other controllers.

Rollback strategies​

When an agent makes a change that causes problems:

Deployment rollback: kubectl rollout undo reverts to the previous ReplicaSet. If the agent scaled or updated a Deployment, this is the fastest recovery.

Git revert: if the change was applied via GitOps, revert the commit. Flux/Argo CD will reconcile back to the previous state.

Admission webhook deny-list: the approval service can maintain a deny-list of changes that caused incidents. Future identical changes are rejected automatically.

PART VIII - Multi-agent architectures on Kubernetes​

As agent deployments scale beyond single agents, Kubernetes provides natural patterns for orchestration.

Orchestrator-worker pattern​

A central orchestrator agent decomposes complex tasks and dispatches them to specialized worker agents:

  • The orchestrator runs as a Deployment, receives tasks via a Service endpoint
  • Worker agents run as Jobs (for one-shot tasks) or Deployments (for long-running tools)
  • Communication uses Kubernetes Services: the orchestrator calls worker Services via DNS
Orchestrator Agent (Deployment)
  ├── Diagnostics Worker (Deployment): reads cluster state
  ├── Remediation Worker (Job)      : applies approved fixes
  └── Reporting Worker (Job)        : generates incident reports

Each worker has its own ServiceAccount with scoped RBAC. The diagnostics worker has read-only access. The remediation worker has limited write access (patch deployments, scale). The reporting worker has read-only access plus access to a shared ConfigMap for results.

Shared tool servers​

Multiple agents can share the same MCP tool server:

Agent A ──┐
Agent B ──┼── kubectl-mcp Service (shared, read-only SA)
Agent C ──┘

The tool server runs with a single ServiceAccount. All three agents get the same permissions when using this tool server, regardless of their own ServiceAccount permissions. This creates a clean separation: the agent's SA controls what the agent can do directly; the tool server's SA controls what the agent can do through tools.

State management​

Agents need to persist state between invocations. Kubernetes provides several options:

  • ConfigMaps: for structured configuration and small state (under 1 MB). Agents can read and write ConfigMaps (with appropriate RBAC) to share context.
  • CRDs: for domain-specific state. An agent that manages incident responses could store incident records as custom resources, queryable via kubectl get incidents.
  • External stores: for large state or state that outlives the cluster. Object storage, databases, or key-value stores accessed via MCP tool servers.

ConfigMaps are the simplest option and the most common for early agent deployments. The limitation is size (1 MB per ConfigMap) and lack of schema validation (any string is valid). CRDs provide schema validation, versioning, and integration with the Kubernetes API: the same benefits that make CRDs valuable for operators (M5) apply to agent state management.

Where you will use this
  • Use the MCP handshake and tool schema when a client connects but tools do not appear or arguments are rejected.
  • Use bound-token claims and audit identity to prove which agent made a Kubernetes request.
  • Use separate tool servers and ServiceAccounts when agents require different authority.
  • Use admission, APF, and sandboxing for risks RBAC cannot control.
  • Delegate diagnosis first, then approval-gated narrow remediation; keep privilege changes and destructive storage actions human-executed.

The production design question is not “how capable is the model?” It is “what is the maximum damage this identity, tool, and runtime can cause when the model is wrong?”

Teardown​

The token command returns a short-lived credential and does not create a persistent Secret. Use the main lab teardown to remove the agent namespace and MCP resources.
