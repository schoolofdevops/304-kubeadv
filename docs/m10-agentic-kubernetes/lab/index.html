Operating Kubernetes through an MCP Tool Server

Before you start

All commands in this lab run against the core-internals cluster and from the root of the lab repo (304-labs/).

The cluster must have audit logging enabled. The core-internals profile enables it by default.

In this lab, you are going to deploy an MCP tool server with a read-only Kubernetes ServiceAccount.

You would call read and write tools, observe the RBAC result and trace each request in the API server audit log.

By the end of this lab, you will:

  • initialize an MCP session and discover tools
  • run allowed read operations
  • prove that Kubernetes rejects write operations
  • connect MCP calls with RBAC and audit evidence

Pre Requisites​

Check the current Kubernetes context.

kubectl config current-context

[ Expected output ]

kind-kubeadv-core

Verify that audit logging is enabled.

bash labs/clusters/core-internals/verify.sh | grep 'audit mode'

[ Expected output ]

audit mode: ENABLED — stream with: kubectl logs -n kube-system kube-apiserver-kubeadv-core-control-plane

Explore the MCP Protocol​

Start a port-forward to the MCP server.

kubectl --context kind-kubeadv-core -n m10-lab port-forward svc/mcp-server 8090:80 &

[ Expected output ]

Forwarding from 127.0.0.1:8090 -> 8080

Initialize the Session​

Begin the MCP session with an initialize request.

curl -s -X POST http://localhost:8090/mcp \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "initialize",
    "params": {
      "protocolVersion": "2025-03-26",
      "capabilities": {},
      "clientInfo": {"name": "lab-client", "version": "1.0"}
    }
  }' | python3 -m json.tool

[ Expected output ]

{
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
        "protocolVersion": "2025-03-26",
        "capabilities": {
            "tools": {
                "listChanged": false
            }
        },
        "serverInfo": {
            "name": "k8s-mcp-readonly",
            "version": "0.1.0"
        }
    }
}

Make sure the response identifies the server as k8s-mcp-readonly and advertises the tools capability.

Discover the Tools​

List the tools exposed by the server.

curl -s -X POST http://localhost:8090/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}' \
  | python3 -c "
import sys, json
data = json.load(sys.stdin)
for t in data['result']['tools']:
    print(f\"  {t['name']:20s} {t['description']}\")
"

[ Expected output ]

  list_namespaces      List all namespaces in the cluster
  list_pods            List pods in a namespace
  get_pod              Get details of a specific pod
  list_nodes           List cluster nodes with status
  list_events          List recent events in a namespace
  create_pod           Create a pod (requires write permissions)
  delete_pod           Delete a pod (requires write permissions)

The server exposes five read tools and two write tools. The Kubernetes API server still applies RBAC to every tool call.

This allows the denied operations to appear in the audit log.

Attempt Write Operations​

Attempt to Create a Pod​

curl -s -X POST http://localhost:8090/mcp \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0", "id": 10,
    "method": "tools/call",
    "params": {
      "name": "create_pod",
      "arguments": {"namespace": "m10-lab", "name": "rogue-pod", "image": "nginx:alpine"}
    }
  }' | python3 -c "
import sys, json
data = json.load(sys.stdin)
result = data['result']
print(f\"isError: {result['isError']}\")
inner = json.loads(result['content'][0]['text'])
print(f\"reason:  {inner['reason']}\")
print(f\"code:    {inner['code']}\")
print(f\"message: {inner['message']}\")
"

[ Expected output ]

isError: True
reason:  Forbidden
code:    403
message: pods is forbidden: User "system:serviceaccount:m10-lab:ai-agent" cannot create resource "pods" in API group "" in the namespace "m10-lab"

The API server denied the request. Examine the ServiceAccount identity, verb, resource and namespace in the error.

Attempt to Delete a Pod​

curl -s -X POST http://localhost:8090/mcp \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0", "id": 11,
    "method": "tools/call",
    "params": {
      "name": "delete_pod",
      "arguments": {"namespace": "m10-lab", "name": "mcp-server-whatever"}
    }
  }' | python3 -c "
import sys, json
data = json.load(sys.stdin)
result = data['result']
print(f\"isError: {result['isError']}\")
inner = json.loads(result['content'][0]['text'])
print(f\"reason:  {inner['reason']}\")
print(f\"code:    {inner['code']}\")
print(f\"message: {inner['message']}\")
"

[ Expected output ]

isError: True
reason:  Forbidden
code:    403
message: pods "mcp-server-whatever" is forbidden: User "system:serviceaccount:m10-lab:ai-agent" cannot delete resource "pods" in API group "" in the namespace "m10-lab"

The delete request is also denied by the API server. The MCP server returns the Kubernetes 403 Forbidden response.

Examine the Audit Trail​

Stop the port-forward.

kill %1 2>/dev/null

[ Expected output ]

(no output)

Filter the API server audit log for requests made by the ai-agent ServiceAccount.

kubectl --context kind-kubeadv-core logs -n kube-system \
  kube-apiserver-kubeadv-core-control-plane --tail=500 \
  | python3 -c "
import sys, json
for line in sys.stdin:
    line = line.strip()
    if not line: continue
    try:
        ev = json.loads(line)
    except: continue
    user = ev.get('user',{}).get('username','')
    if 'ai-agent' not in user: continue
    verb = ev.get('verb','')
    uri = ev.get('requestURI','')
    code = ev.get('responseStatus',{}).get('code',0)
    ua = ev.get('userAgent','')
    print(f'{verb:8s} {code} {uri[:65]}  agent={ua[:20]}')
"

[ sample output ]

list     200 /api/v1/namespaces                                    agent=Python-urllib/3.12
list     200 /api/v1/nodes                                         agent=Python-urllib/3.12
list     200 /api/v1/namespaces/kube-system/pods                   agent=Python-urllib/3.12
create   403 /api/v1/namespaces/m10-lab/pods                       agent=Python-urllib/3.12
delete   403 /api/v1/namespaces/m10-lab/pods/mcp-server-whatever   agent=Python-urllib/3.12

The audit log records the verb, request URI, response code and user agent. The reads returned 200, while the write attempts returned 403.

Inspect a Raw Audit Event​

Examine one denied create event in more detail.

kubectl --context kind-kubeadv-core logs -n kube-system \
  kube-apiserver-kubeadv-core-control-plane --tail=500 \
  | python3 -c "
import sys, json
for line in sys.stdin:
    try: ev = json.loads(line.strip())
    except: continue
    user = ev.get('user',{}).get('username','')
    if 'ai-agent' in user and ev.get('verb') == 'create' and ev.get('responseStatus',{}).get('code') == 403:
        print(json.dumps({
            'verb': ev['verb'],
            'user': ev['user']['username'],
            'groups': ev['user']['groups'],
            'sourceIPs': ev.get('sourceIPs'),
            'userAgent': ev.get('userAgent'),
            'resource': ev.get('objectRef',{}).get('resource'),
            'namespace': ev.get('objectRef',{}).get('namespace'),
            'responseCode': ev['responseStatus']['code'],
            'podName': ev['user'].get('extra',{}).get('authentication.kubernetes.io/pod-name',[''])[0],
        }, indent=2))
        break
"

Examine the RBAC Policy​

Examine the ClusterRole assigned to the agent.

kubectl --context kind-kubeadv-core get clusterrole ai-agent-readonly -o yaml

[ Expected output ]

rules:
- apiGroups:
  - ""
  resources:
  - pods
  - services
  - events
  - namespaces
  - nodes
  - configmaps
  verbs:
  - get
  - list
  - watch
- apiGroups:
  - apps
  resources:
  - deployments
  - replicasets
  - daemonsets
  - statefulsets

  - watch

  - batch

  - jobs
  - cronjobs
  verbs:

Observe what is absent:

  • no create, delete, patch or update verbs
  • no wildcard in resources or verbs
  • no access to Secrets
  • no access to non-resource URLs such as /metrics
Design principle

Start an agent ServiceAccount with the minimum required permissions. Add write access only for a specific verb, resource and namespace.

PART III - Examine Agent Resources and Autonomy​

kagent and Agent Sandbox Walkthrough​

The following resources are walkthroughs and are not installed in the lab cluster.

Examine a kagent Resource​

A kagent Agent resource declares the model, instructions, tools and ServiceAccount.

# kagent Agent CRD (walkthrough — not installed)
apiVersion: kagent.dev/v1alpha1
kind: Agent
metadata:
  name: k8s-diagnostics
  namespace: agents
spec:
  modelConfig:
    provider: openai
    model: gpt-4
  systemPrompt: |
    You are a Kubernetes diagnostics agent.
    You have read-only access to cluster resources.
    Never suggest destructive actions.
  tools:
    - name: kubectl-get
      type: mcp
      mcpServer:
        name: kubectl-mcp
        namespace: agents
    - name: prometheus-query
      type: mcp
      mcpServer:
        name: prom-mcp
        namespace: monitoring
  serviceAccountName: diag-agent

The kagent controller creates the runtime Pod, configures the MCP connections and manages the Agent lifecycle. This uses the same CRD and controller pattern examined in Module 5.

Examine an Agent Sandbox​

The Sandbox resource places generated code in an isolated runtime.

# Agent Sandbox CRD (walkthrough — not installed)
apiVersion: sandbox.k8s.io/v1alpha1
kind: Sandbox
metadata:
  name: code-exec
  namespace: agents
spec:
  runtime: gvisor
  resources:
    limits:
      cpu: "1"
      memory: 512Mi
  networkPolicy:
    egress: deny
  timeout: 30s
  serviceAccountName: sandbox-runner

Examine the controls in the specification:

  • the gVisor runtime isolates the workload from the host
  • egress is denied
  • CPU and memory are limited
  • the execution has a 30-second timeout
  • the dedicated ServiceAccount has no Kubernetes permissions

Classify Operations by Autonomy​

Classify the following Kubernetes operations by autonomy and risk.

#OperationTier
1kubectl get pods -ATier 1: read-only, autonomous
2kubectl delete namespace productionTier 3: never delegated
3kubectl scale deployment/api --replicas=5Tier 2: approval-gated
4kubectl logs pod/api-server-xyzTier 1: read-only, autonomous
5kubectl delete pvc/database-dataTier 3: never delegated (data loss)
6kubectl rollout restart deployment/apiTier 2: approval-gated
7kubectl describe node worker-3Tier 1: read-only, autonomous
8kubectl edit clusterrole adminTier 3: never delegated (privilege escalation)
9kubectl apply -f configmap.yamlTier 2: approval-gated
10kubectl get events --sort-by=lastTimestampTier 1: read-only, autonomous
11kubectl drain node/worker-2 --delete-emptydir-dataTier 3: never delegated
12kubectl cordon node/worker-2Tier 2: approval-gated (reversible with uncordon)

The exact boundary depends on the organisation. In this example, read operations are autonomous, reversible changes require approval, and destructive operations are not delegated.

Validate​

Make sure that:

  • the MCP server is running with the ai-agent ServiceAccount
  • the initialize and tools-list requests succeed
  • list_nodes and list_pods return cluster data
  • create_pod and delete_pod return 403 Forbidden
  • the audit log contains the successful reads and denied writes
  • the ClusterRole has no write verbs, Secrets or wildcards

Troubleshooting​

Troubleshooting
  • Port 8090 is already in use — stop the previous MCP server port-forward.
  • The MCP endpoint does not respond — confirm that the mcp-server Pod is Running and restart the port-forward.
  • A read tool returns 403 Forbidden — inspect the ClusterRoleBinding and confirm that it refers to m10-lab/ai-agent.
  • A write tool succeeds — stop the lab and inspect every RoleBinding and ClusterRoleBinding for the ServiceAccount.
  • No audit event appears — verify the context and confirm that the cluster profile has audit logging enabled.

Teardown​

Delete the namespace and cluster-scoped RBAC objects.

kubectl --context kind-kubeadv-core delete namespace m10-lab
kubectl --context kind-kubeadv-core delete clusterrole ai-agent-readonly
kubectl --context kind-kubeadv-core delete clusterrolebinding ai-agent-readonly-binding

[ Expected output ]

namespace "m10-lab" deleted
clusterrole.rbac.authorization.k8s.io "ai-agent-readonly" deleted
clusterrolebinding.rbac.authorization.k8s.io "ai-agent-readonly-binding" deleted

Summary​

In this lab, you deployed an MCP tool server and called Kubernetes tools through JSON-RPC.

Read operations succeeded because the ServiceAccount had matching RBAC permissions. Write operations were rejected by the API server.

You also traced the same calls in the audit log and classified operations by autonomy and risk. The next module brings these operating practices together in the capstone incident.
