Agentic Kubernetes: platform for and by AI

What you will learn​

  • Separate the agent runtime, tool server, sandbox, and target cluster identities
  • Build a controlled detect, diagnose, propose, approve, execute, and verify loop
  • Explain why MCP tools do not replace Kubernetes security controls
  • Classify agent actions into three operational risk tiers
  • Define a production baseline for identity, tools, approval, audit, and failure

1. AI agents need badges, boundaries, and supervision​

An AI agent reads an alert, checks a recent Deployment, prepares a rollback, and asks an SRE to approve it. The SRE checks the evidence, approves a narrow change, and the agent verifies the result. This can reduce response time without giving the agent unlimited authority.

Now change one detail. Give the same agent cluster-admin. It decides that deleting and recreating a StatefulSet is the fastest repair. It may also delete storage or change a security control. The quality of its reasoning does not reduce the blast radius of its credentials.

Think of a hospital. Each person receives a badge for the rooms required by their role. A nurse, surgeon, intern, and visitor do not share one master key. Important actions may also need a second person, and every door access is recorded.

Use the same model for an agent:

Hospital controlKubernetes control
Named badgeServiceAccount and short-lived token
Door permissionsRole, ClusterRole, and binding
Supervisor approvalHuman or policy approval gate
Door-access recordAPI server audit log
Restricted roomNetworkPolicy and sandbox controls

The rule is simple: an agent's authority should be narrower than its intelligence. Give it the smallest access needed for the present task, not the largest access it might use one day.

2. Four ways Kubernetes hosts AI workloads​

Kubernetes can run AI systems and can also be operated through AI-assisted tools. Keep the runtime and the target separate.

WorkloadPurposeCommon Kubernetes formMain control
Model servingRuns inferenceDeployment or InferenceServiceGPU, model readiness, inference scaling
Agent runtimeRuns the reasoning and control loopDeployment or JobIdentity, model access, tool access
Tool serverExposes bounded actions, often through MCPDeployment and ServiceTyped inputs, ServiceAccount, output limits
SandboxRuns generated or untrusted codeShort-lived isolated PodRuntime isolation, egress, CPU, memory, and timeout

These workloads should not share one identity. A useful design has at least three boundaries:

agent identity
  -> allowed to call selected tool services

tool identity
  -> allowed to perform selected Kubernetes API operations

sandbox identity
  -> allowed to use only the network and resources needed for code execution

If one boundary is compromised, the others still reduce impact. For example, a sandbox should not inherit the tool server's token, and a diagnostic tool should not share credentials with a mutation tool.

Kubernetes AI portability work is also bringing common interfaces to device allocation, batch admission, model routing, and agent hosting. Treat emerging specifications as integration targets, not as a replacement for your own security and operations review.

3. A secure agent control loop on Kubernetes​

An operational agent follows a loop similar to a Kubernetes controller, but it uses a model and tools to choose the next action.

Five of these six stages can be read-only:

StageTypical activityAPI authority
DetectReceive alert, watch Event, query metricRead
DiagnoseGet objects, logs, status, and recent changesRead
ProposePrepare explanation, diff, checks, and rollbackNo cluster write
ApproveHuman or policy evaluates the exact proposalExternal decision
ExecuteApply the approved narrow changeWrite
VerifyCheck status, events, metrics, and user outcomeRead

This means a useful first agent does not need write access. It can collect evidence and prepare a high-quality change proposal. Add one mutation only after the team can validate the plan, approval, audit, rollback, and verification path.

MCP is a tool protocol, not a security boundary​

Model Context Protocol, or MCP, gives an agent a standard way to discover and call tools. An MCP server can run as a normal Kubernetes Deployment and Service.

MCP describes how a tool is called. It does not decide whether that tool should exist, whether its arguments are safe, or whether the Kubernetes request is allowed. Enforce security on the server:

  • Use a small allow-list of typed tools.
  • Validate every argument again at the tool boundary.
  • Limit result size and redact Secrets and sensitive fields.
  • Give each tool service its own ServiceAccount.
  • Use RBAC, admission policy, NetworkPolicy, and audit independently of the prompt.
  • Fail closed when approval, identity, or policy services are unavailable.

Read-only is still sensitive​

Read permission can expose customer data, Secret values, logs, environment variables, and large amounts of cluster metadata. It can also create API pressure through broad LIST requests.

Start with namespace and resource-name scope where possible. The following example is intentionally broader so that you can see its structure, but a production Role should be reduced for the actual diagnostic task:

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: ai-agent-readonly
rules:
  - apiGroups: [""]
    resources: ["pods", "services", "events", "namespaces", "nodes", "configmaps"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets", "daemonsets", "statefulsets"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["batch"]
    resources: ["jobs", "cronjobs"]
    verbs: ["get", "list", "watch"]

There is no create, update, patch, delete, or wildcard. Use kubectl auth can-i and SelfSubjectRulesReview to test the effective permissions. Then test denied operations as well as allowed operations.

Agent configuration is not a security boundary​

Projects such as kagent can represent an agent as a custom resource:

apiVersion: kagent.dev/v1alpha1
kind: Agent
metadata:
  name: k8s-diagnostics
spec:
  modelConfig:
    provider: openai
    model: gpt-4
  systemPrompt: "You are a Kubernetes diagnostics agent..."
  tools:
    - name: kubectl-get
      type: mcp
      mcpServer:
        name: kubectl-mcp
    - name: prometheus-query
      type: mcp
      mcpServer:
        name: prom-mcp

The CRD helps manage configuration and lifecycle. It does not make the configured tools safe. The real boundary remains the tool implementation, credentials, RBAC, policy, network, and audit path.

Sandboxes need fixed platform controls​

Generated code should run in a short-lived environment with a fixed template:

apiVersion: sandbox.k8s.io/v1alpha1
kind: Sandbox
metadata:
  name: code-exec
spec:
  runtime: gvisor
  resources:
    limits:
      cpu: "1"
      memory: 512Mi
  networkPolicy:
    egress: deny
  timeout: 30s

The platform, not the model, should choose the runtime, image, ServiceAccount, seccomp profile, filesystem, egress, resource limits, and timeout. Admission policy should reject attempts to weaken the template.

Walkthrough only

kagent and Agent Sandbox are emerging projects. This course uses their YAML to explain the design. They are not installed in the lab cluster.

4. Three autonomy tiers define approval requirements for production agents​

Store the risk tier as policy. Do not ask the model to decide its own authority for each request.

Tier 1: autonomous read and analysis​

These operations do not change cluster state:

  • Read approved objects, metrics, events, and logs.
  • Correlate evidence.
  • Prepare a diagnostic report.
  • Draft a remediation plan and rollback.

Even Tier 1 needs data scope, rate limits, output controls, and audit.

Tier 2: approval-gated change​

These operations change state but can be narrow and reversible:

  • Scale one approved Deployment within a defined range.
  • Apply one reviewed patch.
  • Restart a selected Deployment.
  • Cordon or uncordon a named node.
  • Update an approved ConfigMap key.

The approval must cover the exact resource, diff, checks, expiry, and rollback. If the proposed diff changes after approval, request approval again.

Tier 3: human-executed high-risk action​

These operations are destructive, create privilege, expose data, or have a wide blast radius:

  • Delete a namespace or PersistentVolumeClaim.
  • Change RBAC, admission webhooks, or cluster-wide security policy.
  • Run unrestricted commands inside a production container.
  • Drain a node while deleting local data.
  • Execute a generic shell or unrestricted kubectl command.

Your organisation may move a well-engineered action between Tier 2 and Tier 3 after controls and evidence improve. The classification must be reviewed by people who own the service and risk.

5. A production agent governance baseline​

Use this baseline before an operational agent reaches production:

ControlRecommended practiceAvoidEvidence
IdentitySeparate short-lived identities for agent, tool, and sandboxShared kubeconfig or administrator tokenToken audience, expiry, ServiceAccount, audit user
ToolsSmall typed allow-list with server-side validationGeneric shell or arbitrary kubectlTool name, validated arguments, bounded output
ReadsScope namespace, resource, name, fields, and result sizeCluster-wide LIST by conveniencecan-i, rules review, audit volume
WritesPlan first; approve exact diff; verify and retain rollbackFree-form autonomous applyProposal, approver, API event, post-check
RuntimeFix network, filesystem, CPU, memory, image, and timeoutTrusting a prompt as a sandboxAdmission result, egress flow, termination reason
FailureFail closed if identity, policy, or approval cannot be checkedContinuing with cached or missing approvalDenied result and operator-visible alert
AuditCorrelate alert, model run, tool call, approval, API request, and resultSeparate logs with no shared request IDEnd-to-end correlation ID
RBAC is necessary, but not sufficient

RBAC decides whether an API request is allowed. It does not prove business intent, control output size, stop an expensive LIST storm, or prevent data from entering a model prompt. Combine RBAC with typed tools, admission policy, API Priority and Fairness, network controls, sandboxing, audit, and human approval.

In the lab, you will deploy an MCP tool server with a read-only ServiceAccount. You will observe a read succeed, a write fail with 403 Forbidden, and both requests appear in the API audit trail. That is the complete control path: identity, permission, tool call, API decision, and evidence.
