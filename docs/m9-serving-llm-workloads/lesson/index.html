Serving AI and LLM workloads at scale

What you will learn​

  • Explain why GPU utilisation can be low while an LLM service is overloaded
  • Use queue depth, KV cache, TTFT, and ITL as serving evidence
  • Explain PagedAttention and continuous batching
  • Separate engine, routing, scaling, and model-lifecycle responsibilities
  • Decide when disaggregated prefill and decode are worth the extra complexity

1. Why low GPU utilisation can still mean overload​

An LLM service starts timing out, but GPU utilisation is only 40 percent. This does not prove that the replica has spare capacity.

Every active request uses GPU memory for a key-value cache, usually called the KV cache. A replica can run out of cache space before it runs out of compute. New requests wait in a queue even though the GPU cores are not fully busy.

Start with these signals:

SignalWhat it tells you
Queue depthRequests are waiting for serving capacity
KV cache utilisationActive sequences are consuming cache memory
Time to first token, or TTFTPrompt processing and queue delay seen by the user
Inter-token latency, or ITLSpeed of token generation after the first token
Tokens per secondUseful serving throughput

GPU utilisation remains useful, but it is not enough by itself. During an incident, inspect queue, cache, TTFT, and ITL before changing replica count.

2. Why LLM serving is not normal web serving​

Think of a normal web API as a fixed-menu restaurant. Most orders follow a similar path. When the kitchen becomes busy, the team can often add another identical kitchen and use normal load balancing.

LLM serving is closer to a tasting-menu restaurant:

  • The kitchen reads the complete order first. This is the prefill phase.
  • It then sends one small course at a time. This is token-by-token decode.
  • It must remember the state of every active guest. This is the KV cache.
  • A long order may use much more time and table space than a short order.
  • A useful host sends new guests to a kitchen with suitable model and cache capacity, not only by round-robin.

An LLM generates one token from all previous tokens. A 500-token response needs 500 sequential decode steps. Two latency measures matter:

  • TTFT measures the wait until the first output token. Prompt length, queue time, and prefill work affect it.
  • ITL measures the delay between later tokens. Decode throughput and interference affect it.

Request cost is also highly variable. A 10-token prompt and a 10,000-token prompt should not be treated as equal requests. Record input tokens, requested output tokens, and actual output tokens. Set supported context and output limits as a product policy, not only as an emergency control.

Why the KV cache matters​

During prefill, the model computes key and value tensors for each layer and token. Decode reuses these tensors so it does not process the full sequence again for every token.

The cache grows with active sequence length and concurrency. Model weights, KV cache, runtime workspace, and memory fragmentation all share the same GPU memory. This is why capacity planning must use the real prompt and output-length distribution, not only an average request.

3. How PagedAttention increases LLM concurrency​

An early cache design reserved one contiguous block for a request's maximum sequence length. If a request could grow to 2,048 tokens, the engine reserved that space even when the response ended at 50 tokens. Much of the memory stayed unused.

PagedAttention manages the KV cache in fixed-size pages:

  1. Split cache memory into small blocks.
  2. Allocate blocks only as the sequence grows.
  3. Map logical token positions to physical blocks through a page table.
  4. Return blocks to the pool when the request finishes.

This reduces wasted cache memory and normally allows more concurrent sequences on the same GPU. It does not create unlimited capacity. Long contexts can still fill the page pool, and queueing can still grow faster than the engine can decode.

4. How continuous batching keeps GPUs busy​

Static batching waits for a group of requests, runs the group, and completes when the slowest member finishes. One long response can keep short requests waiting.

Continuous batching rebuilds the active batch at each decode step. A finished request leaves immediately, and a queued request can take its place. Return to the restaurant example: when one table finishes, the next group sits down. The restaurant does not wait for every table to finish together.

PagedAttention improves cache use. Continuous batching improves how active decode slots are used. Serving engines such as vLLM, TensorRT-LLM, and SGLang combine these ideas.

The trade-off is policy. A very large batch may improve total tokens per second while making TTFT or ITL worse for an individual user. Tune batch size, concurrency, and scheduling from a stated latency objective. Do not maximise throughput without checking the user experience.

5. The LLM serving stack on Kubernetes​

The stack has several owners. Keep the boundaries clear during design and incident response.

LayerMain responsibilityExample systems
Serving engineLoad weights, manage KV cache, batch, and generate tokensvLLM, TensorRT-LLM, SGLang
RoutingChoose model and replica for each requestGateway API Inference Extension, Envoy
AutoscalingAdd or remove replicas from serving signalsHPA, KEDA, Knative
Model lifecycleLoad, version, warm, and roll out modelsKServe, Seldon, custom controllers
Device allocationSelect and prepare GPUsDRA or device plugins from M8

Serving engine evidence​

Expose and collect at least:

queue depth
KV cache utilisation
TTFT histogram
ITL histogram
input and output tokens
tokens per second
request rejection reason

Use percentile latency and request distributions. Averages hide long prompts and noisy tenants.

Model-aware routing​

Round-robin assumes that every backend can accept an equal request. LLM replicas may have different models, queues, active sequences, and free KV cache.

The Gateway API Inference Extension adds resources for model-aware routing:

apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferencePool
metadata:
  name: llm-pool
spec:
  targetPortNumber: 8080
  selector:
    app: vllm-server
  extensionRef:
    name: endpoint-picker
---
apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferenceModel
metadata:
  name: llama-3
spec:
  modelName: meta-llama/Llama-3-8B
  targetModels:
  - name: meta-llama/Llama-3-8B
    weight: 100
  poolRef:
    name: llm-pool

The InferencePool groups serving endpoints. The endpoint picker can consider model and serving state. Treat it as a production component: define availability, timeout, fallback, and failure behaviour. A clever routing algorithm is not useful if the endpoint picker becomes a new single point of failure.

Autoscaling signals​

SignalBest useImportant caution
Queue depthDetect waiting demandA short burst may clear before a new model loads
KV cache utilisationDetect memory pressure before rejectionDifferent context lengths create different future cost
TTFT percentileProtect first-response latencyIncludes queue and prefill, so find the dominant part
ITL percentileProtect streaming qualityCan worsen from decode contention or prefill interference
Tokens per secondMeasure useful throughputHigh throughput can still hide poor tail latency

Model startup may take much longer than a normal web container because weights must be downloaded, loaded, and warmed. Keep enough warm headroom for the startup delay. Predictive scaling may help a known traffic pattern, but it should not replace overload controls.

Model lifecycle with KServe​

KServe provides an InferenceService abstraction:

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: llama-3
spec:
  predictor:
    model:
      modelFormat:
        name: vllm
      runtime: kserve-vllm
      storageUri: s3://models/llama-3-8b
      resources:
        limits:
          nvidia.com/gpu: 1

Readiness should mean that the required model is loaded, warmed, and able to serve a test request. An HTTP process listening on a port is not sufficient. Shift traffic gradually and compare canary TTFT, ITL, errors, and output quality.

6. Disaggregated prefill and decode​

Prefill and decode use hardware differently:

PhaseMain workMemory behaviourUser signal
PrefillProcess all prompt tokensCreates the initial KV cacheTTFT
DecodeGenerate one token at a timeKeeps and grows KV cacheITL

In one replica, a long prefill can compete with active decode work. Disaggregated serving puts prefill and decode on separate workers and transfers the KV cache between them.

This can improve isolation and hardware matching, but it adds a network transfer, more routing state, more failure modes, and another capacity-planning problem. Use it only after measurements show that prefill and decode interference is a material limit. First fix simpler problems such as queue policy, context limits, cache pressure, model loading, or poor placement.

7. A production LLM serving policy​

Define the policy before the service is under pressure.

DecisionRecommended practiceAvoidLeading evidence
CapacitySize weights, cache, runtime overhead, and real context distributionSizing from average prompt lengthCache use, queue, context histogram
RoutingRoute by model and serving state; use affinity only when it helpsPlain round-robin across unequal replicasPer-replica queue, cache, routing decisions
AutoscalingCombine queue, cache, and latency with warm headroomCPU-only HPA or waiting for timeoutQueue, TTFT, load time, ready capacity
LimitsPublish context, output, concurrency, and timeout limitsUnlimited context for every tenantRejections, token distribution, fairness
OverloadReject or queue with clear limits and tenant fairnessAccepting work that cannot meet the objectiveQueue age, rejected reason, tail latency
RolloutLoad, warm, test, and then shift traffic graduallyMarking ready when only the server process startedModel state, warm-up result, canary objectives

Load tests must use the real distribution of prompt lengths, output lengths, concurrency, and stream duration. A test with identical short prompts can report excellent throughput while hiding the production bottleneck.

Diagnose the phase before scaling

High TTFT with low cache pressure points toward queueing, prefill, or model loading. High ITL with normal TTFT points toward decode throughput or interference. More replicas may reduce a queue, but they will not fix slow storage, an unsuitable model, or poor GPU topology.

The practical rule is simple: protect the latency objective before the GPU is full. Use inference-specific evidence to decide whether to route, reject, tune, or scale.
