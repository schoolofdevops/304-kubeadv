Deep Dive - Inference Engines, Routing, and Production Serving

This deep dive examines PagedAttention, KV-cache capacity, inference-aware routing, model loading, disaggregated serving, and production metrics. It also separates Kubernetes responsibilities from inference-engine behavior.

PART I - vLLM internals: how PagedAttention runs​

The lesson described PagedAttention as "virtual memory for the KV cache." Here is how vLLM implements it.

Block manager​

vLLM divides GPU memory into fixed-size blocks: each block holds the KV tensors for a fixed number of tokens (default: 16). The block manager maintains two data structures:

  • Free block list: tracks which physical blocks on GPU are available for allocation.
  • Block table: per-request mapping from logical block index to physical block address. When a request generates its 17th token, the block manager allocates a second physical block and adds the mapping to this table.

The key insight: the block table is a page table. Logical blocks are contiguous (token 0-15, 16-31, 32-47), but the physical blocks they map to can be scattered anywhere in GPU memory. No pre-allocation, no contiguous reservation, no wasted space.

GPU ↔ CPU swap​

When GPU memory fills up, vLLM can swap KV cache blocks to CPU memory (host RAM): the same mechanism an OS uses when physical RAM fills up. A preempted request's blocks move to CPU, freeing GPU memory for higher-priority or newer requests. When the preempted request resumes, blocks swap back to GPU.

The swap path:

  1. Scheduler decides to preempt a request (lowest priority, or oldest)
  2. Block manager copies the request's physical blocks from GPU to CPU via cudaMemcpyAsync
  3. Physical GPU blocks return to the free list
  4. When the request resumes: CPU blocks copy back, block table updates point to new GPU locations

This is expensive: PCIe bandwidth limits swap throughput to ~25 GB/s. A request with 2048 cached tokens in fp16 occupies ~1 GB of KV cache, so a swap takes ~40ms each way. The scheduler avoids swapping when possible, preferring to queue new requests over evicting active ones.

Continuous batching scheduler​

vLLM's scheduler runs at iteration level: every decode step (one forward pass through the model), the scheduler re-evaluates which requests are in the active batch:

  1. Check if any active request has finished (hit EOS token or max length). Remove it; free its blocks.
  2. Check the waiting queue. If freed blocks can accommodate the next waiting request's prefill, add it to the batch.
  3. If no blocks are free but a high-priority request is waiting, preempt a lower-priority active request (swap its blocks to CPU).

The result: the GPU is never idle with a non-empty queue. A finished short request immediately makes room for the next in line. No static batch boundaries, no head-of-line blocking.

Speculative decoding​

Autoregressive generation is sequential: one forward pass per token. Speculative decoding trades compute for latency:

  1. A small draft model (e.g., 1B parameters) generates K candidate tokens quickly.
  2. The main model (e.g., 70B) verifies all K candidates in a single forward pass: this works because the verification pass is just a standard forward pass with K extra input tokens, which parallelizes on GPU.
  3. Accept the longest prefix of candidates that match the main model's distribution. If all K match, you generated K tokens for the cost of one main-model forward pass.

Speedup depends on acceptance rate: typically 60-80% of draft tokens are accepted, yielding 1.5-2× throughput improvement. The draft model adds GPU memory overhead (~2-4 GB for a 1B model), so this trades memory for latency: the opposite of the KV cache tradeoff.

PART II - KV cache math: how many requests fit?​

The KV cache size per request is deterministic. For a transformer with:

  • L layers
  • H attention heads (key + value = 2 projections)
  • D head dimension
  • S sequence length (prompt + generated tokens so far)
  • B bytes per element (2 for fp16, 1 for int8)

KV cache per request = L × 2 × H × D × S × B

Worked example: Llama-3-8B​

ParameterValue
Layers (L)32
Heads (H)32 (8 KV heads with GQA, but each stores D=128)
Head dim (D)128
Sequence (S)4096
Dtype (B)2 (fp16)

With grouped-query attention (GQA), Llama-3-8B uses 8 KV heads (not 32):

Per request = 32 × 2 × 8 × 128 × 4096 × 2 = 537 MB

Per token (S=1): 32 × 2 × 8 × 128 × 1 × 2 = 131 KB

Memory budget​

An A100 (80 GB) running Llama-3-8B:

  • Model weights (fp16): ~16 GB
  • CUDA overhead: ~2 GB
  • Available for KV cache: ~62 GB
  • Requests at 4096 context: 62 GB / 537 MB ≈ 115 concurrent requests
  • Requests at 128K context: 62 GB / 17 GB ≈ 3 concurrent requests

This is why context length dominates capacity planning. A 128K-context request consumes 32× more memory than a 4K-context request. One long-context user can evict dozens of short-context users.

KV cache quantization​

Quantizing KV cache from fp16 to int8 (or int4) halves (or quarters) the per-request memory:

  • int8 KV cache: 131 KB → 65 KB per token, doubles concurrent capacity
  • int4 KV cache: 131 KB → 33 KB per token, quadruples capacity

The accuracy impact is small for most tasks: KV cache values are less sensitive to quantization than model weights. vLLM supports --kv-cache-dtype fp8_e5m2 for fp8 KV cache with minimal quality loss.

PART III - Prefill vs decode: the roofline model​

The two inference phases have fundamentally different compute characteristics.

Prefill​

  • Operation: process all prompt tokens in parallel through the model
  • Arithmetic intensity: high: matrix-matrix multiplications (prompt tokens × model weights)
  • Bottleneck: compute (FLOPS). More GPU cores = faster prefill.
  • Scaling: tensor parallelism across GPUs splits the weight matrices; each GPU processes all tokens but with a fraction of the weights
  • Analogy: a kitchen reading the full menu order and doing all the prep work at once

Decode​

  • Operation: one forward pass per generated token, reading the full KV cache
  • Arithmetic intensity: low: matrix-vector multiplication (one token × model weights), plus reading the entire KV cache
  • Bottleneck: memory bandwidth (GB/s). Faster memory = faster decode.
  • Scaling: larger batch size amortizes the weight-read cost across more requests (each decode step reads weights once for all requests in the batch)
  • Analogy: a kitchen plating one bite at a time, constantly referencing the order notes for each table

The roofline​

On an A100:

  • Compute ceiling: 312 TFLOPS (fp16)
  • Memory bandwidth ceiling: 2 TB/s

Prefill with a 1024-token prompt at batch size 1: arithmetic intensity ~100 FLOP/byte → compute-bound. The GPU cores are the bottleneck.

Decode at batch size 1: arithmetic intensity ~1 FLOP/byte → memory-bandwidth-bound. The GPU spends most of its time reading weights and KV cache from HBM, not computing.

At batch size 32 (continuous batching): decode arithmetic intensity rises to ~32 FLOP/byte → closer to compute-bound. This is why continuous batching matters: it shifts decode from memory-bound to compute-bound by amortizing the memory reads.

PART IV - Gateway API Inference Extension architecture​

The lesson showed the InferencePool and InferenceModel resources. Here is how the routing decision works inside.

The endpoint-picker​

The Gateway API Inference Extension defines an Endpoint Picker Extension: a gRPC service that sits between the gateway (Envoy) and the backend pods:

The picker receives the request metadata (model name, estimated token count) and queries each replica's metrics:

  • KV cache utilization
  • Queue depth
  • Active request count
  • Model name and version

It selects the replica with the best score: typically lowest cache utilization weighted by queue depth. This is not round-robin. A replica at 85% cache gets no new traffic until others catch up.

InferenceModel traffic splitting​

The InferenceModel resource supports weight-based traffic splitting across target models:

spec:
  modelName: llama-3  # what users request
  targetModels:
  - name: meta-llama/Llama-3-8B-v1
    weight: 90
  - name: meta-llama/Llama-3-8B-v2
    weight: 10

This enables canary rollouts for model versions: 10% of traffic goes to the new model version while 90% stays on the proven version. The gateway handles the split; the backend pods are unaware. If the canary shows worse TTFT or higher error rates, you adjust the weights without redeploying.

Why this replaces traditional load balancing​

A standard Kubernetes Service uses iptables or ipvs for round-robin or random selection. This fails for LLM serving because:

  1. Requests are not equal: a 100-token prompt costs 100× less than a 10,000-token prompt. Round-robin sends both to the same replica.
  2. State matters: a replica at 90% KV cache utilization should not receive new traffic. Round-robin has no visibility into backend state.
  3. Model routing: a cluster serving multiple models needs to route by model name, not just by Service selector.

The inference extension solves all three: variable-cost routing, state-aware selection, and model-level routing.

PART V - KServe: InferenceService lifecycle​

KServe wraps model serving in a CRD with a well-defined lifecycle:

The Transformer/Predictor/Explainer pipeline​

KServe's InferenceService can chain three components:

ComponentRoleExample
TransformerPre/post-process data before/after the modelTokenization, detokenization, input validation
PredictorRun the modelvLLM container serving Llama-3
ExplainerGenerate explanations for predictionsSHAP values, attention visualization

Each component is a separate container (or pod). KServe routes requests through the chain: Transformer → Predictor → Transformer (post-process) → client. This separation keeps the model container focused on inference while offloading data transformation to CPU-only containers.

Scale-to-zero​

KServe uses Knative Serving for scale-to-zero: if no requests arrive for a configurable window (default: 5 minutes), the Deployment scales to zero replicas. The next request triggers a cold start:

  1. Knative activator intercepts the request (it runs even when replicas = 0)
  2. Deployment scales to 1 replica
  3. Pod starts, model downloads/loads, warmup completes
  4. Readiness probe passes, traffic flows

Cold start time for LLMs is dominated by model loading: not container startup. A 7B model (14 GB fp16) takes 30-60 seconds to load from network storage into GPU memory. A 70B model: 2-5 minutes. This is why scale-to-zero is practical for low-traffic models (save expensive GPU time) but dangerous for latency-sensitive production endpoints (first user waits minutes).

Mitigations:

  • Pre-cached weights: store model files on local NVMe (hostPath or persistent volume), skip the network download
  • GPU memory pre-warming: load weights into CPU memory during container startup, then cuda.memcpy to GPU (faster than loading from disk)
  • Min replicas: set minReplicas: 1 for production models to avoid cold starts entirely

Canary rollout​

KServe supports traffic splitting between InferenceService revisions:

spec:
  predictor:
    canaryTrafficPercent: 10
    model:
      modelFormat: { name: vllm }
      runtime: kserve-vllm
      storageUri: s3://models/llama-3-8b-v2

10% of traffic goes to the new model version. If metrics are healthy (TTFT, error rate, output quality), increase to 100%. If not, roll back by setting canaryTrafficPercent: 0. The rollout never touches the stable revision's pods: it creates new pods for the canary and adjusts the Service weights.

PART VI - Disaggregated serving​

The lesson introduced disaggregated serving as separating prefill and decode. Here is how it works in practice.

Why separate?​

Prefill is compute-bound: it benefits from high-FLOPS GPUs (H100 SXM at 990 TFLOPS). Decode is memory-bandwidth-bound: it benefits from high-bandwidth GPUs or even CPU+DRAM for small models. Running both on the same GPU creates interference: a large prefill steals compute cycles from in-progress decode steps, causing ITL spikes for all active requests.

Separating them eliminates the interference:

KV cache transfer​

The critical path is transferring the KV cache from the prefill GPU to the decode GPU. For a 2048-token context on Llama-3-8B, the KV cache is ~270 MB. Transfer options:

InterconnectBandwidthTransfer time (270 MB)
NVLink (same node)900 GB/s0.3 ms
InfiniBand HDR200 Gb/s (25 GB/s)11 ms
100 GbE RDMA100 Gb/s (12.5 GB/s)22 ms

NVLink transfers are nearly free. Network transfers add 10-20ms of latency to TTFT: acceptable if prefill takes 50-200ms anyway. The Mooncake paper (Moonshot AI, 2024) showed that disaggregated serving achieves 1.5-2× higher throughput than monolithic serving by allowing prefill and decode GPUs to run at their optimal batch sizes independently.

Kubernetes mapping​

In a disaggregated deployment on Kubernetes:

  • Prefill pool: Deployment with high-FLOPS GPU requests, optimized for large batch prefill
  • Decode pool: Deployment with high-memory GPU requests, optimized for sustained decode
  • Router: Gateway API Inference Extension routes new requests to prefill pool, then redirects the streaming response from the decode pool
  • KV cache transfer: handled by the serving engine (not Kubernetes) over NCCL or custom RDMA transport

The Gateway API Inference Extension's InferencePool design anticipates this: you can define separate pools for prefill and decode backends, with the endpoint-picker routing accordingly.

PART VII - Model loading and cold start​

Model loading is the largest contributor to pod startup time for LLM workloads. A container that serves a traditional web API starts in seconds. An LLM serving container can take minutes.

The loading pipeline​

PhaseDuration (7B fp16)Duration (70B fp16)Bottleneck
Container start1-3s1-3sImage pull (if not cached)
Weight download (S3/GCS)10-30s60-180sNetwork bandwidth
Deserialization (safetensors)2-5s10-30sCPU + disk I/O
GPU transfer (PCIe Gen5)3-5s20-40sPCIe bandwidth (64 GB/s)
Warm-up (first forward pass)2-5s10-20sGPU compute (CUDA kernel compilation)
Total~30-60s~2-5 min:

Optimization techniques​

Tensor parallelism: split the model across multiple GPUs on the same node. Each GPU loads 1/N of the weights. Loading a 70B model across 4 GPUs: each loads ~35 GB instead of 140 GB, cutting transfer time by 4×. But all GPUs must be allocated (DRA) and ready before loading begins.

Weight caching on NVMe: mount a hostPath or local PV containing pre-downloaded model weights. Eliminates the network download phase entirely. The tradeoff: every node that might run the model needs a copy of the weights (hundreds of GB for large models).

Model sharding formats: safetensors supports sharded files (model-00001-of-00008.safetensors). Each shard loads independently, enabling parallel loading from multiple threads or multiple storage backends.

Pre-warming: Kubernetes readiness probes should not pass until the model has completed at least one forward pass. vLLM and SGLang run a warmup inference on startup to compile CUDA kernels. The readiness probe checks GET /health: which the engine only exposes after warmup completes. Traffic does not flow until the model is genuinely ready.

The cache-latency curve​

KV cache utilization and tail latency have a non-linear relationship:

  • 0-70% cache: TTFT is stable. Plenty of free blocks. New requests start immediately.
  • 70-85% cache: TTFT begins to rise. The block manager occasionally needs to wait for blocks to free up. Queue depth creeps above zero.
  • 85-95% cache: TTFT spikes. The engine starts preempting lower-priority requests (swapping KV cache to CPU) to make room. Swapping adds 20-40ms per preempted request.
  • 95%+ cache: throughput collapses. Every new request triggers a swap-out. Effective batch size drops because blocks are being moved instead of used. TTFT can exceed 2 seconds.

The operational takeaway: scale at 80% cache utilization, not at request timeout. By the time users see latency, the engine is already thrashing. The KV cache metric is the leading indicator; TTFT is the lagging one.

Correlating signals​

In a production incident, check signals in this order:

  1. Queue depth > 0? Requests are waiting. Either scale up or find the bottleneck.
  2. KV cache > 85%? Memory pressure. Scale up (more replicas) or reduce max context length.
  3. TTFT high but cache low? Prefill is the bottleneck: prompts are too long, or the GPU is too slow for this model size.
  4. ITL high but TTFT normal? Decode is the bottleneck: batch size is too large for GPU memory bandwidth, or the model is bandwidth-bound at this batch size.
  5. All metrics normal but errors rising? Check model health: CUDA OOM, driver issues, or inference engine crash.

The simulator in the lab produces the same metrics (queue depth, cache utilization, TTFT, ITL). The pattern in the signals is identical to production: only the absolute numbers differ.

Where you will use this
  • Use KV-cache math during capacity planning and before changing maximum context length.
  • Use prefill versus decode signals when one latency metric is bad but the other is healthy.
  • Use model-aware routing when round-robin leaves one replica overloaded and another idle.
  • Use cold-start decomposition before promising scale-to-zero or aggressive autoscaling.
  • Scale before the cache-latency knee; TTFT is a user-visible lagging signal, while queue and cache pressure lead it.

In production, define the supported workload envelope: model, context distribution, output limit, concurrency, and latency objective. Load-test that exact envelope. “Requests per second” alone is not an LLM capacity model.
