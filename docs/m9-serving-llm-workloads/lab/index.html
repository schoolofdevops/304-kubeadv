Deploying and Measuring an LLM Inference Service

Before you start

All commands in this lab run against the core-internals cluster and from the root of the lab repo (304-labs/).

This lab uses a lightweight inference simulator. It does not need a GPU or download real model weights.

In this lab, you are going to deploy an OpenAI-compatible inference simulator.

You would observe token streaming, time to first token, inter-token latency, KV cache pressure and queue depth.

You would then scale the Deployment and compare its serving capacity.

By the end of this lab, you will:

  • send normal and streaming inference requests
  • read inference-specific Prometheus metrics
  • create queue pressure with concurrent requests
  • compare the simulator with Gateway API Inference Extension and KServe resources

Pre Requisites​

Check the current Kubernetes context.

kubectl config current-context

[ Expected output ]

kind-kubeadv-core

PART I - Deploy and Test Inference​

Deploy the Inference Simulator​

Run the setup script as,

bash labs/m9/setup.sh

[ sample output ]

=== M9 Lab Setup: Inference Simulator ===
namespace/m9-lab created
deployment.apps/inference-sim created
service/inference-sim created
deployment "inference-sim" successfully rolled out
=== Setup complete ===
Inference simulator: 2 replicas, model=sim-llm-7b
Namespace: m9-lab

The script deploys two replicas of a lightweight inference simulator. It provides an OpenAI-compatible API and Prometheus metrics without using a GPU.

Check the Pods.

kubectl --context kind-kubeadv-core -n m9-lab get pods

[ sample output ]

NAME                             READY   STATUS    RESTARTS   AGE
inference-sim-77c69684c7-vf5lt   1/1     Running   0          15s
inference-sim-77c69684c7-vg6l8   1/1     Running   0          15s

Start a port-forward to the Service.

kubectl --context kind-kubeadv-core -n m9-lab port-forward svc/inference-sim 8080:80 &

[ Expected output ]

Forwarding from 127.0.0.1:8080 -> 8080

Check the health endpoint.

curl -s http://localhost:8080/healthz | python3 -m json.tool

[ Expected output ]

{
    "status": "ok",
    "model": "sim-llm-7b"
}
curl -s http://localhost:8080/v1/models | python3 -m json.tool

[ Expected output ]

{
    "data": [
        {
            "id": "sim-llm-7b",
            "object": "model"
        }
    ]
}

Send a Single Inference Request​

Send a non-streaming completion request.

curl -s -X POST http://localhost:8080/v1/completions \
  -H "Content-Type: application/json" \
  -d '{"prompt": "Explain how Kubernetes works", "max_tokens": 16}' | python3 -m json.tool

[ sample output ]

{
    "id": "sim-<timestamp>",
    "object": "text_completion",
    "model": "sim-llm-7b",
    "choices": [
        {
            "index": 0,
            "text": "<simulated tokens>",
            "finish_reason": "stop"
        }
    ],
    "usage": {
        "prompt_tokens": 4,
        "completion_tokens": 15,
        "total_tokens": 19
    }
}

Examine the usage field. It reports the prompt, completion and total token counts for the request.

Observe Token Streaming​

Send another request with streaming enabled. The response is returned as Server-Sent Events.

curl -s -N -X POST http://localhost:8080/v1/completions \
  -H "Content-Type: application/json" \
  -d '{"prompt": "Hello world", "max_tokens": 5, "stream": true}'

[ sample output ]

data: {"id": "sim-<ts>", "object": "text_completion", "model": "sim-llm-7b", "choices": [{"index": 0, "text": " <token>", "finish_reason": null}]}

data: {"id": "sim-<ts>", "object": "text_completion", "model": "sim-llm-7b", "choices": [{"index": 0, "text": " <token>", "finish_reason": null}]}

data: {"id": "sim-<ts>", "object": "text_completion", "model": "sim-llm-7b", "choices": [{"index": 0, "text": " <token>", "finish_reason": null}]}

data: {"id": "sim-<ts>", "object": "text_completion", "model": "sim-llm-7b", "choices": [{"index": 0, "text": " <token>", "finish_reason": null}]}

data: {"id": "sim-<ts>", "object": "text_completion", "model": "sim-llm-7b", "choices": [{"index": 0, "text": " <token>", "finish_reason": "stop"}], "usage": {"prompt_tokens": 2, "completion_tokens": 5, "total_tokens": 7}}

data: [DONE]

Each data: line contains one generated token. The last event reports finish_reason: stop and includes the usage summary.

Observe the pause before the first token. This is the time to first token (TTFT). The delay between later tokens is the inter-token latency (ITL).

Read the Prometheus metrics from /metrics.

curl -s http://localhost:8080/metrics

# TYPE inference_kv_cache_utilization gauge

inference_kv_cache_total_slots 32
# HELP inference_errors_total Total errors (503s, timeouts).
# TYPE inference_errors_total counter

Examine the following values:

  • inference_ttft_seconds is the time to first token.
  • inference_itl_seconds is the average delay between generated tokens.
  • inference_queue_depth reports requests waiting for a processing slot.
  • inference_kv_cache_utilization reports cache use by active requests.
  • inference_requests_active reports requests currently being processed.

Drive Concurrent Load​

Send eight requests in parallel. Each request generates 100 tokens so that it remains active long enough to observe the metrics.

for i in $(seq 1 8); do
  curl -s -X POST http://localhost:8080/v1/completions \
    -H "Content-Type: application/json" \
    -d '{"prompt": "Write a detailed analysis of container orchestration patterns in modern cloud native architecture and their impact on system reliability", "max_tokens": 100}' > /dev/null &
done

[ Expected output ]

(no output; requests continue in the background)

While the requests are running, check the active requests, queue depth, KV cache use and token count.

sleep 1 && curl -s http://localhost:8080/metrics | grep -E '(requests_active|queue_depth|kv_cache_util|tokens_generated) ' | grep -v '#'

[ sample output ]

inference_requests_active 4
inference_queue_depth 0
inference_kv_cache_utilization 0.1250
inference_tokens_generated_total 120

Observe that the active request count reaches four and the KV cache use increases. The generated token counter should also increase.

Port-forward targets one pod

kubectl port-forward svc/... connects to one backend Pod. The metrics shown here belong to that Pod only. Prometheus would normally aggregate the metrics from every replica.

Wait for the requests to finish and check the metrics again.

wait
curl -s http://localhost:8080/metrics | grep -E '(requests_total|tokens_generated|requests_active) ' | grep -v '#'

[ sample output ]

inference_requests_total 11
inference_tokens_generated_total 555
inference_requests_active 0

The active request count should return to zero.

Scale the Serving Capacity​

Scale the Deployment down to one replica.

kill %1 2>/dev/null
kubectl --context kind-kubeadv-core -n m9-lab scale deployment inference-sim --replicas=1
kubectl --context kind-kubeadv-core -n m9-lab rollout status deployment/inference-sim --timeout=60s

[ Expected output ]

deployment.apps/inference-sim scaled
deployment "inference-sim" successfully rolled out

Restart the port-forward.

kubectl --context kind-kubeadv-core -n m9-lab port-forward svc/inference-sim 8080:80 &
sleep 2

[ Expected output ]

Forwarding from 127.0.0.1:8080 -> 8080

Send eight concurrent requests to the single replica and check its metrics.

for i in $(seq 1 8); do
  curl -s -X POST http://localhost:8080/v1/completions \
    -H "Content-Type: application/json" \
    -d '{"prompt": "Analyze the impact of distributed systems on modern infrastructure", "max_tokens": 100}' > /dev/null &
done
sleep 1 && curl -s http://localhost:8080/metrics | grep -E '(requests_active|queue_depth|kv_cache_util) ' | grep -v '#'

[ sample output ]

inference_requests_active 4
inference_queue_depth 3
inference_kv_cache_utilization 0.1250

The Pod has four active requests and additional requests in the queue. This shows that the single replica has reached its concurrency limit.

Wait for the requests to finish. Then scale the Deployment to four replicas.

wait
kill %1 2>/dev/null
kubectl --context kind-kubeadv-core -n m9-lab scale deployment inference-sim --replicas=4
kubectl --context kind-kubeadv-core -n m9-lab rollout status deployment/inference-sim --timeout=60s

[ Expected output ]

deployment.apps/inference-sim scaled
deployment "inference-sim" successfully rolled out
kubectl --context kind-kubeadv-core -n m9-lab get pods

[ sample output ]

NAME                             READY   STATUS    RESTARTS   AGE
inference-sim-77c69684c7-abc12   1/1     Running   0          5s
inference-sim-77c69684c7-def34   1/1     Running   0          5s
inference-sim-77c69684c7-ghi56   1/1     Running   0          5s
inference-sim-77c69684c7-jkl78   1/1     Running   0          30s

Four replicas provide 16 processing slots when each Pod supports four active requests.

A possible autoscaling policy based on this observation is:

  • scale up when inference_queue_depth > 0 remains true
  • scale up before queuing when inference_kv_cache_utilization remains high
  • scale down only after both values remain low for a suitable period

PART III - Examine Production Serving Resources​

Gateway API Inference Extension​

The following resources are not installed in the lab. Examine how they represent the same serving concepts in Kubernetes.

An InferencePool groups serving replicas and refers to a model-aware routing extension.

apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferencePool
metadata:
  name: llm-pool
spec:
  targetPortNumber: 8080
  selector:
    app: vllm-server
  extensionRef:
    name: endpoint-picker
  • selector selects the serving Pods.
  • extensionRef points to the endpoint-selection logic.
  • The endpoint picker can use queue depth and KV cache metrics when selecting a backend.

An InferenceModel maps a model name to an InferencePool and assigns traffic weights.

apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferenceModel
metadata:
  name: llama-3
spec:
  modelName: meta-llama/Llama-3-8B
  targetModels:
  - name: meta-llama/Llama-3-8B
    weight: 90
  - name: meta-llama/Llama-3-8B-v2
    weight: 10
  poolRef:
    name: llm-pool
  • targetModels distributes traffic across model versions.
  • poolRef connects the model to the InferencePool.
  • Clients request the model name and the gateway selects a target.

The Gateway API Inference Extension routes requests to serving engines. The serving engine still manages batching, model execution and KV cache inside the Pod.

KServe InferenceService​

An InferenceService manages the model deployment lifecycle.

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: llama-3
spec:
  predictor:
    model:
      modelFormat:
        name: vllm
      runtime: kserve-vllm
      storageUri: s3://models/llama-3-8b
      resources:
        limits:
          nvidia.com/gpu: 1
    minReplicas: 1
    maxReplicas: 8
    scaleTarget: 2
    scaleMetric: concurrency
  • storageUri identifies the model weights.
  • runtime selects the serving engine.
  • scaleTarget and scaleMetric configure autoscaling.
  • minReplicas controls whether a warm replica is kept available.

Compared with a raw Deployment, KServe can manage:

  • model downloading and caching
  • readiness after model loading
  • traffic splitting between model versions
  • scale-to-zero behaviour
  • Transformer, Predictor and Explainer pipelines

Validate​

Make sure that:

  • the streaming response returns one token per SSE event
  • /metrics reports TTFT and ITL
  • KV cache use increases while requests are active
  • one replica reaches four active requests and develops a queue
  • four replicas provide more serving slots
  • the InferencePool, InferenceModel and InferenceService examples map to routing and lifecycle responsibilities

Troubleshooting​

Troubleshooting
  • Port 8080 is already in use — stop the previous port-forward before starting another one.
  • The health endpoint does not respond — check that the simulator Pods are Running and restart the port-forward.
  • Queue depth does not increase — confirm that the Deployment has one replica and sample the metrics while the requests are running.
  • KV cache utilization remains at zero — read the metrics before the concurrent requests complete.
  • The first rollout is slow — the cluster may still be downloading the simulator image.

Teardown​

Stop the port-forward and delete the lab namespace.

# Stop port-forward
kill %1 2>/dev/null

# Remove simulator
kubectl --context kind-kubeadv-core delete namespace m9-lab

# Core-internals cluster remains intact for M10

[ Expected output ]

namespace "m9-lab" deleted

In this lab, you deployed an OpenAI-compatible inference simulator and observed normal and streaming responses.

You measured TTFT, inter-token latency, active requests, queue depth and KV cache use.

You also scaled the Deployment and examined how Gateway API Inference Extension and KServe describe production serving.
