Environment

This page takes you from a bare machine to a fully verified lab environment. Install in the order given — the container runtime comes first because everything else depends on it. At the end, run the verification probe; when all eight commands pass, you are lab-ready.

The toolchain at a glance​

No Docker Desktop, no cloud account, no GPU. All lab images are multi-arch (linux/arm64 + linux/amd64).

Step 1 — Install Rancher Desktop and select the dockerd engine​

Rancher Desktop provides the Docker daemon (Moby/dockerd) that kind uses to run cluster nodes as containers. This course standardizes on the dockerd engine, not containerd — kind talks to a Docker socket, and every lab was validated against dockerd. If you have Docker Desktop installed, quit it; it is not needed and two daemons fighting over the socket causes confusing failures.

  1. Download and install Rancher Desktop from rancherdesktop.io (macOS .dmg, Windows installer, Linux .deb/.rpm/AppImage — see the installation docs).
  2. Launch it. On first run it asks for initial settings — you can set everything now or change it later.
  3. Open Preferences (macOS: Rancher Desktop → Preferences; Windows/Linux: gear icon) and set:
    • Container Engine → select dockerd (moby). This is the critical setting. If it is set to containerd, switch it and let Rancher Desktop restart its VM.
    • Kubernetes → uncheck "Enable Kubernetes". You do not need Rancher Desktop's built-in cluster — kind creates the course clusters — and disabling it returns roughly 1–2 GB of memory to your labs.
    • Virtual Machine → Hardware (macOS/Linux): give the VM at least 4 GB memory (8 GB machines) or 6–8 GB (16 GB machines), and 4 CPUs.
  4. Wait for the VM to finish starting (progress bar disappears), then confirm the daemon answers:
docker version

You should see both a Client: and a Server: section. If the Server: section is missing or you get Cannot connect to the Docker daemon, Rancher Desktop is not running or its VM is still starting.

dockerd (moby), not containerd

The single most common setup failure in this course is Rancher Desktop left on the containerd engine. kind then fails with Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Preferences → Container Engine → dockerd (moby) → restart. Verify with docker version before moving on.

Windows: everything happens inside WSL2

On Windows, Rancher Desktop installs on the Windows side but exposes docker inside your WSL2 distributions. In Preferences → WSL → Integrations, enable your Ubuntu distribution. Then open an Ubuntu (WSL2) terminal — that is your lab terminal for the whole course — and install all remaining tools inside WSL2 using the Linux instructions below.

Step 2 — Install the CLI tools​

macOS (Homebrew)​

brew install kind kubernetes-cli helm kwok cilium-cli hubble git

That is the complete set: kwok provides kwokctl, kubernetes-cli provides kubectl.

macOS: stale binaries can shadow the brew installs

Older copies in /usr/local/bin (e.g. a years-old kind) or Rancher Desktop's shims in ~/.rd/bin (its bundled kubectl) can shadow your brew installs. Check with which -a kind kubectl. If the brew versions are not first, put Homebrew first for your lab sessions:

export PATH="/opt/homebrew/bin:$PATH"   # Apple Silicon (use /usr/local/bin on Intel Macs)

Add it to ~/.zshrc to make it permanent.

Linux — and Windows WSL2 (run inside your Ubuntu terminal)​

Substitute arm64 for amd64 below if you are on an ARM machine.

# kind (≥ 0.32) — https://kind.sigs.k8s.io/docs/user/quick-start/#installation
curl -Lo ./kind https://kind.sigs.k8s.io/dl/latest/kind-linux-amd64
chmod +x ./kind && sudo mv ./kind /usr/local/bin/kind

# kubectl (client ≥ 1.35) — https://kubernetes.io/docs/tasks/tools/install-kubectl-linux/
curl -LO "https://dl.k8s.io/release/$(curl -Ls https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x ./kubectl && sudo mv ./kubectl /usr/local/bin/kubectl

# helm — https://helm.sh/docs/intro/install/
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

# kwokctl — https://kwok.sigs.k8s.io/docs/user/installation/
KWOK_VERSION="$(curl -s https://api.github.com/repos/kubernetes-sigs/kwok/releases/latest | grep -oP '"tag_name": "\K[^"]+')"
curl -Lo ./kwokctl "https://github.com/kubernetes-sigs/kwok/releases/download/${KWOK_VERSION}/kwokctl-linux-amd64"
chmod +x ./kwokctl && sudo mv ./kwokctl /usr/local/bin/kwokctl

# cilium CLI — https://docs.cilium.io/en/stable/gettingstarted/k8s-install-default/#install-the-cilium-cli
CILIUM_CLI_VERSION="$(curl -s https://raw.githubusercontent.com/cilium/cilium-cli/main/stable.txt)"
curl -L "https://github.com/cilium/cilium-cli/releases/download/${CILIUM_CLI_VERSION}/cilium-linux-amd64.tar.gz" | sudo tar xz -C /usr/local/bin

# hubble CLI — https://docs.cilium.io/en/stable/observability/hubble/setup/
HUBBLE_VERSION="$(curl -s https://raw.githubusercontent.com/cilium/hubble/main/stable.txt)"
curl -L "https://github.com/cilium/hubble/releases/download/${HUBBLE_VERSION}/hubble-linux-amd64.tar.gz" | sudo tar xz -C /usr/local/bin

# git
sudo apt-get update && sudo apt-get install -y git   # Debian/Ubuntu

Step 3 — Verify your setup​

You would not fly a plane without a pre-flight checklist, and you will not start Module 1 without this one. Paste the whole block into your lab terminal (from anywhere — no repo needed yet):

docker version
kind version
kubectl version --client
helm version
kwokctl --version
cilium version --client
hubble version
git --version

What each probe must show:

ProbeExpected output pattern
docker versionA Client: and a Server: section (server ≈ 25+). Server section missing → Rancher Desktop not running or wrong engine.
kind versionkind v0.32.x ... or newer. v0.2x → an old binary is shadowing your install (see PATH note above).
kubectl version --clientClient Version: v1.35.x or newer (validated on v1.36.2).
helm versionversion.BuildInfo{Version:"v3.x.x" or "v4.x.x", ...}
kwokctl --versionkwokctl version v0.8.x (or newer).
cilium version --clientcilium-cli: v0.19.x ... — it may add "unable to connect to Kubernetes cluster", which is fine: no cluster exists yet.
hubble versionhubble 1.19.x (no leading v) ... (or newer).
git --versiongit version 2.x.x

All eight answer? Clone the repo if you haven't (Prerequisites) and you are ready for Module 1.

Corporate firewall: host pulls work, Pods fail with x509​

Some corporate networks install their certificate authority in macOS and the host Docker daemon, but not inside kind nodes. In that case this works:

docker pull registry.k8s.io/kwok/kwok:v0.8.0

But a Pod that uses the same image fails with ImagePullBackOff, and kubectl describe pod shows an x509: certificate signed by unknown authority error.

The reason is simple: a kind node is a container with its own containerd image store and its own certificate trust. The host Docker cache is not automatically visible inside that node.

The course repo includes one helper that pulls every pinned course image through host Docker:

bash labs/tools/preload-course-images.sh --pull-only

Expected output pattern:

Pulling 14 course workload images through host Docker ...
  pull nginx:alpine
  ...
  pull kindest/node:v1.35.0 (host only)
Host image cache is ready. Set COURSE_IMAGE_CACHE=1 before creating course clusters.

If kubeadv-core is already running and you want the immediate one-command workshop fix, pull and load everything with:

export COURSE_IMAGE_CACHE=1
bash labs/tools/preload-course-images.sh \
  --cluster kubeadv-core \
  --scope all

Run that command before the workshop while your approved corporate network or VPN can reach the registries. It downloads the images once into host Docker. Then enable cache mode in every workshop terminal:

export COURSE_IMAGE_CACHE=1

Create or reuse the course cluster normally:

bash labs/clusters/core-internals/create.sh

With cache mode enabled, the profile imports the required images into containerd on every kind node. The same behavior is built into the Cilium and capstone profiles. M8, M9, and M10 setup scripts also check this variable before they create workloads.

If the cluster already exists and you only want to load its images, run:

bash labs/tools/preload-course-images.sh \
  --load-only \
  --cluster kubeadv-core \
  --scope core

Expected output pattern:

Saving nginx:alpine once for node import ...
  load nginx:alpine -> kubeadv-core/kubeadv-core-control-plane
  load nginx:alpine -> kubeadv-core/kubeadv-core-worker
...
Course images loaded into: kubeadv-core

The available scopes are core, cilium, and capstone. Use --scope all only when you deliberately want every workload image copied into an existing cluster. You can inspect the exact pinned inventory without pulling anything:

bash labs/tools/preload-course-images.sh --list
What this workaround does and does not fix

This avoids image pulls from inside kind. It does not repair certificate trust. Host docker pull and downloads from GitHub or Helm registries must still work. If host pulls also fail, your corporate IT team must provide the approved proxy, registry mirror, or CA configuration.

Kueue normally publishes its controller with imagePullPolicy: Always. The M8 and capstone setup scripts use the same pinned Kueue image with IfNotPresent, so a preloaded copy is actually used instead of contacting the registry again.

Optional dry run

If you want proof the full path works before class, run the M1 profile once from the repo root: bash labs/clusters/core-internals/create.sh, then bash labs/clusters/core-internals/verify.sh, then bash labs/clusters/core-internals/teardown.sh. The first create pulls the kindest/node:v1.35.0 image (~1 GB, up to ~15 minutes on slow links); every later create is fast. Doing this pre-pull on hotel/venue Wi-Fi the night before is the single best time investment you can make.

Cluster-profile rules​

The course uses a library of cluster profiles under labs/clusters/ — think of them as stage sets: each module's lab plays out on the set built for it, and the crew strikes one set completely before building the next.

  1. Only ONE profile runs at a time. Two kind clusters plus KWOK simulators will exhaust an 8 GB machine and produce exactly the kind of resource-pressure failures you are here to study, not suffer. Before creating a profile, tear down the previous one: bash labs/clusters/<previous-profile>/teardown.sh. Check what exists with kind get clusters.
  2. Every profile has the same three scripts. create.sh (idempotent — safe to re-run; reuses an existing healthy cluster), verify.sh (run it every time before starting lab steps), and teardown.sh (removes the cluster entirely). No profile requires manual kind commands.
  3. Two size variants where it matters. Resource-sensitive profiles (the scale labs in particular) ship an 8 GB variant (1 control-plane + 1 worker, ~250–500 KWOK nodes) and a 16 GB variant (1 control-plane + 2 workers, ~1000 KWOK nodes). Each lab tells you which variant to pick; when in doubt, use the 8 GB variant — it demonstrates every lesson.
  4. Always run from the repo root. Every bash labs/... command in every lab assumes your working directory is the root of the 304-kubeadv clone.
