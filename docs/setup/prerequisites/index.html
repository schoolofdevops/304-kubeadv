Prerequisites

This is an advanced course. You will spend three days deliberately breaking control planes, filling etcd, and racing schedulers — so before you start, make sure both you and your machine are ready. This page covers what you need to know, what hardware you need, and how to get the course repository. The next page — Environment — covers installing and verifying every tool.

What you should already know​

You should be operating Kubernetes in production today. Concretely, that means you can:

  • Read and write Kubernetes YAML without a reference open.
  • Use kubectl fluently — get, describe, logs, exec, apply, -o yaml, label selectors.
  • Debug a failing workload (CrashLoopBackOff, ImagePullBackOff, Pending) without step-by-step instructions.
  • Work comfortably in a terminal with bash, git, and Docker.

We will not review Pods, Deployments, or Services. If you need that foundation first, take our Kubernetes for Beginners program and come back.

System requirements​

Every lab in this course runs locally — no cloud account, no GPU, no paid services. The entire AI-platform track (DRA, Kueue, inference serving) uses simulated devices and lightweight simulators.

RequirementMinimumRecommended
RAM8 GB16 GB
CPU4 cores6+ cores
Free disk30 GB50 GB
OSmacOS 13+, Windows 10/11 with WSL2, or a recent Linux (Ubuntu 22.04+, Fedora 39+)—

Supported architectures:

  • Apple Silicon (arm64) — fully supported. Every lab image is multi-arch (linux/arm64 + linux/amd64).
  • Intel/AMD (amd64) — macOS, Linux, and Windows via WSL2.
  • Windows — labs run inside WSL2 (Ubuntu recommended). Native PowerShell is not a supported lab shell.
8 GB machines work — with the reduced profiles

The cluster-profile library ships two variants of every resource-sensitive profile. On 8 GB machines you run the reduced variant (1 control-plane + 1 worker, ~250–500 simulated KWOK nodes); on 16 GB machines you run the enhanced variant (1 control-plane + 2 workers, ~1000 KWOK nodes). The lessons are identical — only the scale knee moves.

Get the course repo​

All labs live in one repository. Clone it now:

git clone https://github.com/schoolofdevops/304-labs.git
cd 304-labs
Every lab command runs from the repo root

Unless a lab explicitly says otherwise, every command in every lab assumes your current directory is the root of this repo (the 304-labs/ directory you just entered). If a command like bash labs/clusters/core-internals/create.sh fails with "No such file or directory", you are in the wrong directory — cd back to the repo root.

Clone under your home directory. The cluster profile bind-mounts files from this repo into the cluster's nodes (the audit policy, for one), and Rancher Desktop / WSL2 only share certain host paths into their VM — your home directory always, /tmp and system paths often not. A repo outside the shared paths fails cluster creation with a cryptic kubeadm timeout (the mounted file silently becomes an empty directory inside the node).

Repo layout — the two directories you'll live in​

Think of the repo as a workshop with two shelves: one holds the machines (cluster profiles), the other holds the materials (per-module manifests).

304-labs/
├── labs/
│   ├── clusters/                # cluster-profile library — one profile per lab environment
│   │   ├── core-internals/      #   used by M1, M2, M4, M5, M10
│   │   │   ├── create.sh        #   stand the profile up (idempotent)
│   │   │   ├── verify.sh        #   prove it's healthy before you start
│   │   │   └── teardown.sh      #   remove it completely
│   │   ├── etcd-failure/        #   M3
│   │   ├── kwok-scale/          #   M6
│   │   ├── cilium-networking/   #   M7
│   │   ├── ai-scheduling/       #   M8, M9
│   │   └── capstone/            #   M11 (arrives pre-broken)
│   ├── tools/
│   │   └── preload-course-images.sh  # corporate-firewall image cache helper
│   └── m1/, m2/, ... m11/       # per-module materials
│       ├── *.yaml               #   manifests you apply during the lab
│       └── checks.json          #   machine-readable pass/fail checks for the module
└── ...                          # course site source, planning docs — not needed for labs

Two rules govern everything under labs/clusters/:

  1. Every profile ships exactly three scripts — create.sh, verify.sh, teardown.sh. You will always create, always verify before working, and always tear down when the module (or your day) ends.
  2. Only ONE profile runs at a time. Tear down the current profile before creating the next. The Environment page explains why.
