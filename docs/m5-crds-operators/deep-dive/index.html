Deep Dive - Inside the API Extension: Schemas, Admission, Versions, and Garbage Collection

This deep dive examines structural schemas, CEL validation, API versions, admission webhooks, and garbage collection. Use these checks when a custom-resource field disappears, validation behaves unexpectedly, or child resources survive a deletion.

▶ M5: CRDs & Operators Deep DiveOpen fullscreen ↗

Run everything from the repo root against the core-internals profile.

Where this picks up

The Website CRD from the lab is all this page needs: most blocks here are about the API server, not the operator. Install the CRD if the lab's teardown removed it, and seed a working namespace. Both are idempotent: safe to re-run once per terminal session:

kubectl apply -f labs/m5/website-crd.yaml
kubectl wait --for condition=established --timeout=30s crd/websites.kubeadv.io
kubectl create namespace m5-deepdive --dry-run=client -o yaml | kubectl apply -f -

[ Expected output ]

customresourcedefinition.apiextensions.k8s.io/websites.kubeadv.io configured
customresourcedefinition.apiextensions.k8s.io/websites.kubeadv.io condition met
namespace/m5-deepdive created

PART I - The structural schema: pruning and defaulting​

A CRD's schema is not just a validator: it defines the object's structure, and the API server enforces that structure in two directions. Fields it doesn't recognise are pruned (dropped); fields you leave out that carry a default are filled in. This is what makes a CRD behave like a built-in kind rather than a free-form blob.

Modern kubectl sends objects for strict field validation by default, so an unknown field is normally rejected outright: you saw that in the lab with unknown field "spec.tls". To watch the pruning underneath that gate, bypass the client-side strictness with --validate=false and let the server apply the schema:

kubectl apply -n m5-deepdive --validate=false -f - <<'EOF'
apiVersion: kubeadv.io/v1alpha1
kind: Website
metadata: { name: prune, namespace: m5-deepdive }
spec: { host: prune.io, replicas: 1, secretSauce: "should-vanish" }
EOF
kubectl -n m5-deepdive get website prune -o jsonpath='{.spec}'; echo

[ Expected output ]

website.kubeadv.io/prune created
{"host":"prune.io","image":"nginx:1.27-alpine","replicas":1}

Two things happened in one write. The secretSauce field: which the structural schema never declared: was pruned, so it is not in the stored object. And image, which you never set, was defaulted to nginx:1.27-alpine. Both come from the same structural schema. Pruning is why a CRD is safe to store in etcd: the API server never persists fields it cannot account for. The strict-decoding gate in front of it is a usability layer: it turns a silent prune into a loud error so a typo like secretSuace fails at apply time instead of vanishing quietly. Clean up:

kubectl -n m5-deepdive delete website prune --wait=false

[ Expected output ]

website.kubeadv.io "prune" deleted from m5-deepdive namespace

PART II - CEL validation: guardrails inside the API server​

The lab's replicas may not exceed 5 rejection came from a CEL (Common Expression Language) rule baked into the CRD as x-kubernetes-validations. The important internal detail is where it runs: in-process, in the API server, during admission: no webhook, no extra pod, no network hop. Read the rule straight off the CRD:

kubectl get crd websites.kubeadv.io -o yaml | grep -A2 'x-kubernetes-validations:' | grep -E 'message:|rule:'

[ Expected output ]

            - message: replicas may not exceed 5 (guardrail enforced at admission)
              rule: self.replicas <= 5

(Read it as YAML, not JSONPath: -o jsonpath HTML-escapes the < in <= to <, which is just an encoding artifact of the path printer, not what's stored.)

That rule is evaluated for every create and update, with self bound to the object being validated. Before CEL (added as a native feature in 1.25 and GA in 1.29), the only way to enforce a cross-field or bounded rule like this was a validating admission webhook: a separate service the API server calls out to on every request. CEL moves the common cases in-process: faster, no service to run and keep available, no webhook to become a single point of failure. You still reach for a webhook when the rule needs to consult other objects or external state, which CEL deliberately cannot. This is the modern default: encode your guardrails in the CRD and let the API server enforce them.

PART III - Versions, the storage version, and conversion​

A CRD can serve more than one version of a kind at once: v1alpha1, v1beta1, v1: and this is how a custom API matures without breaking existing clients. Read the version machinery on your CRD:

kubectl get crd websites.kubeadv.io -o jsonpath='{range .spec.versions[*]}{.name} served={.served} storage={.storage}{"\n"}{end}status.storedVersions={.status.storedVersions}'; echo

[ Expected output ]

v1alpha1 served=true storage=true
status.storedVersions=["v1alpha1"]

Two flags govern each version. served decides whether the API server answers requests for that version: you can serve several at once. storage marks the single version objects are actually persisted as in etcd; exactly one version carries it. status.storedVersions records every version that has ever been the storage version, which matters when you retire an old one: you cannot drop a version still listed here until every stored object has been rewritten to a newer version.

What conversion does, and why this CRD doesn't need it

When you serve two versions with different schemas, a client asking for v1 must get an object that follows the v1 schema even though it is stored as v1beta1. The API server bridges that with a conversion strategy. The default, None, only relabels the apiVersion and works when the versions are structurally compatible. When they genuinely differ, you set strategy: Webhook and run a conversion webhook the API server calls to translate objects on the fly. This Website CRD serves a single version, so no conversion is involved: but the moment you add a v1beta1 with a renamed or restructured field, a conversion webhook is what keeps old and new clients both working against the same stored objects.

PART IV - Admission webhooks in the M2 request path​

CEL covers validation that can be expressed as an expression over the object itself. Everything beyond that: mutating an object on the way in, or validating it against other cluster state: is the job of admission webhooks, and they live at a specific point in the request lifecycle you traced in M2: after authentication and authorisation, inside admission, before the object is persisted. The two kinds are first-class API resources:

kubectl api-resources | grep webhookconfig

[ Expected output ]

mutatingwebhookconfigurations                    admissionregistration.k8s.io/v1   false        MutatingWebhookConfiguration
validatingwebhookconfigurations                  admissionregistration.k8s.io/v1   false        ValidatingWebhookConfiguration

The order inside admission is fixed and worth memorising: mutating webhooks run first (they can rewrite the object: inject a sidecar, set a default, add a label), then the object is schema-validated, then validating webhooks run (they can only accept or reject). A mutating webhook is how service meshes inject their sidecar container into every pod without you editing your manifests; a validating webhook is how a policy engine like Kyverno or OPA Gatekeeper enforces org-wide rules.

kubectl get validatingwebhookconfigurations --no-headers | wc -l

[ Expected output ]

0

This kind cluster ships with no admission webhooks configured: a clean baseline. That is exactly why CEL is valuable: the replicas <= 5 guardrail you enforced in the lab needed nothing deployed, no webhook service to run and keep highly available. On a production cluster this list is rarely empty; every entry is a service the API server must call: synchronously, in the request path: on matching operations, which is why a broken or slow webhook can wedge object creation cluster-wide. Knowing this list exists, and how to read its failurePolicy, is the difference between diagnosing "why can't I create any pods" in minutes versus hours.

PART V - Garbage collection: the three propagation policies​

ownerReferences drive garbage collection, but how a parent's deletion cascades to its children is a choice: the propagation policy. There are three, and they behave differently enough that picking the wrong one causes real surprises. Seed a parent with a hand-owned child so you can watch one policy in isolation, without the operator's finalizer in the way:

cat <<'EOF' | kubectl apply -f -
apiVersion: kubeadv.io/v1alpha1
kind: Website
metadata: { name: gc, namespace: m5-deepdive }
spec: { host: gc.io, replicas: 1 }
EOF
WSUID=$(kubectl -n m5-deepdive get website gc -o jsonpath='{.metadata.uid}')
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gc-child
  namespace: m5-deepdive
  ownerReferences:
  - { apiVersion: kubeadv.io/v1alpha1, kind: Website, name: gc, uid: ${WSUID}, controller: true }
spec:
  replicas: 1
  selector: { matchLabels: { app: gc-child } }
  template:
    metadata: { labels: { app: gc-child } }
    spec:
      containers: [ { name: web, image: nginx:1.27-alpine } ]
EOF

[ Expected output ]

website.kubeadv.io/gc created
deployment.apps/gc-child created

Now delete the parent with --cascade=orphan and watch the child survive:

kubectl -n m5-deepdive delete website gc --cascade=orphan
kubectl -n m5-deepdive get deploy gc-child -o jsonpath='gc-child ownerReferences={.metadata.ownerReferences}'; echo

[ Expected output ]

website.kubeadv.io "gc" deleted from m5-deepdive namespace
gc-child ownerReferences=

The parent is gone but gc-child remains: and its ownerReferences are now empty. That is orphan: sever the parentage, keep the children. The other two policies delete the children, and differ only in ordering. background (the default) deletes the parent immediately and lets the garbage collector reap the children afterwards: fast, but for a moment the children outlive the parent. foreground holds the parent in a deleting state (via a foregroundDeletion finalizer) until every child is gone first, then removes the parent: slower, but the parent never disappears while its children still exist, which is what you want when something downstream watches the parent as a signal that its resources are cleaned up. Remove the orphan:

kubectl -n m5-deepdive delete deploy gc-child

[ Expected output ]

deployment.apps "gc-child" deleted from m5-deepdive namespace

PART VI - CRD versus aggregated API server​

A CRD is one of two ways to add an API to Kubernetes, and it is worth knowing where its limits are. A CRD is served by the kube-apiserver, stored in etcd, and validated by a schema: you write no server code. The other path is an aggregated API server: your own API server process, which the kube-apiserver registers and proxies requests to, with its own storage and arbitrary logic. The registration objects for both live in the aggregation layer:

kubectl get apiservices | head -5
kubectl get apiservices --no-headers | wc -l

[ Expected output ]

NAME                              SERVICE   AVAILABLE   AGE
v1.                               Local     True        14h
v1.admissionregistration.k8s.io   Local     True        14h
v1.apiextensions.k8s.io           Local     True        14h
v1.apps                           Local     True        14h
22

Every entry marked Local is served by the kube-apiserver itself: the built-in groups and, notably, apiextensions.k8s.io, which is the group that serves your CRDs. An aggregated API would show a real SERVICE reference instead of Local, pointing at the pod that backs it (the classic example is v1beta1.metrics.k8s.io, served by metrics-server). Reach for aggregation only when a CRD's model genuinely does not fit: you need custom storage, non-etcd backends, expensive computed responses, or request handling a schema cannot express. For the overwhelming majority of extensions: including nearly every operator you will run: a CRD is the right tool, and the aggregation layer is something you read, not something you build.

Where you will use this
  • Structural schemas prune unknown fields and apply defaults before storage. Use it when: a field disappears or changes after apply: compare the submitted object with the CRD schema and the stored object before blaming the controller.
  • CEL keeps common validation inside kube-apiserver. Use it when: a rule depends only on the request and object: prefer CEL over adding another synchronous webhook dependency.
  • Only one served version is the storage version. Use it when: planning a CRD upgrade: rewrite stored objects and clear old entries from status.storedVersions before removing an API version.
  • Admission webhooks sit in the write path. Use it when: creates time out across unrelated teams: inspect matching webhook scope, endpoints, latency, timeoutSeconds, and failurePolicy before restarting the API server.
  • Cascade choice changes the deletion contract. Use background when: ordinary asynchronous cleanup is acceptable. Use foreground when: the parent must remain visible until dependants are gone. Use orphan when: children must survive and become independently managed. Avoid orphaning by accident; ownership disappears, but the running cost does not.
  • Aggregated APIs add another API server to operate. Use it when: custom storage or request behaviour is a hard requirement: not merely because a CRD schema feels inconvenient.

Teardown​

kubectl delete namespace m5-deepdive --wait=false

[ Expected output ]

namespace "m5-deepdive" deleted

The CRD stays installed for the rest of your session; the lab's bash labs/m5/setup.sh teardown removes it when you are done. You have now seen the API extension from the inside: a structural schema that prunes and defaults, CEL guardrails enforced in-process, versions and the storage-version/conversion contract, admission webhooks in the request path, the three garbage-collection policies, and the line between a CRD and an aggregated API server: the machinery under every custom resource you will ever run.
