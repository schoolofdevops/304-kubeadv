Extending Kubernetes — CRDs & Operators

Every module so far has taken apart a piece of Kubernetes that shipped in the box: the reconcile loop, the API server, etcd, the scheduler. This module is about the moment you stop being only a user of those parts and start adding your own. Almost every serious tool you run on Kubernetes today (cert-manager, Prometheus Operator, Kueue, KServe) is not built into Kubernetes. It bolts on, using the exact two mechanisms you will learn here: a Custom Resource Definition that teaches the API server a new kind of object, and an operator that gives that object behaviour. On call, this is the pattern of trouble you will meet: a user says "I deleted my resource an hour ago and it is still stuck," or "the operator is not doing anything for my new object." To debug either one you have to know exactly where the CRD ends and the operator begins. That is what we build here, from the ground up.

A CRD is a new register at the government office​

Imagine your local government office. It accepts certain kinds of applications (a passport form, a driving-licence form) and for each one there is a register where those applications are recorded. Now the office decides to accept a brand-new kind of application. What has to happen first? Someone prints a new form, defines what a valid entry looks like, and opens a new register to hold them. From that moment the front desk will accept the new application, check it against the rules, stamp it, and file it away.

A Custom Resource Definition is exactly that: a new register you hand to the API server. The instant you register it, the API server accepts, validates, stores, and serves a new kind of object (a Website, a Certificate, a Job of your own design) with no code deployed anywhere. It becomes a first-class citizen: discovery lists it, kubectl explain describes it, RBAC can guard it, and it is stored in etcd next to Pods and Deployments.

The register carries rules, and the front desk enforces them before anything is filed. In the Website CRD you will build, those rules are a structural schema (every field is declared, so a typo like tls: is rejected), a default (leave image blank and the API server fills in nginx), a CEL validation rule (replicas may not exceed 5, checked in-process at admission, no webhook, no extra pod), and a status subresource (a separate compartment on the object that only the controller writes). All of this runs in the M2 request path you already traced, before the object reaches etcd.

Why a CRD Needs a Controller​

Here is the idea the whole module turns on, and it surprises people every time. You register the Website CRD. You create a Website that clearly asks for two replicas of a web server. You look at the cluster. And there is no Deployment, no Service, no Pod. Nothing ran.

That is not a bug. A CRD is only data. It taught the API server a new schema, nothing more. A register that no clerk ever reads is just paper in a drawer. The new application sits there, perfectly valid, perfectly stored, and completely inert, because nothing in the cluster knows what a Website is supposed to do. Built-in kinds feel alive only because each one already has a controller watching it. A Deployment does something because the deployment-controller reads it. Your custom kind has no such clerk yet.

The operator is the clerk, and it is the M1 reconcile loop​

To give the register meaning you hire a clerk. Every day the clerk opens the register, reads each application, does the real-world work it describes, and keeps the register's status column up to date. That clerk is the operator. And you have already met exactly how it thinks: it is the M1 reconcile loop, now watching your kind.

Observe the desired state (the Website spec), compare it with what actually exists in the cluster, and act to close the gap. Then record what is true in status. Level-triggered, exactly as in M1: the operator does not react to events, it drives reality toward the spec on every pass. Delete the Deployment it created and the operator simply notices, on its next look, that reality no longer matches the register, and recreates it. Stop the operator and the cluster stops converging. That is drift, and it is why an operator that has crashed looks like "my changes are being ignored."

Production operators are written with frameworks like controller-runtime and kubebuilder, in Go, with real informers and work queues, the machinery from M4. The one you deploy in the lab is a small shell reconcile loop instead, so nothing is hidden behind a framework. The mechanics are identical; only the packaging differs.

spec is yours, status is the operator's​

Look at any built-in object and you will see the same split: spec is what the user wants, status is what is actually true. A CRD gets that split too, through the status subresource. You write the Website spec: host, replicas. The operator writes the Website status, a Ready: 2/2 count and a set of conditions. Neither side clobbers the other. When you read kubectl get website and see a number in the READY column, you are reading the operator's report card on its own work.

ownerReferences and Finalizers Control Deletion​

Two more mechanics complete the picture, and both are the answer to a real on-call question.

When the operator creates the child Deployment and Service, it stamps each one with an ownerReference pointing back at the Website. This is parentage on record. The garbage collector (a controller built into the API server) honours it: delete the parent Website, and its owned children are reaped automatically, even if the operator itself is offline. This is the same machinery behind "I deleted the Deployment and its ReplicaSet and Pods disappeared too."

A finalizer is the mirror image, and it explains the stuck-deletion ticket. A finalizer is a no-dues certificate: the API server will not remove an object while a finalizer is on it. When you delete a Website, the API server does not erase it. It sets a deletionTimestamp and leaves the object in Terminating, waiting. The operator sees that timestamp, does its cleanup, and only then removes the finalizer, at which point the deletion it was holding finally completes. The catch you will feel in the lab: if the operator is down, crashed, or was uninstalled before its objects, that finalizer is never removed, and the object hangs in Terminating forever. Nine stuck deletions out of ten are exactly this: a finalizer whose controller cannot sign off.

The two questions this module answers on call

"My resource is stuck deleting." → A finalizer is holding it; the controller that should remove the finalizer is not running. "The operator isn't doing anything for my object." → Either the operator is down (drift), or the object was rejected at admission and never stored. Both become obvious once you can see the CRD, the operator, and the finalizer as three separate things.

When a CRD or Operator Is the Wrong Choice​

Extending Kubernetes is powerful, so it is worth saying where the line is. A CRD plus an operator is the right tool when you have a resource with a lifecycle that needs continuous reconciliation: something to keep converging, clean up, and report status on. It is the wrong tool when a Helm chart or a plain Deployment would do, when the thing has no ongoing behaviour to reconcile, or when you would be reinventing a controller that already exists. And a CRD is not the only way to extend the API: an aggregated API server lets you serve a custom API with its own storage and logic when a CRD's etcd-backed, schema-validated model is not enough. For most cases, though, a CRD served by the API server from etcd is exactly right. And it is what nearly every operator you will run is built on.

Use this decision before you create a new API:

NeedStart withMove to an operator only when
Install a fixed set of Kubernetes resourcesHelm, Kustomize, or GitOpsThe system must keep making domain decisions after installation.
Run a bounded taskJob, CronJob, or workflow engineThe task owns a long-lived resource lifecycle and must continuously repair drift.
Expose application dataAn application API and databaseUsers need Kubernetes-style desired state, RBAC, watch, and reconciliation for that data.
Add a Kubernetes APICRDYou need custom storage or request behaviour that the CRD model cannot provide; then consider an aggregated API server.

Production Requirements for Kubernetes Operators​

Writing a reconcile loop is the easy part. Operating it safely requires a contract around that loop.

ContractProduction recommendationFailure when it is missing
API schema and versionsUse structural schemas, defaults, CEL where possible, and a tested conversion plan before serving another version.Fields disappear, invalid states reach the controller, or an upgrade strands old objects.
ReconciliationMake every action idempotent. Bound retries, use backoff, and expect informer-cache staleness.One bad object creates a hot loop and API pressure.
StatusPublish conditions, observedGeneration, and useful reasons. Update status only when it changed.Users cannot tell whether the controller saw the latest spec, and status writes create noise.
OwnershipSet controller owner references only for objects whose lifecycle truly belongs to the parent.Garbage collection deletes shared infrastructure or leaves abandoned children.
FinalizationAdd the finalizer only when cleanup is required. Make cleanup retryable, observable, and time-bounded. Document the emergency removal procedure.Objects remain in Terminating after the controller is broken or removed.
OperationsExpose reconcile rate, errors, duration, queue depth, retries, and leader state. Alert on sustained backlog, not one retry.The first visible signal is user-reported drift.

Before installing a third-party operator, ask the same questions you would ask of your own: Who owns upgrades? Which fields and children can it change? What happens if it is unavailable? Can its CRDs be removed safely? Where are conversion webhooks and finalizers documented? An operator becomes part of your control plane even when it runs in an application namespace.

Lab: Build and Troubleshoot a Kubernetes Operator​

In the lab you build the whole arc yourself. You install the Website CRD and prove it does nothing on its own. You watch the API server reject three bad specs at admission. You deploy a real in-cluster operator and watch it turn a Website into a running Deployment and Service, write its status, and self-heal drift. Then you break things on purpose: take the operator down and delete a Website to reproduce a stuck Terminating, and isolate garbage collection by ownerReference so you can see it work with the operator switched off. A new lens on the Cluster X-Ray, Extensions, shows you all of it live: your CRDs, your custom resources with their conditions, and the ownership and finalizers that decide what gets cleaned up and what gets stuck.
