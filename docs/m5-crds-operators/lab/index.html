Extending Kubernetes with CRDs and Operators

Before you start

New here? Complete the Setup section first.

All commands below run from the root of the lab repo (304-labs/). This lab continues on the core-internals cluster used in the earlier modules.

In this lab, you are going to create a new Kubernetes resource called Website.

You would first install its Custom Resource Definition (CRD), and then deploy an operator which manages the resource.

By the end of this lab, you will:

  • create and inspect a CRD
  • test schema and CEL validation
  • observe an operator reconcile desired and actual state
  • troubleshoot finalizers and owner references

Pre Requisites​

Check the current Kubernetes context.

kubectl config current-context

[ Expected output ]

kind-kubeadv-core

If the cluster is not running, create it as,

bash labs/clusters/core-internals/create.sh

PART I - Define a Custom Resource​

Verify the Cluster​

To begin with, verify the cluster profile.

bash labs/clusters/core-internals/verify.sh

[ Expected output ]

OK: core-internals profile verified — 2/2 nodes Ready, API server healthy.
audit mode: ENABLED — stream with: kubectl logs -n kube-system kube-apiserver-kubeadv-core-control-plane
etcd quota: 256MB — metrics on :2381 (M3 profile knobs present)
NAME                         STATUS   ROLES           AGE   VERSION
kubeadv-core-control-plane   Ready    control-plane   13h   v1.35.0
kubeadv-core-worker          Ready    <none>          13h   v1.35.0
If verify says the cluster is missing

If kind get clusters does not list kubeadv-core, create it as,

bash labs/clusters/core-internals/create.sh

Install the Website CRD​

Lets now install the CRD for the Website resource.

kubectl apply -f labs/m5/website-crd.yaml
kubectl wait --for condition=established --timeout=30s crd/websites.kubeadv.io

[ Expected output ]

customresourcedefinition.apiextensions.k8s.io/websites.kubeadv.io created
customresourcedefinition.apiextensions.k8s.io/websites.kubeadv.io condition met
Established is not instant

The API extensions controller needs a moment to register the new resource. Wait for the Established condition before creating a Website.

Otherwise, the API server may return no matches for kind Website.

Examine the new resource and its schema.

kubectl api-resources --api-group=kubeadv.io
kubectl explain website.spec

[ Expected output ]

NAME       SHORTNAMES   APIVERSION            NAMESPACED   KIND
websites   wsite        kubeadv.io/v1alpha1   true         Website
GROUP:      kubeadv.io
KIND:       Website
VERSION:    v1alpha1

FIELD: spec <Object>

FIELDS:
  host	<string> -required-
  image	<string>
  replicas	<integer>

Create a Website Resource​

Create a namespace and a Website resource.

kubectl create namespace m5-lab --dry-run=client -o yaml | kubectl apply -f -
cat <<'EOF' | kubectl apply -f -
apiVersion: kubeadv.io/v1alpha1
kind: Website
metadata: { name: hello, namespace: m5-lab }
spec: { host: hello.kubeadv.io, replicas: 2 }
EOF

[ Expected output ]

namespace/m5-lab created
website.kubeadv.io/hello created

Examine the resource. The API server should also add the default image defined in the CRD.

kubectl -n m5-lab get websites
kubectl -n m5-lab get website hello -o jsonpath='stored image = {.spec.image}{"\n"}'

[ Expected output ]

NAME    HOST               REPLICAS   READY   AGE
hello   hello.kubeadv.io   2                  2s
stored image = nginx:1.27-alpine

Check if the Website resource created a Deployment or Service.

kubectl -n m5-lab get deploy,svc

[ Expected output ]

No resources found in m5-lab namespace.

No workload was created. A CRD adds a resource to the Kubernetes API, but it does not implement its behaviour. For that, you need a controller.

Validate the Website Spec​

The API server validates each Website against the schema in the CRD. Lets try three invalid specifications.

The CRD uses a CEL rule to limit replicas to five. Try creating a resource with nine replicas.

cat <<'EOF' | kubectl apply -f -
apiVersion: kubeadv.io/v1alpha1
kind: Website
metadata: { name: toobig, namespace: m5-lab }
spec: { host: big.kubeadv.io, replicas: 9 }
EOF

[ Expected output ]

The Website "toobig" is invalid: spec: Invalid value: replicas may not exceed 5 (guardrail enforced at admission)

The CEL validation runs in the API server. It does not require a webhook or another Pod.

Next, omit the required host field.

printf 'apiVersion: kubeadv.io/v1alpha1\nkind: Website\nmetadata: {name: nohost, namespace: m5-lab}\nspec: {replicas: 2}\n' | kubectl apply -f -

[ Expected output ]

The Website "nohost" is invalid: 
* spec.host: Required value
* <nil>: Invalid value: null: some validation rules were not checked because the object was invalid; correct the existing errors to complete validation

Observe the first error: spec.host: Required value. The API server skipped the CEL rule because the object had already failed schema validation.

Finally, add a field which is not defined in the schema.

cat <<'EOF' | kubectl apply -f -
apiVersion: kubeadv.io/v1alpha1
kind: Website
metadata: { name: bad, namespace: m5-lab }
spec: { host: b.io, replicas: 1, tls: true }
EOF

[ Expected output ]

Error from server (BadRequest): error when creating "STDIN": Website in version "v1alpha1" cannot be handled as a Website: strict decoding error: unknown field "spec.tls"

The API server rejects the unknown tls field. This prevents a misspelled or unsupported field from being stored silently.

PART II - Deploy the Operator​

Start the Website Operator​

Lets now deploy the operator. It watches Website resources and creates one Deployment and one Service for each of them.

kubectl apply -f labs/m5/operator.yaml
kubectl -n m5-system rollout status deploy/website-operator --timeout=240s

[ Expected output ]

namespace/m5-system created
serviceaccount/website-operator created
clusterrole.rbac.authorization.k8s.io/website-operator created
clusterrolebinding.rbac.authorization.k8s.io/website-operator created
configmap/website-operator-src created
deployment.apps/website-operator created
deployment "website-operator" successfully rolled out
First rollout pulls a ~200 MB image

The operator uses the alpine/k8s image. The first image pull may take a couple of minutes.

Check the operator logs.

kubectl -n m5-system logs deploy/website-operator --tail=6

[ Expected output ]

05:11:43 website-operator starting: level-triggered reconcile every 5s
05:11:43 reconcile m5-lab/hello: add finalizer
05:11:44 reconcile m5-lab/hello: host=hello.kubeadv.io replicas=2 ready=0 condition=False

The operator has found the hello resource and added a finalizer. Examine the resources it created.

kubectl -n m5-lab get deploy,svc -l app.kubernetes.io/managed-by=website-operator
kubectl -n m5-lab get websites

[ Expected output ]

NAME                        READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/web-hello   2/2     2            2           44s

NAME                TYPE        CLUSTER-IP    EXTERNAL-IP   PORT(S)   AGE
service/web-hello   ClusterIP   10.96.81.36   <none>        80/TCP    44s

NAME    HOST               REPLICAS   READY   AGE
hello   hello.kubeadv.io   2          2       66s

The operator created the Deployment and Service. It also updated the status of the Website resource. Examine the Ready condition.

kubectl -n m5-lab get website hello -o jsonpath='{.status.conditions[?(@.type=="Ready")].status} — {.status.conditions[?(@.type=="Ready")].message}{"\n"}'

[ Expected output ]

True — 2/2 replicas ready

Open the Extensions View​

Start Cluster X-Ray.

bash labs/tools/xray/serve.sh

Open http://127.0.0.1:8001/xray/ and select the Extensions tab.

  • CRDs shows the group, scope, versions and Established condition.
  • Custom resources shows the Website specification and status.
  • Ownership & finalizers shows the child resources, owner references and finalizers.

Keep this view open for the next part of the lab.

PART III - Observe the Reconcile Loop​

Test Self-Healing and Drift​

Lets now examine how the operator handles changes to the actual state.

Delete the Deployment created by the operator.

kubectl -n m5-lab delete deploy web-hello
sleep 6
kubectl -n m5-lab get deploy web-hello

[ Expected output ]

deployment.apps "web-hello" deleted from m5-lab namespace
NAME        READY   UP-TO-DATE   AVAILABLE   AGE
web-hello   2/2     2            2           7s

Observe the age of the Deployment. The operator noticed that the child was missing and created it again.

Scale the operator to zero and wait for its Pod to stop. Then delete the Deployment again.

kubectl -n m5-system scale deploy/website-operator --replicas=0
kubectl -n m5-system wait --for=delete pod -l app=website-operator --timeout=60s
kubectl -n m5-lab delete deploy web-hello
sleep 6
kubectl -n m5-lab get deploy web-hello

[ Expected output ]

deployment.apps/website-operator scaled
pod/website-operator-6dbd77d9fd-g87pv condition met
deployment.apps "web-hello" deleted from m5-lab namespace
Error from server (NotFound): deployments.apps "web-hello" not found
Wait for the operator pod to actually terminate

Scaling the Deployment to zero does not stop the operator immediately. Wait for the operator Pod to be deleted before changing its managed resources.

With the operator stopped, the Deployment remains missing. Start the operator again and observe what happens.

kubectl -n m5-system scale deploy/website-operator --replicas=1
kubectl -n m5-system rollout status deploy/website-operator --timeout=90s
sleep 6
kubectl -n m5-lab get deploy web-hello

[ Expected output ]

deployment.apps/website-operator scaled
deployment "website-operator" successfully rolled out
NAME        READY   UP-TO-DATE   AVAILABLE   AGE
web-hello   2/2     2            2           9s

Examine Finalizers​

A finalizer prevents the API server from removing an object until its controller completes the required cleanup.

Stop the operator and delete the Website resource.

kubectl -n m5-system scale deploy/website-operator --replicas=0
kubectl -n m5-system wait --for=delete pod -l app=website-operator --timeout=60s
kubectl -n m5-lab delete website hello --wait=false
sleep 2
kubectl -n m5-lab get website hello -o jsonpath='deletionTimestamp={.metadata.deletionTimestamp}  finalizers={.metadata.finalizers}{"\n"}'

[ Expected output ]

website.kubeadv.io "hello" deleted from m5-lab namespace
deletionTimestamp=2026-07-19T05:13:58Z  finalizers=["kubeadv.io/cleanup"]

The delete request was accepted, but the object is still present. It has a deletionTimestamp and the kubeadv.io/cleanup finalizer.

Since the operator is stopped, no controller can complete the cleanup and remove the finalizer.

Start the operator and check the Website and its Deployment again.

kubectl -n m5-system scale deploy/website-operator --replicas=1
kubectl -n m5-system rollout status deploy/website-operator --timeout=90s
sleep 8
kubectl -n m5-lab get website hello
kubectl -n m5-lab get deploy web-hello

[ Expected output ]

Error from server (NotFound): websites.kubeadv.io "hello" not found
Error from server (NotFound): deployments.apps "web-hello" not found

The operator found the deletionTimestamp, removed the child resources and cleared the finalizer. The API server could then remove the Website.

Examine ownerReferences and Garbage Collection​

The operator also adds an ownerReference to each child resource. Kubernetes uses it to remove dependent resources when their owner is deleted.

Create another Website and compare the UID of the parent with the owner reference stored on its Deployment.

cat <<'EOF' | kubectl apply -f -
apiVersion: kubeadv.io/v1alpha1
kind: Website
metadata: { name: blog, namespace: m5-lab }
spec: { host: blog.kubeadv.io, replicas: 1 }
EOF
sleep 8
kubectl -n m5-lab get deploy web-blog -o jsonpath='child ownerRef uid = {.metadata.ownerReferences[0].uid}{"\n"}'
kubectl -n m5-lab get website blog -o jsonpath='parent website uid = {.metadata.uid}{"\n"}'

[ Expected output ]

child ownerRef uid = 81d938a4-c760-4b84-8cc4-3163b419af65
parent website uid = 81d938a4-c760-4b84-8cc4-3163b419af65

Both UIDs should be the same. Now stop the operator, remove the finalizer and delete the parent resource.

kubectl -n m5-system scale deploy/website-operator --replicas=0
kubectl -n m5-system wait --for=delete pod -l app=website-operator --timeout=60s
kubectl -n m5-lab patch website blog --type=merge -p '{"metadata":{"finalizers":[]}}'
kubectl -n m5-lab delete website blog
sleep 8
kubectl -n m5-lab get deploy,svc -l kubeadv.io/website=blog

[ Expected output ]

deployment.apps/website-operator scaled
pod/website-operator-... condition met
website.kubeadv.io/blog patched
website.kubeadv.io "blog" deleted from m5-lab namespace
No resources found in m5-lab namespace.

The operator was not running, but Kubernetes still removed the owned Deployment and Service. This cleanup was handled by the garbage collector using the ownerReference.

Start the operator again.

kubectl -n m5-system scale deploy/website-operator --replicas=1
kubectl -n m5-system rollout status deploy/website-operator --timeout=90s

[ Expected output ]

deployment.apps/website-operator scaled
deployment "website-operator" successfully rolled out

Validate​

Recreate the hello resource and validate the CRD, status, owner reference and finalizer.

cat <<'EOF' | kubectl apply -f -
apiVersion: kubeadv.io/v1alpha1
kind: Website
metadata: { name: hello, namespace: m5-lab }
spec: { host: hello.kubeadv.io, replicas: 2 }
EOF
sleep 12
kubectl get crd websites.kubeadv.io -o jsonpath='CRD established: {.status.conditions[?(@.type=="Established")].status}{"\n"}'
kubectl -n m5-lab get website hello -o jsonpath='Website Ready: {.status.conditions[?(@.type=="Ready")].status}{"\n"}'
kubectl -n m5-lab get deploy web-hello -o jsonpath='child owned by: {.metadata.ownerReferences[?(@.controller==true)].kind}{"\n"}'
kubectl -n m5-lab get website hello -o jsonpath='finalizer: {.metadata.finalizers[0]}{"\n"}'

[ Expected output ]

website.kubeadv.io/hello created
CRD established: True
Website Ready: True
child owned by: Website
finalizer: kubeadv.io/cleanup

Make sure that the CRD is Established, the Website is Ready, the child is owned by the Website, and the finalizer is present.

Troubleshooting
  • no matches for kind "Website" — wait for the CRD to become Established and try again.
  • The operator Pod is ImagePullBackOff — check the image-pull events with kubectl -n m5-system describe pod -l app=website-operator.
  • The operator still restores the Deployment after scaling to zero — wait for the operator Pod to be deleted before removing the child.
  • A Website is stuck in Terminating — start the operator so that it can complete the cleanup. Remove the finalizer manually only when the controller is no longer available and you understand which cleanup will be skipped.
  • The READY column is blank — check the operator Deployment, RBAC and logs.

Cleanup​

Remove the resources created in this lab.

bash labs/m5/setup.sh teardown

[ Expected output ]

== M5 teardown ==
namespace "m5-system" deleted
serviceaccount "website-operator" deleted from m5-system namespace
clusterrole.rbac.authorization.k8s.io "website-operator" deleted
clusterrolebinding.rbac.authorization.k8s.io "website-operator" deleted
configmap "website-operator-src" deleted from m5-system namespace
deployment.apps "website-operator" deleted from m5-system namespace
customresourcedefinition.apiextensions.k8s.io "websites.kubeadv.io" deleted
namespace "m5-lab" deleted
== done (persistent cluster kept) ==
Why teardown drains the finalizers first

The teardown script deletes the Website resources and clears their finalizers before removing the operator.

Removing the operator first could leave its resources in Terminating state.

Confirm that the custom API resource is gone and that the cluster is still running.

kubectl api-resources --api-group=kubeadv.io
kubectl get nodes

[ Expected output ]

NAME                         STATUS   ROLES           AGE   VERSION
kubeadv-core-control-plane   Ready    control-plane   13h   v1.35.0
kubeadv-core-worker          Ready    <none>          13h   v1.35.0

The kubeadv.io API group should not list any resources. Keep the core-internals cluster running for the next module.

Summary​

In this lab, you extended the Kubernetes API with a Website CRD and tested its schema validation.

You then deployed an operator and observed how it writes status, restores a deleted child and corrects drift.

You also examined why a resource could remain in Terminating, and how owner references allow Kubernetes to remove child objects.
