The Reconciliation Engine — Kubernetes Internals

You already run Kubernetes in production. You know how to create a Deployment and troubleshoot a Pod. This module goes below those commands. It shows you how Kubernetes keeps the cluster close to the state you asked for, even after Pod failures, controller restarts, node failures, and changes from other automation. Every advanced topic later in this course, including API pressure, etcd failures, operators, scheduling, and AI workload admission, depends on this one idea: reconciliation.

The four questions an operator should ask

When something is not converging, do not start with a random restart. Ask four questions in this order:

  1. What is the desired state right now?
  2. Who last changed that desired state?
  3. Has the responsible controller processed that revision?
  4. Which handoff in the control loop has not completed?

This module gives you the Kubernetes evidence for answering each question.

Desired and Observed State Drive Reconciliation​

Think of the AC in your room. You don't tell it how to cool the room. You tell it what you want: 22°C. The AC continuously measures the actual temperature, compares it to your setting, and switches the compressor on or off to close the gap. You declare intent once; the device negotiates with reality forever.

Kubernetes is a building full of ACs. Most API objects carry two halves:

  • spec is the desired state. A human, GitOps controller, HPA, or operator may write it. Do not assume that every field belongs to you.
  • status is the observed state. The responsible controller or kubelet writes it. Your deployment manifest should not declare it.

Between the two sits a controller: a loop that reads desired state, measures observed state, and takes the smallest action that moves reality toward intent. The Deployment controller, the ReplicaSet controller, the node lifecycle controller, the scheduler: each is a narrow specialist running the same loop, observe, diff, act. No controller "executes your YAML". Your YAML is a target, and the cluster is perpetually falling toward it.

This is why deleting a Pod owned by a ReplicaSet does not permanently reduce the replica count. Observed state (2 Pods) no longer matches desired state (3), so the ReplicaSet controller creates one. You will do exactly this in the lab and watch the gap close in real time.

Production recommendation: separate intent from evidence

During an incident, first decide which side is wrong:

What you seeRead firstWhat it usually means
The value in spec is wrong or keeps revertingmetadata.managedFields and your GitOps historyTwo actors disagree about desired state, or a manual change has drifted from Git
spec is correct, but status.observedGeneration is behindController health, leader election, work queue, and API accessThe responsible controller has not processed the latest revision
observedGeneration has caught up, but the workload is unhealthyConditions, events, ReplicaSet, scheduler, kubelet, storage, and networkingReconciliation reached a downstream dependency and stopped there

Do not fix an observed-state problem by repeatedly editing spec. Do not fix a desired-state ownership problem by restarting Pods. Those actions change different sides of the contract.

Level-Triggered Controllers Recheck Current State​

Here's the design decision that makes Kubernetes trustworthy: the difference between an AC and a missed call.

A missed call is edge-triggered: it happens at one moment of change. If you were away when the phone rang, that moment is gone. You can see it rang, but you can't get it back. An edge-triggered system is only correct if it catches every event, in order, with no gaps. An AC is level-triggered: it acts on the current measured level, not on the event that changed it. Let it switch off through a warm afternoon, and the moment it wakes, it reads 28°C and starts cooling. Missed events cost nothing, because the current state contains all the truth needed.

Kubernetes controllers are ACs, not missed calls. Yes, they use watches to learn about changes quickly, and that's an optimization for latency. But correctness never depends on the watch. When a controller reconciles, it compares the full current state of the world against desired state. A controller can crash, restart, miss ten thousand events during a network partition, and on its next loop it converges anyway, because it re-reads the level rather than replaying the edges.

Production recommendation: restart only after you know why

Built-in Kubernetes controllers are designed to recover after a missed watch event or process restart. A restart can therefore be a valid recovery when a controller process is unhealthy or its local cache is stuck.

It is not the first diagnostic step. A restart will not correct a bad spec, a field-ownership fight, failed admission, missing RBAC, exhausted quota, an unavailable dependency, or a broken custom controller. In some cases it only makes the same failure happen again.

Before restarting a control-plane component, capture its Lease, logs, generation, observedGeneration, conditions, and recent events. Then restart one component at a time and verify that reconciliation resumes. If you build operators, make every reconcile function idempotent, which means running it again produces the same correct result without duplicate side effects.

kubectl apply Starts the Convergence Path​

Imagine an Udupi restaurant, a South Indian cafe known for quick dishes such as dosa and idli. You first buy a token at the cash counter. You hand that token to the relevant food counter, where it is added to a visible token rail or queue. If you ordered a dosa, the dosa counter picks up the dosa token and prepares it. When it is ready, the serving counter sees the completed order and hands it over. You do not need to chase each counter. Each one reacts to the shared queue and records its own result for the next one.

That is the useful flow behind kubectl apply. Your request puts a durable record into the shared Kubernetes workspace through the API server. Controllers are the specialist counters. They watch the state relevant to their job, make one bounded change, and write the result back so the next specialist can react. etcd is the durable ledger behind that workspace.

Follow one kubectl apply -f deployment.yaml all the way down:

  1. Client → API server. kubectl sends the manifest. The API server authenticates, authorizes, and runs admission, then persists the Deployment object to etcd. That write is the entire success of your command. Nothing has been deployed when your prompt returns; the token is on the rail.
  2. Deployment controller. Watching Deployments, it sees a new one, and creates a ReplicaSet, another API object. It does not create Pods.
  3. ReplicaSet controller. Watching ReplicaSets, it counts desired replicas vs existing Pods and creates Pod objects to close the gap. These Pods have no node yet.
  4. Scheduler. Watching for unbound Pods, it filters and scores nodes, then writes a binding, again just an API update.
  5. kubelet. On the chosen node, watching for Pods bound to it, it pulls images, starts containers (the first moment anything happens outside the control plane) and reports observed state back into status.

Notice what's absent: no orchestrating brain calls each step in sequence. Each specialist watches the API server, acts on its narrow slice, and writes results back for the next specialist to observe. Like the Udupi counters, the chain works because each counter responds to the current token state, not because somebody coordinates every handoff. The "workflow" is an emergent chain of independent reconciliation loops, which is exactly why any link can die and recover without coordination.

Boundary discipline

Every arrow in that diagram goes through the API server. Controllers never talk to each other, never talk to etcd directly, never talk to kubelets. One entry point, one audit point, one consistency model. Keep this in mind: Module 2 is about what happens when that single entry point comes under pressure.

Production recommendation: find the first incomplete handoff

kubectl apply returning success only proves that the API server accepted and stored the object. It does not prove that a Pod is running or serving traffic. When a rollout stalls, follow the object chain and stop at the first missing transition:

HandoffEvidence to inspectTypical failure area
Deployment stored, but no new ReplicaSetDeployment observedGeneration, conditions, Deployment eventsDeployment controller, invalid rollout state, or API write failure
ReplicaSet exists, but expected Pods do notReplicaSet desired/current counts and eventsQuota, admission, policy, or ReplicaSet controller
Pod exists, but has no nodePodScheduled condition and scheduling eventsResources, affinity, taints, topology, or scheduler
Pod has a node, but is not ReadyPod conditions, kubelet events, container statusImage pull, volume, CNI, runtime, startup, or readiness probe

This sequence works in small startup clusters and in large multi-team platforms. Avoid restarting every component together. That removes evidence and makes it harder to see which handoff was broken.

Status Conditions Report Reconciliation Progress​

When you send a revised purchase order to a supplier, two questions matter: have they seen revision 4, or are they still working from revision 3? and what's the current state of the order? Serious suppliers answer with paperwork: an acknowledgment referencing your revision number, and a status report against it.

Kubernetes objects carry exactly this paperwork, and reading it precisely is what separates guessing from diagnosis:

  • metadata.generation: the revision number of your intent. Incremented every time the spec changes.
  • status.observedGeneration: the latest generation the controller has processed. If observedGeneration < generation, everything else in status is a report about your old spec. Ready replicas, conditions: all of it describes yesterday's order. Automation that ignores this comparison routinely reports stale success.
  • status.conditions: structured claims like Available=True or Progressing=True, each with a reason and timestamp. Conditions are the supplier's status report: not a log of events, but the current assessment of named aspects of the object.

This trio forms a contract you can build on. A rollout is genuinely complete when observedGeneration == generation and the conditions you care about are True for that generation. Well-designed controllers expose this contract, including the operators you'll debug in Module 5 and the Kueue admission machinery in Module 8. If a custom controller does not report its observed generation and useful conditions, treat that as an operability gap.

Production recommendation: make automation generation-aware

Use this order in deployment automation and incident triage:

SignalDecision
observedGeneration < generationDo not trust the rest of status yet. The controller is still processing an older revision.
Generations match, but Progressing=False or a failure reason is presentRead the condition reason and message, then inspect the named downstream object or event.
Generations match and conditions are healthyThe controller has accepted the current intent. Continue with application-level checks such as endpoint readiness and a smoke test.
A custom resource has no useful conditions or does not report observed generationTreat this as a controller design gap. Ask for a status contract before using that operator for critical production automation.

Do not build a production gate from the human-readable kubectl get columns alone. They are useful for a quick view, but automation should read structured status fields and apply a timeout.
