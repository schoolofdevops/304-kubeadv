Deep Dive - Under the Hood of Reconciliation

This deep dive examines three parts of reconciliation: field ownership, garbage collection, and controller health. Use these checks when two managers update the same field, a deletion does not complete, or a controller stops processing a new generation.

PART I - Server-Side Apply and managedFields: who owns your spec?​

Think of buying a plot of land in India. The sale deed names the parties and the exact land being transferred. The Sub-Registrar's office records that deed. Before purchase, you would also ask for an Encumbrance Certificate (EC) to see whether the property has registered mortgages or other claims. The records make the existing claim visible before you proceed.

Server-Side Apply uses the same practical idea, but at field level. Each part of an object's spec has a registered field manager, recorded in metadata.managedFields. The API server plays the role of the registration office. If two managers try to control the same field with different values, it rejects the new claim until one manager deliberately takes ownership. This is an analogy, not a statement about land law: an EC reveals claims on a property, while managedFields records who last declared each Kubernetes field.

Apply the gateway again: this time letting the server, not the client, compute the merge:

kubectl apply --server-side -f labs/m1/nimbusai-gateway.yaml

[ Expected output ]

namespace/nimbusai serverside-applied
deployment.apps/nimbusai-gateway serverside-applied

Now read the registry. managedFields is hidden by default, but it's the first thing to open when a field keeps "mysteriously" reverting: the registry tells you exactly which manager keeps writing it:

Two things to find in that output: an entry with operation: Apply and manager kubectl owning the fields your manifest declares, and an entry with operation: Update for kube-controller-manager owning status. These are not two different Deployment statuses. They describe how each manager wrote its fields. Summarize the registry:

kubectl get deploy nimbusai-gateway -n nimbusai -o jsonpath='{range .metadata.managedFields[*]}{.manager}{"  "}{.operation}{"  subresource="}{.subresource}{"\n"}{end}'

[ Expected output ]

kubectl  Apply  subresource=
kube-controller-manager  Update  subresource=status

Read the three columns separately​

managedFields answers three different questions:

FieldQuestion it answersGateway example
managerWho made this write?kubectl, kube-controller-manager, an HPA, Argo CD, or an operator
operationHow did that manager write?Apply for Server-Side Apply; Update for a non-SSA write
subresourceWhich API endpoint did it write through?status for observed state, scale for a scale write, or empty for the main object

The API only permits two operation values: Apply and Update. Apply means the field was last changed through a Server-Side Apply request. Update means it was last changed through a normal, non-SSA write. It does not mean "this is a status update" and it does not mean somebody ran a command named kubectl update.

The Deployment controller happens to use Update against the status subresource because its job is to report what it sees: readyReplicas, availableReplicas, conditions, and observedGeneration. Your server-side apply uses Apply against the main resource because your job is to declare desired fields under spec. The writers are separate, the fields are separate, and this is the healthy expected case.

Client-side apply, Server-Side Apply, and direct writes​

There are two forms of kubectl apply, and they are easy to confuse:

ActionWhere the merge is calculatedWhat Kubernetes records
kubectl apply -fClient, using the last-applied annotationkubectl-client-side-apply, Update
kubectl apply --server-side -f manifest.yamlAPI server, using field ownership in managedFieldsoperation: Apply for the fields that manager declares
edit, patch, scale, controller writeClient performs a direct changeUpdate for changed fields

You can see the client-side path without changing the gateway. Plain kubectl apply creates the legacy last-applied annotation and records its field manager as Update:

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: m1-client-side-apply
  namespace: nimbusai
data:
  mode: calculated-by-client
EOF
kubectl -n nimbusai get configmap m1-client-side-apply -o jsonpath='{range .metadata.managedFields[*]}{.manager}{"  "}{.operation}{"\n"}{end}'

[ Expected output ]

configmap/m1-client-side-apply created
kubectl-client-side-apply  Update

Server-Side Apply does not lock a field. A normal update can change an SSA-managed field and does not fail just because another manager owns it. When it changes the value, field ownership moves to the manager that performed the update. The important consequence arrives on the next SSA attempt: if the original SSA manager tries to change that field again, the API server reports a conflict instead of silently overwriting the other manager.

This is why an HPA, a GitOps controller, and a human can all write a Deployment spec, and why you must assign each field a single intentional owner. SSA-capable clients such as kubectl, Flux, Argo CD, and custom controllers can create Apply entries. Any direct API client can create Update entries. kubectl edit is one such direct update, with kubectl-edit as its default field manager.

Production rule: separate declared intent from live intervention​

The point is not that every write must be SSA. A production operator needs direct writes: scaling during a traffic event, patching a safe mitigation, or testing a hypothesis. The point is that a temporary intervention should not become an unexplained second source of truth.

Field or responsibilityGood long-term ownerWhy
Image, Pod template, labels, resourcesGitOps with SSAReviewed intent with conflict detection
spec.replicas with no autoscalerThe team’s declared deployment configurationOne durable desired count is easy to explain and restore.
spec.replicas with an HPAHPARemove spec.replicas from the GitOps manifest. Otherwise Git and the HPA continually express competing desired counts.
status.*The Kubernetes controllerIt is observed state, not configuration for a human or GitOps tool to declare.
An emergency scale, edit, or patchThe operator temporarilyRecord the decision and reconcile or revert it in the durable configuration after the incident.
Why prefer SSA for new multi-manager workflows?

Client-side apply is not wrong or deprecated. It remains a workable model for established, simple workflows. Prefer Server-Side Apply where your GitOps tool supports it when several declarative actors collaborate: the API server calculates the merge, records field-level intent, and rejects a conflicting declarative change before it silently overwrites another manager. Direct updates still work; SSA makes the resulting ownership boundary visible when the next declarative change arrives.

Production anti-patterns
  • Do not make --force-conflicts the default in a pipeline. It can take fields away from another legitimate manager without a human decision.
  • Do not let GitOps and an HPA manage spec.replicas at the same time. Remove that field from the Git manifest when the HPA is the owner.
  • Do not use kubectl edit as a permanent configuration system. It is useful during an incident, but the final decision must return to Git or another declared source of truth.
  • Do not read manager: kubectl and assume a human owns the field forever. Read manager, operation, subresource, and the actual field path together.

Prove a normal update can take an SSA-managed field​

kubectl edit needs an interactive editor, so this exercise uses a merge patch with an explicit field-manager name. The result is the same category of write as an edit: a non-SSA update. This disposable ConfigMap keeps the experiment away from the NimbusAI Deployment.

Create one field with Server-Side Apply:

kubectl apply --server-side --field-manager=m1-ssa-lab -f - <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: m1-ssa-write-paths
  namespace: nimbusai
data:
  mode: declared-by-ssa
EOF

[ Expected output ]

configmap/m1-ssa-write-paths serverside-applied

Now make a normal merge-patch write to the same field, then inspect the managers:

kubectl -n nimbusai patch configmap m1-ssa-write-paths --type merge --field-manager=m1-direct-update -p '{"data":{"mode":"changed-by-update"}}'
kubectl -n nimbusai get configmap m1-ssa-write-paths -o jsonpath='{range .metadata.managedFields[*]}{.manager}{"  "}{.operation}{"  subresource="}{.subresource}{"\n"}{end}'

[ Expected output ]

configmap/m1-ssa-write-paths patched
m1-direct-update  Update  subresource=

The original m1-ssa-lab row no longer owns data.mode, because the update changed that field's value. This is the point many teams miss: direct writes are allowed, and they can take field ownership. Now ask the original SSA manager to change the same field again:

set +e
kubectl apply --server-side --field-manager=m1-ssa-lab -f - <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: m1-ssa-write-paths
  namespace: nimbusai
data:
  mode: declared-by-ssa-again
EOF
echo "exit=$?"
set -e

[ Expected output ]

error: Apply failed with 1 conflict: conflict with "m1-direct-update" using v1: .data.mode
exit=1

The conflict is not a failure of the earlier patch. It is SSA protecting the next declarative write from undoing a collaborator's later value by accident. If this manager really should own data.mode, reclaim it explicitly:

kubectl apply --server-side --force-conflicts --field-manager=m1-ssa-lab -f - <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: m1-ssa-write-paths
  namespace: nimbusai
data:
  mode: declared-by-ssa
EOF
kubectl -n nimbusai get configmap m1-ssa-write-paths -o jsonpath='mode={.data.mode}{"\n"}{range .metadata.managedFields[*]}{.manager}{"  "}{.operation}{"\n"}{end}'

[ Expected output ]

configmap/m1-ssa-write-paths serverside-applied
mode=declared-by-ssa
m1-ssa-lab  Apply

That is the exact cycle behind the more realistic HPA versus GitOps conflict you will stage next.

Now stage a fight over one field. Scale imperatively: this writes spec.replicas through the scale subresource under a different manager:

kubectl scale deploy nimbusai-gateway -n nimbusai --replicas=3
kubectl get deploy nimbusai-gateway -n nimbusai -o jsonpath='{range .metadata.managedFields[?(@.subresource=="scale")]}{.manager}{"  "}{.operation}{"  subresource="}{.subresource}{"\n"}{end}'

[ Expected output ]

deployment.apps/nimbusai-gateway scaled
kubectl1.35.0  Update  subresource=scale

The manager name can reflect your kubectl version, but Update and subresource=scale are the evidence to read. This tells you exactly how replicas was changed: an ordinary write to the scale endpoint, not a second kind of Deployment status. If you ran kubectl edit instead, you would see an Update entry with a different manager and no scale subresource.

Re-apply your manifest, which still says replicas: 2. Two managers now claim the same field, and the API server refuses:

kubectl apply --server-side -f labs/m1/nimbusai-gateway.yaml

[ Expected output ]

namespace/nimbusai serverside-applied
error: Apply failed with 1 conflict: conflict with "kubectl1.35.0" with subresource "scale" using apps/v1: .spec.replicas
Please review the fields above--they currently have other managers. Here
are the ways you can resolve this warning:
* If you intend to manage all of these fields, please re-run the apply
  command with the `--force-conflicts` flag.
* If you do not intend to manage all of the fields, please edit your
  manifest to remove references to the fields that should keep their
  current managers.
* You may co-own fields by updating your manifest to match the existing
  value; in this case, you'll become the manager if the other manager(s)
  stop managing the field (remove it from their configuration).
See https://kubernetes.io/docs/reference/using-api/server-side-apply/#conflicts

That conflict error is the intended behavior. Client-side apply would have silently overwritten the other manager's value; SSA makes the collision explicit and forces a decision. In the land-record analogy, this is the point where you do not register a second incompatible claim without a valid transfer. Take the field back with a deliberate ownership transfer:

kubectl apply --server-side --force-conflicts -f labs/m1/nimbusai-gateway.yaml

[ Expected output ]

namespace/nimbusai serverside-applied
deployment.apps/nimbusai-gateway serverside-applied

Verify ownership of spec.replicas transferred back and the value reverted:

kubectl get deploy nimbusai-gateway -n nimbusai -o jsonpath='replicas={.spec.replicas}{"\n"}'

[ Expected output ]

replicas=2

This is why SSA matters beyond kubectl. Flux and Argo CD apply as named field managers, so "drift" has a precise definition: another manager took a field. An HPA writing spec.replicas and a GitOps engine applying replicas: 2 is the exact fight you just staged. The practical response is the same discipline as checking a sale deed and EC before changing a record: identify the legitimate owner, then remove the competing claim. For an HPA, that usually means dropping replicas from the Git manifest. Controllers built on SSA declare intent for the fields they own and let the API server merge it.

PART II - The ownership chain and garbage collection​

Imagine an application project being closed inside a large IT company. The project may have service accounts, temporary environments, build agents, and cloud resources attached to it. The company has three choices. It can mark the project closed and let the platform team clean the attached resources afterward. It can keep the project in a closing state until every attached resource is gone. Or it can remove the project link and deliberately leave those resources running for another team to take over.

Kubernetes makes the same lifecycle decision through deletion propagation. The lab showed Deployment → ReplicaSet → Pods as a relay of controllers. The lifecycle links are stored in metadata.ownerReferences, which are child-to-owner pointers read by the garbage collector. Labels help controllers find related objects, but owner references decide what gets deleted with an owner. Trace the chain upward:

POD=$(kubectl get pods -n nimbusai -l app.kubernetes.io/name=nimbusai-gateway -o jsonpath='{.items[0].metadata.name}')
kubectl get pod "$POD" -n nimbusai -o jsonpath='{.metadata.ownerReferences[0].kind}{"/"}{.metadata.ownerReferences[0].name}{"  controller="}{.metadata.ownerReferences[0].controller}{"  blockOwnerDeletion="}{.metadata.ownerReferences[0].blockOwnerDeletion}{"\n"}'

[ Expected output ]

ReplicaSet/nimbusai-gateway-58ddfccb84  controller=true  blockOwnerDeletion=true
RS=$(kubectl get rs -n nimbusai -l app.kubernetes.io/name=nimbusai-gateway -o jsonpath='{.items[0].metadata.name}')
kubectl get rs "$RS" -n nimbusai -o jsonpath='{.metadata.ownerReferences[0].kind}{"/"}{.metadata.ownerReferences[0].name}{"  rs-uid="}{.metadata.uid}{"\n"}'

[ Expected output ]

Deployment/nimbusai-gateway  rs-uid=8939cd7d-f41a-4a01-abd0-a5886fe8f219

Note that rs-uid: you'll need it in a moment. The full graph, including the collector that watches it:

Now delete the ReplicaSet but tell the collector to leave the children alone:

kubectl delete rs "$RS" -n nimbusai --cascade=orphan

[ Expected output ]

replicaset.apps "nimbusai-gateway-58ddfccb84" deleted from nimbusai namespace

Immediately inspect the pods and their owners:

kubectl get pods -n nimbusai -o jsonpath='{range .items[*]}{.metadata.name}{"  owners="}{.metadata.ownerReferences[*].name}{"\n"}{end}'

[ Expected output ]

nimbusai-gateway-58ddfccb84-w266m  owners=nimbusai-gateway-58ddfccb84
nimbusai-gateway-58ddfccb84-zxxxb  owners=nimbusai-gateway-58ddfccb84

The pods never restarted: but look at the ReplicaSet that now owns them:

kubectl get rs -n nimbusai -l app.kubernetes.io/name=nimbusai-gateway -o jsonpath='{.items[0].metadata.name}{"  rs-uid="}{.items[0].metadata.uid}{"\n"}'

[ Expected output ]

nimbusai-gateway-58ddfccb84  rs-uid=24509f90-bd13-4e19-9482-5523961f55df

Same name: the ReplicaSet name is derived from a deterministic hash of the pod template, so an identical template regenerates an identical name. Different UID: this is a brand-new object. Here's the sequence you just triggered, and it's level-triggering operating on the object graph rather than on replica counts: the Deployment controller observed "no ReplicaSet exists for my template" and created one; the new ReplicaSet controller observed "pods matching my selector exist with no controller owner" and adopted the orphans by writing itself into their ownerReferences. Nothing replayed the deletion event. Two controllers each compared current graph state against desired graph state and repaired their own edge.

The --cascade flag is client shorthand for the delete request's propagation policy, and there are exactly three:

  • Background (default): owner deleted immediately; the garbage collector deletes children afterward. Your kubectl delete deploy has always worked this way.
  • Foreground: the owner gets a foregroundDeletion finalizer and stays visible (with a deletionTimestamp) until every child with blockOwnerDeletion: true is gone; then the owner disappears. Use it when something downstream must not see the owner vanish before its children.
  • Orphan: ownerReferences are stripped from children, which survive. What you just did.

The three options are not equal defaults. Use the following decision path:

Which propagation policy should you choose?​

PolicyRecommended useWhat you must verifyAvoid it when
BackgroundRoutine controller-owned resourcesDependants may briefly outlive ownerFull tree must be gone first
ForegroundUninstall or replacementNo child can block foreverYou only want a fast delete
OrphanPlanned ownership transferEvery child has a new ownerSurvivors have no owner

For day-to-day workload deletion, keep the default: background. Use foreground when deletion completion must represent the whole object tree being gone. Treat orphan as a specialist tool. In this lab the Pods survive, but the new ReplicaSet quickly adopts them. That proves orphaning is not a reliable availability strategy. Use a Deployment rollout or a purpose-built migration plan for availability.

Do not remove finalizers by reflex

An object in Terminating is not automatically a garbage-collector problem. Read these fields first:

  1. metadata.deletionTimestamp confirms that deletion has been accepted.
  2. metadata.finalizers names the controller that still owes cleanup.
  3. metadata.ownerReferences shows whether foreground deletion is waiting on dependents.
  4. Events and controller logs show why cleanup has not completed.

Remove a finalizer manually only after you understand its purpose and complete the cleanup another way. Otherwise you may leave a cloud load balancer, volume, DNS record, or security rule outside Kubernetes with no controller left to remove it. Also remember that --force --grace-period=0 changes Pod termination behavior. It is not a general solution for ownership or finalizer problems.

In this Deployment example, deleting a Pod does not cascade upward to its ReplicaSet. Ownership points from the dependent to its owner, not the other way around. The replacement Pod you saw in the lab came from the ReplicaSet controller's replica calculation; it was not created by garbage collection.

Do not turn that example into a universal rule that Pods never own anything. A Pod can have dependents, such as a PVC created for a generic ephemeral volume. Before relying on a cascade assumption in production, inspect metadata.ownerReferences on the objects involved. Deletion-by-ownership and replacement-by-reconciliation are two different subsystems that happen to meet at the same objects.

PART III - Watching the machinery itself​

The controllers you've been reasoning about are processes or loops inside kube-controller-manager. In a highly available control plane, only the elected leader should run the active controller loops. A leader-election Lease records that leader and its renewals:

kubectl get lease -n kube-system kube-controller-manager -o yaml

[ Expected output ]

apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  creationTimestamp: "2026-07-15T07:04:15Z"
  name: kube-controller-manager
  namespace: kube-system
  resourceVersion: "762"
  uid: 895f341f-774d-425b-a806-40fb3e7e4d33
spec:
  acquireTime: "2026-07-15T07:04:15.103237Z"
  holderIdentity: kubeadv-core-control-plane_519fee92-48e8-438a-9a09-6245d034ba40
  leaseDurationSeconds: 15
  leaseTransitions: 0
  renewTime: "2026-07-15T07:06:09.628438Z"

holderIdentity names the current leader; renewTime is its heartbeat. Watch it tick:

for i in 1 2 3; do kubectl get lease -n kube-system kube-controller-manager -o jsonpath='{.spec.renewTime}{"\n"}'; sleep 3; done

[ Expected output ]

2026-07-15T07:06:09.628438Z
2026-07-15T07:06:11.638128Z
2026-07-15T07:06:15.650282Z

If that timestamp goes stale past leaseDurationSeconds, another healthy instance can acquire the lease and resume reconciliation from current API state. During a control-plane incident, this Lease, and the separate scheduler Lease, quickly tell you whether leader election is progressing.

What a healthy Lease does and does not prove

A moving renewTime proves that the leader-election client is renewing its lock through the API server. It does not prove that every controller loop is healthy, that its work queue is moving, or that downstream API writes are succeeding. If the Lease is fresh but observedGeneration remains stale, inspect the specific controller's logs, work-queue metrics, RBAC errors, admission failures, and API throttling.

Next, resourceVersion is the opaque version clients use with reads and watches. In this lab, a no-op leaves the Deployment's version unchanged, while a stored update changes it. Prove that behavior with a no-op:

kubectl get deploy nimbusai-gateway -n nimbusai -o jsonpath='{.metadata.resourceVersion}{"\n"}'
kubectl apply --server-side --force-conflicts -f labs/m1/nimbusai-gateway.yaml
kubectl get deploy nimbusai-gateway -n nimbusai -o jsonpath='{.metadata.resourceVersion}{"\n"}'

[ Expected output ]

731
namespace/nimbusai serverside-applied
deployment.apps/nimbusai-gateway serverside-applied
731

Identical apply, identical registry: the server elides the write entirely and resourceVersion holds still. Now make a real change and watch it move:

kubectl annotate deploy nimbusai-gateway -n nimbusai nimbusai.io/deep-dive=done --overwrite
kubectl get deploy nimbusai-gateway -n nimbusai -o jsonpath='{.metadata.resourceVersion}{"\n"}'

[ Expected output ]

deployment.apps/nimbusai-gateway annotated
779

Treat resourceVersion as an opaque value. Do not parse it as an integer, calculate a difference between two versions, or assume versions are contiguous or globally comparable. In an etcd-backed cluster you will often see large jumps between updates to one Deployment because many other writes happened in between, but clients must rely only on the API contract. A controller uses resource versions to continue a watch. If the requested history is no longer available and the API returns 410 Gone, a well-built client performs a fresh list and starts a new watch from that result.

Finally, drop below kubectl and consume a watch the way every controller does: as a raw, bounded HTTP stream of JSON events:

kubectl get --raw "/apis/apps/v1/namespaces/nimbusai/deployments?watch=1&timeoutSeconds=5"

[ Expected output ]

{"type":"ADDED","object":{"kind":"Deployment","apiVersion":"apps/v1","metadata":{"name":"nimbusai-gateway","namespace":"nimbusai","uid":"8a6e6797-2ebd-4155-a984-ccb782c5e69f","resourceVersion":"779","generation":4,"creationTimestamp":"2026-07-15T07:04:34Z","labels":{"app.kubernetes.io/name":"nimbusai-gateway","app.kubernetes.io/part-of":"…
(single ADDED event carrying the full current object: one long JSON line; the stream then stays silent until the server closes it at the 5s timeout)

You get a synthetic ADDED event carrying the full current object, followed by later changes until the server closes the stream at the timeout. Re-run it while scaling or annotating in your visualizer terminal and MODIFIED events appear inline. Controllers use the same list-and-watch API pattern, normally through shared informers and local caches rather than one raw watch per object.

Always bound raw watches

timeoutSeconds is not optional politeness. An unbounded watch from a script is a connection the API server carries until something breaks it: and thousands of them are a control-plane incident. Module 2 is about exactly that failure mode.

Production triage: when reconciliation appears stuck​

Use the signals together. No single field proves the whole control plane is healthy.

EvidenceWhat it tells youNext actionWhat to avoid
Generation ahead, Lease renewsLeader alive; revision not processedLogs, queue, RBAC, admissionRestarting application Pods
Generation ahead, Lease staleController-manager may be unhealthyPod health, API, certificates, electionReapplying the workload
Generations match; condition failsDownstream problemFollow the condition reasonBlaming controller-manager
Write leaves version unchangedNo-op or wrong objectVerbosity, audit, target objectTreating the version as progress
Watch returns 410 GoneHistory is unavailableRe-list and start a new watchReusing the stale version

For production controllers, use the Kubernetes client library's informer or equivalent shared-cache pattern. Do not create a separate unbounded watch for every object or every reconciliation. For production scripts, add timeoutSeconds, handle reconnects, and set a clear overall deadline.

Summary​

Where you will use this
  • Every field of every object has a registered owner in managedFields, conflicts between managers are detectable and rejectable, and --force-conflicts is a deliberate ownership transfer: not a bigger hammer. Use it when: a value keeps reverting after you change it (HPA vs GitOps, operator vs human): read the registry, name the fighting managers, and assign the field one rightful owner instead of playing whack-a-mole.
  • operation: Apply and operation: Update describe the write path, not two kinds of status. Apply is Server-Side Apply; Update is every non-SSA write, including client-side apply, edit, patch, scale, and controller writes. Use it when: an edit appears to "work" but a later GitOps apply conflicts: inspect the manager, operation, and subresource to identify who took the field and decide whether to transfer it back.
  • The Deployment → ReplicaSet → Pod chain is connected by ownerReferences and handled by two independent subsystems: the garbage collector handles deletion, while controllers handle replacement and adoption. Use it when: an object hangs in Terminating, a delete removes unexpected children, or you are planning an ownership transfer. Use background deletion for normal cleanup, foreground when the full tree must disappear before the owner, and orphan only with a named new owner or cleanup plan.
  • A Lease proves leader renewal, not complete controller health. Combine it with generation, observedGeneration, conditions, logs, and work-queue evidence. Treat resourceVersion as opaque and keep raw watches bounded. Use it when: reconciliation appears stuck. This sequence tells you whether to investigate leader election, a controller queue, or a downstream workload dependency.
