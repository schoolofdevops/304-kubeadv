Lab - Reconciliation Engine

Before you start

Complete the Setup section before you begin. Run every command from the root of the 304-labs/ repository.

This lab uses the core-internals cluster. The first run may take longer because kind downloads the node image.

In this lab, you will deploy the NimbusAI gateway and observe how Kubernetes responds when desired and current state differ.

You will:

  • watch Pods and Events as the controllers work
  • compare generation with observedGeneration
  • identify the controller that owns a replacement Pod
  • read a FailedScheduling event
  • observe the same changes in Cluster X-Ray

Pre Requisites​

Prerequisites

Rancher Desktop must be running with the Moby/dockerd engine. Verify that docker, kind, and kubectl respond before continuing.

Run only one course cluster profile at a time.

Deploy the NimbusAI gateway​

NimbusAI is the sample platform used throughout this course. Start by reviewing its gateway Deployment:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nimbusai-gateway
  namespace: nimbusai
  labels:
    app.kubernetes.io/name: nimbusai-gateway
    app.kubernetes.io/part-of: nimbusai
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: nimbusai-gateway
  template:
    metadata:
      labels:
        app.kubernetes.io/name: nimbusai-gateway
        app.kubernetes.io/part-of: nimbusai
    spec:
      containers:
        - name: gateway
          image: nginx:alpine
          ports:
            - name: http
              containerPort: 80
          resources:
            requests:
              cpu: 25m
              memory: 32Mi
            limits:
              memory: 64Mi

Everything NimbusAI ships in this course carries the app.kubernetes.io/part-of: nimbusai label: that's how you'll find its pieces when there are many. The image is deliberately tiny and multi-arch; this module is about the control plane, not the container.

Apply it (the manifest file also includes the nimbusai Namespace):

kubectl apply -f labs/m1/nimbusai-gateway.yaml

[ Expected output ]

deployment.apps/nimbusai-gateway created

This lab uses client-side apply. It calculates the merge locally and stores its previous configuration in the last-applied-configuration annotation.

The Deep Dive compares this path with Server-Side Apply and creates a safe field-ownership conflict.

apply is not one request: it's discovery, a GET of current state, then a PATCH per object. Each line is a place a slow admission webhook, a broken aggregated API, or an overloaded API server can stall you. Module 2 lives in this layer.

PART II - Disturb the Workload​

Delete a Pod​

Grab one Pod name and delete it:

POD=$(kubectl get pods -n nimbusai -l app.kubernetes.io/name=nimbusai-gateway -o jsonpath='{.items[0].metadata.name}')
kubectl delete pod "$POD" -n nimbusai

[ Expected output ]

pod "nimbusai-gateway-58ddfccb84-6q2j5" deleted from nimbusai namespace

In the visualizer, the replacement appears almost before the deletion completes. Note what did NOT change: metadata.generation. You never touched the spec: observed state drifted, and the ReplicaSet controller (level-triggered) compared the current Pod count against desired and created one. Confirm via the ReplicaSet's events:

kubectl describe rs -n nimbusai -l app.kubernetes.io/name=nimbusai-gateway

[ Expected output ]

Name:           nimbusai-gateway-58ddfccb84
Namespace:      nimbusai
Selector:       app.kubernetes.io/name=nimbusai-gateway,pod-template-hash=58ddfccb84
Labels:         app.kubernetes.io/name=nimbusai-gateway
... (trimmed) ...
Events:
  Type    Reason            Age   From                   Message
  ----    ------            ----  ----                   -------
  Normal  SuccessfulCreate  56s   replicaset-controller  Created pod: nimbusai-gateway-58ddfccb84-889dn
  Normal  SuccessfulCreate  56s   replicaset-controller  Created pod: nimbusai-gateway-58ddfccb84-6q2j5
  Normal  SuccessfulCreate  7s    replicaset-controller  Created pod: nimbusai-gateway-58ddfccb84-cjbdp

Notice the From column: replicaset-controller. Not the Deployment. Prove it on the replacement Pod itself: its ownerReferences name exactly one controller:

kubectl get pods -n nimbusai -l app.kubernetes.io/name=nimbusai-gateway -o jsonpath='{.items[0].metadata.name}{"  owned by: "}{.items[0].metadata.ownerReferences[0].kind}{"/"}{.items[0].metadata.ownerReferences[0].name}{"\n"}'

[ Expected output ]

nimbusai-gateway-58ddfccb84-np6p8  owned by: ReplicaSet/nimbusai-gateway-58ddfccb84

In an incident, this matters: knowing which controller owns an action tells you which logs, events, and leader-election lease to check. "Pods keep getting recreated" is a ReplicaSet-controller conversation; "the ReplicaSet keeps changing" is a Deployment-controller conversation. Chasing the wrong one burns your incident clock.

Scale the Deployment​

Scaling does change the spec: so this time the paperwork updates:

kubectl scale deploy nimbusai-gateway -n nimbusai --replicas=4
kubectl get deploy nimbusai-gateway -n nimbusai -o jsonpath='generation={.metadata.generation} observedGeneration={.status.observedGeneration} ready={.status.readyReplicas}{"\n"}'

[ Expected output ]

deployment.apps/nimbusai-gateway scaled
generation=2 observedGeneration=2 ready=2

kubectl scale does not update the whole Deployment through the normal resource endpoint. It writes spec.replicas through the Deployment's dedicated scale subresource. Inspect the corresponding managed-fields entry:

kubectl get deploy nimbusai-gateway -n nimbusai -o jsonpath='{range .metadata.managedFields[?(@.subresource=="scale")]}{.manager}{"  "}{.operation}{"  subresource="}{.subresource}{"\n"}{end}'

[ Expected output ]

kubectl1.35.0  Update  subresource=scale

Your manager name may differ. The stable evidence is operation=Update and subresource=scale.

This is an imperative write to spec.replicas, not Server-Side Apply.

If you're quick, you can catch observedGeneration trailing generation for a moment: the window where status still describes your old intent. Wait for convergence:

kubectl rollout status deploy nimbusai-gateway -n nimbusai

[ Expected output ]

Waiting for deployment "nimbusai-gateway" rollout to finish: 2 of 4 updated replicas are available...
Waiting for deployment "nimbusai-gateway" rollout to finish: 3 of 4 updated replicas are available...
deployment "nimbusai-gateway" successfully rolled out

The event stream shows the controller's own account of what it did:

kubectl get events -n nimbusai --field-selector reason=ScalingReplicaSet

[ Expected output ]

LAST SEEN   TYPE     REASON              OBJECT                        MESSAGE
67s         Normal   ScalingReplicaSet   deployment/nimbusai-gateway   Scaled up replica set nimbusai-gateway-58ddfccb84 from 0 to 2
1s          Normal   ScalingReplicaSet   deployment/nimbusai-gateway   Scaled up replica set nimbusai-gateway-58ddfccb84 from 2 to 4
Triage: is the controller stuck, or just behind?

generation vs observedGeneration is a production triage instrument, not bookkeeping. When a rollout "isn't happening," read the pair:

What you seeWhat it meansWhere to look next
generation > observedGenerationController has not processed the changeController-manager Lease and logs
Equal, but rollout stalledController is fine; the problem is downstreamReplicaSet events, quota, image pulls, scheduling
generation climbing when nobody deployedTwo systems fighting over the specField ownership: the SSA conflict walkthrough in the Deep Dive
Production ownership rule

Treat this scale as an operational intervention, then reconcile the intended long-term value in your Git or deployment workflow. A later manifest apply can overwrite a manual replica count. If an HPA is responsible for replicas, remove spec.replicas from the Deployment manifest and let the HPA own that one dynamic field. The durable goal is not “always use SSA”; it is one intentional owner for each piece of desired state.

Cordon the worker​

Cordoning marks a node unschedulable. It does not evict running Pods.

kubectl cordon kubeadv-core-worker
kubectl get nodes

[ Expected output ]

node/kubeadv-core-worker cordoned
NAME                         STATUS                     ROLES           AGE    VERSION
kubeadv-core-control-plane   Ready                      control-plane   2m9s   v1.35.0
kubeadv-core-worker          Ready,SchedulingDisabled   <none>          118s   v1.35.0

Your four gateway Pods are still Running: cordon changes future eligibility, it evicts nothing. Now force the scheduler's hand by deleting a Pod while its only landing zone is closed:

POD=$(kubectl get pods -n nimbusai -l app.kubernetes.io/name=nimbusai-gateway -o jsonpath='{.items[0].metadata.name}')
kubectl delete pod "$POD" -n nimbusai
kubectl get pods -n nimbusai

[ Expected output ]

pod "nimbusai-gateway-58ddfccb84-889dn" deleted from nimbusai namespace
NAME                                READY   STATUS    RESTARTS   AGE
nimbusai-gateway-58ddfccb84-5sjcx   0/1     Pending   0          0s
nimbusai-gateway-58ddfccb84-8gsts   1/1     Running   0          17s
nimbusai-gateway-58ddfccb84-cjbdp   1/1     Running   0          34s
nimbusai-gateway-58ddfccb84-wxnrj   1/1     Running   0          17s

The ReplicaSet controller still does its job: it creates the replacement Pod object instantly. But the scheduler's filter phase finds no eligible node, and the Pod parks in Pending. Read the scheduler's exact reasoning:

kubectl describe pod -n nimbusai $(kubectl get pods -n nimbusai --field-selector=status.phase=Pending -o jsonpath='{.items[0].metadata.name}') | grep -A4 Events:

[ Expected output ]

Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  5s    default-scheduler  0/2 nodes are available: 1 node(s) had untolerated taint(s), 1 node(s) were unschedulable. no new claims to deallocate, preemption: 0/2 nodes are available: 2 Preemption is not helpful for scheduling.

That message is dense on purpose: it's the scheduler's filter phase publishing its work, and reading it precisely is scheduling-incident triage. Dissect it:

  • 0/2 nodes are available: the verdict: of 2 nodes evaluated, 0 passed the filters.
  • 1 node(s) had untolerated taint(s): the control-plane node. It always fails for ordinary Pods; in a real cluster with 50 tainted GPU nodes, this count tells you taints are your problem: or aren't.
  • 1 node(s) were unschedulable: your cordon, verbatim. unschedulable in this message always means cordon, nothing else.
  • preemption: 0/2 nodes are available ... Preemption is not helpful: the scheduler also checked whether evicting lower-priority Pods would free an eligible node. It wouldn't: no victim's removal changes a taint or a cordon. When you see "not helpful," stop hoping priorities will save you: the blocker is node eligibility, not capacity.

The counts add up to the node total, and each category points to a different fix. Reopen the worker and let the scheduler retry:

kubectl uncordon kubeadv-core-worker
kubectl rollout status deploy nimbusai-gateway -n nimbusai

[ Expected output ]

node/kubeadv-core-worker uncordoned
Waiting for deployment "nimbusai-gateway" rollout to finish: 3 of 4 updated replicas are available...
deployment "nimbusai-gateway" successfully rolled out

No controller needed to be told the node was back. The level changed; the loops converged.

PART III - Validate the End State​

Confirm the converged state:

kubectl get deploy nimbusai-gateway -n nimbusai -o jsonpath='generation={.metadata.generation} observedGeneration={.status.observedGeneration} ready={.status.readyReplicas}{"\n"}'
kubectl get node kubeadv-core-worker -o jsonpath='unschedulable={.spec.unschedulable}{"\n"}'

[ Expected output ]

generation=2 observedGeneration=2 ready=4
unschedulable=

You want: observedGeneration equal to generation, ready=4, and an empty unschedulable= (the field disappears on uncordon).

Troubleshooting
  • kind create cluster fails or hangs: Rancher Desktop isn't running or isn't using the Moby/dockerd engine. Check docker version, then re-run create.sh (it's idempotent).
  • kubectl talks to the wrong cluster: switch explicitly: kubectl config use-context kind-kubeadv-core.
  • Pods stuck Pending after uncordon: confirm the node really reopened: kubectl get nodes should show no SchedulingDisabled. Then check kubectl describe pod for the newest FailedScheduling message: events at the top of the list may be stale history.
  • Worker node NotReady or missing; kubelet logs show inotify_init: too many open files: kind's best-known host limit. Raise the limits inside the Docker VM: docker run --rm --privileged alpine sh -c "sysctl -w fs.inotify.max_user_instances=1024 fs.inotify.max_user_watches=1048576" (resets on VM restart; add permanently in Rancher Desktop's provisioning if it recurs). More likely when other containers/clusters share the VM.
  • Empty results from event queries: cluster events expire (about an hour). Re-trigger the action (e.g. scale down and up again) rather than hunting for old events.
  • jsonpath output looks cramped: substitute kubectl get deploy nimbusai-gateway -n nimbusai -o yaml and read the generation, observedGeneration, and conditions fields directly (or pipe through yq if you have it installed).

Teardown​

Delete the NimbusAI workload but keep the cluster: the next module (M2, API server at scale) reuses the core-internals profile:

kubectl delete -f labs/m1/nimbusai-gateway.yaml

[ Expected output ]

namespace "nimbusai" deleted
deployment.apps "nimbusai-gateway" deleted from nimbusai namespace

Observe the deletion in Cluster X-Ray. The controllers now converge on an empty namespace.

If you're done for the day (or need to move to a different profile), remove the whole cluster:

bash labs/clusters/core-internals/teardown.sh

[ Expected output ]

Deleting cluster "kubeadv-core" ...
Deleted nodes: ["kubeadv-core-control-plane" "kubeadv-core-worker"]
core-internals profile torn down: cluster 'kubeadv-core' deleted.
