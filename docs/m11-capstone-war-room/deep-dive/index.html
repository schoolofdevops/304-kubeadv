Deep Dive - Production Postmortem & Incident Playbook

This deep dive turns the capstone evidence into a postmortem. You will reconstruct a timeline, separate causes from contributing factors, write verifiable action items, and prepare incident updates.

▶ M11: Capstone War-Room Deep DiveOpen fullscreen ↗

PART I - The postmortem as a learning tool​

A postmortem is not a blame document. It is the organization's mechanism for converting an incident into a permanent improvement. If the same class of failure can happen again, the postmortem failed.

The Swiss cheese model explains why incidents happen: every system has multiple layers of defense (monitoring, alerting, RBAC, review processes), and each layer has holes. An incident occurs when the holes align: a gap in monitoring lines up with a missing runbook and a human error. No single failure caused the incident; the alignment did. The postmortem must identify which layers had holes and how to shrink them.

Two principles:

  • Blameless by default. People make mistakes inside systems that allow those mistakes. The postmortem asks why the system allowed it, not who did it.
  • Contributing factors matter as much as root causes. The direct cause is often obvious. The conditions that let it become an incident are not.

PART II - Timeline reconstruction​

The first step in any postmortem is building the timeline. Kubernetes gives you several timestamp sources:

Events: every scheduling decision, probe failure, image pull, and volume mount is recorded with a timestamp:

kubectl get events -A --sort-by='.lastTimestamp' \
  -o custom-columns='TIME:.lastTimestamp,NS:.involvedObject.namespace,KIND:.involvedObject.kind,NAME:.involvedObject.name,REASON:.reason,MESSAGE:.message'

[ sample output ]

TIME                   NS          KIND   NAME              REASON             MESSAGE
2026-08-18T10:14:02Z   nimbusai    Pod    inference-0       FailedScheduling   0/5 nodes are available

Pod creation timestamps: when was each pod spec submitted vs when did it actually start:

kubectl get pods -A -o custom-columns='NAME:.metadata.name,CREATED:.metadata.creationTimestamp,STARTED:.status.startTime,STATUS:.status.phase'

[ sample output ]

NAME            CREATED                STARTED                STATUS
inference-0     2026-08-18T10:13:58Z   <none>                 Pending

Node conditions: when did a node become unschedulable or report pressure:

kubectl get nodes -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status,SINCE:.status.conditions[?(@.type=="Ready")].lastTransitionTime'

[ sample output ]

NAME                  READY   SINCE
capstone-worker       True    2026-08-18T10:01:21Z

Audit log: every API call, who made it, from where, and what the response was:

kubectl logs -n kube-system kube-apiserver-<node> | \
  python3 -c "import sys,json; [print(json.dumps({k:e.get(k) for k in ['requestReceivedTimestamp','user','verb','objectRef','responseStatus']},default=str)) for line in sys.stdin for e in [json.loads(line)] if e.get('user',{}).get('username','') != 'system:apiserver']" | head -20

[ sample output ]

{"requestReceivedTimestamp":"2026-08-18T10:12:40Z","user":{"username":"kubernetes-admin"},"verb":"patch","objectRef":{"resource":"nodes","name":"capstone-worker"},"responseStatus":{"code":200}}

Build the timeline on paper or in a shared doc before you touch anything. The order of events often reveals the root cause faster than inspecting individual resources.

PART III - Root cause vs contributing factor​

A root cause is the condition that, if removed, would have prevented the incident. A contributing factor is a condition that made the incident worse, more likely, or harder to detect.

Example from the capstone:

CategoryItem
Root cause2000 junk ConfigMaps filling the etcd backend to 80%
Contributing factorNo alerting on etcd backend size
Contributing factorNo automated compaction schedule
Contributing factorThe junk namespace had no owner label: nobody knew it existed

The root cause is specific and fixable. Contributing factors explain why it went undetected and why the blast radius was large. A good postmortem addresses both.

PART IV - The five whys​

Start with the symptom and ask why repeatedly until you reach a systemic cause:

  1. Why were inference-worker pods Pending? Because the only node with the accelerator=gpu label was tainted NoSchedule.
  2. Why was the node tainted? A maintenance operation was started.
  3. Why was the maintenance not completed? The operator was interrupted and forgot to remove the taint.
  4. Why was there no alert for a tainted-but-idle node? No monitoring rule existed for that condition.
  5. Why was there no monitoring rule? Node tainting was treated as a manual, ad-hoc operation with no runbook.

The first why gives you the fix (remove the taint). The fifth why gives you the prevention (add a runbook and an alert). Stop when you reach an organizational or process gap: that is where the action item lives.

PART V - Action item quality​

Bad action items are vague intentions. Good action items are specific, measurable, assigned, and time-bound.

BadGood
"Be careful with taints""Alert on NoSchedule for 30 minutes without maintenance. Owner: platform. Due: sprint 42."
"Monitor etcd""Deploy the etcd-mixin Grafana dashboard and add a PagerDuty alert for backend_db_size exceeding 75% of quota. Owner: SRE. Due: next Monday."
"Don't delete ConfigMaps""Deny deletion of operator-managed ConfigMaps except by the operator. Owner: security. Due: sprint 43."

The test: could someone who was not in the incident read this action item and execute it without asking questions? If not, it is too vague.

PART VI - Incident communication template​

During an active incident, the team needs structured updates. Post them at regular intervals (every 15–30 minutes) to a shared channel:

🔴 INCIDENT UPDATE: [timestamp UTC]

Severity: SEV-2 (partial service degradation)
Impact:   50% of inference-worker pods unschedulable;
          external DNS resolution failing for all pods
Status:   Investigating: etcd degradation identified and
          remediation in progress
ETA:      ~20 min for etcd; DNS fix queued next
Owner:    [your name]
Next update: [timestamp + 15 min]

Rules:

  • State facts, not theories. "etcd backend is at 82% quota" not "etcd might be full."
  • Separate impact from cause. Impact is what the user sees. Cause is what the engineer is fixing.
  • Commit to the next update time. Silence during an incident erodes trust faster than bad news.

PART VII - SRE metrics for incidents​

Three metrics frame how your team handles incidents over time:

MTTD: Mean Time to Detect. From when the fault was introduced to when someone noticed. Shorter MTTD means better monitoring and alerting. In the capstone, if you noticed the etcd degradation before fixing the scheduling fault, your MTTD for etcd was good.

MTTR: Mean Time to Resolve. From detection to full recovery. MTTR includes diagnosis, remediation, and verification. A well-practiced team with runbooks has low MTTR. In the capstone, your total lab time is your MTTR.

MTBF: Mean Time Between Failures. How long the system runs without incidents. MTBF improves through the action items from postmortems: better monitoring, guardrails, automation.

The relationship: availability = MTBF / (MTBF + MTTR). A system with MTBF of 30 days and MTTR of 1 hour has 99.86% availability. Reducing MTTR from 1 hour to 30 minutes improves availability, but increasing MTBF from 30 to 60 days improves it more. Postmortem action items should target MTBF (prevention) over MTTR (faster recovery).

PART VIII - Postmortem template​

Copy this template and fill it in after completing the war-room lab. One page. Every field matters.

# Postmortem: NimbusAI Platform Incident: [date]

## Summary
One sentence: what happened, how long it lasted, what was affected.

## Timeline (UTC)
| Time | Event |
|------|-------|
| HH:MM | First symptom observed (what you saw) |
| HH:MM | Fault 1 identified (evidence gathered) |
| HH:MM | Fault 1 fixed + verified |
| ... | ... |
| HH:MM | All faults resolved, full service restored |

## Root causes
For each of the 6 faults:
- **Fault name:** one-sentence root cause
- **Module skill used:** which M1–M10 technique diagnosed it
- **Evidence command:** the kubectl command that confirmed the diagnosis

## Contributing factors
- Conditions that allowed the faults to go undetected or made them harder to fix.
- Missing monitoring, missing runbooks, missing guardrails.

## Impact
- Which workloads were affected and for how long
- Whether any data was lost (yes/no)
- Which faults had the widest blast radius

## Action items
| Priority | Action | Owner | Due |
|----------|--------|-------|-----|
| P1 | ... | ... | ... |
| P2 | ... | ... | ... |

## What went well
- What worked during the incident (good diagnostic skills, calm triage, etc.)
- Which module skills proved most valuable

## Lessons learned
- What you would do differently next time
- Which fault was hardest to find and why
Where you will use this
  • Use the timeline when several alerts appear close together and sequence determines causality.
  • Separate root cause, trigger, and contributing factors so one repaired component does not become the whole explanation.
  • Use the five whys to move from restoring service to preventing recurrence.
  • Reject action items such as “monitor more” or “be careful”; require an owner, due date, and verifiable completion condition.
  • Track both recovery speed and prevention. A faster runbook improves MTTR; removing the failure mode improves MTBF.

A production-grade postmortem should let a new engineer understand the incident and verify every follow-up without attending the original call.
