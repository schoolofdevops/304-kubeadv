Lab — Production War-Room

Before you start

New here? Complete the Setup section first — repo clone, toolchain, and the verification probe. All commands below run from the root of the lab repo (304-labs/). This lab uses a dedicated capstone cluster — not the core-internals cluster from earlier modules. Tear down any running cluster first.

This lab is different from every other one in this course. You will not be guided step-by-step. You will receive a broken cluster and a set of symptoms. Your job: triage, diagnose, fix, and write a postmortem. The cluster has six independent faults seeded from the skills you built across M1 through M10. Scoring rewards method over speed — evidence gathered before you change anything, a clear triage priority, and a structured postmortem count more than how fast you type.

Scoring — 200 points

Evidence gathered before each fix60 (10 × 6)
Triage priority reasoning20
Fix correctness60 (10 × 6)
Communication log (notes as you go)20

Step 1 — Set up the capstone cluster​

Tear down any running cluster, then bring up the capstone profile. The setup script creates a kind cluster with Kueue and the Website operator installed, deploys baseline workloads, and then injects six faults — all in one command.

bash labs/clusters/core-internals/teardown.sh  # safe if nothing running
bash labs/m11/setup.sh

Expected output (last lines):

=== All 6 faults injected ===

The NimbusAI platform is now experiencing multiple issues.
Hand this cluster to the learner — their mission: triage, diagnose, fix, postmortem.

Set your kubectl context:

kubectl config use-context kind-kubeadv-capstone

From this point forward, every command uses this context. The cluster is yours to inspect and repair.

Step 2 — Initial assessment​

You just got paged. Before you touch anything, observe. Gather evidence with broad diagnostic commands. Write down what you see — you will need this for the postmortem.

kubectl get nodes -o wide

Expected output:

NAME                                 STATUS   ROLES           AGE   VERSION
kubeadv-capstone-control-plane       Ready    control-plane   …     v1.35.0
kubeadv-capstone-worker              Ready    <none>          …     v1.35.0
kubeadv-capstone-worker2             Ready    <none>          …     v1.35.0

All three nodes should show Ready — the faults are above the node level.

kubectl get pods -A | grep -Ev 'Running|Completed'

Expected output (your timestamps will differ):

NAMESPACE     NAME                                READY   STATUS              RESTARTS   AGE
capstone-app  inference-worker-…                  0/1     Pending             0          …
capstone-app  inference-worker-…                  0/1     Pending             0          …
m5-system     website-operator-…                  0/1     ContainerCreating   0          …

Two Pending pods and one stuck in ContainerCreating — three of your six faults are already visible.

kubectl get events -A --sort-by=.lastTimestamp | tail -30

Watch for events mentioning:

  • FailedScheduling with taint or node-selector messages
  • FailedMount with configmap-not-found
  • 429 Too Many Requests from the API server
kubectl -n kube-system get pods

Expected output:

NAME                                                 READY   STATUS    RESTARTS   AGE
coredns-…                                            1/1     Running   0          …
coredns-…                                            1/1     Running   0          …
etcd-kubeadv-capstone-control-plane                  1/1     Running   0          …
kube-apiserver-kubeadv-capstone-control-plane         1/1     Running   0          …
kube-controller-manager-kubeadv-capstone-…            1/1     Running   0          …
kube-scheduler-kubeadv-capstone-…                     1/1     Running   0          …
…

System pods should all be Running — these faults are subtle, not crash-level.

kubectl top nodes 2>/dev/null || echo "(metrics-server not installed — skip)"

You should see a mix of symptoms: pods stuck Pending, a pod stuck in ContainerCreating, system components that may be restarting, and events hinting at scheduling and volume issues. Note every anomaly — do not start fixing yet.

Step 4 — Fault 1: etcd degradation (M3)​

Symptom: API responses feel slow. Something is putting pressure on etcd.

Investigate: look for unusual namespaces and count objects.

kubectl get ns

Expected output (look for the anomaly):

NAME               STATUS   AGE
capstone-app       Active   …
capstone-junk      Active   …
default            Active   …
kube-node-lease    Active   …
kube-public        Active   …
kube-system        Active   …
m5-system          Active   …

capstone-junk does not belong to any application — that is your first clue.

kubectl get cm -n capstone-junk --no-headers | wc -l

Expected output:

2000

Two thousand ConfigMaps stuffed into etcd. Check the backend size from inside etcd:

kubectl -n kube-system exec etcd-kubeadv-capstone-control-plane -- \
  etcdctl endpoint status --write-out=table \
  --cacert /etc/kubernetes/pki/etcd/ca.crt \
  --cert /etc/kubernetes/pki/etcd/server.crt \
  --key /etc/kubernetes/pki/etcd/server.key

Note the DB SIZE column — it should be significantly larger than a healthy cluster.

Fix

Delete the junk namespace (removes all 2000 ConfigMaps):

kubectl delete ns capstone-junk

Wait for the namespace to terminate, then compact and defragment etcd:

# Get the current revision
REV=$(kubectl -n kube-system exec etcd-kubeadv-capstone-control-plane -- \
  etcdctl endpoint status --write-out=json \
  --cacert /etc/kubernetes/pki/etcd/ca.crt \
  --cert /etc/kubernetes/pki/etcd/server.crt \
  --key /etc/kubernetes/pki/etcd/server.key \
  | python3 -c "import sys,json; print(json.loads(sys.stdin.read())[0]['Status']['header']['revision'])")

# Compact to that revision
kubectl -n kube-system exec etcd-kubeadv-capstone-control-plane -- \
  etcdctl compact "$REV" \
  --cacert /etc/kubernetes/pki/etcd/ca.crt \
  --cert /etc/kubernetes/pki/etcd/server.crt \
  --key /etc/kubernetes/pki/etcd/server.key

# Defragment
kubectl -n kube-system exec etcd-kubeadv-capstone-control-plane -- \
  etcdctl defrag \
  --cacert /etc/kubernetes/pki/etcd/ca.crt \
  --cert /etc/kubernetes/pki/etcd/server.crt \
  --key /etc/kubernetes/pki/etcd/server.key

Verify: re-run the endpoint status command. DB SIZE should have dropped substantially.

Step 5 — Fault 2: API throttling (M2)​

Symptom: some requests return HTTP 429. Controllers and operators are sluggish.

Investigate: list FlowSchemas and look for anything that should not be there.

kubectl get flowschemas

Expected output (abbreviated):

NAME                           PRIORITYLEVEL        …   AGE
…
service-accounts               workload-low         …   …
throttle-serviceaccounts       capstone-throttle    …   …
…

throttle-serviceaccounts does not ship with the cluster — that is the rogue entry.

kubectl describe flowschema throttle-serviceaccounts

Check which PriorityLevelConfiguration it points to:

kubectl get prioritylevelconfiguration capstone-throttle -o yaml

Note nominalConcurrencyShares: 1 — this chokes every ServiceAccount-authenticated request down to a single concurrent slot.

You can confirm 429s in the audit log:

kubectl logs -n kube-system kube-apiserver-kubeadv-capstone-control-plane | \
  python3 -c "
import sys, json
for line in sys.stdin:
    try:
        e = json.loads(line)
        if e.get('responseStatus',{}).get('code') == 429:
            print(f\"{e['verb']:6s} {e.get('objectRef',{}).get('resource','?'):20s} user={e['user']['username']}\")
    except: pass
" | head -10
Fix

Delete the bad FlowSchema and its PriorityLevelConfiguration:

kubectl delete flowschema throttle-serviceaccounts
kubectl delete prioritylevelconfiguration capstone-throttle

Verify: re-run kubectl get flowschemas — throttle-serviceaccounts should be gone. No more 429s in the audit stream.

Step 6 — Fault 3: CoreDNS corruption (M7)​

Symptom: pods that depend on external DNS resolution are failing. Internal service discovery (kubernetes.default.svc) still works.

Investigate: test DNS from inside the cluster.

kubectl run dnstest --rm -it --restart=Never --image=busybox:1.36 -- \
  nslookup kubernetes.default.svc.cluster.local

Expected output (internal resolution works):

Server:    10.96.0.10
Address 1: 10.96.0.10 kube-dns.kube-system.svc.cluster.local

Name:      kubernetes.default.svc.cluster.local
Address 1: 10.96.0.1 kubernetes.default.svc.cluster.local

Now test external:

kubectl run dnstest2 --rm -it --restart=Never --image=busybox:1.36 -- \
  nslookup google.com

Expected output (external resolution fails):

;; connection timed out; no servers could be reached

Internal works, external broken — the upstream forwarder is wrong. Check CoreDNS logs:

kubectl -n kube-system logs -l k8s-app=kube-dns --tail=20

Look for connection refused or timeout errors pointing at a suspicious upstream IP. Inspect the Corefile:

kubectl -n kube-system get cm coredns -o jsonpath='{.data.Corefile}'

Expected output (spot the bad upstream):

.:53 {
    …
    forward . 10.0.0.254
    …
}

10.0.0.254 is unreachable — it should be forward . /etc/resolv.conf.

Fix

Edit the ConfigMap and restore the correct upstream:

kubectl -n kube-system get cm coredns -o yaml | \
  sed 's|forward . 10.0.0.254|forward . /etc/resolv.conf|' | \
  kubectl apply -f -

Restart CoreDNS to pick up the change:

kubectl -n kube-system rollout restart deploy/coredns
kubectl -n kube-system rollout status deploy/coredns --timeout=60s

A backup of the original Corefile is at labs/m11/corefile-backup.txt if you need a reference.

Verify: re-run the external DNS test:

kubectl run dnstest3 --rm -it --restart=Never --image=busybox:1.36 -- \
  nslookup google.com

It should resolve successfully.

Step 7 — Fault 4: Scheduling failure (M4)​

Symptom: some inference-worker pods are stuck Pending in the capstone-app namespace.

Investigate:

kubectl -n capstone-app get pods

Expected output:

NAME                                READY   STATUS    RESTARTS   AGE
dns-checker-…                       1/1     Running   0          …
inference-worker-…                  1/1     Running   0          …
inference-worker-…                  1/1     Running   0          …
inference-worker-…                  0/1     Pending   0          …
inference-worker-…                  0/1     Pending   0          …
nimbusai-website-…                  1/1     Running   0          …

Two Running and two Pending — the GPU node has room but something blocks scheduling. Describe one of the Pending pods:

PENDING=$(kubectl -n capstone-app get pods --field-selector=status.phase=Pending \
  -o jsonpath='{.items[0].metadata.name}')
kubectl -n capstone-app describe pod "$PENDING"

The events section should show something like: 0/3 nodes are available: 1 node(s) had untolerated taint {maintenance: true}, 1 node(s) didn't match Pod's node selector/affinity. The pods require nodeSelector: accelerator: gpu, and only one node has that label — but it is tainted with maintenance=true:NoSchedule.

Check node taints and labels:

kubectl get nodes -o custom-columns='NAME:.metadata.name,TAINTS:.spec.taints[*].effect,GPU:.metadata.labels.accelerator'

Expected output (fault injection labels/taints the first worker it finds — this may land on kubeadv-capstone-worker or kubeadv-capstone-worker2 depending on node listing order; read for the pattern, not the exact name):

NAME                                 TAINTS                GPU
kubeadv-capstone-control-plane       NoSchedule            <none>
kubeadv-capstone-worker              NoSchedule            gpu
kubeadv-capstone-worker2             <none>                <none>

Whichever worker carries GPU: gpu also carries the NoSchedule taint — that combination is the fault: the only node with the label the pods require is blocked from scheduling.

Fix

Remove the maintenance taint from the GPU worker:

NODE=$(kubectl get nodes -l accelerator=gpu -o jsonpath='{.items[0].metadata.name}')
kubectl taint nodes "$NODE" maintenance-

Verify: within a few seconds the Pending pods should schedule:

kubectl -n capstone-app get pods -l app=inference-worker -w

Wait until all 4 show Running, then Ctrl-C.

Step 8 — Fault 5: Broken operator (M5)​

Symptom: Website custom resources exist but are not being reconciled — no new Deployment or Service updates are happening.

Investigate:

kubectl -n m5-system get pods

Expected output:

NAME                                READY   STATUS              RESTARTS   AGE
website-operator-…                  0/1     ContainerCreating   0          …

The operator pod is stuck in ContainerCreating — not CrashLoopBackOff, which rules out code errors. Describe it:

kubectl -n m5-system describe pod -l app=website-operator

Look for a volume mount error in the events: MountVolume.SetUp failed for volume "src": configmap "website-operator-src" not found. Someone deleted the ConfigMap that contains the operator's reconciliation script.

Confirm:

kubectl -n m5-system get cm website-operator-src 2>&1

Expected output:

Error from server (NotFound): configmaps "website-operator-src" not found
Fix

A backup of the ConfigMap was saved during fault injection. Restore it:

kubectl apply -f labs/m11/operator-cm-backup.yaml

Delete the stuck pod so a new one starts with the restored ConfigMap:

kubectl -n m5-system delete pod -l app=website-operator

Wait for the new pod:

kubectl -n m5-system rollout status deploy/website-operator --timeout=120s

Verify: the operator should now reconcile the Website CR:

kubectl -n capstone-app get websites
kubectl -n capstone-app get deploy,svc -l app.kubernetes.io/managed-by=website-operator

You should see the Website with a Ready condition and its child Deployment and Service.

Step 9 — Fault 6: Kueue blocked (M8)​

Symptom: the original training job completed earlier, but no new jobs can be admitted. Submit a test job and it stays suspended.

Investigate:

kubectl get clusterqueue capstone-cq -o yaml | grep -A 5 nominalQuota

Expected output — the quota has been zeroed out:

          - name: cpu
            nominalQuota: "0"
          - name: memory
            nominalQuota: "0"

No workload can be admitted with zero capacity.

Fix

Restore reasonable quota to the ClusterQueue:

kubectl patch clusterqueue capstone-cq --type=merge -p '{
  "spec": {
    "resourceGroups": [{
      "coveredResources": ["cpu", "memory"],
      "flavors": [{
        "name": "capstone-flavor",
        "resources": [
          {"name": "cpu", "nominalQuota": "4"},
          {"name": "memory", "nominalQuota": "4Gi"}
        ]
      }]
    }]
  }
}'

Verify: submit a test job and confirm Kueue admits it:

kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: test-admit
  namespace: capstone-app
  labels:
    kueue.x-k8s.io/queue-name: capstone-queue
spec:
  suspend: true
  template:
    spec:
      containers:
        - name: test
          image: busybox:1.36
          command: ["echo", "admitted"]
          resources:
            requests:
              cpu: "100m"
              memory: "64Mi"
      restartPolicy: Never
EOF
sleep 5
kubectl get workloads -n capstone-app

The new workload should show Admitted=True.

Step 10 — Full verification​

All six faults should be fixed. Run the cluster verification script:

bash labs/clusters/capstone/verify.sh

Check for remaining non-Running pods:

kubectl get pods -A | grep -Ev 'Running|Completed'

Expected output: no lines returned — every pod in the cluster should be Running or Completed. If anything still shows, revisit that fault.

Step 11 — Write the postmortem​

The technical fixes are half the job. A good postmortem captures what happened so the team learns from it. Fill in every section:

# Incident Postmortem: NimbusAI Platform Degradation

Date:       ____
Duration:   ____ minutes (from first symptom to all-clear)
Severity:   ____ (S1/S2/S3)
Author:     ____

## Timeline
- HH:MM — Paged: multiple symptoms reported
- HH:MM — Initial assessment complete, triage priority established
- HH:MM — Fix 1 (etcd): deleted junk namespace, compacted, defragmented
- HH:MM — Fix 2 (API throttling): removed rogue FlowSchema
- HH:MM — Fix 3 (CoreDNS): restored Corefile upstream
- HH:MM — Fix 4 (Scheduling): removed maintenance taint
- HH:MM — Fix 5 (Operator): restored ConfigMap, restarted pod
- HH:MM — Fix 6 (Kueue): restored ClusterQueue quota
- HH:MM — All-clear: verification passed

## Root Causes
1. etcd backend bloated with 2000 junk ConfigMaps in capstone-junk namespace
2. FlowSchema throttle-serviceaccounts routing SAs to 1-concurrency PriorityLevel
3. CoreDNS Corefile upstream forwarder changed to unreachable IP 10.0.0.254
4. GPU worker node tainted maintenance=true:NoSchedule without removing workloads
5. Website operator ConfigMap deleted, pod restart failed to mount volume
6. Kueue ClusterQueue nominalQuota set to 0
