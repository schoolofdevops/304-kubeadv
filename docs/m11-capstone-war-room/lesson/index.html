Capstone — Production War-Room

Six alerts fire in ten minutes. Pods are Pending. DNS lookups are timing out. The training pipeline is stalled. An operator has stopped reconciling. API responses are sluggish. A batch queue has gone silent.

You know how to fix each of these individually. You have done exactly that across the last ten modules. The question now is not can you fix them. It is: which one do you fix first, and how do you prove each diagnosis before you change anything?

That is what separates troubleshooting from incident response. Troubleshooting is fixing one broken thing. Incident response is fixing six broken things in the right order, under pressure, while keeping your team informed and your decisions auditable.

The analogy: emergency room triage​

When six patients arrive at an ER simultaneously, the doctor does not treat them in the order they walked in. A triage nurse assesses each patient in under two minutes (airway, breathing, circulation) and assigns a priority tag. The patient with a blocked airway goes first, even if the patient with a broken arm arrived earlier and is louder about it.

The same principle applies to a Kubernetes incident. A degraded etcd backend that slows every API call across every namespace is a higher priority than two inference-worker pods stuck Pending in one namespace, even if the Pending alert fired first. Blast radius determines priority, not arrival order and not volume of noise.

Incident Response Follows a Repeatable Control Loop​

Every fault you encounter in the war-room follows the same diagnostic cycle. Run it once per fault, in priority order.

Evidence before action

At every stage, you gather evidence before you change anything. Run kubectl get, kubectl describe, kubectl logs. Read the audit trail. Check events. Only after you have a written record of the current state do you apply a fix. A fix without evidence is a guess. And in production, guesses compound.

Blast Radius Determines Incident Priority​

When multiple faults are active, rank them by how much of the cluster they affect. Fix the widest blast radius first.

PriorityBlast radiusExamplesModule
1: CriticalCluster-wideetcd degradation, API server throttlingM3, M2
2: HighCross-namespaceDNS failure, networking breakageM7
3: MediumSingle namespaceOperator not reconciling, scheduling failureM5, M4
4: LowSingle workloadBatch queue misconfigurationM8

This is not rigid. A single-namespace fault that affects your revenue-critical service may jump to priority 1. Context matters. But as a starting framework, scope beats severity every time.

Incident Communication Tracks Impact, Action, and Ownership​

Fixing the cluster is half the job. The other half is making sure everyone involved knows what is happening.

Roles. In a team setting, assign three roles up front. The incident commander decides priority and approves changes. The investigator runs diagnostics and proposes fixes. The communicator posts status updates at fixed intervals. Every 10 minutes is a reasonable cadence for the war-room.

Decision log. Every diagnosis, every fix, and every verification goes into a shared log. One line per action: timestamp, what you observed, what you changed, what happened after. This log becomes the spine of your postmortem. If you work alone, write the log for yourself. It forces you to slow down and think before you type.

Postmortems Convert Evidence into Preventive Work​

A postmortem is not blame. It is a structured record of what happened, why it happened, and what you will change so it does not happen the same way again.

Format (one page):

  1. Timeline: when each fault was detected, diagnosed, and resolved
  2. Root cause chain: for each fault, the sequence of events that led to it
  3. What went well: which diagnostic steps or tools saved time
  4. Action items: concrete changes to prevent recurrence (monitoring, guardrails, process)

The deep-dive page for this module includes a postmortem template you can fill in after the lab.

Production Incident Rules Preserve Service and Evidence​

During a real incident, technical skill is necessary but sequence matters more. Use these rules as the operating contract for the war-room:

MomentRecommended actionAvoid
First five minutesName an incident commander, start a timestamped log, confirm customer impact and blast radiusLetting every engineer run changes independently
DiagnosisSeparate facts, hypotheses, and proposed tests; capture evidence before mutationTreating the loudest alert as the root cause
RemediationChoose the smallest reversible change, state rollback, assign one executorBundling several “likely fixes” together
VerificationCheck the original symptom, control-plane health, and customer pathDeclaring success because one Pod is Running
HandoverRecord current state, remaining risk, owner, and next checkpointRelying on chat history or memory
PostmortemImprove detection, guardrails, and design; assign owners and dates“Be more careful” action items or blame
When business criticality changes the order

Blast radius is the starting point, not a rigid formula. A single-namespace failure serving payments or a major customer may outrank a broad but low-impact degradation. State the impact and the reason for changing priority in the decision log.

Capstone Lab: Diagnose and Recover Six Kubernetes Faults​

The NimbusAI platform (the same fictional AI workload you have deployed, stressed, and debugged throughout this course) has arrived pre-broken. Six faults are active, spanning skills from M2 through M8:

  • API throttling: a FlowSchema is choking ServiceAccount requests (M2)
  • etcd degradation: the backend is filling with junk, API responses are slow (M3)
  • Scheduling failure: inference-worker pods are stuck Pending (M4)
  • Broken operator: Website custom resources are not being reconciled (M5)
  • CoreDNS corruption: external DNS lookups are failing (M7)
  • Kueue queue blocked: training jobs are suspended and will not start (M8)

Your mission: triage by blast radius, diagnose each fault with evidence, fix each one, verify the fix, and write a one-page postmortem.

Scoring: method over speed
CategoryPoints
Evidence gathered before each fix60
Triage priority reasoning20
Fix correctness (10 per fault)60
Communication / decision log20
Postmortem quality40
Total200

Speed is not scored. A methodical approach that takes 90 minutes beats a fast but undocumented fix in 30. The goal is to build the habit of evidence-first diagnosis, the habit that separates a senior engineer from someone who just restarts pods.
