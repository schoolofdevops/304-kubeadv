Troubleshooting Pending Pods and Node Failures

Before you start

New here? Complete the Setup section first. Rancher Desktop should be running with the Moby/dockerd engine, and docker, kind, and kubectl should all respond.

All commands below run from the root of the lab repo (304-labs/). This lab continues on the core-internals cluster used in the earlier modules.

In this lab, you are going to troubleshoot three different reasons why a Pod could remain in Pending state. You would also create fake nodes with KWOK and observe how Kubernetes evicts a Pod from a node.

By the end of this lab, you will:

  • read FailedScheduling events
  • identify resource, selector and taint related failures
  • schedule a Pod on a fake KWOK node
  • trigger and observe a TaintManagerEviction

Pre Requisites​

Check the current Kubernetes context.

kubectl config current-context

[ Expected output ]

kind-kubeadv-core
If the core-internals cluster is missing

Create the cluster as,

bash labs/clusters/core-internals/create.sh

[ Expected output ]

Creating kind cluster 'kubeadv-core' ...
Waiting for all nodes to be Ready ...
OK: core-internals profile verified — 2/2 nodes Ready, API server healthy.

Then run the verification command from the next section.

Add Fake Nodes with KWOK​

The current cluster has one control-plane and one worker. This is not enough to test different scheduling conditions without affecting the real worker.

KWOK, which is called as Kubernetes WithOut Kubelet, creates fake Node objects. The scheduler can place Pods on these nodes, but no containers are actually started.

Run the setup script as,

bash labs/m4/kwok-setup.sh

[ sample output ]

==> Installing kwok v0.8.0 in-cluster controller + CRDs + RBAC ...
deployment "kwok-controller" successfully rolled out
==> Creating 3 fake node(s) ...
node/kwok-node-0 created
node/kwok-node-1 created
node/kwok-node-2 created
==> Waiting for fake nodes to report Ready (kwok node-initialize stage) ...
NAME                         STATUS   ROLES           AGE   VERSION
kubeadv-core-control-plane   Ready    control-plane   56m   v1.35.0
kubeadv-core-worker          Ready    <none>          56m   v1.35.0
kwok-node-0                  Ready    agent           13s   fake
kwok-node-1                  Ready    agent           4s    fake
kwok-node-2                  Ready    agent           4s    fake

kwok v0.8.0 in-cluster: controller Running, 3 fake node(s) Ready.

List the nodes.

kubectl get nodes

[ Expected output ]

NAME                         STATUS   ROLES           AGE   VERSION
kubeadv-core-control-plane   Ready    control-plane   56m   v1.35.0
kubeadv-core-worker          Ready    <none>          56m   v1.35.0

kwok-node-1                  Ready    agent           7s    fake
kwok-node-2                  Ready    agent           7s    fake

You should now have five nodes. The three kwok-node-* nodes are fake.

KWOK adds the following taint to its nodes:

kwok.x-k8s.io/node=fake:NoSchedule

This prevents normal workloads from getting scheduled on a fake node. A Pod would need a matching toleration before it can use one of these nodes.

Open http://127.0.0.1:8001/xray/ and select the Scheduling tab.

You should see:

  • all five nodes with their status, resources and taints
  • Pending Pods along with their FailedScheduling reason

PART II - Troubleshoot Pending Pods​

A Pod remains in Pending state when the scheduler cannot find a suitable node. Lets create three such Pods and examine the reason for each one.

Insufficient CPU​

Create the lab namespace and a Pod which asks for more CPU than any node has.

kubectl create namespace m4-lab --dry-run=client -o yaml | kubectl apply -f -
cat <<'EOF' | kubectl apply -n m4-lab -f -
apiVersion: v1
kind: Pod
metadata:
  name: too-big
spec:
  tolerations:
  - key: kwok.x-k8s.io/node
    operator: Exists
    effect: NoSchedule
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
    resources:
      requests:
        cpu: "9000"
EOF

[ Expected output ]

namespace/m4-lab created
pod/too-big created

The Pod tolerates the KWOK taint, so the scheduler can consider all three fake nodes. However, it asks for 9000 CPU.

Check the scheduling events.

kubectl describe pod too-big -n m4-lab | grep -A3 Events

[ sample output ]

Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  7s    default-scheduler  0/5 nodes are available: 1 node(s) had untolerated taint(s), 4 Insufficient cpu. no new claims to deallocate, preemption: 0/5 nodes are available: 5 Preemption is not helpful for scheduling.

Observe the message 4 Insufficient cpu. The real worker and all three KWOK nodes are rejected because the CPU request is too high. The control-plane is rejected because of its taint.

Wrong Node Selector​

Lets now create a Pod which requires a node label that does not exist.

cat <<'EOF' | kubectl apply -n m4-lab -f -
apiVersion: v1
kind: Pod
metadata:
  name: wrong-selector
spec:
  nodeSelector:
    disktype: nvme-that-does-not-exist
  tolerations:
  - key: kwok.x-k8s.io/node
    operator: Exists
    effect: NoSchedule
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
EOF

[ Expected output ]

pod/wrong-selector created

Check its events.

kubectl describe pod wrong-selector -n m4-lab | grep -A3 Events

[ sample output ]

Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  5s    default-scheduler  0/5 nodes are available: 1 node(s) had untolerated taint(s), 4 node(s) didn't match Pod's node affinity/selector. no new claims to deallocate, preemption: 0/5 nodes are available: 5 Preemption is not helpful for scheduling.

This time the message reports didn't match Pod's node affinity/selector.

What happened?

  • The Pod requires disktype: nvme-that-does-not-exist.
  • None of the nodes has this label.
  • You could fix it either by correcting the selector or by adding the required label to a suitable node.

Missing Toleration​

The fake nodes have the label type: kwok and a NoSchedule taint. Create a Pod which selects these nodes but does not tolerate their taint.

cat <<'EOF' | kubectl apply -n m4-lab -f -
apiVersion: v1
kind: Pod
metadata:
  name: no-toleration
spec:
  nodeSelector:
    type: kwok
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
EOF

[ Expected output ]

pod/no-toleration created

Check the scheduling events.

kubectl describe pod no-toleration -n m4-lab | grep -A3 Events

[ sample output ]

Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  6s    default-scheduler  0/5 nodes are available: 1 node(s) didn't match Pod's node affinity/selector, 4 node(s) had untolerated taint(s). no new claims to deallocate, preemption: 0/5 nodes are available: 5 Preemption is not helpful for scheduling.

The Pod selected the KWOK nodes, but it did not have permission to sit on them. The scheduler reports had untolerated taint(s).

Go back to the Scheduling view. All three Pending Pods should now be visible along with their reasons.

Your view should look similar to the screenshot. The Pod ages may differ, but each card should show the matching reason: insufficient CPU, a selector mismatch, or an untolerated taint.

Reading Pending Pod Events

Use the following command before changing a Pending Pod:

kubectl describe pod <pod-name> | grep -A3 Events

Look for one of these messages:

  • Insufficient cpu or Insufficient memory
  • didn't match Pod's node affinity/selector
  • had untolerated taint(s)

Each message points to a different fix. Read the event before changing the Pod or the node.

Fix the Pending Pods​

You have identified all three causes. Lets now fix them one at a time and confirm that the scheduler can place every Pod.

Reduce the CPU Request​

The too-big Pod asks for 9000 CPU. A Pod's resource requests cannot be changed after it is created, so delete it and recreate it with a request of 100m.

kubectl delete pod too-big -n m4-lab
cat <<'EOF' | kubectl apply -n m4-lab -f -
apiVersion: v1
kind: Pod
metadata:
  name: too-big
spec:
  tolerations:
  - key: kwok.x-k8s.io/node
    operator: Exists
    effect: NoSchedule
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
    resources:
      requests:
        cpu: "100m"
EOF
kubectl wait --for=condition=Ready pod/too-big -n m4-lab --timeout=60s

[ Expected output ]

pod "too-big" deleted from m4-lab namespace
pod/too-big created
pod/too-big condition met

The Pod now requests an amount of CPU available on the cluster.

Add the Required Node Label​

The wrong-selector Pod requires disktype=nvme-that-does-not-exist. Add this label to one fake node and wait for the existing Pod to schedule.

kubectl label node kwok-node-1 disktype=nvme-that-does-not-exist --overwrite
kubectl wait --for=condition=Ready pod/wrong-selector -n m4-lab --timeout=60s

[ Expected output ]

node/kwok-node-1 labeled
pod/wrong-selector condition met

You did not change the Pod. You changed the available node inventory so that one node now matches its requirement.

Add the Missing Toleration​

The no-toleration Pod selects the KWOK nodes but cannot tolerate their taint. Delete it and recreate it with the matching toleration.

kubectl delete pod no-toleration -n m4-lab
cat <<'EOF' | kubectl apply -n m4-lab -f -
apiVersion: v1
kind: Pod
metadata:
  name: no-toleration
spec:
  nodeSelector:
    type: kwok
  tolerations:
  - key: kwok.x-k8s.io/node
    operator: Exists
    effect: NoSchedule
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
EOF
kubectl wait --for=condition=Ready pod/no-toleration -n m4-lab --timeout=60s

[ Expected output ]

pod "no-toleration" deleted from m4-lab namespace
pod/no-toleration created
pod/no-toleration condition met

Check all three Pods.

kubectl get pod too-big wrong-selector no-toleration -n m4-lab -o wide

[ sample output ]

NAME             READY   STATUS    RESTARTS   AGE   IP            NODE
too-big          1/1     Running   0          30s   10.244.8.2    kwok-node-0
wrong-selector   1/1     Running   0          2m    10.244.9.1    kwok-node-1
no-toleration    1/1     Running   0          10s   10.244.10.1   kwok-node-2

The node names may differ. Make sure all three Pods report Running.

PART III - Schedule and Evict a Pod​

Schedule a Pod on a Fake Node​

Lets now give a Pod both the selector and toleration required to use a KWOK node.

cat <<'EOF' | kubectl apply -n m4-lab -f -
apiVersion: v1
kind: Pod
metadata:
  name: on-fake
spec:
  nodeSelector:
    type: kwok
  tolerations:
  - key: kwok.x-k8s.io/node
    operator: Exists
    effect: NoSchedule
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
EOF
kubectl wait --for=condition=Ready pod/on-fake -n m4-lab --timeout=60s

[ Expected output ]

pod/on-fake created
pod/on-fake condition met

Check where it was scheduled.

kubectl get pod on-fake -n m4-lab -o wide

[ sample output ]

NAME      READY   STATUS    RESTARTS   AGE   IP           NODE          NOMINATED NODE   READINESS GATES
on-fake   1/1     Running   0          6s    10.244.8.1   kwok-node-0   <none>           <none>

The node name may differ, but it should begin with kwok-node-.

KWOK reports this Pod as Running. There is no real kubelet or container behind it.

Examine the Default Eviction Tolerations​

Kubernetes adds two tolerations to every Pod. Examine them as,

kubectl get pod on-fake -n m4-lab -o yaml | grep -A2 -e not-ready -e unreachable

[ Expected output ]

    key: node.kubernetes.io/not-ready
    operator: Exists
    tolerationSeconds: 300
--
    key: node.kubernetes.io/unreachable
    operator: Exists
    tolerationSeconds: 300

If a real node becomes NotReady or Unreachable, these tolerations allow the Pod to remain there for 300 seconds. After that, the Taint Manager can evict it.

Trigger an Eviction​

Why this lab uses a custom NoExecute taint

KWOK continuously brings its fake nodes back to the configured healthy state. If you mark a fake node as NotReady, KWOK would reverse the change.

For this lab, you would use a custom NoExecute taint. It goes through the same Taint Manager eviction path without KWOK reversing it.

Find the node running the on-fake Pod and add the taint.

node=$(kubectl get pod on-fake -n m4-lab -o jsonpath='{.spec.nodeName}')
echo "on-fake is on ${node}; tainting it NoExecute"
kubectl taint node "${node}" maintenance=cordon:NoExecute --overwrite

[ sample output ]

on-fake is on kwok-node-0; tainting it NoExecute
node/kwok-node-0 modified

The Pod does not tolerate this taint, so the Taint Manager marks it for deletion. Read the event from the namespace as,

kubectl get events -n m4-lab --field-selector reason=TaintManagerEviction \
  -o custom-columns=REASON:.reason,OBJECT:.involvedObject.name,MESSAGE:.message --no-headers

[ Expected output ]

TaintManagerEviction   on-fake   Marking for deletion Pod m4-lab/on-fake

The Pod may already be deleted by the time you run the command. The namespace event remains available and shows why it was removed.

Validate​

Run the following checks.

kubectl get nodes -l type=kwok --no-headers | wc -l
for pod in too-big wrong-selector no-toleration; do
  printf "%s=" "$pod"
  kubectl get pod "$pod" -n m4-lab -o jsonpath='{.status.phase}{"\n"}'
done
kubectl get events -n m4-lab --field-selector reason=TaintManagerEviction -o jsonpath='{range .items[*]}{.reason}{"\n"}{end}' | head -1

[ Expected output ]

       3
too-big=Running
wrong-selector=Running
no-toleration=Running
TaintManagerEviction

Make sure that:

  • three KWOK nodes are present
  • all three repaired Pods report Running
  • a TaintManagerEviction event exists

Troubleshooting​

Troubleshooting
  • No kwok-node-* nodes are listed — run bash labs/m4/kwok-setup.sh again. Also check that kubectl config current-context reports kind-kubeadv-core.
  • A Pending Pod has no events — wait for a few seconds and describe it again. If the Pod is already running, check whether its resource request, selector or taint was applied correctly.
  • The scheduling message reports 0/2 instead of 0/5 — the three fake nodes are not available. Run the KWOK setup script again.
  • The on-fake Pod remains Pending — check that the fake nodes are Ready. The Pod must have both nodeSelector: type: kwok and the KWOK toleration.
  • The node was tainted but no eviction event appeared — make sure you tainted the same node that was running on-fake. The taint effect must be NoExecute; NoSchedule does not evict a running Pod.
  • The fake node changed back to Ready — this is KWOK reconciling it. Use the custom maintenance=cordon:NoExecute taint from this lab instead of changing the node status.

Cleanup​

Remove the custom taint and delete the lab namespace.

node=$(kubectl get nodes -l type=kwok -o jsonpath='{.items[0].metadata.name}' 2>/dev/null)
[ -n "${node}" ] && kubectl taint node "${node}" maintenance- 2>/dev/null || true
kubectl delete namespace m4-lab --wait=false

[ sample output ]

node/kwok-node-0 untainted
namespace "m4-lab" deleted

Remove the KWOK controller and fake nodes.

bash labs/m4/kwok-teardown.sh

[ Expected output ]

==> Removing fake nodes (kwok-node-*) ...
==> Removing kwok stages + controller + CRDs + RBAC ...
==> Remaining nodes (expect the real 2):
NAME                         STATUS   ROLES           AGE   VERSION
kubeadv-core-control-plane   Ready    control-plane   10h   v1.35.0
kubeadv-core-worker          Ready    <none>          10h   v1.35.0

Confirm that only the two real nodes remain.

kubectl get nodes

[ Expected output ]

NAME                         STATUS   ROLES           AGE   VERSION
kubeadv-core-control-plane   Ready    control-plane   10h   v1.35.0
kubeadv-core-worker          Ready    <none>          10h   v1.35.0

Keep the core-internals cluster running. You are going to use it again in Module 5.

Summary​

In this lab, you created three Pending Pods and read the scheduler's reason for each one. You then fixed the CPU request, added a missing node label and added the required toleration. All three Pods became schedulable.

You also scheduled a Pod on a fake KWOK node and triggered a TaintManagerEviction. In the next module, you are going to extend Kubernetes with CRDs and controllers.
