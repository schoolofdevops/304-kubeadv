Deep Dive - Inside the Scheduler Framework and the Controller Underneath a Controller

This deep dive examines scheduler stages, scheduling gates, priority and preemption, controller workqueues, and node-eviction timing. Use these checks when a Pod remains Pending or a controller appears to stop reconciling.

The cluster from the lab is still running (recreate with bash labs/clusters/core-internals/create.sh if not). This page seeds its own working set: a probe namespace and a couple of small pods: and re-running is safe: every seed goes through kubectl apply, which converges whether or not the lab's teardown removed things. kubectl create namespace m4-deepdive --dry-run=client -o yaml | kubectl apply -f -

PART I - The scheduler framework: reading the pipeline through its decisions​

Think of allocating a room in a hostel. First the warden strikes out every room that simply cannot take you: wrong wing, already full, reserved for staff. That is the filter step: it turns "all rooms" into "rooms that fit". Then, among the ones left, the warden ranks them: this one is closer to the mess, that one already has your batchmates: and picks the best. That is the score step. The Kubernetes scheduler is exactly this two-phase warden, except the phases have names, they are plugins, and each one leaves a fingerprint in the reasons a pod is rejected.

Since Kubernetes 1.19 the scheduler is a framework: one pod's journey from the queue to a node runs through a fixed set of extension points, and at each point a list of plugins runs. The default build ships plugins you already reason about without knowing their names: NodeResourcesFit (the filter that rejects a too-big pod), TaintToleration (the filter that rejects an untolerated pod), NodeAffinity (the filter behind a nodeSelector mismatch), PodTopologySpread, InterPodAffinity. You don't need the scheduler's metrics endpoint to watch these run: the Filter plugins name themselves in the FailedScheduling reason of any pod they reject. Seed a pod that no node can satisfy and read which plugins struck out which node:

kubectl apply -n m4-deepdive -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: filter-probe
spec:
  nodeSelector:
    disktype: nonexistent-ssd
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
EOF
kubectl get events -n m4-deepdive --field-selector involvedObject.name=filter-probe,reason=FailedScheduling -o jsonpath='{range .items[*]}{.message}{"\n"}{end}' | tail -1

[ Expected output ]

0/2 nodes are available: 1 node(s) didn't match Pod's node affinity/selector, 1 node(s) had untolerated taint(s). no new claims to deallocate, preemption: 0/2 nodes are available: 2 Preemption is not helpful for scheduling.

Read that one line as the Filter stage running per node. The worker was struck out by the NodeAffinity plugin: "didn't match Pod's node affinity/selector" is that plugin's exact rejection, because no node carries disktype: nonexistent-ssd. The control-plane was struck out by the TaintToleration plugin: "had untolerated taint(s)", because it carries node-role.kubernetes.io/control-plane:NoSchedule and this pod tolerates nothing. A too-big pod would instead read "Insufficient memory/cpu": that is the NodeResourcesFit plugin. Same pipeline, three different plugins, each announcing itself in plain text. The preemption: clause after the comma is the PostFilter stage reporting it found no victims (section 3 makes it find one).

Why not read the scheduler's own metrics here

The scheduler exposes per-plugin latency at scheduler_framework_extension_point_duration_seconds_count on its own secure port (:10259), not on the API server's /metrics. On kind that port is bound to 127.0.0.1 inside the control-plane container and isn't reachable through kubectl proxy or pod-proxy, so we read the framework through its decisions: the FailedScheduling reasons above: instead. On a cluster where the scheduler's metrics endpoint is reachable (most managed control planes expose it), that metric shows the same pipeline as per-plugin latency counts: one line per extension point (Filter, Score, Bind, …) with how many pods passed through it.

Read the extension points in order and you have the pipeline: PreFilter (compute once what every filter needs), Filter (eliminate nodes that cannot run the pod: the warden striking out rooms, and the stage you just watched name its plugins), PostFilter (only runs when Filter left zero nodes; this is where preemption lives, section 3), PreScore and Score (rank the survivors), Reserve (tentatively claim the node's resources so two pods don't grab the same slot), Permit (the one place a plugin can delay or hold a pod: how gang-scheduling waits for a whole set), and Bind (write the Pod→Node binding to the API server: the only step that changes cluster state). Everything before Bind is deliberation; Bind is the commit.

This is where custom scheduling logic hooks in. A scheduler plugin registers itself at one or more of these points: a custom Filter to keep GPU pods off spot nodes, a custom Score to pack pods for bin-packing instead of spreading them, a Permit plugin to gang-schedule a training job. You build the plugin, compile it into a scheduler binary, and name it in the scheduler's config; the framework runs it at its point alongside the defaults. Clean up the probe before moving on:

kubectl delete pod filter-probe -n m4-deepdive

[ Expected output ]

pod "filter-probe" deleted from m4-deepdive namespace

When you evaluate a third-party scheduler (Volcano, the Kueue scheduler, a bin-packing plugin), this is the honest question to ask its authors: which extension points do you register, and what do you do at each? The answer tells you exactly where in this pipeline their behaviour lands: and a FailedScheduling reason naming an unfamiliar plugin is your first sign a custom Filter is in play.

PART II - Scheduling gates: holding a pod out of the queue entirely​

A Pending pod is a pod the scheduler is actively trying and failing to place: it is in the queue, being rejected every cycle. A scheduling gate is different: it is a pod the scheduler has been told not to look at yet. Think of a flight where you have checked in but the gate hasn't opened: you are a confirmed passenger, you are just not allowed down the jet bridge until someone removes the barrier. A gated pod isn't unschedulable; it is not yet a candidate. It never enters the filter/score pipeline at all, so it costs the scheduler nothing.

This is the mechanism behind quota-gating, sequenced rollouts, and Kueue's job admission: hold the pod as a normal API object, let other controllers do their work, then release it when the precondition is met. Create a pod with a gate:

kubectl apply -n m4-deepdive -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: gated
spec:
  schedulingGates:
  - name: m4-deepdive/ready
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
EOF

[ Expected output ]

pod/gated created

Read its status. It is not Pending in the way a too-big pod is: the phase field shows the gate:

kubectl get pod gated -n m4-deepdive -o jsonpath='{.status.phase}{"  "}{range .status.conditions[*]}{.reason}{" "}{end}{"\n"}'
kubectl get events -n m4-deepdive --field-selector involvedObject.name=gated -o jsonpath='{range .items[*]}{.reason}{"\n"}{end}'

[ Expected output ]

Pending  SchedulingGated

(The second command prints nothing: there are no events for gated at all.) The pod is Pending with the condition reason SchedulingGated, and there is no FailedScheduling event: the lab's Pending pods all had one, because the scheduler tried and failed. This one produced no scheduling event at all, because the scheduler never considered it. That absence is the whole point: a gated pod does not churn the scheduling queue.

Now open the gate. The only way to release a gated pod is to remove entries from spec.schedulingGates: you can delete gates but never add them, so a released pod cannot be re-gated:

kubectl patch pod gated -n m4-deepdive --type merge -p '{"spec":{"schedulingGates":null}}'
kubectl get pod gated -n m4-deepdive -o jsonpath='{.status.phase}{"  node="}{.spec.nodeName}{"\n"}'

[ Expected output ]

Running  node=kubeadv-core-worker

The instant the gate came off, the pod entered the queue, ran the filter/score pipeline from section 1, and bound to the real kind worker. When you debug "why is this Kueue job / Argo workflow pod stuck with no scheduling events," this is the first field to read: spec.schedulingGates tells you a controller is deliberately holding it, and which controller (the gate name is the owner's signature).

PART III - PriorityClass and preemption: who gets evicted to make room​

Under pressure, something has to give: the question is what. Preemption is the scheduler's answer: when a high-priority pod cannot fit, the scheduler is allowed to evict lower-priority pods to make room. Think of an emergency ward. Beds are full, and a critical case arrives. Triage doesn't grow the ward; it moves a stable patient out of a bed so the critical one gets it. PriorityClass is the triage rank stamped on each pod, and PostFilter (section 1) is where the scheduler runs the eviction.

Create two priority classes: a low one for background work and a high one for the workload that must win:

kubectl apply -f - <<'EOF'
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: m4-low
value: 100
globalDefault: false
description: "Preemptible background work"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: m4-high
value: 1000000
globalDefault: false
description: "Critical workload: may preempt m4-low"
EOF

[ Expected output ]

priorityclass.scheduling.k8s.io/m4-low created
priorityclass.scheduling.k8s.io/m4-high created

Now fill the worker node with low-priority pods sized so that a second high-priority pod of the same size cannot fit. Each requests a large slice of memory (the worker has ~8 GiB allocatable), and the deployment scales up until the node is packed. The pods target the worker by hostname: the control-plane is tainted NoSchedule, so a plain pod already avoids it:

kubectl apply -n m4-deepdive -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: filler
spec:
  replicas: 4
  selector:
    matchLabels: {app: filler}
  template:
    metadata:
      labels: {app: filler}
    spec:
      priorityClassName: m4-low
      nodeSelector:
        kubernetes.io/hostname: kubeadv-core-worker
      containers:
      - name: pause
        image: registry.k8s.io/pause:3.9
        resources:
          requests:
            memory: "2Gi"
EOF
kubectl rollout status deploy/filler -n m4-deepdive --timeout=60s
kubectl get pods -n m4-deepdive -l app=filler -o wide

[ Expected output ]

Waiting for deployment "filler" rollout to finish: 3 of 4 updated replicas are available...
NAME                     READY   STATUS    RESTARTS   AGE   IP            NODE                  NOMINATED NODE   READINESS GATES
filler-bf5dd4fff-59z4m   0/1     Pending   0          8s    <none>        <none>                <none>           <none>
filler-bf5dd4fff-bnsbl   1/1     Running   0          8s    10.244.1.10   kubeadv-core-worker   <none>           <none>
filler-bf5dd4fff-ggfwl   1/1     Running   0          8s    10.244.1.8    kubeadv-core-worker   <none>           <none>
filler-bf5dd4fff-ztxjk   1/1     Running   0          8s    10.244.1.9    kubeadv-core-worker   <none>           <none>

Three filler pods are Running (as many as the node's ~8 GiB allows at 2 GiB each) and one is Pending: the node is full. The rollout status command returns non-zero when the 4th replica never becomes available; that is expected here (the node is deliberately packed), so run the get pods line next regardless. Now drop in one high-priority pod that needs a slice the node cannot spare, and watch the scheduler evict a low-priority pod to seat it:

kubectl apply -n m4-deepdive -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: critical
spec:
  priorityClassName: m4-high
  nodeSelector:
    kubernetes.io/hostname: kubeadv-core-worker
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
    resources:
      requests:
        memory: "2Gi"
EOF
kubectl wait --for=condition=Ready pod/critical -n m4-deepdive --timeout=60s
kubectl get events -n m4-deepdive --field-selector reason=Preempted -o jsonpath='{range .items[*]}{.involvedObject.name}{": "}{.message}{"\n"}{end}'

[ Expected output ]

pod/critical condition met
filler-bf5dd4fff-ggfwl: Preempted by pod 0590edfd-7e84-4cad-927e-4ed37631c6a6 on node kubeadv-core-worker

The Preempted event names the victim: a low-priority filler pod the scheduler deleted to seat critical. That is preemption end to end: PostFilter found zero feasible nodes for critical, looked for the smallest set of lower-priority pods whose removal would make room, deleted them, and bound critical. The evicted pod's owner (the Deployment) will try to reschedule it, and it goes Pending because the node is still full: the low-priority work yields to the high-priority work exactly as designed.

Two production rules fall out of this. First, preemptionPolicy: Never on a PriorityClass makes a pod high-priority for queue ordering: it jumps the line: without letting it evict anyone; use it for important-but-not-critical work. Second, priority is cluster-wide leverage, so an unbounded high-priority class is a foot-gun: one team stamping system-cluster-critical on everything can evict another team's workloads at will. This is why priority belongs behind a ResourceQuota (scopeSelector on PriorityClass), and why the two built-in system-*-critical classes sit far above anything you should hand out.

PART IV - The controller underneath a controller​

The node-controller from the lab, the ReplicaSet controller from M1, the Deployment controller: they are not bespoke programs. They are the same skeleton with different logic bolted in, and the skeleton is worth knowing because it explains every "why is it slow / stuck / flapping" you will ever debug. The pattern is a newsroom. An informer is the wire service: it maintains one local, always-current copy of the objects the controller cares about (a shared cache: many controllers read one informer, the way one press pool feeds every desk), so controllers never hammer the API server with polls. When an object changes, the informer drops a key: just the namespace/name, not the object: onto a workqueue. A worker pulls a key, reads the current object from the cache, and reconciles.

Three properties of that workqueue are the whole game. It dedupes: ten changes to one object while it sits in the queue collapse to a single key, so a controller processes an object's latest state once, not ten stale times. It rate-limits: a token-bucket limiter caps how fast keys are handed out, so a controller can't melt the API server. And it backs off: when reconciling a key fails, the key is re-queued with an exponential delay (per-item, so one wedged object doesn't slow the healthy ones), which is why a broken reconcile retries slowly instead of hot-looping. You can see these queues live: the API server runs its own informer→workqueue controllers (aggregation, CRD naming, availability), and exposes their metrics on /metrics. Depth is how many keys are waiting; a depth that climbs and never drains is the signature of a controller falling behind:

kubectl get --raw /metrics | grep '^workqueue_depth' | head
kubectl get --raw /metrics | grep 'workqueue_adds_total' | sort -t' ' -k2 -rn | head -5

[ Expected output ]

workqueue_depth{name="APIServiceRegistrationController"} 0
workqueue_depth{name="DiscoveryController"} 0
workqueue_depth{name="DynamicCABundle-aggregator-proxy-cert"} 0
workqueue_depth{name="DynamicCABundle-client-ca-bundle"} 0
workqueue_depth{name="DynamicCABundle-request-header"} 0
workqueue_depth{name="DynamicCABundle-serving-cert"} 0
workqueue_depth{name="DynamicClientCertificate"} 0
workqueue_depth{name="DynamicServingCertificateController"} 0
workqueue_adds_total{name="open_api_v3_aggregation_controller"} 13618
workqueue_adds_total{name="RemoteAvailabilityController"} 3366
workqueue_adds_total{name="LocalAvailabilityController"} 3366
workqueue_adds_total{name="crd_naming_condition_controller"} 718
workqueue_adds_total{name="autoregister"} 693

Each name="..." is one controller's queue: here the API server's own APIServiceRegistrationController, open_api_v3_aggregation_controller, and so on, each an informer→workqueue loop inside the kube-apiserver process (the kube-controller-manager runs the same pattern for node_lifecycle_controller and friends, on its own metrics port). Every depth reads 0: the queues are drained, the healthy steady state. adds_total is lifetime work done; a depth near zero with a high, still-rising adds is a controller keeping up. A depth that climbs and stays up is the one to page on.

And the reason exactly one instance of all this runs: no split brain, no two node-controllers fighting over the same node: is the same leader-election Lease you watched heartbeat in the M1 deep dive. That mechanism isn't only for the controller-manager; the scheduler holds one too. Read it:

kubectl get lease -n kube-system kube-scheduler -o jsonpath='holder={.spec.holderIdentity}{"  renew="}{.spec.renewTime}{"  duration="}{.spec.leaseDurationSeconds}s{"\n"}'

[ Expected output ]

holder=kubeadv-core-control-plane_c5ae4b3b-d850-4f21-acbe-baf19339297b  renew=2026-07-19T03:06:26.887487Z  duration=15s

holderIdentity is the live scheduler; renewTime is its heartbeat. If it goes stale past leaseDurationSeconds, nothing schedules until another instance grabs the lease: which is why, during a control-plane incident, "pods are Pending and no FailedScheduling events are appearing" points you at the scheduler's Lease before anything else. The controller machinery and the scheduler are the same skeleton: informer, queue, workers, and one Lease deciding who is allowed to drive.

PART V - Node-controller eviction timing: the clock behind the eviction​

In the lab you flipped a node to NotReady and watched its pods get evicted. That eviction was not instant, and the delay is not arbitrary: it is a two-stage clock, and knowing both stages is the difference between "the cluster is broken" and "the cluster is behaving exactly as configured, wait 40 more seconds." Think of a fire drill with a grace period: the alarm sounds (the node stops reporting), but the building isn't cleared the instant it sounds: there is a fixed grace window to confirm it's real, and only then does evacuation begin, and even then some people (with a pass) are allowed to stay longer.

Stage one is the node-monitor-grace-period: the node-controller waits this long (default ~40s) after a node stops renewing its heartbeat before it declares the node unhealthy and stamps a taint on it: node.kubernetes.io/not-ready or node.kubernetes.io/unreachable. Stage two is tolerationSeconds: once the taint is on the node, each pod is evicted only after its own toleration for that taint expires. And here is the part most operators never see: the API server injects those tolerations onto every pod automatically. Read them on the pod you scheduled in section 2:

kubectl get pod gated -n m4-deepdive -o yaml | grep -A8 'tolerations:'

[ Expected output ]

  tolerations:
  - effect: NoExecute
    key: node.kubernetes.io/not-ready
    operator: Exists
    tolerationSeconds: 300
  - effect: NoExecute
    key: node.kubernetes.io/unreachable
    operator: Exists
    tolerationSeconds: 300

You never wrote those tolerations. The admission plugin DefaultTolerationSeconds added them: node.kubernetes.io/not-ready and node.kubernetes.io/unreachable, each with tolerationSeconds: 300. That 300 is the second clock: a pod tolerates its node being unreachable for five minutes before the node-controller evicts it. So the full timeline after a node goes silent is: ~40s of grace before the taint appears, then 300s of toleration before the pod is deleted: roughly five and a half minutes end to end, by default, before a pod on a dead node is rescheduled elsewhere.

That default is tuned for a node blipping, not for a workload that must fail over fast. When you run a latency-sensitive service, you shorten its own toleration: set tolerationSeconds: 30 on the not-ready/unreachable tolerations in the pod spec, and it fails over in half a minute instead of five. When you run a batch job that survives a flaky node, you lengthen it to avoid needless churn. The knob is per-pod, it's in the spec you can read above, and it is the honest answer to "why did it take so long for pods to move off the dead node": the cluster was counting down two clocks you can see and change.

Summary​

Where you will use this
  • The scheduler is a framework of named extension points: PreFilter, Filter, PostFilter, Score, Reserve, Permit, Bind: and its Filter plugins name themselves in FailedScheduling reasons (NodeAffinity → "didn't match node affinity/selector", TaintToleration → "untolerated taint", NodeResourcesFit → "Insufficient memory"). Use it when: a pod won't schedule: read the reason to see which plugin rejected which node; and when evaluating a custom or third-party scheduler (Volcano, Kueue, a bin-packer), ask which extension points it registers. Where the scheduler's own metrics endpoint is reachable, scheduler_framework_extension_point_duration_seconds_count shows per-plugin latency (not reachable on kind: its scheduler binds :10259 to localhost).
  • A scheduling gate holds a pod out of the queue entirely: SchedulingGated phase, no FailedScheduling event: and only removing gates releases it. Use it when: a Kueue/Argo pod is stuck with no scheduling events at all; read spec.schedulingGates to see which controller is deliberately holding it, rather than hunting for a scheduling failure that isn't there.
  • Preemption evicts lower-priority pods to seat a higher-priority one via PostFilter, and the Preempted event names the victim. Use it when: a critical workload must win under node pressure (set a high PriorityClass), or when a team's pods are being evicted mysteriously: read the Preempted events and audit who is handing out high priority (put it behind a ResourceQuota).
  • Every controller is informer → workqueue → rate-limiter → backoff, with one leader-election Lease deciding who drives. Use it when: a controller seems stuck: workqueue_depth that climbs and never drains means it's falling behind, and a stale scheduler/controller-manager Lease means nothing is driving at all; thirty seconds of metric + lease reading tells you which.
  • Node eviction is a two-stage clock: ~40s node-monitor-grace before the taint, then per-pod tolerationSeconds (default 300s, injected by admission) before eviction. Use it when: pods took "too long" to move off a dead node (they didn't: read the two clocks), or a latency-sensitive service must fail over fast (set tolerationSeconds: 30 on its not-ready/unreachable tolerations).
