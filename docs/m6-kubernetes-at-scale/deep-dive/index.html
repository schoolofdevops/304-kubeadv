Deep Dive - Reading the Control Plane at Scale: Histograms, Pagination, and APF

This deep dive reads API-server histograms, pagination tokens, watch-cache behavior, APF state, and etcd object counts. Use these signals to locate the scale limit before increasing cluster size or request volume.

▶ M6: Kubernetes at Scale Deep DiveOpen fullscreen ↗

Run everything from the repo root against the kwok-scale cluster from the lab (still up, or recreate with bash labs/clusters/kwok-scale/create.sh then bash labs/clusters/kwok-scale/grow.sh 1000 5000).

Where this picks up

You need the scale cluster with some pods on it. If the lab tore it down, bring it back and put ~5,000 pods on ~1,000 nodes: enough to see every effect below without stressing the machine:

export KUBECONFIG=/tmp/m6.kubeconfig
bash labs/clusters/kwok-scale/create.sh
bash labs/clusters/kwok-scale/grow.sh 1000 5000

[ Expected output ]

kwok-scale profile ready
Grow complete: 1000 nodes, 5000 pods requested

PART I - Reading the latency histogram for a real percentile​

apiserver_request_duration_seconds is a histogram: not an average, but a set of cumulative buckets. Each _bucket{le="X"} counts requests that finished in ≤ X seconds. To get a percentile you find the bucket where the count crosses that fraction of the total. Read the buckets for a cluster-scope LIST of pods:

kubectl get --raw /metrics \
  | grep 'apiserver_request_duration_seconds_bucket.*resource="pods",scope="cluster",subresource="",verb="LIST"' \
  | grep -E 'le="(0.5|1|2|4|8|+Inf)"'

[ Expected output ]

apiserver_request_duration_seconds_bucket{...verb="LIST",...,le="0.5"} 1144
apiserver_request_duration_seconds_bucket{...verb="LIST",...,le="1"} 1144
apiserver_request_duration_seconds_bucket{...verb="LIST",...,le="2"} 1144
apiserver_request_duration_seconds_bucket{...verb="LIST",...,le="4"} 1144
apiserver_request_duration_seconds_bucket{...verb="LIST",...,le="+Inf"} 1144

Every bucket holds the same count (1144): meaning all those LISTs finished in under half a second, server-side. The p99 is < 0.5s. This is the number that stays green while the client waits seconds: the histogram measures how long the API server spent handling the request, which is cheap because it serves from the watch cache. The lesson from the lab, stated in metrics: apiserver_request_duration is necessary but not sufficient: pair it with response size and client latency, or the knee hides.

The bucket-math shortcut

To estimate p99 by hand: total = the +Inf count; find 0.99 × total; the smallest le whose bucket count ≥ that value is your p99 bucket. Prometheus' histogram_quantile(0.99, ...) does exactly this, interpolating within the bucket. Here 0.99 × 1144 ≈ 1133, and the le="0.5" bucket already holds 1144: so p99 ≤ 0.5s.

PART II - Pagination: the continue token is a cursor into etcd​

--chunk-size (the limit API parameter) returns a page plus a continue token; the next request hands that token back to resume. The token is not opaque magic: it encodes the etcd revision the list is reading at plus the key to resume after, so pagination stays consistent even as the cluster changes. See it:

kubectl get pods -A --chunk-size=500 -o json \
  | python3 -c 'import sys,json; d=json.load(sys.stdin); print("returned:", len(d["items"])); print("continue token (first 60):", d["metadata"].get("continue","<none>")[:60])'

[ Expected output ]

returned: 500
continue token (first 60): eyJ2IjoibWV0YS5rOHMuaW8vdjEiLCJydiI6M...

The response holds only 500 pods and a continue token. That token pins the read to a single etcd revision, so paging through 5,000 pods gives you a consistent snapshot, not a smear of five different moments. The API server never materialises all 5,000 at once: it walks etcd 500 keys at a time. That is the memory protection chunking buys, spelled out: bounded server-side allocation per request, at the cost of more round trips.

PART III - The watch cache and resourceVersion=0​

Why is a full LIST cheap server-side even at scale? Because the API server keeps a watch cache: an in-memory mirror of recent object state per resource: and serves most reads from it instead of hitting etcd. A list with resourceVersion=0 explicitly says "cache is fine, I don't need the very latest," and is served entirely from memory:

# cache-served (resourceVersion=0): the API server answers from its watch cache
time kubectl get pods -A -o name --raw '/api/v1/pods?resourceVersion=0&limit=500' >/dev/null 2>&1 \
  || time kubectl get --raw '/api/v1/pods?resourceVersion=0&limit=500' >/dev/null

[ Expected output ]

real    0m0.0XXs

A resourceVersion=0 read never touches etcd: it is the cheapest possible list, and it is what informers use on startup. A read without it (the default for a strongly-consistent list) can require a quorum read from etcd, which is more expensive. This is the knob behind "list from cache" versus "list from etcd," and why controllers are careful to prime from the cache. Callback to M3: every read that reaches etcd competes for the same backend as every write.

PART IV - The etcd object board: what actually fills the store​

etcd size is driven by object count × size × churn, not node count. apiserver_storage_objects is the per-kind inventory: the board you watch to predict etcd pressure:

kubectl get --raw /metrics | grep '^apiserver_storage_objects{' \
  | sort -t' ' -k2 -rn | head -6

[ Expected output ]

apiserver_storage_objects{resource="events"} 5983
apiserver_storage_objects{resource="pods"} 5000
apiserver_storage_objects{resource="leases.coordination.k8s.io"} 1003
apiserver_storage_objects{resource="nodes"} 1000
...

Two things to read here. First, leases track nodes: every node renews a Lease heartbeat (M1), so 1,000 nodes means 1,003 leases churning every few seconds; at 10,000 nodes that lease write rate alone is significant, which is why node-heartbeat frequency is a real scale tuning knob. Second, events lead the board: high-churn, and by default in the same etcd as everything else. This is the metric that would have warned OpenAI before events overwhelmed etcd; watching it is how you catch the problem while it is still a graph and not an outage.

PART V - API Priority and Fairness at scale​

When expensive lists flood in, something must protect the cheap-but-critical traffic: health checks, leader-election, node heartbeats. That is API Priority and Fairness (M2), and at scale it is load-bearing. It sorts requests into priority levels, each with a share of concurrency (seats); a flood in one level cannot starve another. Look at the levels and their configured shares:

kubectl get prioritylevelconfigurations

[ Expected output ]

NAME              TYPE      NOMINALCONCURRENCYSHARES   QUEUES   HANDSIZE   QUEUELENGTHLIMIT
catch-all         Limited   5                          <none>   <none>     <none>
exempt            Exempt    <none>                     <none>   <none>     <none>
global-default    Limited   20                         128      6          50
leader-election   Limited   10                         16       4          50
node-high         Limited   40                         64       6          50
system            Limited   30                         64       6          50
workload-high     Limited   40                         128      6          50
workload-low      Limited   9                          128      6          50

Read the design: leader-election and node-high get their own guaranteed shares, so a storm of workload-low list requests can be queued or rejected (HTTP 429, "APF is protecting the cluster") without taking down leader election or node heartbeats. On a large cluster this is what keeps a single misbehaving controller from cascading into a control-plane outage. The apiserver_flowcontrol_* metrics (rejected requests, request wait time per level) are where you confirm APF is shedding load rather than the API server falling over.

PART VI - EndpointSlices: sharding the write storm​

One more scale failure mode worth naming, because it is invisible until it bites. A Service with N backing pods once maintained a single Endpoints object listing all N. Every time one pod changed, that entire object was rewritten and pushed to every kube-proxy watching it: an O(N) write and fan-out on every single pod churn. At thousands of endpoints this is a write storm that hammers etcd and every node at once.

EndpointSlices fix it by sharding that list into slices of ~100 endpoints each. A pod change rewrites one slice, not the whole set: O(100) instead of O(N), and only the watchers of that slice get the update. This is why EndpointSlices are the default and why large Services depend on them. You can see the slices for any Service with kubectl get endpointslices. The transferable principle is the same one behind pagination and watch: bound the size of the thing that changes, so churn cost stays flat as the cluster grows.

PART VII - When one control plane isn't enough​

Everything above pushes a single control plane further up its curve. Past a point, the answer is not to push harder but to scale out. Three patterns, in rising order of isolation:

  • Cells: partition one logical platform into multiple independent control planes ("cells"), each holding a bounded slice of the workload, with a routing layer above. A cell's blast radius and scale limit are bounded by design.
  • Sharding: split by dimension (namespace, tenant, region) across control planes so no single etcd holds everything.
  • Multi-cluster: separate clusters federated at the application layer, trading cross-cluster complexity for hard isolation.

Google's framing ties it together: scalability is a set of SLOs (for example, 99% of API calls fast) measured across many dimensions at once, guaranteed on a given hardware and configuration. Your cluster's real limit is where your SLOs break: and the engineering discipline is to watch the metrics in this deep dive so you see the knee coming and choose "scale out" deliberately, rather than discovering it during an incident.

Teardown​

Where you will use this
  • Use histograms when an average looks healthy but users report slow tail requests.
  • Use pagination and selectors in controllers, inventory jobs, and platform APIs that must list large collections.
  • Use watch-cache and resourceVersion evidence to separate freshness requirements from avoidable etcd reads.
  • Use APF metrics to prove whether Kubernetes is protecting critical traffic or the API server is genuinely saturated.
  • Move to cells or multi-cluster when blast radius and recovery objectives matter more than squeezing more objects into one control plane.

The production rule is simple: measure the knee under your real object and churn profile, then operate with headroom. Do not use a vendor's maximum as your normal load.

bash labs/clusters/kwok-scale/teardown.sh

[ Expected output ]

==> Deleting kwokctl cluster 'kwok-scale' ...
==> Recreating the persistent core-internals cluster (idempotent, ~40s) ...
==> Done. kwok-scale gone; core-internals is back for the next module.

You can now read a control plane the way its own operators do: a histogram for real percentiles, a continue token as an etcd cursor, resourceVersion=0 as the cache path, the object board as the etcd forecast, APF as the load shield, and EndpointSlices as churn control: the exact instruments behind running Kubernetes at tens of thousands of nodes.
