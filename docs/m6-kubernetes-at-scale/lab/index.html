Finding the Kubernetes Control-Plane Limit

Before you start

New here? Complete the Setup section first.

All commands below run from the root of the lab repo (304-labs/). This module uses a dedicated kwok-scale cluster.

The teardown recreates the core-internals cluster for the next module.

In this lab, you are going to create a Kubernetes control plane with thousands of fake Nodes and Pods.

You would then measure how a cluster-wide list changes as the number of objects increases.

By the end of this lab, you will:

  • create a scale-testing cluster with kwokctl
  • grow it to 1,000 nodes and about 10,000 Pods
  • compare client delay, payload size and API server latency
  • test selectors, pagination and watches as scale controls

Pre Requisites​

Check that kwokctl v0.8.0 is installed.

kwokctl --version

[ sample output ]

kwokctl version v0.8.0

This lab uses more memory as the Pod count grows. Close other heavy applications before continuing.

PART I - Create the Scale Cluster​

Create the kwok-scale Cluster​

kwokctl creates a real control plane and represents Nodes and Pods as API objects.

This allows you to test the API server and etcd without running thousands of kubelets and containers.

Create the cluster as,

bash labs/clusters/kwok-scale/create.sh

[ Expected output ]

==> Creating kwokctl cluster 'kwok-scale' (docker runtime) ...
==> Waiting for the API server to answer /healthz ...
==> API server healthy.

kwok-scale ready — a full control plane with ZERO nodes yet.
Grow it:   bash grow.sh <nodes> [pods]      e.g. bash grow.sh 1000 10000
Context:   kwok-kwok-scale   (KUBECONFIG=/tmp/m6.kubeconfig)

The profile writes a separate kubeconfig at /tmp/m6.kubeconfig. Export it and switch to the new context.

export KUBECONFIG=/tmp/m6.kubeconfig
kubectl config use-context kwok-kwok-scale
kubectl get nodes

[ Expected output ]

Switched to context "kwok-kwok-scale".
No resources found

The control plane is running without any Nodes. You are going to add the fake Nodes next.

Add One Thousand Nodes​

Grow the cluster to 1,000 fake Nodes.

bash labs/clusters/kwok-scale/grow.sh 1000

[ sample output ]

==> Scaling to 1000 fake node(s) ...

===================== control-plane snapshot =====================
nodes (Ready):   1000
pods (all ns):   0
--- objects in etcd (apiserver_storage_objects, top 5) ---
{resource="leases.coordination.k8s.io"} 1003
{resource="nodes"} 1000
{resource="clusterroles.rbac.authorization.k8s.io"} 69
...
--- inflight requests ---
apiserver_current_inflight_requests{request_kind="mutating"} 1
apiserver_current_inflight_requests{request_kind="readOnly"} 1
--- full unpaginated `get pods -A` wall-clock (what a controller feels) ---
  wall-clock: 0.08s   payload: 0.0 MB

Make sure the snapshot reports 1,000 Ready Nodes. Also examine the Lease count. Each Node adds a Lease used for its heartbeat.

The Pod list is still fast because there are no Pods in the cluster.

PART II - Find the Control-Plane Limit​

Grow the Pod Count​

Add Pods in three stages. Run each command separately and record the wall-clock value printed by the snapshot.

bash labs/clusters/kwok-scale/grow.sh 1000 1000
bash labs/clusters/kwok-scale/grow.sh 1000 5000
bash labs/clusters/kwok-scale/grow.sh 1000 10000

[ sample output ]

# after grow.sh 1000 1000
  wall-clock: 0.53s   payload: 6.3 MB
# after grow.sh 1000 5000
  wall-clock: 2.22s   payload: 31.0 MB
# after grow.sh 1000 10000
  wall-clock: 4.85s   payload: 62.0 MB

Compare the results.

podsfull get pods -A
0~0.08s
1,000~0.5s
5,000~2.2s
10,000~4.9s

The full list becomes slower as the Pod count grows. The exact timings depend on your machine.

The point where latency starts increasing sharply is the control-plane knee for this environment.

kwokctl scale pod is slow at large N

Each fake Pod is created and bound by the real scheduler. Creating 10,000 Pods may take a few minutes. Do not increase the lab to 20,000 Pods.

Compare Client and Server Time​

At about 10,000 Pods, measure the client time, payload size and API server latency for a cluster-wide list.

# client wall-clock + payload size of one unpaginated list
time kubectl get pods -A -o json | wc -c
# now ask the API server how long IT thinks that list took (server-side, from its histogram):
kubectl get --raw /metrics \
  | grep 'apiserver_request_duration_seconds_sum.*resource="pods",scope="cluster",subresource="",verb="LIST"'
kubectl get --raw /metrics \
  | grep 'apiserver_request_duration_seconds_count.*resource="pods",scope="cluster",subresource="",verb="LIST"'

[ sample output ]

71468say   68624119     # ~68 MB of JSON, and the client...
kubectl get pods -A -o json  0.9s user  0.2s system   ... 7.28s total
apiserver_request_duration_seconds_sum{...resource="pods",scope="cluster",...,verb="LIST",...} 17.89
apiserver_request_duration_seconds_count{...resource="pods",scope="cluster",...,verb="LIST",...} 1144

Compare the three values.

  • The client waited about seven seconds.
  • The response contained about 68 MB of JSON.
  • The server-side average was 17.89 / 1144, or about 16 milliseconds.

The client delay is mainly the cost of transferring and processing the large response. The API server metric alone does not show this client-side cost.

A controller which performs an unbounded LIST during every reconciliation would repeatedly pay this cost.

Open the Scale View​

Start Cluster X-Ray against the scale cluster.

bash labs/tools/xray/serve.sh

[ Expected output ]

│  context : kwok-kwok-scale
│  open    : http://127.0.0.1:8001/xray/
│  Ctrl-C stops the proxy. Port busy? PORT=8002 bash serve.sh

Open http://127.0.0.1:8001/xray/ and select the Scale tab.

Your values may differ, but the view should show the Node and Pod counts, API server load and the estimated payload for a cluster-wide Pod list.

  • Cluster size shows the object count for each resource stored in etcd.
  • API server load shows inflight requests, request rate and server-side list latency.
  • Read amplification estimates the payload of a full Pod list and shows the open watch count.

Keep this view open while testing the scale controls.

PART III - Test the Scale Controls​

Filter, Page and Watch​

Lets now compare a field selector, pagination and a watch.

First, use a field selector to list Pods assigned to one Node.

kubectl get nodes -o name | head -1     # pick a node name, e.g. node-000000
time kubectl get pods -A --field-selector spec.nodeName=node-000000 -o name | wc -l

[ sample output ]

node/node-000000
...
0.10s total

The API server returns only the Pods assigned to the selected Node. This reduces the response size and client time.

Next, request the same list in chunks of 500 objects.

time kubectl get pods -A -o name --chunk-size=500 >/dev/null

[ sample output ]

6.02s total

The total time may be similar because the client still receives every object. Pagination limits the size of each response and reduces the memory required for one request.

A watch performs one initial list and then receives only changes. Controllers use this list-and-watch pattern instead of repeatedly listing every object.

Compare Events, Pods and Nodes​

Compare the number of Events, Pods and Nodes.

kubectl get --raw /metrics | grep -E '^apiserver_storage_objects\{resource="(events|pods|nodes)"\}'

[ sample output ]

apiserver_storage_objects{resource="events"} 11983
apiserver_storage_objects{resource="pods"} 10981
apiserver_storage_objects{resource="nodes"} 1000

The Event count may be higher than the Pod count. Events are short-lived, high-churn objects stored in etcd by default.

Large clusters can use a separate etcd backend for Events so that Event traffic does not compete with workload state.

Validate​

kubectl get --raw /metrics | grep '^apiserver_storage_objects{resource="pods"}'
kubectl get --raw /metrics | grep '^apiserver_current_inflight_requests'

[ sample output ]

apiserver_storage_objects{resource="pods"} 10981
apiserver_current_inflight_requests{request_kind="mutating"} 2
apiserver_current_inflight_requests{request_kind="readOnly"} 1

Make sure that the Pod count is close to 10,000 and that the API server reports both read-only and mutating inflight requests.

Your measurements should also show the difference between client time, response size and server-side request latency.

Troubleshooting
  • kwokctl: command not found — install kwokctl v0.8.0 and run the prerequisite check again.
  • The API server returns errors at a high Pod count — scale back to 5,000 Pods or close other applications to free memory.
  • Pod creation appears to stop — check the current count with kubectl get --raw /metrics | grep 'storage_objects{resource="pods"}'. Creating and binding thousands of Pods takes time.
  • Your timings do not match the sample — the timings depend on available CPU, memory and storage. Compare the change as the object count increases.

Teardown​

Delete the scale cluster and recreate the persistent core-internals cluster.

bash labs/clusters/kwok-scale/teardown.sh

[ Expected output ]

==> Deleting kwokctl cluster 'kwok-scale' ...
==> Recreating the persistent core-internals cluster (idempotent, ~40s) ...
 ✓ Cluster "kubeadv-core" is ready
==> Done. kwok-scale gone; core-internals is back for the next module.

The kwok-scale cluster and all its fake objects are now removed. Keep the recreated core-internals cluster for Module 7.

Summary​

In this lab, you grew a Kubernetes control plane to 1,000 Nodes and about 10,000 Pods.

You observed how a cluster-wide list became slower because of response size and client-side processing.

You also tested field selectors, pagination and watches. In the next module, you are going to examine Kubernetes networking with Cilium and Hubble.
