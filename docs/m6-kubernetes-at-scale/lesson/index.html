Kubernetes at scale: OpenAI and GKE engineering lessons

So far, we have looked at one control-plane component at a time. In this module, we will look at what happens when all those components work together in a large cluster.

Why should you care about this? Imagine that every node is Ready and the existing Pods are running. But kubectl get pods -A takes several seconds. A controller is falling behind. Events arrive late. Your automation starts timing out.

The nodes look healthy, but the cluster feels slow.

Adding more nodes may make this worse. Every new node adds Leases, status updates, Pods, watches, and endpoint changes. All this work reaches the same shared control-plane services.

This module will help you answer a practical question:

When a large cluster becomes slow, which part of the request path is paying the cost?

You will study the scale limit, find the point where performance starts getting much worse, and compare client-side time with API-server time. You will then apply lessons from OpenAI and Google GKE to define a safe production limit for your own cluster.

Lesson 1: Why healthy nodes can still produce a slow cluster​

When a cluster becomes slow, many teams start with the worker nodes. That is useful when Pods are failing because of CPU, memory, disk, or network problems. But node health does not explain every control-plane slowdown.

Start by checking where the delay appears:

  • If Pod lists are slow but Secret reads are normal, the Pod count or response size may be the problem.
  • If writes across many resource types slow down together, check admission, API Priority and Fairness, and etcd.
  • If only one controller is falling behind, inspect that controller's Kubernetes client, cache, and work queue before scaling the control plane.

Build a timeline across the full request path. Compare the user's total wait time with API-server latency, response size, inflight requests, APF queueing, etcd commit latency, controller queue age, and client CPU and memory.

A green API-server dashboard does not prove that the complete request was fast.

Lesson 2: The Kubernetes scalability envelope​

The booking counter, not the trains​

Let's use an Indian Railways example during festival season.

The trains may be running normally. There may also be enough coaches and seats. But the reservation system can still become slow because thousands of people are checking and changing bookings at the same time.

The trains are like Kubernetes nodes. The booking counters are like API servers. The central reservation database is like etcd.

Adding more trains does not reduce the queue at the booking counter. In the same way, adding worker nodes does not repair an overloaded control plane.

Every kubelet renews Leases and reports status. Every controller reads and writes objects. Every kubectl command and automation client enters through the API server. The API server then uses its caches and etcd.

Scale is more than node count​

Node count alone is a poor scale target.

One cluster may have many mostly empty nodes. Another may have fewer nodes but hundreds of thousands of Pods, Services, Secrets, ConfigMaps, and EndpointSlices. A third may have a smaller object count but may create and delete objects very quickly.

Watch clients add another limit. Ten thousand objects watched by five clients create a very different workload from the same objects watched by five hundred clients. Each long-running client may keep its own informer cache and process every change.

Your scalability envelope therefore includes:

  • node, Pod, Service, Secret, and ConfigMap counts;
  • total objects stored in etcd;
  • object create, update, and delete rates;
  • watch clients, reconnects, and relists;
  • API payload size and request rate;
  • controller convergence time;
  • etcd storage and disk latency;
  • the CPU, memory, disk, and network available to the control plane.

Let's say two clusters both have 5,000 nodes. The first runs a small number of stable system Pods. The second runs short jobs that create and delete hundreds of thousands of Pods and Events every hour. The node count is the same, but the API-server and etcd workload is not.

This is why capacity reviews must include both counts and rates. Measure how much state exists and how quickly that state changes.

Lesson 3: Finding the scale knee before production finds it​

A full list looks harmless in a small cluster. The same request can become a large network and memory operation after the object count grows.

The following results came from a live KWOK scale experiment:

PodsFull kubectl get pods -A
0about 0.08 seconds
1,000about 0.53 seconds
5,000about 2.2 seconds
10,000about 4.85 seconds
around 20,000unusable in that environment

For some time, the cost grows in a way that looks manageable. Then a small increase in object count causes a much larger delay. This bend in the curve is called the knee.

The exact numbers belong to that laptop, Kubernetes version, payload, and configuration. Your numbers will be different. The curve pattern is what matters.

Do not use the failure point as your production limit. Define a safe limit below the knee. Keep enough room for traffic bursts, upgrades, incident commands, controller restarts, and cache rebuilds.

Use the simulator above to increase the Pod count. Watch the client latency and response payload grow. Also notice that the API server's own latency can remain low.

Test steady state and recovery​

A steady cluster may look healthy even when recovery is unsafe. A controller restart may force it to rebuild a large informer cache. If several controllers restart together, they may all issue large list requests at the same time.

Test both conditions:

  1. Increase one scale dimension while keeping the workload profile constant.
  2. Record client wall time, response bytes, server duration, memory, queue depth, and error rate.
  3. Restart a representative controller or force an informer cache rebuild.
  4. Check whether the cluster returns to steady state within your service-level objective (SLO).

Repeat this test after a Kubernetes upgrade, a major admission change, a new API extension, or the onboarding of a large tenant. The knee can move.

Lesson 4: When the API server is fast but the client is slow​

If a kubectl list takes seven seconds, most teams open the API-server latency dashboard. But what if that dashboard says the server completed its work in less than one tenth of a second?

At roughly 11,000 Pods in the measured experiment, the numbers looked like this:

MeasurementResult
Client wall time7.28 seconds
Response payloadabout 68 MB
API-server handling timeabout 0.093 seconds

The API server returned the data quickly from its available read path. Most of the remaining time was spent transferring the response, decoding JSON, allocating objects, and formatting or caching the result on the client.

This also affects controllers. A controller that performs an unbounded list during every reconcile can repeatedly download and decode the complete collection. The API-server duration may look healthy while the controller uses more CPU and memory and keeps falling behind.

Measure both ends of the request

Record the verb, resource, selector scope, returned item count, response size, server duration, and total client time. For a controller, also inspect its CPU, memory, garbage collection, queue age, watch reconnects, and relists.

A log line that says reconcile took 8s is not enough. You need to know how much of that time was spent waiting for and decoding Kubernetes API data.

Do not solve this only by increasing client timeouts. A longer timeout allows the same unbounded request to run for longer.

Ask for less data:

  • Use a label or field selector when the client needs only a subset.
  • Use pagination when the client must read a large collection.
  • For a long-running client, build the initial state and then watch changes.

The API server's compute time is only one part of API performance. Payload transfer and client work can create the delay that the user sees.

Lesson 5: What breaks first at Kubernetes scale​

Scale problems usually come from familiar Kubernetes mechanisms handling much more work. The useful question is: which mechanism is paying the cost first?

etcd​

etcd may show a growing database, slower WAL fsync, slower backend commits, or delayed proposals. This is the Module 3 storage path under higher object count and churn.

Keep etcd on predictable, low-latency storage. Measure database growth and write rate. Do not raise the quota before you understand which resource is creating the growth.

API server and clients​

The API server may face broad lists, cache memory pressure, and too many inflight requests. Clients may receive large responses and rebuild large caches.

API Priority and Fairness can queue or reject expensive traffic to protect important requests. But APF cannot make an unbounded list cheap. It controls which request waits. You still need to fix the client access pattern.

Events​

Events are short-lived, but every Event is still an API write, an etcd revision, a stored object, a watch notification, and a later delete.

In the live cluster used for this module, there were 11,983 Events and 10,981 Pods. Events outnumbered the workload objects.

During a failure, the system may create Events even faster while the control plane is already busy. OpenAI separated Events into another etcd cluster at very large scale so Event churn could not slow down the store holding critical workload state.

Do not copy this design automatically. First measure the Event write rate, storage-object count, etcd growth, and watch traffic. Separate Events only when this lower-value, high-churn data threatens the primary source of truth.

Endpoint updates​

The old Endpoints API stored all backend addresses for a Service in one large object. A Pod change could rewrite that large object.

EndpointSlices divide the backend set into smaller objects. One Pod change can update one smaller slice instead of one very large Endpoints object.

Filter, page, and watch​

Read amplification happens when one client repeatedly reads far more data than it needs. Use these three controls to reduce it:

  1. Filter when the client needs only a subset. Selectors reduce objects and bytes at the source.
  2. Page when the client must traverse a large collection. Pagination limits the peak memory and response size for each request.
  3. Watch when the client needs continuous state. Build an initial view, then receive changes instead of listing everything again.

Pagination may not reduce the total bytes or total wall time. Its main benefit is that the server and client can process smaller pages instead of holding one giant response.

For controller code, use shared informers when several controllers in one process need the same resource. They can share one watch and one local cache. Scope watches by namespace, label, or field where possible. Avoid creating one broad informer for every tenant.

The production rule is simple: do not list everything when a selector will do. Do not poll when a watch will do. Page the large collections that you truly need.

Lesson 6: Lessons from OpenAI, GKE, and the M6 scale lab​

Large-cluster case studies are useful when you take the operating principle, not only the headline number.

OpenAI: about 7,500 nodes​

OpenAI's experience reinforces three practices:

  • Give etcd predictable resources and tune it for the real workload.
  • Separate high-churn Events when they threaten critical state.
  • Find and remove unbounded lists from clients and controllers.

These are not special fixes available only to one company. They are the same storage, API, and client behaviors covered in this course.

The important point is to measure the workload profile. Object count, Event rate, list payload, watch fan-out, and churn explain more than node count alone.

GKE: scale is an SLO, not a node headline​

Google's published limits show what can be achieved with different hardware, control-plane design, and testing.

The useful target is not simply "65,000 nodes." The useful target is the service-level objective that remains true at that scale. API calls must return within the target latency. Scheduling must remain timely. Controllers must converge. Errors must stay within budget.

Your cluster has different admission webhooks, operators, CRDs, client code, workload churn, and infrastructure. You must prove its safe limit against its own SLOs.

Use p50, p95, and p99. Measure watch delivery and controller convergence, not only average request latency. An average can look healthy while the slowest requests are already breaking automation.

When one control plane is no longer enough​

Some limits should be solved with more control planes instead of one larger control plane.

  • Cells divide the platform into repeated failure domains.
  • Sharding assigns tenants or resources using a clear partition key.
  • Multi-cluster platforms provide shared management while workloads run across separate clusters.

These designs reduce the failure area and allow teams to scale out. They also add work across placement, policy, identity, networking, observability, and upgrades.

Choose the partition key carefully. A cell works best when a tenant or workload can stay inside one failure domain. A poor shard key creates constant work between cells and moves the bottleneck to another shared service.

Also watch the management layer. A global management cluster can become the new booking counter if every tenant and workload cluster depends on it for every action.

Move the boundary while the current cluster still has enough capacity. Do not wait until the control plane is already at its knee.

A production scale policy​

"The cluster supports 5,000 nodes" is not a safe operating policy. Define a limit below the knee and prove that the cluster can recover within its SLO.

Do not hide the warning

Increasing API limits, etcd quota, or client timeouts may move the visible symptom without removing the cause.

First identify whether the pressure comes from object count, churn, payload size, or one badly behaved client. Change the smallest relevant control, then repeat the same test.

Lab: measure the scalability knee​

In the lab, you will use KWOK to grow a real Kubernetes control plane without running thousands of real machines.

You will increase node and Pod counts, time full lists, measure payload size, and compare client wall time with API-server handling time. You will then test selectors, pagination, and watch behavior.

You will also inspect storage-object counts and see how Events can outgrow the workload objects you normally monitor.

Keep these five points from the module:

  1. The scalability envelope has many dimensions. Node count is only one.
  2. Performance often bends at a knee. Operate below it with room for recovery and incidents.
  3. Server metrics can remain healthy while payload transfer and client work become slow.
  4. Object churn, Events, broad lists, watch fan-out, and endpoint changes can pressure different parts of the same control plane.
  5. Filter, page, and watch before increasing limits. When one control plane no longer has enough safe capacity, scale out into cells or multiple clusters.

After the lab, Module 7 will follow workload traffic through the networking data plane. You will learn how to test that path one link at a time.
