The API Server & the Request Lifecycle at Scale

Module 1 established one design fact: every control-plane component talks through kube-apiserver. That makes the API server both a coordination point and a shared production dependency. When it slows down, kubectl slows down, controller watches fall behind, leader election can fail, and autoscalers may act on old information.

This module helps you answer the questions that come up during those incidents. Where did a request stop? Who sent the expensive traffic? Was it denied, queued, or admitted? Did a successful write only change the API object, or did the workload become healthy as well?

The five questions to ask during an API incident
  1. Is the problem affecting one client, one priority level, or the whole API server?
  2. Which request verb, resource, scope, and user are involved?
  3. Did the request fail authentication, authorization, admission, flow control, or storage?
  4. Is the client doing repeated LIST calls when it should keep a watch and local cache?
  5. If the write succeeded, which controller or node-side handoff is still incomplete?

API Request Checkpoints Locate Failures​

Imagine you are an Indian technology professional arriving at London Heathrow or Singapore Changi for a new assignment. You have your passport, visa, or work permit with you. Passport control first checks who you are. After that, airport staff may route you through a separate queue, but that queue does not decide whether you may enter the country. Immigration checks whether your visa permits this visit. Customs may inspect your luggage and reject something that is not allowed. Once you pass the checks, the border system records your arrival. Each checkpoint answers a different question, so a failure at each checkpoint needs a different fix.

The API server works in the same way:

  1. Authentication establishes the identity. The result is a username and a set of groups. Client certificates, ServiceAccount tokens, and OIDC tokens are common inputs.
  2. API Priority and Fairness, or APF, classifies authenticated traffic early. It may dispatch, queue, or reject a request before the server spends more work on it. APF does not grant permission.
  3. Authorization checks whether that identity may perform this verb on this resource and scope. RBAC is the common authorizer, but it is not the only possible one.
  4. Admission and validation inspect a write request. Mutation may add or change fields. Schema validation and validating admission then decide whether the resulting object is acceptable.
  5. Storage persists the accepted API object. For built-in persisted resources, that normally means a write through the storage layer to etcd.
  6. Watch delivery makes the new version available to clients watching that resource. Controllers then perform their own reconciliation work.

What does the response tell you?​

Do not treat every failed kubectl command as the same API-server problem. Start with the response and the audit event.

EvidenceWhat it usually meansFirst place to look
TLS or certificate error before an HTTP responseThe client could not establish a trusted connectionCertificate dates, CA chain, endpoint, load balancer, and time sync
401 UnauthorizedAuthentication did not produce an accepted identityToken, client certificate, OIDC configuration, or authenticating proxy
403 ForbiddenThe identity is known, but the requested action is not authorizedkubectl auth can-i, RBAC bindings, authorizer reason in audit logs
400, 409, 422, or a webhook-specific denialThe request reached validation, admission, or optimistic concurrency checksAPI Status reason/message, field errors, managed-fields conflict, webhook response
429 Too Many Requests with Retry-AfterAPF or another rate limit asked the client to slow downAPF response headers, rejected-request metrics, queue wait, client retry behavior

Production recommendation: separate API success from workload success

deployment.apps/gateway created means the API request succeeded. It does not mean a Pod was scheduled, an image was pulled, readiness passed, or traffic reached the application.

After a successful write, check generation, observedGeneration, conditions, Events, and the next object in the ownership chain. Do not keep applying the same manifest when the API object already contains the intended state.

Choose the Lowest-Risk Admission Mechanism​

Admission is the checkpoint that can inspect the object being written. Mutating admission runs before validating admission. A mutating webhook may also be reinvoked, so you must not depend on a fixed order among several mutating webhooks. Validation must judge the final object after mutation.

There are several ways to enforce policy. They are not equal in operational cost.

RequirementPreferred mechanismWhy
Validate or default fields in a CRDCRD schema, defaulting, and CEL validation rulesThe rule remains with the API type and adds no service dependency
Validate a Kubernetes object using object and request dataValidatingAdmissionPolicy with CELIt runs in the API server and avoids a network call
Perform a simple supported mutation using CELMutatingAdmissionPolicy where the cluster version and feature state support itIt avoids running another service for a small deterministic change
Consult an external system or run logic that CEL cannot expressAdmission webhookA webhook can call custom code and external data, but it becomes part of the write path

A webhook is similar to the airport officer calling another office for approval. Every matching request now depends on DNS, networking, TLS, the Service, the webhook Pods, and the code behind them. The default webhook failurePolicy is Fail, and the default timeout is ten seconds. One broad and unhealthy webhook can therefore delay or block many unrelated writes.

Production recommendation: treat webhooks as control-plane dependencies
  • Prefer built-in CRD validation or CEL when the rule fits.
  • Match only the operations, resources, and namespaces that need the webhook.
  • Exclude the webhook's own namespace and any critical dependency it needs to recover.
  • Run multiple backends behind a Service, use a small timeout, and monitor latency and rejection metrics.
  • Make mutations idempotent. The same object may pass through mutating logic more than once.
  • Choose Fail or Ignore from the business and security consequence, not from habit. Fail protects enforcement but can block healthy deployments. Ignore protects availability but may allow an object without the policy being applied.

Do not solve a webhook outage by changing failurePolicy during the incident without understanding what policy you are bypassing. Restore the dependency or use an approved break-glass procedure with an audit trail.

LIST and WATCH Build Local Controller State​

Imagine a team operating a large parcel hub. One clerk maintains the central register. Every sorting counter needs an up-to-date view, but asking the clerk to print the complete register every few seconds would overload the desk. A better design gives each counter an initial copy and then sends only the changes.

That is the problem Kubernetes solves with LIST and WATCH.

First establish state, then follow changes​

The classic client pattern is:

  1. LIST returns a consistent collection and the collection's resourceVersion.
  2. The client stores that initial state locally.
  3. WATCH continues from that resourceVersion and delivers later ADDED, MODIFIED, and DELETED events.
  4. If the watch closes, the client reconnects or lists again when its previous version is no longer available.

Treat resourceVersion as an opaque synchronization cursor: “I have observed this collection through here.” Pass it back unchanged. Do not build application logic that treats it as a timestamp, a database ID, or a cluster-wide counter.

Reflector synchronizes; Informer makes the copy useful​

The API server only provides API operations such as LIST and WATCH. Reflector and Informer are client-side machinery, most commonly from Go's client-go library. They run inside the process using them; there is no central Informer service in the cluster.

  • A Reflector maintains synchronization. It consumes LIST/WATCH data and reflects changes into a supplied local store or queue. It does not make business decisions.
  • An Informer builds the controller-friendly system around that flow: an eventually consistent local cache, indexes, and Add/Update/Delete notifications.
  • A Lister reads from the Informer's local cache. It does not send a GET to the API server.
  • A SharedInformer lets several controllers in the same process share one watch and one cache for a resource.

The cache is deliberately eventually consistent. A controller can write an object to the API server and briefly read the older value from its local cache. Controller code must reconcile repeatedly instead of assuming read-after-write consistency.

Who uses this machinery?​

Client or componentWhat normally happens
kubectl get podsMakes a request, prints the result, and exits. No long-lived Informer cache is needed.
kubectl get pods --watchOpens a WATCH and prints events. A WATCH by itself is not an Informer.
A direct REST or SDK clientUses GET, LIST, or WATCH only when its code asks for them. Importing an SDK does not automatically create an Informer.
Kubernetes controllers and many Go operatorsUse SharedInformers heavily so reconciliation reads mostly from local memory. Frameworks such as controller-runtime usually hide much of this machinery.
kubeletUses client-go Reflector machinery for important paths. Its API-server Pod source scopes the watch to Pods assigned to that node.
A non-Go Kubernetes clientCan implement the same LIST/WATCH-and-cache pattern, but may not call the component a Reflector or Informer.

This distinction matters during an incident. “The client has a watch” does not prove that it has a bounded, shared, indexed cache. Inspect what it watches, how many replicas open the same watch, how it reconnects, and whether its normal reads hit local memory or the API server.

Streaming Lists reduce the startup cost​

There is still a scaling problem in the classic model: a controller restart may require one large LIST before steady-state watching can begin. Kubernetes 1.35 supports streaming lists to build the initial state on the watch connection itself.

With sendInitialEvents=true, the watch begins with synthetic ADDED events for objects that already exist. Those events mean “add this object to your initial local state,” not “this object was created just now.” A BOOKMARK marks the resource version at which that initial state is complete, and the same connection then continues with normal changes.

classic startup:    one large LIST response ──> WATCH later changes

streaming startup:  ADDED existing objects ──> BOOKMARK ──> normal watch events
                    └──── build initial state ────┘

The production reason to care is cache rebuild cost:

WATCH makes steady-state synchronization cheap. Streaming Lists make entering that steady state cheaper.

Streaming Lists do not reduce the number of objects a client must hold. They avoid constructing and transferring one giant initial collection response. Scope caches with namespace, label, and field selectors first; then use streaming startup when the client library and cluster support it.

Do not confuse the two cache levels​

The API server has its own watch cache, an in-memory view and recent event history for each resource. A client process has a separate Informer cache containing only the objects that client watches. In a highly available control plane, every API-server instance has its own server-side cache; every controller or operator process has its own client-side cache.

The server-side watch cache serves watches and many LIST operations without asking etcd to rebuild the same result for every client. In Kubernetes 1.35, even a most-recent consistent LIST can be served from the watch cache after the server confirms cache freshness using etcd progress notifications.

Choose the request by the guarantee your client needs:

RequestWhat the client is asking forWhen to use itWhat to watch for
resourceVersion=0Any available version; strong consistency is not requiredCache warm-up or discovery where slightly older state is acceptableDo not use it when a decision requires the latest confirmed state
resourceVersion unsetThe most recent consistent collectionInteractive commands and correctness-sensitive reads“Most recent” does not mean “must read directly from etcd”; a sufficiently fresh watch cache may serve it
A version with resourceVersionMatch=NotOlderThanA collection at least as new as that versionReconnecting a cache when newer state is acceptableHandle 410 Gone and re-establish state when the requested history is unavailable
A version with resourceVersionMatch=ExactThe collection at exactly that versionSnapshot-sensitive work and consistent paginationThe exact snapshot may expire; handle 410 Gone instead of retrying the same version forever

That gives you an important rule:

resourceVersion describes the freshness contract. It does not tell you which internal storage path the server must use on every Kubernetes version.

In production, choose the weakest freshness guarantee that is still correct for the decision being made. A dashboard refresh can often tolerate more flexibility than an automation step that is about to modify or delete resources. Do not force every client toward the strongest read simply because it sounds safer; unnecessary strong reads can add avoidable control-plane work.

Production recommendation: review clients by behavior, not only request rate

One long-lived watch can be cheaper than repeated LIST calls even if both appear as API traffic. During a review, ask:

  • Does the client use a SharedInformer inside each process, or open duplicate watches and caches?
  • Are namespaces, labels, and fields scoped as narrowly as possible?
  • Does it back off with jitter after 429, 410, and transport errors?
  • Do many replicas perform the same cluster-wide LIST independently?
  • Does a restart cause every replica to rebuild its cache at the same time?

Stagger controller and agent rollouts when each replica must rebuild a large cache. Avoid deploying a DaemonSet where every node independently watches large cluster-wide resources unless the design truly needs it.

Broad LIST Requests Increase Control-Plane Load​

An unpaginated kubectl get configmaps -A -o json --chunk-size=0 asks for the entire matching collection in one response. The API server must retrieve the objects from an eligible source, decode and convert them, apply filtering, serialize the response, and keep response data in memory while it is sent. Concurrency multiplies that work.

Pagination with limit and continue preserves one consistent collection snapshot while splitting the result into smaller responses. It does not remove the total work of reading all objects. It limits the peak response size, improves client progress, and gives APF opportunities to schedule other requests between pages.

OpenAI reported up to 70 GB of heap per API server in a 7,500-node cluster. They also found an N-squared watch amplification problem around large Endpoints objects: a change produced a large response for kube-proxy watchers across the node fleet. EndpointSlice reduced that load by splitting one large object into smaller pieces.

Use the following approximation during design reviews:

read cost grows with object count, object size, concurrent clients, and fan-out

Do not use the formula as an exact capacity model. Use it to find which multiplier is growing.

API Priority and Fairness Controls Concurrency​

Think of a busy government hospital. OPD patients use the token queue, while emergency care has protected capacity. The hospital does not make every patient wait in one line. It classifies the work, gives each category a share of capacity, and controls how a sudden crowd is queued.

APF uses two API objects because classification and capacity are separate decisions:

  • A FlowSchema matches who is calling and what they are requesting. matchingPrecedence decides which matching rule wins. A distinguisher divides matched requests into flows so one user or namespace does not dominate every queue.
  • A PriorityLevelConfiguration decides how that class of traffic shares concurrency. It defines nominal concurrency shares, lending and borrowing limits, and whether excess requests queue or receive 429.

Seats represent estimated work, not request count. A large LIST may occupy several seats. A watch uses seats for its initial delivery, and writes may include additional seat cost for watch notifications.

The total API-server concurrency budget is fixed by server configuration and then divided among limited priority levels. Adding a new priority level or increasing nominalConcurrencyShares does not create capacity. It changes the share available to other levels. lendablePercent: 0 means that other levels cannot borrow this level's nominal seats when it is idle. It does not stop this level from borrowing, and it does not guarantee low latency when storage or admission is slow.

Production recommendation: isolate the noisy flow before promoting everything else
SituationRecommended moveAvoid
One operator repeatedly performs expensive LIST callsFix the client and place that narrow traffic in a low-share priority level while you recoverIncreasing global concurrency and allowing the client to consume more memory
A platform controller must progress during tenant overloadMatch its exact ServiceAccount and required verbs/resources into a measured priority levelBroad users: ["*"], resources: ["*"], or application traffic in exempt
Several priority levels queue at the same timeInvestigate API CPU, memory, admission latency, storage latency, and downstream dependenciesAssuming every multi-level slowdown is an APF classification problem
Clients receive 429Honor Retry-After, use exponential backoff with jitter, and inspect rejection reasonsImmediate retry loops, which increase the overload

Do not edit auto-maintained default FlowSchemas casually. Create a narrow custom rule, verify the matched FlowSchema and priority-level response headers, observe queue and rejection metrics, and test under bounded load. Every extra share assigned to one level has an effect elsewhere.
