Lab - API Server Request Lifecycle

Before you start

Complete the Setup section before you begin. Run every command from the root of the 304-labs/ repository.

This lab reuses the core-internals cluster from Module 1. If it is not running, use bash labs/clusters/core-internals/create.sh.

In this lab, you will trace one API request, generate bounded API load, and protect critical traffic with API Priority and Fairness.

You will:

  • find a request in the API audit stream
  • observe APF seats and queues during a LIST storm
  • identify the matching FlowSchema
  • create a FlowSchema for a critical ServiceAccount
  • verify that critical and rogue traffic are classified separately

Pre Requisites​

Prerequisites

Rancher Desktop must be running with the Moby/dockerd engine. Verify that docker, kind, and kubectl respond before continuing.

Run only one course cluster profile at a time.

Every triage question of the form "who did that, and did the server allow it?" is answered by exactly what you're about to read. This is postmortem evidence, not debugging trivia: when a namespace disappears or a webhook mysteriously rejects deploys, the audit stream is where the answer lives.

Read the audit event field by field:

  • auditID: one UUID per request. In a busy log, this is how you correlate the stages of a single request.
  • user.username and user.groups: authentication's result. Your kind admin credential resolves to a user in the kubeadm:cluster-admins group, not system:masters.
  • annotations."authorization.k8s.io/decision" and .../reason: authorization's verdict, including which RBAC binding allowed the request. When you're debugging RBAC, this annotation names the exact rule that matched: faster and more trustworthy than re-deriving it by reading Role manifests.
  • verb, requestURI, objectRef: what was actually asked of the API, in API terms rather than kubectl terms.
  • requestReceivedTimestamp → stageTimestamp: wall-clock evidence of how long the request spent inside the server. During the storm, this gap includes queueing time.

Leave the ticker terminal running: you'll want the audit stream again later. Ctrl-C it if you need the terminal back; nothing depends on it staying up.

What this evidence proves

The event proves which identity reached the API server, what it requested, which authorization decision applied, and how the API server responded. It does not prove that a later controller completed its work.

For a denied request, start with responseStatus, the authorization annotation, and the audit stage. For a successful write followed by an unhealthy workload, stop investigating authentication and RBAC. Follow the object generation, conditions, Events, and controller chain from Module 1.

In production, use Metadata as the broad audit baseline. Capture request bodies only for narrow resources and verbs that need them. Do not log every request and response body across the cluster. That creates avoidable I/O and can place sensitive data in the audit backend.

PART II - Generate and Observe API Load​

Seed a bounded object set​

A LIST storm needs something to list. You'll seed a fixed, known count of small ConfigMaps: bounded on purpose. The point of this lab is to observe queuing and fairness deterministically, not to find your laptop's crash threshold; an unbounded seed would turn an APF demonstration into an etcd-capacity experiment (that's Module 3's job).

The script generates the manifests and applies them in one pass: here's its core:

COUNT="${COUNT:-300}"                      # 8 GB profile default; COUNT=600 on 16 GB
payload="$(head -c $((PAYLOAD_KB * 1024)) /dev/zero | tr '\0' 'x')"
# ... emits COUNT ConfigMaps (label module=m2, ~4 KiB payload each)
# into namespace 'apiload', piped to a single 'kubectl apply -f -'

Run it (use COUNT=600 bash labs/m2/seed-configmaps.sh on a 16 GB machine):

bash labs/m2/seed-configmaps.sh

[ Expected output ]

The missing annotation will be patched automatically.

At ~4 KiB each, 300 ConfigMaps means every unpaginated LIST moves roughly 1.2 MiB of serialized objects through the API server: per request. Multiply by ten concurrent workers and the arithmetic from the lesson stops being abstract.

Watch the meter while it runs. The live bar and sparkline show point-in-time pressure; the counters under THIS OBSERVATION WINDOW preserve what happened even if a short spike occurred between screen refreshes. The exact height depends on your machine: slower disks and CPUs hold seats longer and queue sooner.

Press Ctrl-C after the storm. This was the final summary from the validation run:

THIS OBSERVATION WINDOW
Dispatched: +1406    Rejected: +0
Wide requests (>4 seats): +635
Average estimated cost: 3.7 seats/request
Peak seats: 22    Peak active average: 8.0 seats/request

Here is how to read it:

  • +635 wide requests exactly matches the storm's 635 LISTs succeeded. The API server estimated each of these requests at more than four seats.
  • +1406 dispatched is larger because it includes the meter's /metrics reads, kubectl discovery, and other global-default traffic. A raw apiserver_flowcontrol_dispatched_requests_total value such as 5367 is a lifetime counter, not the cost of this one storm.
  • Peak seats: 22 is point-in-time work in progress. The active average is across all matching requests at that instant; do not treat it as the exact width of every LIST.
  • Rejected: +0 and a queue that stays at zero are valid results. They mean this API server dispatched the bounded load without exhausting the queue.

[ Expected output ]

Meter final summary from the same run

THIS OBSERVATION WINDOW
Dispatched: +726    Rejected: +0
Wide requests (>4 seats): +332
Average estimated cost: 3.7 seats/request
Peak seats: 43    Peak active average: 7.5 seats/request

This heavier validation briefly showed 1 request / 7 seats in the queue and still rejected nothing. That is APF working as designed: it made overflow wait instead of fail. Rejections (429) appear only when queues cannot absorb more work. Do not keep increasing concurrency merely to force a rejection; the operational lesson is to identify the noisy flow and protect critical traffic, which you will do next.

How to read this in production
  • One FlowSchema queuing while other levels remain healthy usually points to one client or traffic class.
  • Several priority levels queuing together can mean the API server, admission chain, or storage path is slow. Changing FlowSchemas will not repair a slow webhook or etcd member.
  • A client receiving 429 should honor Retry-After and use exponential backoff with jitter. An immediate retry loop creates more pressure.
  • Do not increase the storm concurrency outside the documented bounds on a shared or production cluster.

Protect critical traffic with a FlowSchema​

Now set up the incident scenario. A misbehaving operator is flooding the API server with LIST calls. A critical platform controller must still read its ConfigMaps in the nimbusai namespace. Both identities are ServiceAccounts, so they initially match the built-in service-accounts FlowSchema and share the workload-low priority level.

In production, your first move would be to fix or isolate the noisy operator. This exercise protects one narrow critical path because it makes the before-and-after classification easy to prove. It does not make the critical ServiceAccount exempt from flow control.

Create both identities and give them read access to ConfigMaps:

kubectl create namespace nimbusai --dry-run=client -o yaml | kubectl apply -f -
kubectl create serviceaccount rogue-operator -n apiload
kubectl create serviceaccount nimbusai-critical -n nimbusai
kubectl create clusterrole configmap-reader --verb=get,list,watch --resource=configmaps
kubectl create clusterrolebinding rogue-operator-read --clusterrole=configmap-reader --serviceaccount=apiload:rogue-operator
kubectl create clusterrolebinding nimbusai-critical-read --clusterrole=configmap-reader --serviceaccount=nimbusai:nimbusai-critical

Now the fix. Here is M2's addition to the NimbusAI platform: a dedicated ward for the critical identity:

apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: PriorityLevelConfiguration
metadata:
  name: nimbusai-critical
spec:
  type: Limited
  limited:
    nominalConcurrencyShares: 30
    lendablePercent: 0
    limitResponse:
      type: Queue
      queuing:
        queues: 16
        handSize: 4
        queueLengthLimit: 50
---
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata:
  name: nimbusai-critical
spec:
  priorityLevelConfiguration:
    name: nimbusai-critical
  matchingPrecedence: 800
  distinguisherMethod:
    type: ByUser
  rules:
    - subjects:
        - kind: ServiceAccount
          serviceAccount:
            name: nimbusai-critical
            namespace: nimbusai
      resourceRules:
        - verbs: ["get", "list"]
          apiGroups: [""]
          resources: ["configmaps"]
          clusterScope: false
          namespaces: ["nimbusai"]

Read four decisions closely:

  1. matchingPrecedence: 800 is evaluated before the built-in service-accounts schema at 9000.
  2. The subject matches one ServiceAccount, not every application identity.
  3. The resource rule matches only get and list for namespaced ConfigMaps in nimbusai.
  4. nominalConcurrencyShares: 30 contributes to this level's share of the fixed server concurrency budget. lendablePercent: 0 prevents other levels from borrowing its nominal seats while it is idle.

Creating this priority level does not create API-server capacity. Its nominal shares affect the allocation available to other limited levels. Measure the result under realistic load before carrying an APF configuration into production.

Protect a critical flow only when its identity and request scope are precise and you understand how the new shares affect the rest of the server. PART IV - Validate the End State​

Confirm the final state:

kubectl get configmaps -n apiload -l module=m2 --no-headers | wc -l
kubectl get flowschema nimbusai-critical -o jsonpath='priorityLevel: {.spec.priorityLevelConfiguration.name}{"\n"}'
kubectl get prioritylevelconfiguration nimbusai-critical -o jsonpath='type: {.spec.type} / {.spec.limited.limitResponse.type}{"\n"}'
kubectl get --raw /metrics | grep 'apiserver_flowcontrol_dispatched_requests_total' | grep -c 'nimbusai-critical'
kubectl logs -n kube-system kube-apiserver-kubeadv-core-control-plane --tail=500 | grep -c 'audit.k8s.io/v1'

[ Expected output ]

300
priorityLevel: nimbusai-critical
type: Limited / Queue
1
498

You want: the seeded ConfigMap count (300, or 600 on 16 GB), priorityLevel: nimbusai-critical, type: Limited / Queue, a non-zero count of dispatched-requests metric lines for nimbusai-critical, and a non-zero count of audit events in the recent log window.

Troubleshooting
  • No audit events in the API server logs: the cluster wasn't created with the flag. Confirm with kubectl get pod -n kube-system kube-apiserver-kubeadv-core-control-plane -o yaml | grep audit: if nothing shows, recreate the profile once: bash labs/clusters/core-internals/teardown.sh && bash labs/clusters/core-internals/create.sh.
  • kubectl logs says the apiserver pod isn't found: you're on the wrong context or profile. kubectl config use-context kind-kubeadv-core, and check the pod name with kubectl get pods -n kube-system.
  • The meter shows nothing moving during the storm: the storm may be finishing LISTs too fast to queue. Increase pressure: CONCURRENCY=20 bash labs/m2/list-storm.sh (16 GB), or re-seed with COUNT=600 to make each LIST heavier.
  • --as requests fail with Forbidden: reapply the ClusterRoleBinding and verify the ServiceAccount string. The format is system:serviceaccount:<namespace>:<name>.
  • x-kubernetes-pf grep returns nothing: response headers only print at -v=8 or higher, and stderr must be captured: the 2>&1 in the command is load-bearing.
  • Everything is slow, including the meter: your laptop is genuinely saturated. Ctrl-C the storm (it's safe to interrupt), let the queues drain for ~30 seconds, and re-run with lower CONCURRENCY. The storm is bounded precisely so you can iterate like this.
