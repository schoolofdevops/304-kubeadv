Lab - API Server Request Lifecycle

Before you start

Run commands from the root of the 304-labs/ repository. This lab reuses the core-internals cluster from Module 1. Start it with bash labs/clusters/core-internals/create.sh if needed.

During an incident, a noisy controller can make large API LIST requests while a platform controller still needs a small, dependable read path. In this lab you will see both kinds of traffic arrive at the API server, then put each into its own APF lane.

You will:

  • trace one ordinary request through the API server
  • create a noisy rogue lane and a protected NimbusAI lane
  • run both workloads at the same time
  • watch the two lanes independently in Cluster X-Ray

PART I - See the request path​

Verify the cluster and open Cluster X-Ray:

bash labs/clusters/core-internals/verify.sh
bash labs/tools/xray/serve.sh

[ Expected output ]

OK: core-internals profile verified: 2/2 nodes Ready, API server healthy.
│  open    : http://127.0.0.1:8001/xray/
Starting to serve on 127.0.0.1:8001

Open http://127.0.0.1:8001/xray/ and select Control Plane. The centre diagram is the request path. The APF panel is the visual proof you will use later.

In a second terminal, start a live audit ticker for the object you are about to create:

kubectl logs -n kube-system kube-apiserver-kubeadv-core-control-plane -f --tail=0 | grep --line-buffered trace-me

[ Expected output ]

(silent until the next command creates and reads trace-me)

Create and read one ConfigMap. It gives the visualizer and audit stream a small, deliberate request to show:

kubectl create namespace apiload --dry-run=client -o yaml | kubectl apply -f -
kubectl create configmap trace-me -n apiload --from-literal=owner=m2 --dry-run=client -o yaml | kubectl apply -f -
kubectl get configmap trace-me -n apiload -o name

[ Expected output ]

namespace/apiload configured
configmap/trace-me configured
configmap/trace-me

In X-Ray, enable show system users if the audit list is quiet. You should see the request reach the API server and return successfully. That is the normal path you are protecting.

Pull the same request from the API-server audit log and format it for reading:

kubectl logs -n kube-system kube-apiserver-kubeadv-core-control-plane --tail=5000 | grep '"name":"trace-me"' | tail -1 | tr ',' '\n'

[ Expected output ]

{"kind":"Event"
"apiVersion":"audit.k8s.io/v1"
"stage":"ResponseComplete"
"requestURI":"/api/v1/namespaces/apiload/configmaps/trace-me"
"verb":"get"
"user":{"username":"kubernetes-admin"
"objectRef":{"resource":"configmaps"
"namespace":"apiload"
"name":"trace-me"
"responseStatus":{"metadata":{}
"code":200}
"requestReceivedTimestamp":"<timestamp>"
"stageTimestamp":"<timestamp>"
"annotations":{"authorization.k8s.io/decision":"allow"}

Read the audit event field by field:

  • auditID: one UUID per request. In a busy log, this is how you correlate the stages of a single request.
  • user.username and user.groups: authentication's result. Your kind admin credential resolves to a user in the kubeadm:cluster-admins group, not system:masters.
  • annotations."authorization.k8s.io/decision" and .../reason: authorization's verdict, including which RBAC binding allowed the request. When you are debugging RBAC, this annotation names the exact rule that matched: faster and more trustworthy than re-deriving it by reading Role manifests.
  • verb, requestURI, objectRef: what was actually asked of the API, in API terms rather than kubectl terms.
  • requestReceivedTimestamp → stageTimestamp: wall-clock evidence of how long the request spent inside the server. During the storm, this gap includes queueing time.

Leave the ticker terminal running: you will want the audit stream again later. Ctrl-C it if you need the terminal back; nothing depends on it staying up. The APF exercise below changes only how the server allocates concurrency after it classifies a request; it does not replace authentication or RBAC.

PART II - Generate and Observe API Load​

Run the bounded LIST storm​

Start the single-lane meter in a second terminal before triggering load. It establishes the quiet baseline for the default APF lane:

python3 labs/m2/apf-seat-meter.py

[ Expected output ]

APF SEAT METER · global-default · <time>

EXECUTING
<seats> seats / <requests> active requests

QUEUE
0 requests / 0 seats

Your numbers will differ. At rest, the queue is normally empty. The nominal marker is the assured share for that priority level. Green is work within the nominal share, yellow is borrowed capacity, and red means requests are waiting.

In a third terminal, run the bounded storm:

bash labs/m2/list-storm.sh

[ Expected output ]

LIST storm: 10 workers x unpaginated 'kubectl get configmaps -A -o json --chunk-size=0' for 30s
Storm complete: <number> LISTs succeeded, <number> failed or rejected, across 10 workers in 30s.

Watch the meter and Cluster X-Ray while it runs. The exact bars depend on your laptop. The important result is that a broad, unpaginated LIST is visibly more expensive than the one-object request from Part I. Stop the meter with Ctrl-C when the storm completes.

PART III - Classify and Protect Traffic​

Think of APF as a building with separate reception desks. A busy queue at the rogue desk should not consume the places reserved at the critical-controller desk. Kubernetes implements those desks with a FlowSchema (which requests belong together) and a PriorityLevelConfiguration (the lane they use).

This is the relevant part of labs/m2/flowschema.yaml before you apply it:

apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: PriorityLevelConfiguration
metadata:
  name: rogue-operator
spec:
  type: Limited
  limited:
    nominalConcurrencyShares: 5
    lendablePercent: 0
    limitResponse:
      type: Queue
---
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata:
  name: rogue-operator
spec:
  priorityLevelConfiguration:
    name: rogue-operator
  matchingPrecedence: 700
  rules:
    - subjects:
        - kind: ServiceAccount
          serviceAccount: {name: rogue-operator, namespace: apiload}
      resourceRules:
        - verbs: ["get", "list"]
          apiGroups: [""]
          resources: ["configmaps"]
          clusterScope: true
---
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: PriorityLevelConfiguration
metadata:
  name: nimbusai-critical
spec:
  type: Limited
  limited:
    nominalConcurrencyShares: 30
    lendablePercent: 0
    limitResponse:
      type: Queue
---
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata:
  name: nimbusai-critical
spec:
  priorityLevelConfiguration:
    name: nimbusai-critical
  matchingPrecedence: 800
  rules:
    - subjects:
        - kind: ServiceAccount
          serviceAccount: {name: nimbusai-critical, namespace: nimbusai}
      resourceRules:
        - verbs: ["get", "list"]
          apiGroups: [""]
          resources: ["configmaps"]
          clusterScope: false
          namespaces: ["nimbusai"]

The lower precedence number wins. The rogue rule matches its all-namespace LIST request, so it uses clusterScope: true; the critical rule matches ConfigMap reads only in nimbusai. The complete manifest also defines queues and labels used by the lab.

Create the two workload identities and grant only ConfigMap reads:

kubectl create namespace nimbusai --dry-run=client -o yaml | kubectl apply -f -
kubectl create serviceaccount rogue-operator -n apiload --dry-run=client -o yaml | kubectl apply -f -
kubectl create serviceaccount nimbusai-critical -n nimbusai --dry-run=client -o yaml | kubectl apply -f -
kubectl create clusterrole configmap-reader --verb=get,list,watch --resource=configmaps --dry-run=client -o yaml | kubectl apply -f -
kubectl create clusterrolebinding rogue-operator-read --clusterrole=configmap-reader --serviceaccount=apiload:rogue-operator --dry-run=client -o yaml | kubectl apply -f -
kubectl create clusterrolebinding nimbusai-critical-read --clusterrole=configmap-reader --serviceaccount=nimbusai:nimbusai-critical --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -f labs/m2/flowschema.yaml

[ Expected output ]

serviceaccount/rogue-operator configured
serviceaccount/nimbusai-critical configured
clusterrole.rbac.authorization.k8s.io/configmap-reader configured
clusterrolebinding.rbac.authorization.k8s.io/rogue-operator-read configured
clusterrolebinding.rbac.authorization.k8s.io/nimbusai-critical-read configured
prioritylevelconfiguration.flowcontrol.apiserver.k8s.io/rogue-operator configured
flowschema.flowcontrol.apiserver.k8s.io/rogue-operator configured
prioritylevelconfiguration.flowcontrol.apiserver.k8s.io/nimbusai-critical configured
flowschema.flowcontrol.apiserver.k8s.io/nimbusai-critical configured

The manifest creates these two lanes:

WorkloadRequestAPF lane
rogue-operatorbroad ConfigMap LIST across namespacesrogue-operator — deliberately constrained and queued
nimbusai-criticalConfigMap read in nimbusainimbusai-critical — separate reserved allocation

Confirm the API server classified both identities into the intended lane. First print the names and UIDs you will compare:

kubectl get flowschemas -o custom-columns=NAME:.metadata.name,UID:.metadata.uid,PRIORITY:.spec.priorityLevelConfiguration.name | grep -E 'NAME|rogue-operator|nimbusai-critical'
kubectl get prioritylevelconfigurations -o custom-columns=NAME:.metadata.name,UID:.metadata.uid | grep -E 'NAME|rogue-operator|nimbusai-critical'
kubectl get configmaps -A --as=system:serviceaccount:apiload:rogue-operator -v=8 2>&1 | grep -i 'x-kubernetes-pf'
kubectl get configmaps -n nimbusai --as=system:serviceaccount:nimbusai:nimbusai-critical -v=8 2>&1 | grep -i 'x-kubernetes-pf'

[ Expected output ]

NAME                 UID                                    PRIORITY
nimbusai-critical    <critical FlowSchema UID>               nimbusai-critical
rogue-operator       <rogue FlowSchema UID>                  rogue-operator
NAME                 UID
nimbusai-critical    <critical PriorityLevel UID>
rogue-operator       <rogue PriorityLevel UID>
X-Kubernetes-Pf-Flowschema-Uid: <rogue FlowSchema UID>
X-Kubernetes-Pf-Prioritylevel-Uid: <rogue PriorityLevel UID>
X-Kubernetes-Pf-Flowschema-Uid: <critical FlowSchema UID>
X-Kubernetes-Pf-Prioritylevel-Uid: <critical PriorityLevel UID>

The server headers now have names: each pair of header UIDs maps to one row in the two tables. This proves the request reached the intended FlowSchema and PriorityLevel.

Run both workloads together​

Keep Cluster X-Ray open on Control Plane. Refresh the page once if you opened it before this step. The nimbusai-critical and rogue-operator rows are pinned at the top of the APF panel, above Kubernetes background traffic. The blue requests +N value records activity for each lane since X-Ray opened.

In a second terminal, open the two-lane meter. It is a useful companion visual: X-Ray shows the lanes in the browser, while this terminal keeps the rogue and critical comparison in one compact table.

python3 labs/m2/apf-seat-meter.py --both

[ Expected output ]

APF TWO-LANE SEAT METER · <time>
Rogue may queue here; critical activity must continue in its own lane.

APF SEAT METER · rogue-operator · <time>
...
EXECUTING
<seats> seats / <requests> active requests
...
SEAT HISTORY
<graph>
════════════════════════════════════════
APF SEAT METER · nimbusai-critical · <time>
...
SEAT HISTORY
<graph>

Start the critical controller's steady read loop in a third terminal:

DURATION=45 bash labs/m2/critical-read-loop.sh

[ Expected output ]

Critical reads: one nimbusai ConfigMap LIST every 0.2s for 45s as system:serviceaccount:nimbusai:nimbusai-critical
Critical read loop complete: 120 reads succeeded, 0 failed.

Immediately start the rogue LIST storm in a fourth terminal:

AS=system:serviceaccount:apiload:rogue-operator CONCURRENCY=25 DURATION=45 bash labs/m2/list-storm.sh

[ Expected output ]

LIST storm: 25 workers x unpaginated 'kubectl get configmaps -A -o json --chunk-size=0' for 45s as system:serviceaccount:apiload:rogue-operator
Storm complete: <number> LISTs succeeded, <number> failed or rejected, across 25 workers in 45s.

Watch X-Ray while both commands run.

  • The rogue-operator row receives the LIST traffic. Its queue bar can rise on a slower laptop; that is APF holding excess rogue work in its own lane.
  • The nimbusai-critical row flashes, shows flowing +N, and fills its green traffic bar at each poll while the critical loop is active. Its requests are not counted as rogue work and do not enter the rogue queue. Its seat bar can still read zero: these small reads finish between samples.
  • A zero queue is still a valid result on a fast laptop. The visual proof is two active, separately named lanes—not a forced failure or a particular latency number.
What this demonstrates

APF does not create CPU or network capacity. A large LIST can still use shared machine resources. Its job is narrower and valuable: classify requests and stop one flow from consuming another flow's allocated API-server concurrency.

PART IV - Verify and clean up​

Confirm the two FlowSchemas still point to different lanes:

kubectl get flowschema rogue-operator -o jsonpath='rogue lane: {.spec.priorityLevelConfiguration.name}{"\n"}'
kubectl get flowschema nimbusai-critical -o jsonpath='critical lane: {.spec.priorityLevelConfiguration.name}{"\n"}'

[ Expected output ]

rogue lane: rogue-operator
critical lane: nimbusai-critical

If you are continuing to the Deep Dive, keep the cluster and apiload namespace. Otherwise remove the lab resources:

kubectl delete -f labs/m2/flowschema.yaml
kubectl delete clusterrolebinding rogue-operator-read nimbusai-critical-read
kubectl delete clusterrole configmap-reader
kubectl delete namespace apiload nimbusai

[ Expected output ]

prioritylevelconfiguration.flowcontrol.apiserver.k8s.io "rogue-operator" deleted
flowschema.flowcontrol.apiserver.k8s.io "rogue-operator" deleted
prioritylevelconfiguration.flowcontrol.apiserver.k8s.io "nimbusai-critical" deleted
flowschema.flowcontrol.apiserver.k8s.io "nimbusai-critical" deleted
clusterrolebinding.rbac.authorization.k8s.io "rogue-operator-read" deleted
clusterrolebinding.rbac.authorization.k8s.io "nimbusai-critical-read" deleted
clusterrole.rbac.authorization.k8s.io "configmap-reader" deleted
namespace "apiload" deleted
namespace "nimbusai" deleted
