Deep Dive - Pagination, the Watch Cache, and APF Internals

This deep dive examines pagination, freshness guarantees, streaming lists, audit-policy cost, and APF queue state. Use these checks when a client reports a slow API or many controllers reconnect at the same time.

▶ M2: API Server Deep DiveOpen fullscreen ↗

Run everything from the repo root against the core-internals profile.

Where this picks up

The cluster from the lab is still running (recreate with bash labs/clusters/core-internals/create.sh if not). This page seeds its own working set: 300 small ConfigMaps in a dedicated namespace: so it doesn't matter what the lab's teardown removed. The apply stream below is idempotent; re-running it is safe.

kubectl create namespace m2-deepdive --dry-run=client -o yaml | kubectl apply -f -
for i in $(seq -w 1 300); do
  printf 'apiVersion: v1\nkind: ConfigMap\nmetadata:\n  name: page-cm-%s\n  namespace: m2-deepdive\ndata:\n  idx: "%s"\n---\n' "$i" "$i"
done | kubectl apply -f -

[ Expected output ]

namespace/m2-deepdive created
configmap/page-cm-298 created
configmap/page-cm-299 created
configmap/page-cm-300 created

PART I - Pagination: limit, continue, and what a LIST really costs​

Think of a records office. You can demand a certified copy of the entire ledger: the clerk photocopies every page while you (and everyone behind you) wait: or you can ask for fifty pages at a time, and the clerk hands you a bookmark recording exactly where the copy stopped and which edition of the ledger it came from. Kubernetes LIST pagination is the second protocol: limit is the page size, and the continue token is the clerk's bookmark: opaque to you, but encoding the last key returned and the etcd revision the page was served at, so every subsequent page comes from the same edition.

kubectl has paginated for years (default chunk size 500). Shrink the chunk so the round trips become visible, and let -v=7 print each request:

kubectl get configmaps -n m2-deepdive --chunk-size=50 -v=7 2>&1 | grep -o 'verb="GET" url="[^"]*"'

[ Expected output ]

verb="GET" url="https://127.0.0.1:59622/api/v1/namespaces/m2-deepdive/configmaps?limit=50"
verb="GET" url="https://127.0.0.1:59622/api/v1/namespaces/m2-deepdive/configmaps?continue=eyJ2IjoibWV0YS5rOHMuaW8vdjEiLCJydiI6Mjg3Nywic3RhcnQiOiIvcGFnZS1jbS0wNDlcdTAwMDAifQ&limit=50"
verb="GET" url="https://127.0.0.1:59622/api/v1/namespaces/m2-deepdive/configmaps?continue=eyJ2IjoibWV0YS5rOHMuaW8vdjEiLCJydiI6Mjg3Nywic3RhcnQiOiIvcGFnZS1jbS0wOTlcdTAwMDAifQ&limit=50"
verb="GET" url="https://127.0.0.1:59622/api/v1/namespaces/m2-deepdive/configmaps?continue=eyJ2IjoibWV0YS5rOHMuaW8vdjEiLCJydiI6Mjg3Nywic3RhcnQiOiIvcGFnZS1jbS0xNDlcdTAwMDAifQ&limit=50"
verb="GET" url="https://127.0.0.1:59622/api/v1/namespaces/m2-deepdive/configmaps?continue=eyJ2IjoibWV0YS5rOHMuaW8vdjEiLCJydiI6Mjg3Nywic3RhcnQiOiIvcGFnZS1jbS0xOTlcdTAwMDAifQ&limit=50"
verb="GET" url="https://127.0.0.1:59622/api/v1/namespaces/m2-deepdive/configmaps?continue=eyJ2IjoibWV0YS5rOHMuaW8vdjEiLCJydiI6Mjg3Nywic3RhcnQiOiIvcGFnZS1jbS0yNDlcdTAwMDAifQ&limit=50"
verb="GET" url="https://127.0.0.1:59622/api/v1/namespaces/m2-deepdive/configmaps?continue=eyJ2IjoibWV0YS5rOHMuaW8vdjEiLCJydiI6Mjg3Nywic3RhcnQiOiIvcGFnZS1jbS0yOTlcdTAwMDAifQ&limit=50"

One GET per page: the first with limit=50, every subsequent one spending the continue token the previous page returned. Now do what kubectl does, by hand. Fetch page one raw and extract the bookmark:

CONT=$(kubectl get --raw "/api/v1/namespaces/m2-deepdive/configmaps?limit=50" | grep -o '"continue":"[^"]*"' | cut -d'"' -f4)
echo "${CONT}"

[ Expected output ]

eyJ2IjoibWV0YS5rOHMuaW8vdjEiLCJydiI6Mjg1Miwic3RhcnQiOiIvcGFnZS1jbS0wNDlcdTAwMDAifQ… (opaque token: yours will differ)

Spend the token to fetch page two, and count what comes back:

kubectl get --raw "/api/v1/namespaces/m2-deepdive/configmaps?limit=50&continue=${CONT}" | grep -o '"name":"page-cm-[0-9]*"' | wc -l

[ Expected output ]

50

The list metadata also carries remainingItemCount, and the final page returns no continue token. An unpaginated LIST of 100,000 Pods at about 1.5 KB each produces about 150 MB of object data before protocol and processing overhead. The server must retrieve the objects from an eligible cache or storage path, decode and convert them, apply filtering, serialize the response, and send it to the client. Twenty clients rebuilding the same state together can create gigabytes of temporary allocation.

Pagination does not reduce the total number of objects a client eventually reads. It bounds each response, lets the client make progress, and allows APF to schedule other work between pages. Treat the continue token as opaque, keep the original query parameters unchanged, and consume it promptly. A token can expire, commonly after about five minutes. A client receiving 410 Gone must restart the paginated LIST or follow the replacement token behavior it explicitly supports.

PART II - resourceVersion on LIST: choose the freshness guarantee​

Think of a newspaper archive. You may ask for any available copy, the latest confirmed edition, or one exact numbered edition. That choice describes the result you need. It does not tell the archive clerk which shelf or internal index must serve it.

Kubernetes uses resourceVersion in the same way:

RequestGuaranteeProduction use
resourceVersion=0Any version, usually the newest available, but strong consistency is not requiredCache warm-up where the client can tolerate older state
resourceVersion unsetMost recent, with a consistent-read guaranteeInteractive and correctness-sensitive reads that need current state
Version plus resourceVersionMatch=NotOlderThanAt least as new as the requested collection versionReconnect and cache continuation where newer data is acceptable
Version plus resourceVersionMatch=ExactThe exact collection version, or an error when it cannot be servedSnapshot-sensitive workflows and paginated continuation

In Kubernetes 1.35, most-recent reads can be served from the watch cache after the API server confirms freshness through etcd progress notifications. Exact and continuation reads may also use cache snapshots. The freshness contract is stable; the internal serving path changes as Kubernetes improves.

Your kubectl sends no resourceVersion at all: verify with -v=7, where the request URL carries limit but no resourceVersion parameter:

kubectl get configmaps -n m2-deepdive -v=7 2>&1 | grep -o 'verb="GET" url="[^"]*"' | head -2

[ Expected output ]

verb="GET" url="https://127.0.0.1:59622/api/v1/namespaces/m2-deepdive/configmaps?limit=500"

Now request resourceVersion=0 and observe this cluster's behavior:

kubectl get --raw "/api/v1/namespaces/m2-deepdive/configmaps?limit=50&resourceVersion=0" | grep -o '"name":"page-cm-[0-9]*"' | wc -l

[ Expected output ]

300

This Kubernetes 1.35 cluster returns all 300 objects even though the request includes limit=50. That is an observed implementation behavior for this resourceVersion=0 request, not a portable promise that every API server must ignore limit. The API contract allows an "Any" version response and servers may choose not to paginate a particular request. Client code must use the returned continue field, not the requested limit, to decide whether another page exists.

Now ask for an exact collection version:

RV=$(kubectl get --raw "/api/v1/namespaces/m2-deepdive/configmaps?limit=1" | grep -o '"resourceVersion":"[0-9]*"' | head -1 | grep -o '[0-9]*')
kubectl get --raw "/api/v1/namespaces/m2-deepdive/configmaps?resourceVersion=${RV}&resourceVersionMatch=Exact&limit=5" | grep -o '"resourceVersion":"[0-9]*"' | head -1

[ Expected output ]

"resourceVersion":"2972"

If a watch requests history that the server no longer retains, it can receive 410 Gone. The client must establish current state again and start a new watch. One re-list is normal. A fleet of agents restarting together can rebuild the same large cache at the same time and overload the control plane.

Do not confuse this with an informer resync. A resync replays items from the informer's local cache to its handlers. It does not mean a fresh API LIST. This difference matters when you are explaining API traffic during a controller incident.

PART III - Streaming lists, the watch cache, and bookmarks​

The watch cache is similar to a press pool. The API server keeps a shared in-memory view and recent history for a resource. API clients read that shared feed instead of each opening a direct watch against etcd. In a highly available control plane, each API-server instance has its own caches and storage watches, so do not interpret “one shared feed” as one watch for the whole cluster.

Open the client-side box​

The API server implements LIST, WATCH, selectors, and resourceVersion semantics. It does not run your Informer. In Go controllers, the standard client-side path is:

Read the responsibilities from left to right:

PartResponsibilityWhat it does not do
ReflectorMaintains the LIST/WATCH loop, reconnects, and reflects changes into a store or queueDoes not reconcile business intent
DeltaFIFOAccumulates ordered object deltas for processingIs not the controller's query interface
Indexer / Informer cacheHolds an eventually consistent local view and indexes it for efficient lookupIs not an API-server or etcd cache
Event handlerConverts an object change into a small key such as namespace/nameShould not perform slow reconciliation inline
WorkqueueBuffers keys and provides retry/backoff behaviorDoes not hold authoritative object state
ListerReads the local Indexer safelyDoes not issue an API GET

The workqueue boundary is important in production. A slow cloud API call or a failed reconciliation should delay that key, not block the Informer from consuming watch events. The worker can retry a key; when it does, it reads the latest cached object instead of relying on an old event payload.

A SharedInformer shares one watch and one cache among consumers in the same process. It does not share memory between replicas:

operator replica A: one Pod SharedInformer ──> controller A + controller B
operator replica B: another Pod SharedInformer ──> controller A + controller B

Scaling an operator from one replica to ten can therefore create ten independent caches and watches. Leader election may prevent nine replicas from writing, but it does not automatically prove that nine replicas avoid cache synchronization. Check the framework's startup and leader-election behavior before assuming standby replicas are cheap.

Also keep the vocabulary precise:

  • kubectl get pods -w consumes a watch stream but does not need an indexed Informer cache.
  • A client-go ClientSet supports LIST and WATCH, but creates no Informer unless the program asks for one.
  • controller-runtime and Operator SDK normally build informer-backed caches for controllers, even when the reconcile code only shows calls such as Get and List.
  • kubelet uses Reflector machinery in important paths; its API-server Pod source narrows the watch with spec.nodeName=<this-node>.
  • Other language SDKs can build the same architecture without using the Go names Reflector and Informer.

Why Streaming Lists exist​

Kubernetes 1.35 supports streaming lists, enabled by default as a beta feature. With sendInitialEvents=true, one watch can deliver synthetic ADDED events for the current objects, a BOOKMARK marking the completed initial state, and then later changes. The request also uses resourceVersionMatch=NotOlderThan. This avoids constructing one large initial LIST response before starting the watch.

Those initial ADDED events describe objects that already exist. They are instructions to populate the empty client cache, not evidence that the objects were created at controller startup. The initial-state bookmark can be identified by the k8s.io/initial-events-end: "true" annotation.

The operational comparison is:

classic startup
API server builds one large collection response ──> client decodes it ──> WATCH

streaming startup
API server streams existing objects ──> client builds cache incrementally ──> same WATCH continues

Both approaches produce the same logical local state. Streaming Lists reduce the large temporary allocation around initial delivery; they do not reduce the final client-cache size. At scale, combine them with narrower selectors and staggered restarts.

A normal bookmark tells a client that events through a resource version have been sent. It helps a reconnecting client resume from a newer point even when the watched objects were quiet. Requesting bookmarks does not guarantee when, or even whether, the API server sends one. The following bounded watch often shows one on this lab cluster:

RV=$(kubectl get --raw "/api/v1/namespaces/m2-deepdive/configmaps?limit=1" | grep -o '"resourceVersion":"[0-9]*"' | head -1 | grep -o '[0-9]*')
kubectl get --raw "/api/v1/namespaces/m2-deepdive/configmaps?watch=1&allowWatchBookmarks=true&resourceVersion=${RV}&timeoutSeconds=15"

[ Expected output ]

{"type":"BOOKMARK","object":{"kind":"ConfigMap","apiVersion":"v1","metadata":{"resourceVersion":"2987"}}}

When a bookmark appears, the object carries little more than metadata.resourceVersion. If this run produces no output, that is also valid. The API contract does not promise a bookmark interval. Production clients must handle watch closure, 410 Gone, timeouts, and reconnects even when no bookmark arrives.

Production recommendation: design reconnects before rollout day
  • Share informer factories inside a process instead of opening duplicate watches for the same resource.
  • Scope caches by namespace, label, or field when the controller does not need the whole cluster.
  • Use exponential backoff with jitter after failures.
  • Stagger large agent and controller rollouts so every replica does not rebuild state together.
  • Use streaming lists where your client library and compatibility requirements support them.

PART IV - Audit policy: collect enough evidence without recording everything​

An audit policy is similar to CCTV coverage in a large office. Entrances need useful records, but recording every screen and every document at full detail creates cost and may capture sensitive information. More data is not automatically better evidence.

Inspect the lab policy:

sed '/^[[:space:]]*#/d;/^[[:space:]]*$/d' labs/clusters/core-internals/audit-policy.yaml

[ Expected output ]

apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
  - RequestReceived
rules:
  - level: Request
    resources:
      - group: flowcontrol.apiserver.k8s.io
        resources: ["flowschemas", "prioritylevelconfigurations"]
  - level: Request
    namespaces: ["nimbusai"]
    resources:
      - group: apps
        resources: ["deployments"]
  - level: Metadata

The policy uses Metadata for the broad baseline, which records who, what, when, source, result, and timing without request or response bodies. It raises selected resources to Request only where the lab needs the submitted body. It also omits the RequestReceived stage to reduce duplicate volume.

Production audit rules
  • Do not enable RequestResponse for every resource. Bodies increase memory, I/O, storage, and exposure of sensitive data.
  • Exclude or carefully limit sensitive resources such as Secrets, TokenReviews, and authentication material.
  • Set retention, rotation, access control, encryption, and alerting for the audit backend. Audit logs are security data.
  • Send logs to a backend that remains available if one control-plane node fails.
  • During an investigation, add a narrow temporary rule for the exact resource and verb, then remove it after collecting evidence.

Audit tells you what the API server observed. It does not prove that an external system completed its side effect or that a controller later reconciled the object.

kubectl get --raw /debug/api_priority_and_fairness/dump_requests

On this kind cluster, the admin identity belongs to kubeadm:cluster-admins. The lab proved that it lands in global-default, not exempt. The built-in exempt FlowSchema matches system:masters and bypasses APF limits. Do not route application traffic there. A bug or retry loop in exempt traffic can consume API-server capacity without APF containing it.

Use the following triage sequence in production:

EvidenceLikely interpretationNext action
One FlowSchema queues; others are healthyOne client or request class is noisyIdentify user and verb; fix retries; isolate if needed
Several levels queue; latency risesShared API, admission, or storage work is slowCheck API, webhook, and storage latency
Rejections rise with queue-fullThe burst exceeds the configured waiting roomFix the source, verify client backoff, then review queue length and shares
Rejections rise with concurrency-limitThe priority level uses immediate reject instead of queueConfirm that rejection is intentional for that traffic class
Important traffic matches wrong schemaA rule is too broadCorrect it and verify response-header UIDs
Do not turn debug output into a monitoring API

The debug endpoints are useful for an incident snapshot, but their text format is for people and can change. Use supported Prometheus metrics for dashboards and alerts. Use audit events and APF response headers for attribution. Restrict access because detailed request output can expose usernames, paths, namespaces, and object names.

Summary​

Where you will use this
  • Pagination bounds each response, not the total work of reading every object. The pages belong to one consistent collection snapshot, and the continue token is an opaque cursor. Use it when: an API server or client runs out of memory during cache rebuilds. Find unpaginated LIST calls, narrow their scope, and fix the client before adding memory.
  • resourceVersion is a freshness contract, not a storage-path switch. Kubernetes 1.35 can serve several consistent and exact read forms from watch-cache state or snapshots. Use it when: reviewing a controller, fleet script, or dashboard. Choose the weakest freshness guarantee that is correct, and handle 410 Gone explicitly.
  • Reflectors and Informers are client-side machinery. A Reflector synchronizes; an Informer maintains an eventually consistent indexed cache and distributes changes; a SharedInformer shares that work only inside one process. Use it when: reviewing controller scale or stale reads. Count caches per process, keep handlers fast, queue keys for reconciliation, and remember that a direct WATCH is not automatically an Informer.
  • Streaming lists can reduce the initial-state memory spike. Synthetic ADDED events build state before a bookmark marks the completed snapshot. Use it when: a large informer cache produces expensive relists. Confirm client-library support, scope the cache, and stagger restarts.
  • Audit policy is a cost and security decision. Metadata is a useful broad baseline; request bodies belong in narrow rules. Use it when: you need to attribute a change or rejection. Raise detail only for the relevant resource and protect the audit backend as security data.
  • APF evidence must separate a noisy flow from a slow server. One queued level suggests classification or client behavior; many queued levels suggest shared latency. Use it when: one team reports a slow API or several controllers fall behind. Combine metrics, debug snapshots, audit events, and response-header UIDs before changing shares.
